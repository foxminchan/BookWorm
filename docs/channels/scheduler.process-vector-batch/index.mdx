`scheduler.process-vector-batch` (v1.0.0) is the unprefixed Kafka topic owned by Scheduler that triggers periodic vector-embedding synchronization in Catalog Ingestion. Unlike all other BookWorm Kafka topics, `ProcessVectorBatchIntegrationEvent` sets `AppendPrefix = false` in `IntegrationMessageOwnerAttribute`, so the topic name omits `bookworm.{env}.` across all environments.

## Parameters and fields

### Topic parameters

This channel accepts no topic parameters. `KafkaTopicRouter.CreateTopicName` returns `scheduler.process-vector-batch` verbatim because `ProcessVectorBatchIntegrationEvent` declares `AppendPrefix = false`.

## Delivery, partitioning, and consumer behavior

- **Quartz.NET schedule:** `ProcessVectorBatchJob` (decorated with `[DisallowConcurrentExecution]`) runs on cron `0 0/5 * * * ?` UTC (every five minutes) with `MisfireInstruction: FireOnceNow` (`src/Services/Scheduler/BookWorm.Scheduler/jobs.json`). Scheduler publishes `ProcessVectorBatchIntegrationEvent` through Wolverine's PostgreSQL outbox (`schedulerdb`, `wolverine` schema).
- **Azure Functions trigger:** `ProcessVectorBatchFunction` subscribes to `scheduler.process-vector-batch` on `%BrokerList%` with `ConsumerGroup = "catalog-ingestion"`, unwraps the CloudEvents `data` object with `CloudEventsMessageParser.Deserialize`, and invokes `IVectorBatchProcessor.ProcessAsync`.
- **Idempotent batch synchronization:** `VectorBatchProcessor` acquires a PostgreSQL session advisory lock (`pg_try_advisory_lock(740031001)`) in `catalogdb` so overlapping or duplicate triggers return immediately (`0` processed). While holding the lock, it reads up to `200` rows from `pending_vector_updates` ordered by `updated_at, book_id`, generates embeddings via Microsoft Foundry (`Cohere.EmbedV40`), upserts or deletes points in Qdrant (`vectordb`), and deletes only rows whose `(book_id, revision)` still match so concurrent book edits survive.

## Error responses and dead-letter behavior

| Condition                                                                | Handling behavior                                                                                                                           | Recovery behavior                                                                                                                                     |
| :----------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Another worker holds advisory lock `740031001`                           | `pg_try_advisory_lock` returns `false`; `ProcessAsync` exits cleanly with `0` rows processed.                                               | Expected concurrency guard; pending rows are picked up on the next five-minute trigger.                                                               |
| Embedding service returns an incomplete batch or Qdrant/PostgreSQL fails | `VectorBatchProcessor` throws and releases advisory lock `740031001` in its `finally` block without acknowledging `pending_vector_updates`. | Unacknowledged rows remain in `pending_vector_updates` and are retried on the next trigger.                                                           |
| Invalid JSON or malformed CloudEvents payload                            | `CloudEventsMessageParser.Deserialize` throws inside `ProcessVectorBatchFunction`.                                                          | Inspect `catalog-ingestion` Azure Functions logs and consumer group `catalog-ingestion` offsets; no Wolverine native DLQ is attached to this trigger. |
| Quartz publish failure in Scheduler                                      | `ProcessVectorBatchJob` logs the error and throws `JobExecutionException`.                                                                  | Check `scheduler` logs, `schedulerdb` connectivity, and Kafka broker health.                                                                          |

The Finance and Catalog Ingestion `host.json` files contain no Kafka retry or commit overrides. With `Microsoft.Azure.Functions.Worker.Extensions.Kafka` 4.3.3 defaults, `CommitOnFailure` is `true`: a failed invocation's offset is stored for auto-commit and the message is not retried. If disabled, the extension retries the message in place up to five times, then force-commits and skips it. See the versioned [`KafkaOptions`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Config/KafkaOptions.cs), [`SingleItemFunctionExecutor`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Trigger/SingleItemFunctionExecutor.cs), and [`AsyncCommitStrategy`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Trigger/AsyncCommitStrategy.cs) sources.
