`bookworm.{env}.basket.delete-failed` (v1.0.0) is the Kafka topic owned by Basket API that reports a checkout basket that could not be deleted. Finance consumes `BasketDeletedFailedIntegrationEvent`, ends the saga as `BasketDeletionFailed`, and asks Ordering API to soft-delete the order. Finance sends no customer email for this outcome.

## Delivery, partitioning, and consumer behavior

- **When Basket API publishes:** Only when `IBasketRepository.DeleteBasketAsync` returns `false`, such as a missing basket key in Redis. A thrown exception does not produce this event; the handler releases its idempotency key and rethrows, so Wolverine retries and eventually routes to [[channel|bookworm.&#123;env&#125;.basket.dead-letter-queue]].
- **Partitioning:** Keyed by `OrderId`.
- **Finance consumption:** `BasketDeletedFailedTrigger` raises external event `BasketDeletedFailedIntegrationEvent` on `OrderOrchestrator` instance `orderId`. `BasketDeletedFailedStep` moves the saga to terminal `OrderStatus.BasketDeletionFailed` and publishes [[channel|bookworm.&#123;env&#125;.finance.delete-basket-failed]]. Ordering API then soft-deletes the order.
- **Duplicates:** The orchestrator waits for this event only while the basket is not marked deleted and the saga is not terminal.

## Error responses and dead-letter behavior

| Condition                          | Handling behavior                                                              | Recovery behavior                                            |
| :--------------------------------- | :----------------------------------------------------------------------------- | :----------------------------------------------------------- |
| Malformed CloudEvents payload      | `CloudEventsMessageParser.Deserialize` throws in `BasketDeletedFailedTrigger`. | Inspect `finance` Functions logs and consumer group offsets. |
| Durable Task Scheduler unreachable | `RaiseEventAsync` throws.                                                      | Restore `finance-taskhub` connectivity.                      |
| Orchestration already terminal     | Durable Task ignores events for finished instances.                            | Inspect instance status by `orderId`.                        |

The Finance and Catalog Ingestion `host.json` files contain no Kafka retry or commit overrides. With `Microsoft.Azure.Functions.Worker.Extensions.Kafka` 4.3.3 defaults, `CommitOnFailure` is `true`: a failed invocation's offset is stored for auto-commit and the message is not retried. If disabled, the extension retries the message in place up to five times, then force-commits and skips it. See the versioned [`KafkaOptions`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Config/KafkaOptions.cs), [`SingleItemFunctionExecutor`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Trigger/SingleItemFunctionExecutor.cs), and [`AsyncCommitStrategy`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Trigger/AsyncCommitStrategy.cs) sources.
