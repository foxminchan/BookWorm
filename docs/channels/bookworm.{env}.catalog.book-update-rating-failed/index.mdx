`bookworm.{env}.catalog.book-update-rating-failed` (v1.0.0) is the Kafka topic owned by Catalog API that sends a compensating signal to Rating API. Catalog API publishes `BookUpdatedRatingFailedIntegrationEvent` when a `FeedbackCreatedIntegrationEvent` references a book that does not exist. Rating API then deletes the orphaned Feedback record.

## Delivery, partitioning, and consumer behavior

- **Producer:** `FeedbackCreatedIntegrationEventHandler` looks up the book in `catalogdb`. If the book is missing, it returns this event as a Wolverine cascaded message, published through the PostgreSQL outbox (`catalogdb`, `wolverine` schema).
- **Not emitted for deletes:** `FeedbackDeletedIntegrationEventHandler` treats a missing book as a no-op and publishes nothing.
- **Partitioning:** Keyed by `FeedbackId`.
- **Consumer:** `BookUpdatedRatingFailedIntegrationEventHandler` acquires a 24-hour Redis/FusionCache key (`idempotency:BookUpdatedRatingFailedIntegrationEventHandler:{id:N}`), loads the Feedback from Cosmos DB (`ratingdb` / `feedbacks`), calls `feedback.Revert()`, deletes it, and saves. A missing Feedback is a no-op, so replays are safe.

## Error responses and dead-letter behavior

| Condition                                                                                               | Handling behavior                                                                                                    | Recovery behavior                                                                                                                |
| :------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| Feedback already deleted                                                                                | Handler returns without changes.                                                                                     | None needed.                                                                                                                     |
| `TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException` | Redis key released; Wolverine retries at `50ms`, `250ms`, `1s` with full jitter.                                     | Moved to [[channel\|bookworm.&#123;env&#125;.rating.dead-letter-queue]] after retries.                                           |
| `JsonException` or `FormatException`                                                                    | No retries.                                                                                                          | Moved to the Rating DLQ.                                                                                                         |
| Cosmos DB errors (`CosmosException`)                                                                    | Not matched by a configured rule; Wolverine's continuation fallback moves the message to the native DLQ immediately. | `WolverineHostExtensions.ConfigureDefaultErrorHandling`; Wolverine 6.65.1 `FailureRuleCollection.DetermineExecutionContinuation` |

BookWorm configures exception-specific policies but does not set a catch-all `MaximumAttempts` rule. An exception that matches none of them, including `CosmosException`, uses Wolverine 6.65.1's `MoveToErrorQueue` fallback and reaches the native DLQ on the first failure. The [version-pinned continuation fallback](https://github.com/JasperFx/wolverine/blob/V6.65.1/src/Wolverine/ErrorHandling/FailureRuleCollection.cs) and [dead-letter guide](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#when-does-a-message-get-dead-lettered) distinguish this configured-policy case from the general default used when no error policies are configured.
