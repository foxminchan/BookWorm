`bookworm.{env}.rating.dead-letter-queue` (v1.0.0) is the native Kafka dead-letter topic for Rating API. Wolverine routes incoming `BookUpdatedRatingFailedIntegrationEvent` envelopes here when Rating API exhausts its retry policy or cannot deserialize the payload. Rating API persists Feedback records and Wolverine messages in Azure Cosmos DB (`ratingdb`), not PostgreSQL.

A dead-lettered record preserves the original `BookUpdatedRatingFailedIntegrationEvent` CloudEvents value and Kafka key (`feedbackId`, from Catalog API partitioning).

Wolverine 6.65.1 adds `exception-type`, `exception-message`, `exception-stack` (truncated to 8,192 characters), `failed-at` (Unix milliseconds), and `original-destination` to native dead-letter records; Kafka records also include `original-partition` and `original-offset`. The delivery-attempt count is in the `attempts` header. See the [version-pinned diagnostic header reference](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#diagnostic-headers-on-dead-letter-messages).

## Routing rules

| Exception                                                                                               | Retries before DLQ                                                                                                  | Source                                                                                                                           |
| :------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------- |
| `TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException` | `3` retries at `50ms`, `250ms`, `1s` with full jitter, then DLQ                                                     | `ConfigureDefaultErrorHandling`                                                                                                  |
| `JsonException`, `FormatException`                                                                      | None (immediate DLQ)                                                                                                | `ConfigureDefaultErrorHandling`                                                                                                  |
| Cosmos DB errors (`CosmosException`)                                                                    | Not matched by a configured rule; Wolverine's continuation fallback moves the message to the native DLQ immediately | `WolverineHostExtensions.ConfigureDefaultErrorHandling`; Wolverine 6.65.1 `FailureRuleCollection.DetermineExecutionContinuation` |

BookWorm configures exception-specific policies but does not set a catch-all `MaximumAttempts` rule. An exception that matches none of them, including `CosmosException`, uses Wolverine 6.65.1's `MoveToErrorQueue` fallback and reaches the native DLQ on the first failure. The [version-pinned continuation fallback](https://github.com/JasperFx/wolverine/blob/V6.65.1/src/Wolverine/ErrorHandling/FailureRuleCollection.cs) and [dead-letter guide](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#when-does-a-message-get-dead-lettered) distinguish this configured-policy case from the general default used when no error policies are configured.

:::note
`DeadLetterQueueExpiration = 7 days` applies to Wolverine's durable Cosmos DB storage (`ratingdb`). Kafka topic retention for `bookworm.{env}.rating.dead-letter-queue` is governed by broker configuration.
:::

## Replay safety

| Check                                           | Why it matters                                                                                                                                                                                                                                                                                                          |
| :---------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Verify book absence in Catalog API**          | Confirm the referenced book is truly missing before replaying; if the book exists in `catalogdb`, stop and investigate a projection or contract defect.                                                                                                                                                                 |
| **Cosmos DB (`ratingdb` / `feedbacks`) health** | Restore Cosmos DB connectivity before replaying envelopes that failed due to transient store outages.                                                                                                                                                                                                                   |
| **Idempotency and revert behavior**             | `BookUpdatedRatingFailedIntegrationEventHandler` uses `IIntegrationEventIdempotencyGuard` (`idempotency:BookUpdatedRatingFailedIntegrationEventHandler:{id:N}`, 24-hour TTL), releases the key on failure, calls `feedback.Revert()` then deletes the record, and treats an already-missing `Feedback` as a safe no-op. |
