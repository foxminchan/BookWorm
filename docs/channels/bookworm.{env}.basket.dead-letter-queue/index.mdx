`bookworm.{env}.basket.dead-letter-queue` (v1.0.0) is the native Kafka dead-letter topic for Basket API. Wolverine moves an incoming envelope here when Basket API exhausts its retry policy or cannot deserialize the payload. The only Kafka listener in Basket API consumes `PlaceOrderCommand` from `bookworm.{env}.finance.place-order`.

A dead-lettered record keeps the original `PlaceOrderCommand` CloudEvents value and Kafka key (`orderId`).

Wolverine 6.65.1 adds `exception-type`, `exception-message`, `exception-stack` (truncated to 8,192 characters), `failed-at` (Unix milliseconds), and `original-destination` to native dead-letter records; Kafka records also include `original-partition` and `original-offset`. The delivery-attempt count is in the `attempts` header. See the [version-pinned diagnostic header reference](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#diagnostic-headers-on-dead-letter-messages).

## Routing rules

| Exception                                                                                               | Retries before DLQ                                                                                                                        | Source                                                                                                                           |
| :------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| `TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException` | `3` retries with `50ms`, `250ms`, `1s` cooldown and full jitter                                                                           | `ConfigureDefaultErrorHandling`                                                                                                  |
| `JsonException`, `FormatException`                                                                      | None                                                                                                                                      | `ConfigureDefaultErrorHandling`                                                                                                  |
| Other exceptions, such as `RedisConnectionException`                                                    | Immediate DLQ on the first failure: no BookWorm policy matches, so Wolverine's continuation fallback moves the message to the error queue | `WolverineHostExtensions.ConfigureDefaultErrorHandling`; Wolverine 6.65.1 `FailureRuleCollection.DetermineExecutionContinuation` |

This BookWorm configuration defines exception-specific policies but does not set a catch-all `MaximumAttempts` rule. Exceptions that match no policy therefore use Wolverine 6.65.1's `MoveToErrorQueue` fallback and reach the native DLQ immediately. The general three-attempt default documented by Wolverine applies when no error policies are configured; it should not be inferred for this service's custom policy set. See the [version-pinned continuation fallback](https://github.com/JasperFx/wolverine/blob/V6.65.1/src/Wolverine/ErrorHandling/FailureRuleCollection.cs) and [dead-letter guide](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#when-does-a-message-get-dead-lettered).

:::note
`DeadLetterQueueExpiration = 7 days` in `WolverineHostExtensions` applies to Wolverine durable message storage. Basket API has no such store, so the Kafka topic's own retention controls how long records stay.
:::

## Replay safety

| Check                                                              | Why it matters                                                                                                                                                                                         |
| :----------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Order status and soft-delete state in Ordering API                 | Replaying after the saga ended has no effect on the order.                                                                                                                                             |
| Redis health for Basket API                                        | Separates transient outages from contract errors.                                                                                                                                                      |
| Idempotency key `idempotency:PlaceOrderCommandHandler:{orderId:N}` | `PlaceOrderCommandHandler` releases the key when it throws, so a replay re-runs the delete. A replay after a successful delete returns `BasketDeletedCompleteIntegrationEvent` without deleting again. |
| Shared topic                                                       | `PlaceOrderCommand` also reaches Notification; replay only to Basket API to avoid a second email.                                                                                                      |
