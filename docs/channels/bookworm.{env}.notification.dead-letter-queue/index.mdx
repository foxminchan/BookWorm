`bookworm.{env}.notification.dead-letter-queue` (v1.0.0) is the native Kafka dead-letter topic for Notification. Wolverine routes incoming order-email commands here when Notification exhausts retries, fails MJML rendering or SMTP submission, or cannot deserialize the payload. All three Finance notification command channels feed this single per-service DLQ.

A dead-lettered record preserves the original CloudEvents value (`PlaceOrderCommand`, `CompleteOrderCommand`, or `CancelOrderCommand`) and Kafka key (`orderId`).

Wolverine 6.65.1 adds `exception-type`, `exception-message`, `exception-stack` (truncated to 8,192 characters), `failed-at` (Unix milliseconds), and `original-destination` to native dead-letter records; Kafka records also include `original-partition` and `original-offset`. The delivery-attempt count is in the `attempts` header. See the [version-pinned diagnostic header reference](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#diagnostic-headers-on-dead-letter-messages).

## Routing rules

| Exception or failure                                                                                                                      | Handling before DLQ                                                                                                                                                                                 | Source                                        |
| :---------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------- |
| Transient SMTP failure (`CommandException` transient, `ProtocolException`, `IOException`, `TimeoutException`, `TimeoutRejectedException`) | Retried inside the `Notification` Polly pipeline (circuit breaker, exponential retry with jitter, `30s` timeout). If retries exhaust, `MailKitSender` wraps the failure in `NotificationException`. | `ResilienceExtensions.cs`, `MailKitSender.cs` |
| `NotificationException` or MJML rendering failure                                                                                         | `IIntegrationEventIdempotencyGuard.ExecuteAsync` releases the Redis key and rethrows. `NotificationException` is not in `ConfigureDefaultErrorHandling`'s transient retry list.                     | `MailKitSender.cs`, `MjmlTemplateRenderer.cs` |
| `TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException`                                   | `3` Wolverine retries at `50ms`, `250ms`, `1s` with full jitter, then DLQ.                                                                                                                          | `ConfigureDefaultErrorHandling`               |
| `JsonException`, `FormatException`                                                                                                        | DLQ immediately with zero retries.                                                                                                                                                                  | `ConfigureDefaultErrorHandling`               |

`NotificationException` is not matched by the explicit BookWorm policies. BookWorm does not configure a catch-all `MaximumAttempts` rule, so Wolverine 6.65.1's unmatched-exception fallback moves it to the native DLQ on the first failure. See the [version-pinned continuation fallback](https://github.com/JasperFx/wolverine/blob/V6.65.1/src/Wolverine/ErrorHandling/FailureRuleCollection.cs) and [dead-letter guide](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#when-does-a-message-get-dead-lettered).

:::note
`DeadLetterQueueExpiration = 7 days` in `WolverineHostExtensions` applies to Wolverine durable message stores. Notification has no SQL message store, so Kafka broker topic retention governs how long dead-lettered records persist.
:::

## Replay safety and privacy

| Check                                | Why it matters                                                                                                                                                                                                                                          |
| :----------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **PII hygiene**                      | Dead-lettered payloads contain customer `fullName` and `email`. Never copy recipient addresses or names into incident tickets or logs; correlate using `orderId`, `id`, and `traceparent`.                                                              |
| **Redis idempotency key**            | Notification handlers guard execution with `idempotency:{HandlerName}:{id:N}` (24-hour TTL). Failed attempts release the key, so replaying a dead-lettered message re-runs delivery; replaying an already delivered `id` within 24 hours is suppressed. |
| **SMTP provider check**              | Because Notification has no email database and an SMTP timeout can occur after the provider accepted the message, check Mailpit (local) or SendGrid activity logs (cloud) before replaying to avoid duplicate customer emails.                          |
| **Shared `PlaceOrderCommand` topic** | Do not blindly republish `PlaceOrderCommand` to `bookworm.{env}.finance.place-order` without verifying Basket API state, because both services subscribe to that topic.                                                                                 |
