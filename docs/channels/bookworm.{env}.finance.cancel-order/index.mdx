`bookworm.{env}.finance.cancel-order` (v1.0.0) is the Kafka topic owned by Finance that delivers `CancelOrderCommand` messages to Notification for canceled-order emails. Finance publishes this command from the `OrderOrchestrator` Durable Task saga; Notification consumes it to render an MJML email and submit it over SMTP. This channel belongs to Finance and does not represent order-state confirmation in Ordering API.

## Delivery, partitioning, and consumer behavior

- **Publication triggers:** Finance dispatches `CancelOrderCommand` via `PublishCancelOrderActivity` (Durable Task activity retry policy: `3` attempts, `5s` initial delay, `2.0x` backoff) only when `Order.CanSendNotification` is true (both `FullName` and `Email` are non-blank). Dispatch occurs on explicit `OrderCancelledStep`, on `CancelDueToMaxRetriesAsync` after exceeding `OrderStateMachine.MaxAttempts` (default `3`), or during LIFO saga compensation on `TaskFailedException` or `FinanceDomainException`.
- **Partitioning and ordering:** Finance partitions messages by `OrderId`, preserving per-order ordering within this topic. Ordering is not guaranteed across separate lifecycle topics such as `bookworm.{env}.finance.place-order` and `bookworm.{env}.finance.cancel-order`.
- **Stateless email processing with Redis idempotency:** Notification has no SQL database or email outbox table. `CancelOrderCommandHandler` acquires a 24-hour Redis/FusionCache lock via `IIntegrationEventIdempotencyGuard` (`idempotency:CancelOrderCommandHandler:{id:N}`), skips blank `email` values, renders the embedded `Orders/OrderEmail` MJML template with subject `"BookWorm: Your Order Has Been Canceled - Important Information"`, and sends via `MailKitSender` (Mailpit locally on port `587`, SendGrid SMTP in cloud).
- **Duplicate semantics:** Duplicate Kafka deliveries of the same `id` are suppressed for 24 hours by the Redis idempotency guard. Reissued commands carrying a new `id` are processed as new messages and can send another email. No delivery confirmation event is published back to Finance or Ordering API.

## Error responses and dead-letter behavior

| Condition                                                                                                                                         | Handling behavior                                                                                                                                                                                    | Recovery behavior                                                                                                            |
| :------------------------------------------------------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------- |
| `email` is `null` or whitespace                                                                                                                   | `OrderNotificationHelper.SendAsync` returns immediately without rendering or calling SMTP.                                                                                                           | Expected no-op; no retry or dead-lettering occurs.                                                                           |
| Transient SMTP failure (`CommandException` transient, `ProtocolException`, `IOException`, `TimeoutException`, `TimeoutRejectedException`)         | `MailKitSender` executes inside the `Notification` Polly resilience pipeline (circuit breaker, exponential retry with jitter, `30s` timeout).                                                        | If SMTP recovers within the pipeline window, email delivery succeeds without moving to DLQ.                                  |
| Exhausted SMTP retries or MJML rendering failure                                                                                                  | `MailKitSender` wraps non-cancellation exceptions in `NotificationException` and rethrows; `IIntegrationEventIdempotencyGuard.ExecuteAsync` releases the Redis key so retries or replays can re-run. | Wolverine routes unhandled `NotificationException` to [[channel\|bookworm.&#123;env&#125;.notification.dead-letter-queue]].  |
| Transient Wolverine listener exceptions (`TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException`) | `WolverineHostExtensions.ConfigureDefaultErrorHandling` retries with `50ms`, `250ms`, and `1s` cooldown intervals plus full jitter.                                                                  | After retries exhaust, Wolverine moves the envelope to [[channel\|bookworm.&#123;env&#125;.notification.dead-letter-queue]]. |
| `JsonException` or `FormatException`                                                                                                              | Immediately moved to [[channel\|bookworm.&#123;env&#125;.notification.dead-letter-queue]] with zero retries.                                                                                         | Fix producer schema drift before replaying.                                                                                  |

`NotificationException` is not matched by the explicit BookWorm policies. BookWorm does not configure a catch-all `MaximumAttempts` rule, so Wolverine 6.65.1's unmatched-exception fallback moves it to the native DLQ on the first failure. See the [version-pinned continuation fallback](https://github.com/JasperFx/wolverine/blob/V6.65.1/src/Wolverine/ErrorHandling/FailureRuleCollection.cs) and [dead-letter guide](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#when-does-a-message-get-dead-lettered).
