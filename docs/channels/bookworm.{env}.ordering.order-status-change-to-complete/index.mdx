`bookworm.{env}.ordering.order-status-change-to-complete` (v1.0.0) is the Kafka topic owned by Ordering API that reports an `Order` transitioning from `New` to `Completed`. Finance consumes `OrderStatusChangedToCompleteIntegrationEvent` through an Azure Functions Kafka trigger to finish the `OrderOrchestrator` saga instance. This channel reports business completion state and does not confirm downstream email delivery.

## Delivery, partitioning, and consumer behavior

- **Transactional outbox:** Ordering API publishes `OrderStatusChangedToCompleteIntegrationEvent` via Wolverine's PostgreSQL outbox (`orderingdb`, `wolverine` schema) tied to EF Core transactions (`UsePostgresOutbox`), ensuring at-least-once dispatch after committing the `Order` status update.
- **Partitioning:** Ordering API partitions by `OrderId` so events for the same order stay on a single partition within this topic.
- **Finance Durable Functions consumption:** `OrderCompletedTrigger` subscribes to `%KafkaTopics:OrderStatusChangedToComplete%` with `ConsumerGroup = "finance"`, deserializes the CloudEvents `data` payload through `CloudEventsMessageParser.Deserialize`, and raises external event `OrderStatusChangedToCompleteIntegrationEvent` on `OrderOrchestrator` instance `orderId` in Durable Task Scheduler (`finance-taskhub`).
- **Saga transition:** `OrderCompletedStep` transitions the saga aggregate to terminal `OrderStatus.Completed` and, when `Order.CanSendNotification` is true (both `FullName` and `Email` are non-blank), dispatches `CompleteOrderCommand` on [[channel|bookworm.&#123;env&#125;.finance.complete-order]].

## Error responses and dead-letter behavior

| Condition                                                                                         | Handling behavior                                                                                                                                                            | Recovery behavior                                                                                                                                           |
| :------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invalid JSON or malformed CloudEvents envelope                                                    | `CloudEventsMessageParser.Deserialize` throws `JsonException` or `InvalidOperationException` in `OrderCompletedTrigger`.                                                     | Inspect `finance` Azure Functions logs and consumer group `finance` offsets; Finance does not configure a Wolverine native DLQ for incoming Kafka triggers. |
| Durable Task Scheduler (`finance-taskhub`) unreachable                                            | `client.RaiseEventAsync` fails inside `OrderCompletedTrigger`.                                                                                                               | Verify Durable Task Scheduler health and Azure Functions logs before replaying or resetting offsets.                                                        |
| Order already in terminal saga state (`Completed`, `Cancelled`, `BasketDeletionFailed`, `Failed`) | `OrderLifecycleDecider` rejects invalid transitions with `FinanceDomainException` if active; events raised to an already finished orchestration are ignored by Durable Task. | Inspect `OrderOrchestrator` instance status (`orderId`) in Durable Task Scheduler.                                                                          |

The Finance and Catalog Ingestion `host.json` files contain no Kafka retry or commit overrides. With `Microsoft.Azure.Functions.Worker.Extensions.Kafka` 4.3.3 defaults, `CommitOnFailure` is `true`: a failed invocation's offset is stored for auto-commit and the message is not retried. If disabled, the extension retries the message in place up to five times, then force-commits and skips it. See the versioned [`KafkaOptions`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Config/KafkaOptions.cs), [`SingleItemFunctionExecutor`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Trigger/SingleItemFunctionExecutor.cs), and [`AsyncCommitStrategy`](https://github.com/Azure/azure-functions-kafka-extension/blob/4.3.3/src/Microsoft.Azure.WebJobs.Extensions.Kafka/Trigger/AsyncCommitStrategy.cs) sources.
