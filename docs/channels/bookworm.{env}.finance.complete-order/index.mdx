`bookworm.{env}.finance.complete-order` (v1.0.0) is the Kafka topic owned by Finance that delivers `CompleteOrderCommand` to Notification for completed-order emails. Finance publishes the command from the `OrderOrchestrator` saga after Ordering API reports completion. A successful SMTP submission does not confirm final recipient delivery, and no result event is published back.

## Delivery, partitioning, and consumer behavior

- **Publication trigger:** `OrderCompletedStep` moves the saga to terminal `OrderStatus.Completed`. If `Order.CanSendNotification` is true (both `FullName` and `Email` non-blank), it calls `PublishCompleteOrderActivity` (Durable Task retry policy: `3` attempts, `5s` initial delay, `2.0x` backoff).
- **Partitioning:** Records are keyed by `OrderId`. Ordering holds within this topic only, not across lifecycle topics.
- **Consumer processing:** `CompleteOrderCommandHandler` acquires a 24-hour Redis/FusionCache key (`idempotency:CompleteOrderCommandHandler:{id:N}`), skips blank `email`, renders the `Orders/OrderEmail` MJML template with subject `"BookWorm: Your Order Has Been Completed and Shipped"`, and sends through `MailKitSender` (Mailpit locally, SendGrid SMTP in cloud). Notification has no database or email outbox.
- **Duplicates:** Redeliveries of the same `id` are suppressed for 24 hours. A newly issued command with a new `id` sends another email.

## Error responses and dead-letter behavior

| Condition                                                                                                                                 | Handling behavior                                                                                            | Recovery behavior                                                                      |
| :---------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| `email` is blank                                                                                                                          | `OrderNotificationHelper.SendAsync` returns without sending.                                                 | Expected no-op.                                                                        |
| Transient SMTP failure (`CommandException` transient, `ProtocolException`, `IOException`, `TimeoutException`, `TimeoutRejectedException`) | Retried inside the `Notification` Polly pipeline (circuit breaker, exponential jitter retry, `30s` timeout). | Succeeds without DLQ if SMTP recovers.                                                 |
| Exhausted SMTP retries or MJML rendering failure                                                                                          | `MailKitSender` throws `NotificationException`; the idempotency guard releases its Redis key.                | Envelope reaches [[channel\|bookworm.&#123;env&#125;.notification.dead-letter-queue]]. |
| `TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException`                                   | Wolverine retries at `50ms`, `250ms`, `1s` with full jitter.                                                 | Moved to the Notification DLQ after retries.                                           |
| `JsonException` or `FormatException`                                                                                                      | Moved to the Notification DLQ with zero retries.                                                             | Fix producer schema drift before replay.                                               |

`NotificationException` is not matched by the explicit BookWorm policies. BookWorm does not configure a catch-all `MaximumAttempts` rule, so Wolverine 6.65.1's unmatched-exception fallback moves it to the native DLQ on the first failure. See the [version-pinned continuation fallback](https://github.com/JasperFx/wolverine/blob/V6.65.1/src/Wolverine/ErrorHandling/FailureRuleCollection.cs) and [dead-letter guide](https://github.com/JasperFx/wolverine/blob/V6.65.1/docs/tutorials/dead-letter-queues.md#when-does-a-message-get-dead-lettered).
