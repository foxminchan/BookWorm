## Purpose & Scope

This topic transports checkout integration events published by [[service|order-api]] immediately after a new order is persisted. [[service|order-orchestration]] consumes these events to start the post-checkout saga, which coordinates basket cleanup and confirmation emails. The event confirms order persistence onlyâ€”not basket deletion or email delivery.

:::note
In current payloads, the `basketId` field carries the buyer identifier rather than an independent Basket service record identifier.
:::

## Ordering, Retries & Failure Handling

- **Partition-key ordering:** Keying by `orderId` ensures checkout initiation precedes subsequent status change events for the same order on that partition.
- **Transient retries:** [[service|order-orchestration]] applies bounded retry/backoff on transient orchestration host or state faults.
- **Poison & failure posture:** Direct worker consumption has no dedicated service DLQ; inspect Finance worker diagnostics and orchestration state before resetting offsets or replaying.
- **Consumer idempotency:** [[service|order-orchestration]] keys saga instances by `orderId` and ignores duplicate checkout events once an orchestration instance exists.
