## Context

BookWorm coordinates work across capabilities without requiring every consumer to finish inside the initiating request. Several documented flows already use Kafka through a shared event framework.

## Decision

Retain Kafka through Wolverine as the configured asynchronous integration backbone for those flows. Producers and consumers use owned message contracts and routing metadata. A missing broker connection means the shared framework does not configure that transport; asynchronous capability must be verified in the deployed host.

This is a whole-system transport choice, not a replacement for the Finance or Notification intake ADRs, nor a requirement to replace every local queue.

## Decision drivers

- Decouple request latency from downstream processing.
- Reuse the existing messaging framework and contract conventions.
- Keep ownership explicit across asynchronous boundaries.

## Alternatives considered

| Alternative                                    | Assessment                                                                          |
| ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| Synchronous calls for all coordination         | Simplifies immediate outcomes but couples availability and execution time.          |
| Different broker per integration               | Allows local choices but adds adapters and operational variation.                   |
| Database polling for all cross-capability work | Can preserve local work but lacks the established shared integration contract path. |

## Consequences

- Consumers can process independently of the originating request.
- Broker deployment, routing, permissions, and failure diagnosis become operational responsibilities.
- Ordering, replay, retention, and delivery guarantees must be checked for the actual configuration rather than assumed system-wide.
