## Context and problem statement

BookWorm coordinates checkout, shopping-cart cleanup, emails, review updates, and scheduled search maintenance across independent areas. Running all follow-up work while the customer is still waiting makes a response slow and creates unnecessary dependence on other areas.

BookWorm needs one standard background-update system for work that does not require an immediate response. Areas that do not need it may continue to operate without it.

## Decision drivers

- **Decoupling:** Keep the original response independent from later work.
- **Standardization:** Use consistent update formats and naming rules.
- **Explicit ownership:** Let the area that publishes an update define its meaning and name.

## Considered options

1. Use one shared background messaging system
2. Handle follow-up work through immediate web requests
3. Let each area choose a different messaging system
4. Coordinate work by repeatedly checking shared records

## Decision outcome

**Chosen option:** Use one shared background messaging system across the platform.

This approach lets different parts of BookWorm work independently while keeping updates organized, consistent, and easy to track.

Eight core parts of BookWorm connect to this shared system. Features that rely on instant, real-time responses—such as the chat assistant—intentionally skip it. All background updates follow one standard format and clear naming rules. If a background task fails, the system automatically retries it a few times after brief pauses. If it still cannot finish, the task moves to a dedicated holding area for that specific feature so the team can review and fix it without losing data. The team uses a local version with a visual dashboard for testing, and a managed cloud service for the live platform.

### Consequences

- **Positive:** Areas publish outcomes without waiting for later steps to finish.
- **Negative:** The messaging system needs monitoring and recovery procedures.
- **Follow-up:** Define how each area protects work from loss or duplication and how updates remain traceable.

## Pros and cons of the options

### Use one shared background messaging system

- **Good**, because publishing and receiving areas can grow independently.
- **Good**, because updates can be replayed and processed in a reliable order.
- **Bad**, because the system requires storage, monitoring, and failed-update recovery.

### Handle follow-up work through immediate web requests

- **Good**, because callers receive immediate success or failure.
- **Bad**, because one unavailable area can block checkout or other dependent work.

### Let each area choose a different messaging system

- **Good**, because each area can choose a system suited to its needs.
- **Bad**, because exchanging updates becomes more complex and requires more operational guidance.

### Coordinate work by repeatedly checking shared records

- **Good**, because work stays in familiar storage.
- **Bad**, because repeated checking conflicts with clear area ownership and gives slower, less consistent updates.
