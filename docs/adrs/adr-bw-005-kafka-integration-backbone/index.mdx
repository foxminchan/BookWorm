## Context & Problem Statement

BookWorm coordinates checkout, basket cleanup, email delivery, rating projection, and scheduled vector indexing across independent services. Executing these follow-up steps synchronously would inflate user-facing latency and couple service availability. BookWorm needs one standard asynchronous integration backbone for decoupled workflows while allowing purely interactive services (like [[service|chat-api]]) to opt out.

## Decision Drivers

- **Temporal decoupling:** Keep user-facing writes fast and resilient to downstream downtime.
- **Standardized operations:** Use uniform topic naming, retry policies, and dead-letter queues.
- **Explicit contract ownership:** Let each publisher define its integration event or command schema.

## Options Considered

| Option                                                     | Pros                                                                   | Cons                                                                |
| :--------------------------------------------------------- | :--------------------------------------------------------------------- | :------------------------------------------------------------------ |
| **Shared Kafka backbone (WolverineFx) for async services** | Independent scaling, durable logs, replayability, and per-service DLQs | Requires broker monitoring, lag alerting, and DLQ replay procedures |
| **Synchronous HTTP chains for follow-up work**             | Immediate success/failure feedback                                     | Downstream outages block checkout and review submissions            |
| **Per-service broker choice**                              | Tailored to individual workloads                                       | Fragments operational tooling, monitoring, and retry semantics      |
| **Shared-database polling**                                | No separate broker required                                            | Violates service data ownership and adds polling load               |

## Decision & Consequences

**Chosen Option:** Use Kafka (via WolverineFx) as the standard asynchronous integration backbone across event-driven services, with bounded retries and per-service dead-letter queues. Purely synchronous or interactive services (such as [[service|chat-api]] and [[service|mcp-server]]) intentionally omit broker integration.

- **Positive:** Publishers and consumers evolve and scale independently; failed deliveries route cleanly to service-owned DLQs.
- **Negative:** Operators must monitor consumer lag and maintain DLQ replay procedures.

### Compliance Criteria

- Asynchronous cross-service events and commands must use configured Kafka channels following BookWorm's environment-prefixed naming convention.
- Every Kafka consumer must configure bounded retries and a dedicated dead-letter queue.
- Services without asynchronous integration needs must not register unnecessary broker dependencies.
