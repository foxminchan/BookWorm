## Context and problem statement

BookWorm coordinates checkout orchestration, basket cleanup, email notifications, rating projections, and scheduled vector-index refreshes across independent services. Executing downstream work synchronously inside the initiating request couples latency and availability across bounded contexts.

BookWorm needs one standard asynchronous transport backbone for cross-capability integration events and commands without imposing a broker on services that have no asynchronous messaging role.

## Decision drivers

- **Decoupling:** Isolate request latency and uptime from downstream asynchronous consumers.
- **Standardization:** Reuse one messaging library, CloudEvents serialization format, topic-naming convention, and dead-letter queue pattern.
- **Explicit ownership:** Keep message contracts, topic names, and partition keys owned by the publishing bounded context.

## Considered options

1. Use Apache Kafka through Wolverine as the configured asynchronous integration backbone
2. Coordinate all cross-capability workflows through synchronous HTTP or gRPC calls
3. Adopt different message brokers per bounded context
4. Coordinate cross-capability work through shared database polling

## Decision outcome

Chosen option: **Use Apache Kafka through Wolverine as the configured asynchronous integration backbone**, because it decouples producers from consumers while standardizing serialization, correlation, partitioning, and dead-letter routing across messaging-enabled hosts.

Eight backend services connect to Kafka (`catalog`, `catalog-ingestion`, `basket`, `ordering`, `rating`, `notification`, `scheduler`, and `finance`), while Chat API and MCP Tools intentionally omit Kafka because they operate synchronously. `BookWorm.Chassis` configures Wolverine (`WolverineFx.Kafka` `6.65.1`) with CloudEvents JSON serialization, topic naming (`bookworm.{environment-kebab}.{owner-service}.{topic-name}` by default, or `{owner-service}.{topic-name}` when `AppendPrefix = false` as in `scheduler.process-vector-batch`), per-service dead-letter queues (`bookworm.{environment-kebab}.{service-kebab}.dead-letter-queue`), and jittered retries (`50ms`, `250ms`, `1s`). Locally, Aspire runs a Kafka container with Kafka UI; in cloud deployments, `ConnectionStrings__broker` connects to Confluent Cloud.

### Consequences

- **Positive:** Services publish domain outcomes without waiting for downstream consumers to complete, and partition keys (`OrderId`, `BookId`, `FeedbackId`) preserve per-entity ordering.
- **Negative:** Broker provisioning, topic permissions, consumer lag monitoring, and dead-letter triage become ongoing operational responsibilities, and a missing broker connection string disables Kafka transport registration on a host.
- **Follow-up:** Verify per-service durability and idempotency boundaries under ADR-BW-008 and confirm message correlation rules under ADR-BW-010.

## Pros and cons of the options

### Use Apache Kafka through Wolverine as the configured asynchronous integration backbone

- **Good**, because producers and consumers evolve and scale independently using one shared CloudEvents and topic-routing convention.
- **Good**, because partitioned logs support replay and deterministic per-entity ordering.
- **Bad**, because Kafka introduces operational complexity for retention, partitioning, and dead-letter recovery.

### Coordinate all cross-capability workflows through synchronous HTTP or gRPC calls

- **Good**, because callers observe immediate success or failure within one request.
- **Bad**, because any downstream outage or latency spike blocks checkout, feedback submission, or maintenance jobs.

### Adopt different message brokers per bounded context

- **Good**, because each service can pick a broker optimized for its local pattern.
- **Bad**, because every cross-context integration requires bridge adapters and duplicated operational runbooks.

### Coordinate cross-capability work through shared database polling

- **Good**, because local work stays inside a single relational database.
- **Bad**, because polling breaks service-owned persistence boundaries (ADR-BW-006) and lacks BookWorm's standardized integration contracts.
