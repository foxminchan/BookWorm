## Context & Problem Statement

[[domain|bookworm]]'s backend services share common tooling for hosting, resilience, observability, testing, and centralized package management. Allowing each service to adopt a different runtime or independently pin package versions would fragment operational tooling, duplicate integration effort, and complicate security patching.

## Decision Drivers

- **Tooling reuse:** Share proven runtime defaults across backend services.
- **Dependency hygiene:** Prevent version drift and conflicting transitive packages.
- **Contributor onboarding:** Provide one predictable build, lint, and test workflow.
- **Patch velocity:** Apply security and runtime upgrades consistently across services.

## Options Considered

| Option                                                        | Pros                                                                | Cons                                                                    |
| :------------------------------------------------------------ | :------------------------------------------------------------------ | :---------------------------------------------------------------------- |
| **Standardize on .NET baseline + central package management** | Consistent setup, quality gates, and single-point security patching | Services cannot adopt a different runtime without an explicit exception |
| **Per-service runtime choice**                                | Optimal fit for niche workloads                                     | Multiplies monitoring, CI, and security maintenance overhead            |
| **Migrate all services to a different runtime**               | Aligns with an alternative ecosystem                                | High rewrite cost with no direct customer or operational gain           |
| **Independent per-project package versioning**                | Individual services can upgrade dependencies early                  | Causes version skew and subtle cross-service incompatibilities          |

## Decision & Consequences

**Chosen Option:** Retain the established .NET and C# baseline with centralized package version management for all core backend services. Storefront microfrontends, external providers (such as [[service|presidio-api]]), and specialized datastores remain free to use their native ecosystems.

- **Positive:** Consistent quality gates, predictable onboarding, and coordinated security updates across services.
- **Negative:** Major framework or shared-package upgrades require validation across all backend services.

### Compliance Criteria

- Backend application services must target the repository's established .NET SDK baseline.
- Package versions must be managed centrally rather than pinned in individual service project files.
- Non-.NET runtimes are permitted only for specialized external containers or frontend applications.
