## Context and problem statement

BookWorm's main parts already share common tools for running, checking, protecting, connecting, and testing the system. They also use one approach for keeping supporting software consistent.

If each part chose a different foundation or different versions of supporting software, teams would need to maintain more tools, repeat connection work, and spend more time upgrading the system. BookWorm needs one clear foundation for its main parts while allowing websites, helper programs, and external providers to use the technology that suits them.

## Decision drivers

- **Reuse:** Let the main parts share proven tools for everyday needs.
- **Easy to maintain:** Prevent different foundations and inconsistent software versions from spreading across the system.
- **Easy for newcomers:** Give new contributors one consistent way to build and check the software.
- **Reliable upgrades:** Make improvements and security updates easier to apply across the main parts.

## Considered options

1. Use one established foundation and manage supporting software centrally
2. Let each main part choose its own foundation
3. Move all main parts to a different foundation
4. Choose supporting software versions independently for each main part

## Decision outcome

Chosen option: **Use one established foundation and manage supporting software centrally**.

All main parts will use the foundation already selected for the project. They will follow the same setup, quality, and security rules, and supporting software will have approved versions managed from one place.

This decision does not limit future upgrades. Future foundation improvements will follow the project's approved approach. Websites, helper programs, and stored information systems can continue using the approaches that work best for them.

### Consequences

- **Positive:** Main parts share reliable tools without repeating the same work.
- **Positive:** Security fixes and updates can reach every main part consistently.
- **Positive:** Contributors work with familiar rules and expectations.
- **Negative:** Foundation or shared-tool upgrades require checks across every main part.
- **Follow-up:** Record formal approval and continue checking that supporting software remains centrally managed.

## Pros and cons of the options

### Use one established foundation and manage supporting software centrally

- **Good**, because every main part shares the same setup tools and quality rules.
- **Good**, because approved improvements and security fixes can be introduced in one controlled place.
- **Bad**, because a main part cannot choose a different foundation without a formal exception.

### Let each main part choose its own foundation

- **Good**, because teams can select a foundation that suits a particular need.
- **Bad**, because each new foundation requires separate monitoring, security, communication, and release work.

### Move all main parts to a different foundation

- **Good**, because it could align the system with a different approach if strong needs emerged.
- **Bad**, because moving to it would require substantial rewriting without a clear benefit for customers or day-to-day operation.

### Choose supporting software versions independently for each main part

- **Good**, because one main part could upgrade supporting software before the others.
- **Bad**, because different versions can stop the main parts from working together and create extra maintenance.
