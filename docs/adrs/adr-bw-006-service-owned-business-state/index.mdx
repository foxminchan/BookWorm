## Context & Problem Statement

Books, baskets, orders, reviews, chat sessions, and scheduled jobs have distinct consistency, retention, and scaling requirements. Allowing multiple services to read or mutate the same database tables bypasses domain invariants and prevents independent schema evolution.

## Decision Drivers

- **Invariant enforcement:** Route every state mutation through a single authoritative service.
- **Storage autonomy:** Let each capability choose the datastore best suited to its workload.
- **Schema freedom:** Evolve internal tables and document schemas without breaking other services.

## Options Considered

| Option                                               | Pros                                                                             | Cons                                                               |
| :--------------------------------------------------- | :------------------------------------------------------------------------------- | :----------------------------------------------------------------- |
| **Capability-owned state and persistence access**    | Single authority for invariants; polyglot storage (PostgreSQL, Redis, Cosmos DB) | Cross-domain queries require API composition or projections        |
| **Shared relational database across services**       | Simple cross-domain SQL joins                                                    | Tight coupling; schema changes risk breaking unrelated services    |
| **Centralized data-access service**                  | Single access gatekeeper                                                         | Creates a central bottleneck that must understand all domain rules |
| **Physically isolated servers for every tiny store** | Maximum hardware isolation                                                       | Unnecessary infrastructure cost for lightweight caches/queues      |

## Decision & Consequences

**Chosen Option:** Keep all business state and persistence access strictly owned by the responsible capability. Each service selects its optimal datastore (e.g., [[container|catalog-database]], [[container|basket-database]], [[container|order-database]], [[container|rating-database]]) and exposes data solely via public contracts.

- **Positive:** Domain invariants cannot be bypassed; internal schema refactors do not impact consumers.
- **Negative:** Cross-domain reporting or enrichment requires explicit API calls or derived projections.

### Compliance Criteria

- Only the owning service may hold read/write credentials or schemas for its authoritative datastore.
- Cross-service data access must use published HTTP, gRPC, or event contractsâ€”never cross-schema SQL queries.
- Shared infrastructure hosts (such as Redis) must isolate keys by service-owned prefixes.
