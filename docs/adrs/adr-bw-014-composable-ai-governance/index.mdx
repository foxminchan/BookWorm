## Context and problem statement

Chat API, Rating API, and MCP Tools process untrusted customer prompts and user-authored review text before invoking Microsoft Foundry models (`ModelRouter`, `MicrosoftDecision1`, Cohere `EmbedV40`) and tool endpoints. Rebuilding prompt-injection defenses, PII redaction, and tool-access policies separately inside each agent creates security drift, whereas assuming a shared library automatically protects every code path leaves newly added AI routes unexamined.

BookWorm needs a composable AI governance model that shares reusable security middleware while enforcing explicit per-agent policies and tool boundaries.

## Decision drivers

- **Defense in depth:** Combine PII detection/anonymization, input/output guardrails, policy enforcement, and scoped identities on every AI execution path.
- **Least privilege:** Restrict each agent and Model Context Protocol (MCP) tool to the minimum read-only data and permissions required.
- **Explicit coverage verification:** Require every new model call or agent route to register governance policies explicitly rather than assuming global coverage.

## Considered options

1. Compose shared `BookWorm.Chassis` AI governance, Presidio PII middleware, and per-service YAML policies across Chat API, Rating API, and MCP Tools
2. Rely solely on system-prompt instructions to restrict model behavior
3. Implement isolated governance and PII controls independently inside each AI service
4. Assume registering a governance package once protects every AI code path automatically

## Decision outcome

Chosen option: **Compose shared `BookWorm.Chassis` AI governance, Presidio PII middleware, and per-service YAML policies across Chat API, Rating API, and MCP Tools**, because it reuses verified middleware while tailoring tool permissions, identity rings, and guardrails per agent.

BookWorm composes four verified layers:

- **Policy kernel (`Microsoft.AgentGovernance.Extensions` `5.0.0`):** `GovernanceKernel` in `BookWorm.Chassis` enforces base rules (`Policies/default.yaml`) plus service-specific policies (`Policies/chat-agents.yaml` in Chat API, `Policies/rating-agent.yaml` in Rating API, and `Policies/mcp-tools.yaml` in MCP Tools).
- **PII protection (Presidio):** Internal `presidio-analyzer` and `presidio-anonymizer` sidecars back `PIIMiddleware` on Chat API and Rating API to detect and anonymize PII before model invocation.
- **Guardrails and deterministic routing:** `GuardrailMiddleware`, `RatingOutputGuardrailMiddleware`, `DecisionToolSelectionMiddleware`, and Microsoft-Decision-1 (`IDecisionClient`) validate inputs, restrict tool selection, and separate trusted instructions from untrusted content.
- **Agent identity isolation:** Microsoft Entra ID Agent Identities (`entra-agent-identities.bicep` provisioning `blueprintAppId`, `chatAgentId`, and `ratingAgentId`) and `UseClaimsBasedAgentIsolation()` isolate agent permissions from end-user tokens.

### Consequences

- **Positive:** Chat API, Rating API, and MCP Tools share consistent PII filtering, injection detection, and policy telemetry while preserving least-privilege tool lists per agent.
- **Negative:** Running Presidio sidecars and governance middleware adds runtime latency, container dependencies, and YAML policy maintenance.
- **Follow-up:** Review YAML policy files, tool allowlists, and Presidio failure behavior whenever adding a new agent, skill, or MCP tool.

## Pros and cons of the options

### Compose shared `BookWorm.Chassis` AI governance, Presidio PII middleware, and per-service YAML policies across Chat API, Rating API, and MCP Tools

- **Good**, because security primitives live in one audited chassis layer while permissions stay scoped to each service's YAML policy.
- **Good**, because Entra ID Agent Identities and claims isolation bound cross-agent A2A and MCP calls.
- **Bad**, because PII detection and guardrails remain defense-in-depth controls rather than an absolute guarantee against novel prompt-injection attacks.

### Rely solely on system-prompt instructions to restrict model behavior

- **Good**, because services avoid extra middleware and sidecar containers.
- **Bad**, because prompt text provides no enforceable runtime boundary against prompt injection or unauthorized tool invocation.

### Implement isolated governance and PII controls independently inside each AI service

- **Good**, because every agent has full local autonomy over its filters.
- **Bad**, because security fixes must be duplicated across Chat API, Rating API, and MCP Tools, inviting policy drift.

### Assume registering a governance package once protects every AI code path automatically

- **Good**, because onboarding a new endpoint looks faster initially.
- **Bad**, because direct `IChatClient` calls or new endpoints can bypass middleware unless explicitly verified during code review.
