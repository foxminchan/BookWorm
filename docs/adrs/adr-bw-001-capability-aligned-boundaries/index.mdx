## Context & Problem Statement

Book discovery, shopping, ordering, reviews, conversations, and platform operations evolve at different cadences and serve distinct business goals. Sharing a single business layer or mutable data model across these areas creates hidden coupling and forces coordinated releases. [[domain|bookworm]] needs a consistent structural boundary so each business capability owns its rules and outcomes independently.

## Decision Drivers

- **Change isolation:** Keep domain rule changes localized to the owning capability.
- **Independent deployability:** Ship compatible improvements without synchronized cross-team releases.
- **Clear accountability:** Assign each business outcome to one owning service and team.
- **Shared technical leverage:** Reuse infrastructure defaults without leaking domain rules into shared libraries.

## Options Considered

| Option                                                  | Pros                                                                 | Cons                                                                |
| :------------------------------------------------------ | :------------------------------------------------------------------- | :------------------------------------------------------------------ |
| **Decompose by business capability (bounded contexts)** | Rules and data stay with the owning team; areas evolve independently | Cross-area journeys require explicit contracts and async recovery   |
| **Single unified application**                          | Fast in-process calls; simpler local debugging                       | Changes couple all domains; failures blast across the entire system |
| **Modular monolith (logical modules, single deploy)**   | Clear logical boundaries without network overhead                    | All capabilities deploy together and share runtime availability     |
| **Split by technical layer (frontend, API, DB teams)**  | Deep functional specialization                                       | Every customer feature spans multiple teams, blurring ownership     |

## Decision & Consequences

**Chosen Option:** Decompose [[domain|bookworm]] by business capability. Each subdomain (Catalog, Shopping, Ordering, Reviews, Conversational, and Platform) owns its rules, persistence, and public contracts, communicating exclusively through explicit APIs and events. Shared building blocks provide technical plumbing only and never encode domain-specific logic.

- **Positive:** Teams release independently, isolate failures, and trace incorrect behavior to a single owning service.
- **Negative:** Cross-boundary workflows (such as checkout and rating projection) require explicit contracts, correlation, and compensation.

### Compliance Criteria

- New features must map to an existing bounded context or justify a new capability boundary.
- Shared libraries must not reference domain entities, business rules, or capability-specific state.
- Cross-capability communication must use documented HTTP, gRPC, or Kafka contracts—never direct database or internal handler calls.
