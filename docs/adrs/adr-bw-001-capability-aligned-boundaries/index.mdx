## Context and problem statement

Catalog, Shopping, Ordering, Reviews, Conversational, and Platform evolve for distinct business reasons and at different paces. Organizing BookWorm around a shared business model or technical layers forces routine changes across ownership boundaries and obscures accountability for business outcomes.

BookWorm requires a whole-system decomposition rule that keeps business logic with its owning capability while allowing shared libraries to supply technical mechanisms.

## Decision drivers

- **Modifiability:** Keep each business-rule change confined to a single owning capability.
- **Deployability:** Release compatible changes independently without coordinating a platform-wide deployment.
- **Correctness:** Assign unambiguous responsibility for every accepted business outcome.

## Considered options

1. Retain capability-aligned bounded contexts with independently deployable services
2. Consolidate into a single deployable monolith
3. Refactor into a modular monolith
4. Split services by technical layer

## Decision outcome

Chosen option: **Retain capability-aligned bounded contexts with independently deployable services**, because it aligns service ownership, data authority, and release boundaries directly with BookWorm's six business domains.

Each bounded context owns its domain model, persistence, and runtime behavior, exposing explicit HTTP, gRPC, or Kafka contracts to other contexts. Shared packages under `src/BuildingBlocks/` provide technical mechanisms rather than a shared business layer. This record governs whole-system decomposition, not the internal design of any individual service.

### Consequences

- **Positive:** Impact analysis, code ownership, and domain evolution follow clear business capabilities across all 10 backend services and 3 frontend applications.
- **Negative:** Cross-context workflows require explicit contracts, failure compensation, and distributed correlation, increasing operational and diagnostic complexity.
- **Follow-up:** Enforce bounded-context dependency rules continuously through `tests/BookWorm.ArchTests` and confirm formal acceptance status with platform maintainers.

## Pros and cons of the options

### Retain capability-aligned bounded contexts with independently deployable services

- **Good**, because business rules and schema changes stay with one accountable owner.
- **Good**, because services can scale and deploy independently when contracts remain compatible.
- **Bad**, because distributed execution adds network latency, partial failure modes, and observability overhead.

### Consolidate into a single deployable monolith

- **Good**, because in-process calls eliminate network hops and simplify local transactions.
- **Bad**, because it conflicts with BookWorm's established independent-service architecture and couples release cycles across all domains.

### Refactor into a modular monolith

- **Good**, because logical modules preserve domain boundaries with lower infrastructure overhead.
- **Bad**, because it reverses the established microservices deployment model and still shares a single release unit and runtime failure domain.

### Split services by technical layer

- **Good**, because teams can specialize in isolated technical tiers.
- **Bad**, because a single business feature spans multiple services and blurs accountability for domain invariants.
