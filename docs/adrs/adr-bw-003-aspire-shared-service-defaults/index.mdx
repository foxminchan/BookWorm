## Context & Problem Statement

BookWorm's services and microfrontends require consistent service discovery, health probes, rate limiting, resilience defaults, and telemetry wiring. Re-implementing this plumbing per service invites configuration drift, while centralizing domain logic in shared host defaults violates service ownership.

## Decision Drivers

- **Operational consistency:** Enforce uniform health, telemetry, and resilience baselines.
- **Reduced boilerplate:** Eliminate repeated technical host configuration across services.
- **Boundary preservation:** Keep shared defaults strictly technical and domain-agnostic.

## Options Considered

| Option                                                     | Pros                                                                               | Cons                                                                       |
| :--------------------------------------------------------- | :--------------------------------------------------------------------------------- | :------------------------------------------------------------------------- |
| **Shared technical defaults + Aspire local orchestration** | Uniform discovery, telemetry, and resilience; services opt in to optional features | Shared-default defects can impact multiple services simultaneously         |
| **Per-service custom host setup**                          | Zero shared-package coupling                                                       | Telemetry, health probes, and rate limits drift over time                  |
| **Centralized business-logic host**                        | Shared rules visible in one place                                                  | Couples unrelated domains and breaks bounded-context ownership             |
| **Treat local Aspire setup as production**                 | Single topology to maintain                                                        | Local emulators lack production durability, scaling, and security controls |

## Decision & Consequences

**Chosen Option:** Reuse Aspire orchestration and shared technical service defaults for discovery, OpenTelemetry, health checks, resilience, and rate limiting. Each service retains ownership of its domain behavior and may override technical defaults where justified.

- **Positive:** New services inherit production-grade observability and resilience defaults immediately.
- **Negative:** Changes to shared defaults require cross-service regression testing.

### Compliance Criteria

- Every backend service must register the shared service defaults for health checks and telemetry.
- Shared defaults must remain free of domain entities, business rules, and capability-specific endpoints.
- Local Aspire emulator settings must not be assumed identical to live Azure environment configuration.
