## Context and problem statement

BookWorm has several core applications and customer-facing websites. They need reliable and consistent setup for finding other parts of the system, handling temporary failures, limiting requests, and reporting health and activity.

BookWorm needs common setup tools that reduce repeated work. Each business area must still keep control of its own rules and decide which shared tools it uses.

## Decision drivers

- **Consistency:** Apply the same health, activity, and failure-handling expectations across the system.
- **Easy maintenance:** Avoid repeating the same technical setup in every area.
- **Clear ownership:** Keep common tools separate from each area's business rules.

## Considered options

1. Use shared setup and local system coordination
2. Configure every area separately
3. Put shared business work in one central area
4. Treat the local setup as the live system setup

## Decision outcome

Chosen option: **Use shared setup and local system coordination**.

BookWorm will use one common technical foundation for local coordination and routine setup. It will include activity reporting, controlled retries, request limits, and shared connection rules.

The live system setup can differ from the local setup. Each business area will still choose and override the options it needs and remain responsible for its own behavior.

### Consequences

- **Positive:** New areas receive dependable defaults and consistent reporting with less repeated setup.
- **Negative:** A change to shared setup can affect several areas at once.
- **Follow-up:** Document local and live differences separately and test shared changes across the system.

## Pros and cons of the options

### Use shared setup and local system coordination

- **Good**, because connection, reporting, and failure handling follow one proven approach.
- **Good**, because each area controls the optional tools it enables.
- **Bad**, because a defect in shared setup can affect several areas.

### Configure every area separately

- **Good**, because every area avoids dependence on shared setup.
- **Bad**, because reporting, limits, and security rules may drift apart over time.

### Put shared business work in one central area

- **Good**, because common business work is visible in one place.
- **Bad**, because it gives one central area responsibility for decisions that belong to separate businesses.

### Treat the local setup as the live system setup

- **Good**, because teams maintain only one setup description.
- **Bad**, because local test tools do not provide the same reliability or availability as live services.
