## Context and problem statement

Ten backend projects and three frontend applications require consistent startup wiring, service discovery, outbound HTTP resilience, rate limiting, Kestrel limits, OpenAPI setup, and OpenTelemetry export. Reimplementing these technical defaults inside every service host causes configuration drift and slows cross-cutting maintenance.

BookWorm needs a shared orchestration and host-default layer that standardizes technical plumbing while keeping domain rules and explicit overrides inside each owning service.

## Decision drivers

- **Consistency:** Apply uniform telemetry, service discovery, Kestrel limits, and outbound HTTP resilience defaults across services.
- **Maintainability:** Eliminate duplicated technical host setup across independent service projects.
- **Boundary preservation:** Keep shared infrastructure free of domain rules so services retain full business ownership.

## Considered options

1. Use Aspire orchestration and `BookWorm.ServiceDefaults` for shared technical configuration
2. Maintain standalone host configuration independently in every service
3. Move shared business execution into a central platform service
4. Treat local Aspire orchestration topology as an implicit production topology specification

## Decision outcome

Chosen option: **Use Aspire orchestration and `BookWorm.ServiceDefaults` for shared technical configuration**, because it provides repeatable local development, standardized Azure Container Apps publishing via Aspire 17, and uniform technical defaults without leaking business rules into shared code.

`src/Aspire/BookWorm.AppHost/AppHost.cs` wires resources, backing stores, YARP gateway routes, and environment-specific provisioning (`aspire start` locally, `aspire deploy` for Azure Container Apps). `src/Aspire/BookWorm.ServiceDefaults/` supplies OpenTelemetry instrumentation, budgeted HTTP retries, Kestrel HTTP/2 limits, development-only `/health` and `/alive` endpoints, OpenAPI transformers, and rate-limiting policies. Each service host explicitly calls the registration helpers it requires and defines its own domain behavior and configuration overrides.

### Consequences

- **Positive:** New and existing services gain consistent diagnostics, service discovery, resilience defaults, and local emulator wiring with minimal boilerplate.
- **Negative:** Changes to `BookWorm.ServiceDefaults` affect every registered service and require regression verification across the solution.
- **Follow-up:** Keep environment-specific deployment behavior documented explicitly under ADR-BW-015 because defining a helper in `BookWorm.ServiceDefaults` does not activate it unless the host registers it.

## Pros and cons of the options

### Use Aspire orchestration and `BookWorm.ServiceDefaults` for shared technical configuration

- **Good**, because service discovery, OpenTelemetry, and HTTP resilience follow one verified convention across hosts.
- **Good**, because services keep local control over which optional capabilities they register and override.
- **Bad**, because a defect in shared service defaults can impact multiple services simultaneously.

### Maintain standalone host configuration independently in every service

- **Good**, because every service has zero coupling to a shared defaults assembly.
- **Bad**, because telemetry schemas, timeout budgets, and security headers drift across hosts over time.

### Move shared business execution into a central platform service

- **Good**, because common orchestration logic lives in one runtime process.
- **Bad**, because it violates capability-aligned ownership established in ADR-BW-001.

### Treat local Aspire orchestration topology as an implicit production topology specification

- **Good**, because teams maintain only one topology description.
- **Bad**, because local emulators (Azurite, Mailpit, Cosmos DB emulator, Durable Task Scheduler emulator) differ materially from production Azure resources and SLAs.
