## Context and problem statement

Customer journeys cross websites, web gateways, core areas, background jobs, and outside providers. Separate text logs cannot show how a failure moved across these parts or how quickly work completed.

BookWorm needs one monitoring approach that connects activity across the system while protecting private information and controlling cost.

## Decision drivers

- **Cross-area diagnosis:** Connect records across customer requests, internal requests, background work, and failures.
- **Open reporting:** Use a standard format that does not depend on one vendor.
- **Privacy and cost:** Hide personal data and collect only the activity needed for diagnosis.

## Considered options

1. Use standard activity records with privacy protection and environment-sensitive sampling
2. Use separate text logs for every area
3. Record every trace and log everywhere
4. Build one vendor's monitoring tool into every area

## Decision outcome

Chosen option: **Use standard activity records with privacy protection and environment-sensitive sampling**.

BookWorm will use consistent activity records across customer-facing and core areas. Local work will record more detail, while live environments will sample activity to control cost.

Areas that handle personal data will remove or hide it before recording. Health checks and monitoring retention will be configured separately for each environment.

### Consequences

- **Positive:** Teams can follow activity from a website through the connected services.
- **Negative:** Sampling may omit details for some live executions.
- **Follow-up:** Verify health checks, alerts, privacy protection, and monitoring costs before each release.

## Pros and cons of the options

### Use standard activity records with privacy protection and environment-sensitive sampling

- **Good**, because websites and core areas share consistent trace references.
- **Good**, because privacy and cost controls apply across environments.
- **Bad**, because each deployment must confirm that recording and redaction remain active.

### Use separate text logs for every area

- **Good**, because setup is simple.
- **Bad**, because teams cannot connect failures across areas or measure journeys reliably.

### Record every trace and log everywhere

- **Good**, because nearly every execution can be inspected.
- **Bad**, because high traffic creates excessive storage and cost.

### Build one vendor's monitoring tool into every area

- **Good**, because one vendor provides all features.
- **Bad**, because switching vendors or local monitoring tools becomes difficult.
