## Context

Failures span HTTP, gRPC, messages, background work, and external dependencies. Isolated text logs cannot consistently explain where work failed or which capability owns the outcome.

## Decision

Reuse shared structured logging and OpenTelemetry instrumentation, W3C trace context, and configured OTLP export. Preserve environment-sensitive sampling and verify host health endpoint mapping for each deployment. Use request and message context for diagnosis without logging raw request or response values.

Process health and execution traces do not replace queries of the owning business state.

## Decision drivers

- Diagnosis across independently executing services.
- Consistent telemetry mechanisms without a mandatory production backend.
- Data minimization and controlled telemetry volume.

## Alternatives considered

| Alternative                         | Assessment                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| Local logs only                     | Has low setup cost but weakens cross-service diagnosis.                      |
| Fully sample every production trace | Improves coverage while increasing volume and cost without an agreed budget. |
| Hard-code one observability vendor  | Simplifies one deployment while exceeding the documented backend choice.     |

## Consequences

- Operators can correlate configured signals across boundaries.
- Sampling can omit individual executions; export requires an endpoint and operational backend.
- Production probes, redaction registration, retention, and alert thresholds need deployment verification.
- No numerical service-level objective follows from instrumentation alone.
