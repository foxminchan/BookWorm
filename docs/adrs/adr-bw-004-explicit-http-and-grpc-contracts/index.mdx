## Context

Checkout, basket presentation, and domain adapters need current information from another capability. Direct access to its persistence or handler classes couples the consumer to implementation details.

## Decision

Use the owning service's published request-response contract. Retain HTTP APIs with OpenAPI descriptions where provided and the defined Basket and Catalog gRPC interfaces with Protocol Buffer schemas. Select the existing contract appropriate to the interaction; do not make gRPC universal or convert asynchronous workflows into synchronous call chains.

## Decision drivers

- Interoperability and explicit ownership.
- Typed, reviewable interface shapes.
- Separation of public semantics from internal persistence.

## Alternatives considered

| Alternative                | Assessment                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| Direct database reads      | Avoids a network API but bypasses ownership and leaks schema details.                     |
| HTTP-only standardization  | Simplifies protocol variety but replaces established gRPC consumers.                      |
| gRPC for every interaction | Provides consistent typed calls but does not fit every external or asynchronous boundary. |

## Consequences

- Consumers depend on an explicit contract rather than another service's internals.
- Synchronous calls create runtime availability and latency dependencies.
- HTTP and Protocol Buffer contracts require separate validation and consumer migration practices.
