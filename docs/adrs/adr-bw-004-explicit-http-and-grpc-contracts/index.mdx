## Context and problem statement

Checkout checks, shopping-cart updates, and customer-assistant tools sometimes need an immediate answer from another area. If an area reads another area's private records or calls its internal work directly, it becomes dependent on details that should remain private.

BookWorm needs clear rules for immediate requests between areas.

## Decision drivers

- **Ownership:** Separate public information from private records and internal work.
- **Interoperability:** Give both customers and connected areas clear, reviewable ways to request answers.
- **Boundary clarity:** Use immediate requests only when an answer is genuinely needed now.

## Considered options

1. Use clearly owned and versioned request agreements
2. Read another area's records directly
3. Use one web-request format for every immediate interaction
4. Use one fast internal-request format for every immediate interaction

## Decision outcome

Chosen option: **Use clearly owned and versioned request agreements**.

Outside clients use documented web requests. Areas use typed internal requests when they need immediate answers from a trusted source. Long-running work does not have to block while waiting and can continue through background updates.

### Consequences

- **Positive:** Requesting areas depend only on public agreements, not private records or internal methods.
- **Negative:** Immediate calls can slow down or fail if the other area is unavailable.
- **Follow-up:** Review web and internal request agreements together before release.

## Pros and cons of the options

### Use clearly owned and versioned request agreements

- **Good**, because customer-facing and internal callers receive an appropriate request format.
- **Good**, because the owning area checks access and information before answering.
- **Bad**, because two request formats require more documentation and review.

### Read another area's records directly

- **Good**, because it avoids a separate network request.
- **Bad**, because it exposes private details and bypasses the area's own checks.

### Use one web-request format for every immediate interaction

- **Good**, because every caller uses familiar web tools.
- **Bad**, because it does not suit every internal call and can add more data to each request.

### Use one fast internal-request format for every immediate interaction

- **Good**, because internal agreements use one consistent structure.
- **Bad**, because websites and outside callers still need a web-based bridge.
