## Context and problem statement

Checkout validation, basket enrichment, and AI tool adapters require synchronous reads from another bounded context. Allowing a consumer to query another service's database or invoke its internal handlers couples services to private implementation details and bypasses domain validation and authorization.

BookWorm needs a clear boundary rule governing synchronous request-response integration across services.

## Decision drivers

- **Ownership:** Keep public interface semantics strictly separated from internal persistence models and handlers.
- **Interoperability:** Provide typed, reviewable contracts suited to both external web clients and internal service-to-service calls.
- **Boundary clarity:** Match the transport protocol to the interaction pattern without forcing asynchronous workflows into synchronous chains.

## Considered options

1. Use service-owned versioned HTTP APIs and Protocol Buffer gRPC contracts
2. Read another service's database directly for synchronous lookups
3. Standardize every synchronous interaction on HTTP JSON only
4. Standardize every synchronous interaction on gRPC only

## Decision outcome

Chosen option: **Use service-owned versioned HTTP APIs and Protocol Buffer gRPC contracts**, because it protects internal models while choosing the right protocol for each consumer boundary.

External clients and the YARP API Gateway call versioned HTTP Minimal APIs (`ApiVersions.V1`, `/api/v1/...`) documented with OpenAPI schemas. Internal service-to-service lookups use explicit Protocol Buffer (`edition = "2023"`) gRPC contracts: `book.v1.BookGrpcService` (served by Catalog API for Basket API, Ordering API, and MCP Tools), `basket.v1.BasketGrpcService` (served by Basket API for Ordering API), and A2A gRPC (served by Rating API for Chat API). Multi-step workflows that do not require an immediate synchronous response continue to use asynchronous Kafka messaging under ADR-BW-005.

### Consequences

- **Positive:** Consumers depend solely on explicit, versioned contracts rather than private schemas or handler classes.
- **Negative:** Synchronous calls introduce runtime latency and availability coupling, and teams must maintain separate linting and evolution workflows for OpenAPI and `.proto` contracts.
- **Follow-up:** Run Protocol Buffer linting and breaking-change checks alongside API contract reviews per ADR-BW-017.

## Pros and cons of the options

### Use service-owned versioned HTTP APIs and Protocol Buffer gRPC contracts

- **Good**, because HTTP APIs serve browser microfrontends and gateway callers cleanly while gRPC gives internal services strongly typed, low-overhead calls.
- **Good**, because owning services enforce authentication, authorization, and validation at the boundary.
- **Bad**, because maintaining both HTTP and gRPC endpoints adds serialization and contract-governance surface area.

### Read another service's database directly for synchronous lookups

- **Good**, because it avoids network serialization overhead.
- **Bad**, because it breaks bounded-context encapsulation, leaks internal table schemas, and bypasses domain authorization rules.

### Standardize every synchronous interaction on HTTP JSON only

- **Good**, because every client and server shares one HTTP tooling stack.
- **Bad**, because it replaces established typed gRPC contracts (`BookGrpcService`, `BasketGrpcService`, A2A gRPC) and loses compile-time Protobuf schema guarantees.

### Standardize every synchronous interaction on gRPC only

- **Good**, because all synchronous contracts use one binary schema language.
- **Bad**, because browser clients, webhooks, and external HTTP callers require HTTP/JSON or gateway transcoding anyway.
