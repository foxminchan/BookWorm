## Context & Problem Statement

Synchronous interactions—such as checkout price validation between [[service|order-api]] and [[service|catalog-api]], basket reads, and [[service|mcp-server]] tool calls—require immediate responses. Reading another service's database or invoking internal handlers directly couples callers to private implementation details and bypasses authorization.

## Decision Drivers

- **Encapsulation:** Separate public contracts from private persistence and internal handlers.
- **Protocol fit:** Serve external clients via RESTful HTTP and internal service-to-service queries via typed gRPC.
- **Synchronous restraint:** Reserve request-response calls for operations that genuinely require an immediate answer.

## Options Considered

| Option                                              | Pros                                                                        | Cons                                                                      |
| :-------------------------------------------------- | :-------------------------------------------------------------------------- | :------------------------------------------------------------------------ |
| **Owned HTTP APIs + typed internal gRPC contracts** | Strong encapsulation, authorization at boundaries, and typed internal calls | Requires maintaining both OpenAPI and Protocol Buffer definitions         |
| **Direct cross-service database reads**             | Zero network hop                                                            | Exposes private schemas and bypasses domain validation and auth           |
| **HTTP/JSON only for all calls**                    | Uniform tooling everywhere                                                  | Higher serialization overhead and weaker schema typing for internal calls |
| **gRPC only for all calls**                         | Single typed contract format                                                | Browsers and external clients still require an HTTP/REST gateway          |

## Decision & Consequences

**Chosen Option:** Integrate synchronous operations exclusively through service-owned HTTP APIs (for frontend and external consumers) and typed gRPC contracts (for internal service-to-service reads such as [[service|catalog-api]] and [[service|basket-api]]). Work that does not require an immediate response must use asynchronous messaging instead.

- **Positive:** Callers depend only on versioned public contracts; owning services enforce all validation and authorization.
- **Negative:** Synchronous calls remain sensitive to downstream availability and require explicit timeouts and fallbacks.

### Compliance Criteria

- Services must never query another service's database, cache, or internal mediator handlers.
- External and frontend endpoints must expose documented HTTP/OpenAPI contracts; internal synchronous reads should prefer typed gRPC contracts.
- Long-running or post-commit side effects must be offloaded to asynchronous events rather than blocking HTTP/gRPC calls.
