## Context and problem statement

BookWorm documents architectural structure across arc42 chapters while recording individual whole-system and per-system design decisions in ADRs. Copying full decision rationale or lifecycle status into arc42 Section 9 creates duplicate sources of truth that drift out of sync whenever a service switches backing stores (such as Rating moving to Azure Cosmos DB or Finance adopting Azure Durable Task Scheduler).

BookWorm needs one single-source documentation rule that keeps each decision authoritative in one MADR file while using the ADR register strictly as a navigable index.

## Decision drivers

- **Traceability:** Give architects and contributors one canonical location to inspect decision context, alternatives, consequences, and superseding links.
- **Zero duplication:** Prevent conflicting status labels and stale rationale between arc42 chapters and individual ADRs.
- **Clear scope separation:** Distinguish whole-system platform principles (`platform/`) from system-specific implementation decisions (`systems/`).

## Considered options

1. Store one authoritative MADR file per decision split into `platform/` and `systems/`, indexed from a single ADR register
2. Embed full decision rationale inline inside arc42 Section 9
3. Flatten all system-specific ADRs into one ungrouped root folder
4. Keep ADRs exclusively inside individual bounded-context folders with no central register

## Decision outcome

Chosen option: **Store one authoritative MADR file per decision split into `platform/` and `systems/`, indexed from a single ADR register**, because it preserves clear ownership between whole-system and system-level decisions while giving readers one entry point to discover active and superseded records.

Whole-system platform decisions (`ADR-BW-001` through `ADR-BW-018`) reside under `explanation/adrs/platform/`, and system-specific decisions—including superseding records when runtime architecture evolves—reside under `explanation/adrs/systems/`. The ADR register ([[doc|arc42/09-architecture-decisions]], corresponding to arc42 Section 9) lists stable IDs, scopes, statuses, and relative links without copying full decision prose. Whenever a service replaces a previously documented technology choice, maintainers add a new superseding MADR record and update lifecycle links rather than silently rewriting history.

### Consequences

- **Positive:** Readers navigate directly from arc42 views or `llms.txt` to one canonical decision record with verified source links and explicit lifecycle status.
- **Negative:** Adding or superseding a decision requires updating both the ADR file's metadata and its entry in the central register.
- **Follow-up:** Surface active platform and superseding system ADRs in `llms.txt` and keep reconstructed platform records marked `Proposed` until formally accepted by maintainers.

## Pros and cons of the options

### Store one authoritative MADR file per decision split into `platform/` and `systems/`, indexed from a single ADR register

- **Good**, because every decision has one canonical URL, stable ID, and explicit `Superseded by` chain.
- **Good**, because separating `platform/` and `systems/` prevents cross-cutting principles from being buried inside service folders.
- **Bad**, because contributors must remember to register new or superseding ADRs in `explanation/adrs/index.md`.

### Embed full decision rationale inline inside arc42 Section 9

- **Good**, because readers can scroll through every decision on one long page.
- **Bad**, because long inline prose duplicates individual ADRs and causes rapid status and accuracy drift.

### Flatten all system-specific ADRs into one ungrouped root folder

- **Good**, because every ADR sits in a single directory.
- **Bad**, because mixing 18 platform principles with dozens of local service records obscures scope and ownership.

### Keep ADRs exclusively inside individual bounded-context folders with no central register

- **Good**, because local service teams manage their files in isolation.
- **Bad**, because whole-system decisions lack a clear home and cross-cutting readers miss superseded system records.
