## Context and problem statement

Invalid input payloads, missing entities, concurrency conflicts, rate-limit rejections, and unhandled exceptions happen across every HTTP service. Implementing ad hoc validation checks and custom error JSON shapes in each endpoint forces Storefront, Commerce, and Backoffice clients to write service-specific error parsers and risks leaking stack traces or internal schema names.

BookWorm requires a shared validation pipeline and uniform HTTP error contract across its Minimal API services.

## Decision drivers

- **Input correctness:** Reject malformed requests before domain handlers execute or touch persistence.
- **Predictable client contracts:** Expose standardized RFC 7807 `ProblemDetails` responses across all APIs.
- **Security and diagnosability:** Attach correlation trace identifiers to client errors while confining raw exception details to server logs.

## Considered options

1. Validate CQRS requests with FluentValidation pipeline behavior and return standardized `ProblemDetails` via shared ASP.NET Core exception handlers
2. Validate inputs and build error JSON manually inside each endpoint
3. Return raw exception messages and stack traces in HTTP error responses
4. Wrap failures inside HTTP `200 OK` responses with custom error flags

## Decision outcome

Chosen option: **Validate CQRS requests with FluentValidation pipeline behavior and return standardized `ProblemDetails` via shared ASP.NET Core exception handlers**, because it stops invalid requests before domain execution and gives frontend clients one consistent error format.

API services register `FluentValidation` (`12.2.0`) validators and `BookWorm.Chassis.CQRS.ValidationBehavior` alongside shared exception handlers (`AddValidationExceptionHandler`, `AddNotFoundExceptionHandler`, `AddGlobalExceptionHandler`, and `AddProblemDetails`). Validation failures return field-grouped `400 Bad Request` problem responses, missing entities map to `404 Not Found`, rate-limit rejections return `429 Too Many Requests` `ProblemDetails` with a `Retry-After` header, and unexpected errors return generic `500 Internal Server Error` problem payloads carrying a trace identifier. Internal exception details stay in structured logs. Each host explicitly registers its validators, exception handlers, and domain-specific conflict mappings.

### Consequences

- **Positive:** Frontend applications (`@workspace/api-client`) and API consumers parse one uniform `ProblemDetails` contract across Catalog API, Basket API, Ordering API, Rating API, and Chat API.
- **Negative:** Contributors must register validators and custom domain exception mappings explicitly in each host and keep validation rules synchronized with API contracts.
- **Follow-up:** Verify exception-handler registration and problem-details responses in service unit tests and OpenAPI documentation.

## Pros and cons of the options

### Validate CQRS requests with FluentValidation pipeline behavior and return standardized `ProblemDetails` via shared ASP.NET Core exception handlers

- **Good**, because invalid commands never reach domain repositories or external dependencies.
- **Good**, because RFC 7807 `ProblemDetails` aligns natively with ASP.NET Core Minimal APIs and OpenAPI schemas.
- **Bad**, because teams must verify that every host wires the shared handlers and maps service-specific domain conflicts intentionally.

### Validate inputs and build error JSON manually inside each endpoint

- **Good**, because endpoints have zero dependency on shared middleware.
- **Bad**, because validation logic and error formats diverge quickly across endpoints and services.

### Return raw exception messages and stack traces in HTTP error responses

- **Good**, because developers see failure details directly in browser network tabs.
- **Bad**, because exposing internal stack traces, SQL/Cosmos error messages, or connection metadata creates a security disclosure risk.

### Wrap failures inside HTTP `200 OK` responses with custom error flags

- **Good**, because transport status codes never vary.
- **Bad**, because it breaks HTTP semantics, confuses gateway/client retries, and undermines OpenTelemetry error-rate metrics.
