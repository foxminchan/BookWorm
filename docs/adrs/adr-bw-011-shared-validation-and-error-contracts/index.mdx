## Context & Problem Statement

Every HTTP API in [[domain|bookworm]] handles invalid payloads, missing resources, rate limits, and unexpected faults. If each service invents its own error schema or leaks raw stack traces, microfrontends become brittle and internal implementation details are exposed to callers.

## Decision Drivers

- **Early rejection:** Validate inputs before executing business logic or database writes.
- **Contract consistency:** Return RFC-compliant `ProblemDetails` across all HTTP services.
- **Information security:** Keep stack traces and internal exception details out of client responses.

## Options Considered

| Option                                                            | Pros                                                             | Cons                                                            |
| :---------------------------------------------------------------- | :--------------------------------------------------------------- | :-------------------------------------------------------------- |
| **Shared validation pipeline + standard `ProblemDetails` errors** | Consistent client error handling; invalid requests blocked early | Services must register validators and domain exception mappings |
| **Ad-hoc per-endpoint validation and errors**                     | Zero shared-pipeline setup                                       | Error formats and status codes diverge across services          |
| **Return raw exception details to clients**                       | Faster ad-hoc debugging                                          | Leaks internal schemas, paths, and stack traces                 |
| **Mask failures behind `200 OK` responses**                       | Uniform HTTP status                                              | Breaks HTTP semantics and misleads retry logic                  |

## Decision & Consequences

**Chosen Option:** Validate requests in a shared pre-handler pipeline and map failures to standardized `ProblemDetails` HTTP responses carrying a correlation trace ID. Detailed exception diagnostics remain strictly in protected OpenTelemetry logs.

- **Positive:** Storefront and Backoffice handle validation, `404`, `409`, `429`, and `500` responses uniformly.
- **Negative:** Every new command or query must include an explicit validator and exception mapping where applicable.

### Compliance Criteria

- HTTP APIs must return `ProblemDetails` for validation (`400`), missing (`404`), conflict (`409`), rate-limit (`429`), and server (`500`) errors.
- Production error responses must never expose stack traces, SQL errors, or internal file paths.
- Request validation must run in the shared pipeline before handler execution.
