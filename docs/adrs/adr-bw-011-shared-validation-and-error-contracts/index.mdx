## Context and problem statement

Invalid entries, missing items, changed records, and unexpected failures can occur in every customer-facing area. If each area returns errors differently, websites must understand many formats and may expose technical details.

BookWorm needs consistent input checks and understandable error responses.

## Decision drivers

- **Input correctness:** Reject malformed requests before they change or read business information.
- **Predictable answers:** Use one consistent error format across areas.
- **Security:** Hide technical details while giving support teams enough information to diagnose a problem.

## Considered options

1. Check requests in a shared pipeline and return one standard error format
2. Build validation and errors separately in every connection point
3. Show technical failure details to customers
4. Hide failures behind successful responses

## Decision outcome

Chosen option: **Check requests in a shared pipeline and return one standard error format**.

Each area checks inputs before business work begins. Missing items and too many requests receive clear and consistent messages.

Unexpected errors receive a safe generic message plus a trace reference for support. Technical details remain in protected system logs.

### Consequences

- **Positive:** Customer applications receive predictable answers across all areas.
- **Negative:** Every area must register and maintain its own rules and conflict responses.
- **Follow-up:** Test error responses whenever an area or customer request changes.

## Pros and cons of the options

### Check requests in a shared pipeline and return one standard error format

- **Good**, because invalid work never reaches business or outside systems.
- **Good**, because customer applications understand one consistent format.
- **Bad**, because each area must confirm that it uses the shared checks correctly.

### Build validation and errors separately in every connection point

- **Good**, because each connection point works independently.
- **Bad**, because formats and rules quickly diverge.

### Show technical failure details to customers

- **Good**, because developers can see detailed information immediately.
- **Bad**, because customers or attackers may learn private system details.

### Hide failures behind successful responses

- **Good**, because a website may receive a consistent status.
- **Bad**, because it makes success, failure, and retry decisions misleading.
