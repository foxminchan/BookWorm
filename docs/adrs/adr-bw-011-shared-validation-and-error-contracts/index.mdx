## Context

Invalid requests and unexpected failures occur across APIs. Ad hoc validation and error formats force consumers to interpret inconsistent responses and risk exposing implementation details.

## Decision

Reuse the FluentValidation CQRS behavior for applicable requests and the shared ASP.NET Core exception handlers where registered. Preserve field-grouped validation problems, documented argument and conflict mappings, and generic unexpected-error responses with a trace identifier. Log internal exception detail rather than returning it to clients.

Each host must register validators and exception handling explicitly; service-specific domain errors still require deliberate mapping.

## Decision drivers

- Correctness before business-handler execution.
- Predictable consumer error handling.
- Diagnostic traceability without internal-detail disclosure.

## Alternatives considered

| Alternative                                  | Assessment                                                                         |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| Validate independently inside every endpoint | Allows local flexibility but duplicates checks and response mapping.               |
| Return raw exception text                    | Helps immediate debugging but leaks implementation and potentially sensitive data. |
| Convert all errors to success responses      | Simplifies response shape while hiding failure from consumers and operators.       |

## Consequences

- Registered request paths expose consistent error semantics.
- Validators and mappings must evolve with the owning contract.
- Shared helpers do not prove universal registration or identical mapping for every domain exception.
