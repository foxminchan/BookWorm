## Context & Problem Statement

Transient network or provider faults affect read queries, checkout writes, scheduled batches, and SMTP email delivery differently. Applying identical aggressive retries everywhere can duplicate orders or emails, while disabling retries altogether turns brief blips into customer-visible outages.

## Decision Drivers

- **Transient recovery:** Absorb brief network or dependency hiccups automatically.
- **Side-effect safety:** Prevent blind retries from duplicating orders, charges, or emails.
- **Bounded failure:** Enforce timeouts, circuit breakers, and dead-letter queues so outages stay visible.

## Options Considered

| Option                                                       | Pros                                                                 | Cons                                                                         |
| :----------------------------------------------------------- | :------------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **Shared outbound defaults + operation-specific resilience** | Safe retries for reads; idempotency/circuit-breakers/DLQs for writes | Each integration must review its timeout and retry semantics                 |
| **Uniform aggressive retries everywhere**                    | Simple global policy                                                 | Duplicates non-idempotent side effects and amplifies outages                 |
| **Zero retries anywhere**                                    | Never repeats an external call                                       | Brief transient blips cause immediate user-facing failures                   |
| **Assume idempotency guards guarantee exactly-once**         | Simpler mental model                                                 | Time-bounded guards and external SMTP timeouts cannot guarantee exactly-once |

## Decision & Consequences

**Chosen Option:** Apply shared outbound resilience defaults (timeouts, jittered retries, circuit breakers) tailored to operation semantics—combining idempotency keys, bounded saga retries ([[service|order-orchestration]]), misfire policies ([[service|scheduler-service]]), and DLQs ([[service|notification-api]]) without claiming exactly-once external side effects.

- **Positive:** Read paths recover transparently while stateful and external integrations remain protected against amplification and silent loss.
- **Negative:** Every new outbound client or consumer must explicitly configure and document its retry/timeout bounds.

### Compliance Criteria

- Non-idempotent write endpoints (such as order creation) must require client idempotency keys (`x-request-id`).
- Outbound HTTP/gRPC/SMTP clients must configure explicit timeouts and circuit breakers.
- Architecture and operational docs must describe at-least-once delivery with idempotent handling rather than claiming exactly-once.
