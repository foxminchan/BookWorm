## Context and problem statement

Network calls and outside services can fail temporarily. Retrying a harmless search has different consequences from retrying an order, a refund, or an email.

BookWorm needs protection matched to the work being performed. It must avoid repeated attempts that duplicate customer actions or overload another system.

## Decision drivers

- **Transient recoverability:** Recover from short interruptions without failing unnecessarily.
- **Side-effect safety:** Prevent duplicate orders, emails, or refunds.
- **Controlled failure:** Set clear limits and record failures so teams can respond.

## Considered options

1. Use shared limits plus protection matched to each operation
2. Retry every operation in the same way
3. Disable retries everywhere
4. Assume duplicate protection guarantees an all-or-nothing outcome everywhere

## Decision outcome

Chosen option: **Use shared limits plus protection matched to each operation**.

BookWorm will limit retries and waiting time for quick requests. It will pause temporarily failing systems when repeated attempts would be harmful. It will recognize repeated updates and undo work when an automated correction is possible.

No retry or duplicate-guard system should be described as guaranteeing that every outside action happens exactly once.

### Consequences

- **Positive:** Temporary failures recover without removing important protections.
- **Negative:** Every new connection must define suitable timeouts and duplicate handling.
- **Follow-up:** Set live limits only after service-level performance needs are known.

## Pros and cons of the options

### Use shared limits plus protection matched to each operation

- **Good**, because quick reads and sensitive actions receive appropriate handling.
- **Good**, because sustained failures remain visible.
- **Bad**, because settings must be reviewed for every workflow.

### Retry every operation in the same way

- **Good**, because configuration is simple.
- **Bad**, because blind retries can duplicate sensitive actions and overload other systems.

### Disable retries everywhere

- **Good**, because the system never repeats an outside action.
- **Bad**, because a short interruption immediately fails customer work.

### Assume duplicate protection guarantees an all-or-nothing outcome everywhere

- **Good**, because teams write less recovery code.
- **Bad**, because outside providers and temporary guards cannot guarantee one exact outcome.
