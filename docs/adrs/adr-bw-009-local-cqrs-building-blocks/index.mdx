## Context and problem statement

Web and internal requests need consistent checking, activity recording, validation, and coordinated changes. Putting business work directly into connection points repeats support work and makes it harder to test.

BookWorm needs one consistent way to organize work inside each area. That internal organization must not become an agreement shared between areas.

## Decision drivers

- **Easy testing:** Test actions and questions independently from connection methods.
- **Reliable performance:** Prepare routine work before the system runs rather than discovering it repeatedly.
- **Consistent handling:** Apply the same logging, checking, and change rules everywhere.

## Considered options

1. Use small, area-owned action and read units
2. Use another coordination library
3. Put business work directly into connection points
4. Share internal action units across areas

## Decision outcome

Chosen option: **Use small, area-owned action and read units**.

Each area will separate customer actions from information reads and keep those units close to the relevant business feature. Shared support will provide consistent logging, tracing, validation, and change handling.

This is an internal organization pattern. It does not require every area to use separate storage or recreate event history.

### Consequences

- **Positive:** Work units remain small and easy to test independently.
- **Negative:** Contributors must follow one internal organization and shared setup pattern.
- **Follow-up:** Check that units stay within the correct area and do not become shared agreements.

## Pros and cons of the options

### Use small, area-owned action and read units

- **Good**, because setup and support rules remain consistent.
- **Good**, because each unit is easy to test and understand.
- **Bad**, because contributors must learn the agreed organization pattern.

### Use another coordination library

- **Good**, because it may be familiar to some teams.
- **Bad**, because it can introduce incompatible internal patterns and extra complexity.

### Put business work directly into connection points

- **Good**, because requests do not pass through another internal step.
- **Bad**, because connection points become crowded and harder to test.

### Share internal action units across areas

- **Good**, because areas avoid creating separate agreements.
- **Bad**, because it couples deployments and exposes internal work.
