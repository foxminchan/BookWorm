## Context and problem statement

Service endpoints need isolated, testable command and query handlers wrapped in consistent logging, tracing, validation, and transaction behaviors. Placing domain orchestration directly inside HTTP Minimal API or gRPC endpoints duplicates cross-cutting plumbing and couples business logic to transport types.

BookWorm needs one compile-time, in-process CQRS mediator standard across services while ensuring local command and query records are never mistaken for cross-service integration contracts.

## Decision drivers

- **Testability:** Unit-test commands, queries, and domain invariants independently of ASP.NET Core or gRPC transports.
- **Performance and AOT readiness:** Generate dispatch tables at compile time without reflection-based runtime scanning.
- **Pipeline consistency:** Reuse standardized behaviors from `BookWorm.Chassis` across every API service.

## Considered options

1. Use local Vertical Slice CQRS handlers with `Mediator.SourceGenerator` (`3.0.2`) and `BookWorm.Chassis` pipeline behaviors
2. Adopt `MediatR` as the in-process mediator library
3. Implement business logic directly inside HTTP and gRPC endpoints
4. Share local command handlers directly across service boundaries

## Decision outcome

Chosen option: **Use local Vertical Slice CQRS handlers with `Mediator.SourceGenerator` (`3.0.2`) and `BookWorm.Chassis` pipeline behaviors**, because source generation eliminates reflection overhead while keeping validation, telemetry, and transaction handling uniform across services.

API services register `Mediator.SourceGenerator` (`3.0.2`) and `Mediator.Abstractions` (`3.0.2`) alongside `BookWorm.Chassis.CQRS` behaviors (`LoggingBehavior`, `ActivityBehavior`, `ValidationBehavior`, and `TransactionBehavior` where applicable) plus command and query metrics. Services must not add `MediatR` as a competing mediator. CQRS here is strictly an in-process code organization pattern; it does not mandate event sourcing or separate read/write databases (only Ordering API pairs CQRS with Marten event sourcing).

### Consequences

- **Positive:** Handlers remain small, `sealed`, and directly testable under TUnit with `Moq` and `Shouldly`, while compile-time source generation catches missing registrations early.
- **Negative:** Contributors must follow `Mediator.SourceGenerator` handler signatures and pipeline registration order, and changes to shared behaviors require testing across all host boundaries.
- **Follow-up:** Enforce handler naming, sealing, and vertical-slice boundaries automatically in `tests/BookWorm.ArchTests`.

## Pros and cons of the options

### Use local Vertical Slice CQRS handlers with `Mediator.SourceGenerator` (`3.0.2`) and `BookWorm.Chassis` pipeline behaviors

- **Good**, because compile-time source generation removes runtime reflection overhead and aligns with modern .NET 11 patterns.
- **Good**, because every registered service reuses `LoggingBehavior`, `ActivityBehavior`, `ValidationBehavior`, and `TransactionBehavior`.
- **Bad**, because developers unfamiliar with source-generated mediators must learn its registration and lifetime rules (`ServiceLifetime.Scoped`).

### Adopt `MediatR` as the in-process mediator library

- **Good**, because `MediatR` is widely recognized across older .NET codebases.
- **Bad**, because BookWorm explicitly bans `MediatR` to avoid reflection dispatch, commercial licensing friction, and competing mediator abstractions inside `BookWorm.Chassis`.

### Implement business logic directly inside HTTP and gRPC endpoints

- **Good**, because request handling avoids an extra handler indirection layer.
- **Bad**, because endpoints duplicate validation, logging, tracing, and transaction management and become harder to unit-test in isolation.

### Share local command handlers directly across service boundaries

- **Good**, because services avoid writing cross-boundary DTOs.
- **Bad**, because sharing internal handlers couples service deployments and violates ADR-BW-001 and ADR-BW-004.
