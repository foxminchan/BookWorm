## Context

Service endpoints need testable business handlers and common validation and logging behaviors. Embedding all logic in endpoints duplicates technical concerns and makes focused tests harder.

## Decision

Follow the established local CQRS pattern with Mediator.SourceGenerator and reusable handler behaviors where applicable. Do not introduce MediatR as a competing mediator or expose another service's handlers as a shortcut around its contract.

CQRS here is an in-process organization technique. It does not mandate event sourcing, separate physical read/write databases, or broker delivery for every command.

## Decision drivers

- Testability of handlers and domain behavior.
- Consistent validation and logging pipelines.
- Compatibility with existing repository libraries and conventions.

## Alternatives considered

| Alternative                                  | Assessment                                                                 |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| Endpoint-only business logic                 | Reduces indirection but repeats cross-cutting behavior and mixes concerns. |
| Introduce a second mediator library          | Adds dependency and pipeline variation without an established need.        |
| Use local handlers across service boundaries | Reuses implementation at the cost of deployment and ownership coupling.    |

## Consequences

- Business behavior can be tested apart from transport entry points.
- Contributors must understand handler and pipeline conventions.
- Shared pipeline changes need tests at registered host boundaries; local command types are not automatically integration contracts.
