## Context and problem statement

Independent releases fail when one area changes a web request, internal agreement, background update, or route name without warning the areas that use it.

BookWorm needs rules that keep routine releases compatible and coordinate unavoidable breaking changes.

## Decision drivers

- **Interoperability:** Keep publishers and consumers compatible during rolling releases.
- **Independent releases:** Let safe additions ship without updating every area.
- **Meaningful changes:** Protect names, routing, and business meaning as well as technical formats.

## Considered options

1. Review impact and compatibility before publishing a change
2. Let publishers change agreements freely
3. Update recorded agreements before checking compatibility
4. Release every area together for every change

## Decision outcome

Chosen option: **Review impact and compatibility before publishing a change**.

Before changing a web request, internal agreement, or background update:

1. Identify the owner and every known user.
2. Prefer additions that older users can accept.
3. Run compatibility checks before approved agreements change.
4. Coordinate a migration when a breaking or meaning-changing adjustment is unavoidable.

### Consequences

- **Positive:** Compatible improvements can ship independently.
- **Negative:** Breaking changes require planning, approval, and documentation.
- **Follow-up:** Keep the list of users current and require compatibility checks for every agreement change.

## Pros and cons of the options

### Review impact and compatibility before publishing a change

- **Good**, because automated checks catch incompatible removals and format changes.
- **Good**, because versioning provides a clear migration path.
- **Bad**, because automated tools cannot detect every change in meaning.

### Let publishers change agreements freely

- **Good**, because publishers iterate without coordination.
- **Bad**, because unannounced changes break customer journeys and connected areas.

### Update recorded agreements before checking compatibility

- **Good**, because checks pass immediately.
- **Bad**, because rewriting the baseline removes the safety net.

### Release every area together for every change

- **Good**, because all areas use matching versions.
- **Bad**, because it removes independent release ability and creates large rollout risk.
