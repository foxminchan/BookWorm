## Context

Independent deployment is unsafe when a producer changes interface shape, routing identity, or business meaning without considering consumers. Updating a compatibility baseline too early can hide an incompatible schema change.

## Decision

Identify the owner and known consumers before changing a contract. Prefer additive changes that preserve existing behavior, verify asynchronous consumer/provider contracts, and check Protocol Buffer lint and breaking compatibility against the committed baseline before updating it. Commit validated schema and baseline changes together.

Coordinate a migration for breaking changes, including semantic changes that schema tools cannot detect. Independent release is conditional on compatibility, not merely on separate deployment units.

## Decision drivers

- Interoperability across service versions.
- Deployability without forced platform-wide releases for compatible changes.
- Preservation of event identity, routing, and business semantics.

## Alternatives considered

| Alternative                                        | Assessment                                                            |
| -------------------------------------------------- | --------------------------------------------------------------------- |
| Change the producer and expect consumers to follow | Gives local speed but creates runtime incompatibility.                |
| Update the baseline before compatibility checks    | Silences evidence instead of validating the change.                   |
| Release all services together for every change     | Reduces version variation but discards intended release independence. |

## Consequences

- Compatible changes can preserve independent service evolution.
- Breaking changes require coordination, migration, and updated documentation.
- Known-consumer tests cannot prove compatibility with undiscovered consumers; ownership and consumer inventory still matter.
