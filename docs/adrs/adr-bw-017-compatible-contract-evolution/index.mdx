## Context & Problem Statement

Independent service deployments break when a publisher removes fields, renames topics, or alters semantic meaning in HTTP, gRPC, or Kafka contracts without coordinating with consumers. BookWorm needs clear evolution rules so routine additive changes ship independently while breaking changes follow a controlled migration.

## Decision Drivers

- **Rolling-upgrade safety:** Keep producers and consumers compatible during staggered deployments.
- **Independent velocity:** Ship additive contract improvements without lockstep releases.
- **Semantic integrity:** Protect business meaning and topic routing, not just wire syntax.

## Options Considered

| Option                                                                 | Pros                                            | Cons                                                    |
| :--------------------------------------------------------------------- | :---------------------------------------------- | :------------------------------------------------------ |
| **Backward-compatible evolution + impact review for breaking changes** | Safe independent deploys; clear versioning path | Automated checks cannot catch every semantic shift      |
| **Unrestricted publisher changes**                                     | Fast for single-team iteration                  | Breaks downstream consumers and customer journeys       |
| **Overwrite contract baselines before testing**                        | Checks pass immediately                         | Defeats the safety net of contract testing              |
| **Lockstep releases across all services**                              | Versions always match                           | Eliminates independent deployability; high rollout risk |

## Decision & Consequences

**Chosen Option:** Require backward-compatible (additive, optional) evolution for existing HTTP, gRPC, and Kafka contracts, gated by consumer-impact review and automated contract/schema checks. Unavoidable breaking changes must introduce a new API version or topic and coordinate consumer migration.

- **Positive:** Services deploy independently without breaking active consumers.
- **Negative:** Breaking migrations require dual-support periods and explicit deprecation.

### Compliance Criteria

- Existing required fields, enum values, or topic names must not be removed or renamed in place.
- Contract changes must be reflected in OpenAPI/Protobuf/JSON schemas and verified against consumer contract tests.
- Breaking HTTP changes must increment the explicit API version (e.g., `v1` to `v2`).
