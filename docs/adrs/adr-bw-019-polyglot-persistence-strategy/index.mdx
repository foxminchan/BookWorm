## Context & Problem Statement

BookWorm's capabilities have markedly different data access patterns: transactional catalog & event-sourced ordering, high-volume per-book feedback documents, ephemeral low-latency shopping carts, and semantic vector similarity search. Forcing every service onto a single database engine would either compromise latency/search quality or introduce awkward schema workarounds.

## Decision Drivers

- **Capability autonomy:** Each service owns its private store with zero cross-service database sharing.
- **Workload fit:** Relational ACID + Marten event store for Ordering/Catalog, partitioned document storage for Reviews, sub-millisecond key-value storage for Shopping, and vector similarity search for Discovery.
- **Operational clarity:** Keep the set of approved storage engines small and well-supported by Aspire hosting.

## Decision & Consequences

**Chosen Option:** Standardize on four purpose-matched persistence engines:

- **PostgreSQL:** Authoritative relational/event-store persistence for [[service|catalog-api]], [[service|order-api]] (Marten), [[service|notification-api]], and [[service|scheduler-service]] (Quartz).
- **Azure Cosmos DB:** Partitioned document store (`/bookId`) with ETag concurrency for [[service|rating-api]] (`ratingdb`/`feedbacks`).
- **Redis:** Authoritative ephemeral store for [[service|basket-api]], FusionCache backplane, and distributed idempotency/checkout locks.
- **Qdrant:** Derived vector index populated asynchronously by [[service|catalog-ingestion]] for semantic book discovery.

- **Positive:** Optimal latency, partitioning, and query semantics per bounded context.
- **Negative:** Platform operations must maintain backup, monitoring, and restore runbooks for four distinct storage technologies.
