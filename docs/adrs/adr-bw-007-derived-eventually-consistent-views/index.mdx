## Context and problem statement

Book discovery requires fast hybrid vector search and precomputed book rating summaries, whereas authoritative product records live in Catalog's PostgreSQL database (`catalogdb`) and authoritative individual customer `Feedback` records live in Rating API's Azure Cosmos DB container (`ratingdb` / `feedbacks`). Treating a search index or aggregate summary as an authoritative system of record causes silent divergence during indexing lag or event failures.

BookWorm needs a cross-system consistency principle that separates rebuildable derived views from authoritative sources of truth.

## Decision drivers

- **Read independence:** Optimize discovery, vector search, and summary queries without transferring source-data ownership.
- **Transactional correctness:** Ensure checkout and mutation flows validate against authoritative owners rather than stale projections.
- **Operational transparency:** Make eventual-consistency lag and rebuild paths explicit to operators and consumers.

## Considered options

1. Maintain derived views separately from authoritative stores with explicit eventual-consistency semantics
2. Treat search indexes and aggregate summaries as authoritative sources of truth
3. Update all cross-domain projections synchronously inside every source write
4. Query authoritative stores across domains on every discovery request

## Decision outcome

Chosen option: **Maintain derived views separately from authoritative stores with explicit eventual-consistency semantics**, because it isolates read scaling and specialized indexing from write availability while keeping source authority unambiguous.

In BookWorm:

- **Catalog vector embeddings (Qdrant `vectordb`):** Derived from `catalogdb` via scheduled `ProcessVectorBatchIntegrationEvent` batches processed by Catalog Ingestion (`catalog-ingestion`).
- **Catalog rating summary (average rating and review count on a book):** Derived asynchronously from Rating API's `FeedbackCreatedIntegrationEvent` and `FeedbackDeletedIntegrationEvent` events; mismatches trigger `BookUpdatedRatingFailedIntegrationEvent` compensation.
- **Ordering read projections (Marten `OrderSummary`):** Derived from Ordering's authoritative order stream in `orderingdb`.
- **AI rating summaries:** Generated on demand by Rating API from Cosmos DB `Feedback` records and never treated as authoritative review storage.

Purchase validation always queries authoritative owners over gRPC (`BookGrpcService`, `BasketGrpcService`) rather than relying on cached or derived discovery views.

### Consequences

- **Positive:** Discovery indexes, caches, and summaries can be rebuilt or re-indexed independently without altering authoritative domain stores.
- **Negative:** Users can briefly observe stale search rankings or rating counts while Kafka consumers or scheduled ingestion jobs catch up.
- **Follow-up:** Monitor projection lag, dead-letter queues, and scheduled ingestion runs; numeric freshness SLOs remain to be defined for production environments.

## Pros and cons of the options

### Maintain derived views separately from authoritative stores with explicit eventual-consistency semantics

- **Good**, because read models use specialized engines (Qdrant, denormalized rating summary columns, FusionCache) without coupling source writes to downstream uptime.
- **Good**, because rebuildable views keep recovery procedures clear when projection state drifts.
- **Bad**, because consumers and UI surfaces must tolerate temporary staleness and handle missing-reference compensations.

### Treat search indexes and aggregate summaries as authoritative sources of truth

- **Good**, because reads and writes target a single projection store.
- **Bad**, because specialized indexes and aggregate counters lack full domain lifecycle history and conflict-resolution guarantees.

### Update all cross-domain projections synchronously inside every source write

- **Good**, because projections reflect mutations immediately.
- **Bad**, because an outage in Qdrant or a downstream service blocks primary catalog updates or feedback submissions.

### Query authoritative stores across domains on every discovery request

- **Good**, because results are always up to date.
- **Bad**, because cross-service fan-out degrades browse latency and removes hybrid semantic search capabilities.
