## Context & Problem Statement

Book discovery relies on fast semantic search in [[container|catalog-vector]] and pre-aggregated rating summaries on [[entity|book]] records, while authoritative product and review records live in [[container|catalog-database]] and [[container|rating-database]]. Treating derived caches or search projections as authoritative truth risks exposing stale prices or orphaned data.

## Decision Drivers

- **Read performance:** Support rich search and fast browsing without overloading primary stores.
- **Commercial accuracy:** Ensure checkout and mutations always read authoritative state.
- **Rebuildability:** Allow derived views to be reconstructed from source data after drift or loss.

## Options Considered

| Option                                                        | Pros                                                        | Cons                                                           |
| :------------------------------------------------------------ | :---------------------------------------------------------- | :------------------------------------------------------------- |
| **Separate derived views with explicit eventual consistency** | High read throughput; derived stores can be rebuilt anytime | Users may see brief staleness windows during async propagation |
| **Treat search index / projections as authoritative**         | Single read/write path                                      | Risks silent drift, lost history, and stale checkout pricing   |
| **Synchronous two-phase updates to all views**                | Zero propagation lag                                        | Outages in search or projections block core writes             |
| **Query primary stores for every search**                     | Always up to date                                           | Slow cross-service reads and poor semantic search capabilities |

## Decision & Consequences

**Chosen Option:** Treat search indexes, read caches, and cross-domain projections as non-authoritative derived views updated asynchronously. Purchase validation and mutations must always resolve against the authoritative system of record.

- **Positive:** Derived stores scale independently and can be rebuilt from primary records without data loss.
- **Negative:** UIs and operators must account for bounded eventual consistency windows.

### Compliance Criteria

- Checkout price and availability checks must read from [[container|catalog-database]] (via [[service|catalog-api]]), never from [[container|catalog-vector]] or cache payloads.
- Every derived view must document its authoritative source, expected lag, and rebuild/reconciliation procedure.
- Derived projections must be read-only to external callers.
