## Context and problem statement

An area can stop or restart after saving a change but before notifying another area. Without durable handoffs, pending updates can be lost.

BookWorm needs background updates to survive restarts and to avoid applying the same update twice. It must use each area's existing storage instead of forcing every area to adopt the same storage.

## Decision drivers

- **Recoverability:** Preserve pending updates across restarts.
- **Architectural honesty:** Match protection to what each area already uses.
- **Clear delivery:** Treat background updates as potentially repeated and protect against duplicate effects.

## Considered options

1. Match durable handoffs to each area's existing storage
2. Require the same relational storage for every background-messaging area
3. Send updates directly from memory without protection
4. Create one transaction across every database and outside provider

## Decision outcome

Chosen option: **Match durable handoffs to each area's existing storage**.

Stateful areas preserve their outgoing updates with their own records. Areas using Redis, task orchestration, or temporary workers use those mechanisms without adding storage they do not need.

Every background update may be delivered more than once. Receiving areas must recognize repeats and avoid applying them twice.

### Consequences

- **Positive:** Areas preserve updates without adding unnecessary storage.
- **Negative:** Operators must understand the different protection methods used by each area.
- **Follow-up:** Review duplicate handling and recovery whenever a background update changes.

## Pros and cons of the options

### Match durable handoffs to each area's existing storage

- **Good**, because durable work stays close to the area's authoritative information.
- **Good**, because lightweight areas avoid expensive extra storage.
- **Bad**, because recovery differs depending on the area.

### Require the same relational storage for every background-messaging area

- **Good**, because every messaging area uses the same storage pattern.
- **Bad**, because some areas need unnecessary databases and maintenance.

### Send updates directly from memory without protection

- **Good**, because setup is minimal.
- **Bad**, because a restart can permanently lose pending updates.

### Create one transaction across every database and outside provider

- **Good**, because it attempts to make every part succeed together.
- **Bad**, because outside providers cannot join one database transaction and distributed coordination reduces availability.
