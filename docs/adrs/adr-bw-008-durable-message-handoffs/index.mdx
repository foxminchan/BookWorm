## Context and problem statement

A service process can crash or restart between updating local state and publishing or acknowledging a Kafka message. Relying solely on in-memory message dispatch loses pending outbound events during failures. However, not every BookWorm service owns a PostgreSQL database: earlier documentation inaccurately assumed PostgreSQL Wolverine outboxes across Finance, Rating, and Notification, creating severe drift from the live runtime architecture.

BookWorm needs an accurate whole-system rule that pairs Wolverine Kafka messaging with each service's actual persistence and idempotency mechanism while keeping transport durability distinct from end-to-end business completion.

## Decision drivers

- **Recoverability:** Preserve pending message handoffs across process restarts on stateful transactional services.
- **Architectural honesty:** Align messaging durability with each service's real backing store rather than forcing unused PostgreSQL databases onto stateless or non-relational services.
- **Explicit delivery semantics:** Treat Kafka and Wolverine handoffs as at-least-once and require consumer idempotency rather than claiming exactly-once distributed transactions.

## Considered options

1. Match Wolverine durability and idempotency to each service's native persistence model
2. Mandate PostgreSQL Wolverine inbox/outbox tables on every Kafka-enabled service
3. Publish directly to Kafka in memory without any durable handoff or idempotency guard
4. Coordinate distributed two-phase commit transactions across databases, Kafka, and SMTP providers

## Decision outcome

Chosen option: **Match Wolverine durability and idempotency to each service's native persistence model**, because it protects stateful domain writes without forcing unnecessary relational databases onto Cosmos DB, Durable Functions, Redis, or stateless worker services.

Current verified messaging durability per Kafka-enabled service:

| Service                                     | Backing store                                                    | Verified messaging durability and idempotency mechanism                                                                           |
| :------------------------------------------ | :--------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| **Catalog API** (`catalog`)                 | PostgreSQL (`catalogdb`)                                         | Wolverine PostgreSQL outbox/inbox (`wolverine` schema) + Redis FusionCache idempotency                                            |
| **Catalog Ingestion** (`catalog-ingestion`) | PostgreSQL (`catalogdb`) + Qdrant                                | Kafka trigger + Wolverine PostgreSQL outbox (`catalogdb`)                                                                         |
| **Ordering API** (`ordering`)               | PostgreSQL (`orderingdb`, EF Core + Marten)                      | Wolverine PostgreSQL outbox/inbox (`wolverine` schema) + Redis idempotency                                                        |
| **Scheduler** (`scheduler`)                 | PostgreSQL (`schedulerdb`)                                       | Wolverine PostgreSQL outbox/inbox (`wolverine` schema)                                                                            |
| **Rating API** (`rating`)                   | Azure Cosmos DB (`ratingdb` / `feedbacks`)                       | Wolverine Cosmos DB persistence (`WolverineFx.CosmosDb`) + Redis idempotency                                                      |
| **Finance** (`finance`)                     | Azure Durable Task Scheduler (`finance-taskhub`) + Azure Storage | Durable Functions saga state replay + Kafka triggers + Wolverine Kafka publisher (no PostgreSQL)                                  |
| **Basket API** (`basket`)                   | Redis                                                            | Wolverine Kafka + Redis 24-hour `IIntegrationEventIdempotencyGuard` (no SQL outbox)                                               |
| **Notification** (`notification`)           | Redis (idempotency only)                                         | Stateless Kafka consumer + MailKit resilience pipeline + Redis 24-hour `IIntegrationEventIdempotencyGuard` (no PostgreSQL outbox) |

Across all hosts, Wolverine configures CloudEvents JSON serialization, jittered retry cooldowns (`50ms`, `250ms`, `1s`), and per-service Kafka dead-letter queues (`bookworm.{environment-kebab}.{service-kebab}.dead-letter-queue`).

### Consequences

- **Positive:** Stateful services eliminate local dual-write gaps using their native stores, while Finance, Basket API, and Notification avoid provisioning unneeded PostgreSQL instances.
- **Negative:** Operators and contributors must verify each host's exact durability and retry configuration rather than assuming one universal PostgreSQL outbox across the platform.
- **Follow-up:** Keep consumers idempotent against duplicate delivery and consult the superseding system ADRs for Rating, Finance, and Notification storage details.

## Pros and cons of the options

### Match Wolverine durability and idempotency to each service's native persistence model

- **Good**, because Catalog, Ordering, Scheduler, and Rating align message durability with their authoritative stores while Finance delegates workflow durability to Durable Task Scheduler.
- **Good**, because Notification and Basket remain lean without extra relational schema operations.
- **Bad**, because persistence troubleshooting differs across PostgreSQL, Cosmos DB, Durable Task Scheduler, and Redis idempotency paths.

### Mandate PostgreSQL Wolverine inbox/outbox tables on every Kafka-enabled service

- **Good**, because every messaging service uses identical SQL envelope tables.
- **Bad**, because it introduces unnecessary PostgreSQL databases, migrations, and operational failure modes for Finance, Rating, Basket API, and Notification.

### Publish directly to Kafka in memory without any durable handoff or idempotency guard

- **Good**, because host registration requires minimal configuration.
- **Bad**, because crashes between database commits and broker sends lose integration events permanently.

### Coordinate distributed two-phase commit transactions across databases, Kafka, and SMTP providers

- **Good**, because it aims for cross-system atomicity.
- **Bad**, because external brokers and SMTP providers do not participate in ACID database transactions, and distributed locks severely degrade availability.
