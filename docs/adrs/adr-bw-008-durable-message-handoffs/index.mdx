## Context & Problem Statement

A service can crash or restart after committing local state but before publishing an integration event to Kafka. Without durable handoffs, downstream workflows stall silently. At the same time, forcing stateless or Redis-backed workers to adopt a relational database just for an outbox adds unnecessary operational weight.

## Decision Drivers

- **Crash recovery:** Preserve pending outgoing messages across process restarts.
- **Storage proportionality:** Match durability mechanisms to each service's existing persistence model.
- **At-least-once honesty:** Require idempotent consumers rather than claiming exactly-once delivery.

## Options Considered

| Option                                                      | Pros                                                                   | Cons                                                             |
| :---------------------------------------------------------- | :--------------------------------------------------------------------- | :--------------------------------------------------------------- |
| **Match durable handoffs to each service's native storage** | Atomic outbox where relational DBs exist; lightweight guards elsewhere | Recovery tooling varies slightly by service storage type         |
| **Mandate PostgreSQL outbox for every service**             | Uniform SQL outbox pattern everywhere                                  | Forces unnecessary databases onto stateless/Redis services       |
| **In-memory fire-and-forget publishing**                    | Minimal setup                                                          | Process crashes permanently lose pending integration events      |
| **Distributed two-phase commit (2PC)**                      | Attempts atomic cross-system commits                                   | Fragile, unsupported by external APIs, and degrades availability |

## Decision & Consequences

**Chosen Option:** Persist broker handoffs using each service's native durability mechanism (transactional PostgreSQL outboxes in [[service|catalog-api]], [[service|order-api]], [[service|order-orchestration]], and [[service|scheduler-service]]; idempotency guards and DLQs in Redis/stateless workers). All consumers must treat delivery as at-least-once and handle duplicates idempotently.

- **Positive:** Prevents lost events on crash without burdening stateless services with extra databases.
- **Negative:** Operators must understand both SQL outbox inspection and Redis/DLQ recovery paths.

### Compliance Criteria

- Relational-backed services publishing Kafka messages must use a transactional outbox.
- All Kafka consumers must implement idempotent handling (e.g., 24-hour idempotency guards or natural idempotency).
- Documentation must never claim "exactly-once" side effects across external brokers or SMTP providers.
