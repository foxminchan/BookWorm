## Context and problem statement

BookWorm runs locally with Aspire-managed containers and emulators (`aspire start`), yet deploys to Azure Container Apps (`Development`, `Staging`, and `Production`) through Aspire 17 (`aspire deploy`). Several platform capabilities—including Kafka transport activation, OTLP telemetry export, Cosmos DB persistence, and development-only health/OpenAPI routes—change behavior based on environment settings and connection strings. Inferring production topology from local containers or legacy `azd` instructions causes operational drift.

BookWorm needs a strict separation between logical architecture contracts and explicit per-environment infrastructure configuration.

## Decision drivers

- **Operational accuracy:** Prevent teams from assuming local emulator defaults match Staging or Production SKUs, HA settings, or security postures.
- **Conditional clarity:** Make environment-gated behaviors (such as dev-only `/health` and `/openapi`, or conditional Kafka/OTLP wiring) explicit and verifiable.
- **Single deployment workflow:** Align cloud provisioning with the verified Aspire 17 `aspire deploy` model rather than stale CLI assumptions.

## Considered options

1. Separate logical service architecture from explicit per-environment configuration and Aspire 17 `aspire deploy` targets
2. Treat local Aspire emulator wiring as the production deployment topology
3. Assume all environments share identical SKUs, connection strings, and middleware settings
4. Hard-code a fixed physical production topology inside logical architecture ADRs

## Decision outcome

Chosen option: **Separate logical service architecture from explicit per-environment configuration and Aspire 17 `aspire deploy` targets**, because it keeps domain contracts portable while recording concrete differences between local run mode and Azure publish mode.

In `src/Aspire/BookWorm.AppHost/AppHost.cs` and `.github/workflows/apphost-cd.yml`:

- **Local run mode (`mise run run` / `aspire start`):** Runs local containers and emulators (PostgreSQL + pgAdmin, Cosmos DB emulator + Data Explorer, Azurite + Storage Explorer, Redis + RedisInsight, Kafka + Kafka UI, Qdrant, Mailpit, Durable Task Scheduler emulator, Scalar API Reference, and MCP Inspector).
- **Cloud publish mode (`aspire deploy` via Aspire 17 CLI — no `azure.yaml` or `azd up`):** Provisions Azure Container Apps (`Consumption` workload profile), environment-tiered Azure Managed Redis (`BalancedB0`/`B1`/`B5`), Azure PostgreSQL Flexible Server (`Standard_B1ms`/`D2ds_v5`/`D4ds_v5`, PgBouncer and zone-redundant HA in non-Dev), Azure Cosmos DB (`DisableLocalAuth = true` in non-Dev), Azure Storage (`StandardLrs`/`Zrs`/`Gzrs`), custom Bicep for Durable Task Scheduler and Entra ID Agent Identities, and external connection strings for Confluent Cloud Kafka, Qdrant Cloud, and SendGrid SMTP.

Every environment deployment must verify active broker connectivity, OTLP export, authentication RBAC, and health probes directly on the target host.

### Consequences

- **Positive:** Logical architecture diagrams remain stable across environments while operators have an exact matrix of local vs. cloud backing resources and SKUs.
- **Negative:** Teams must maintain explicit environment documentation and secrets (`KAFKA_BROKER`, `QDRANT_CLOUD_CONNECTION`, SMTP credentials, Azure OIDC variables) for each deployment tier.
- **Follow-up:** Keep cloud deployment guides synchronized with `.github/workflows/apphost-cd.yml` and `AppHost.cs` whenever Aspire hosting extensions change.

## Pros and cons of the options

### Separate logical service architecture from explicit per-environment configuration and Aspire 17 `aspire deploy` targets

- **Good**, because local developer onboarding stays self-contained with emulators while cloud environments enforce production SKUs, HA, and managed identities.
- **Good**, because `aspire deploy` derives Azure provisioning directly from `AppHost.cs` and two minimal Bicep modules.
- **Bad**, because environment-conditional switches (such as `IsDevelopment()` gates on `/health` and Mailpit) must be checked carefully before promoting releases.

### Treat local Aspire emulator wiring as the production deployment topology

- **Good**, because documentation covers only one configuration.
- **Bad**, because emulators lack production durability, HA, TLS termination, and RBAC guarantees.

### Assume all environments share identical SKUs, connection strings, and middleware settings

- **Good**, because fewer environment flags exist.
- **Bad**, because it conceals critical differences such as Dev burstable SKUs, `AlwaysOnSampler`, and local-auth restrictions in Staging and Production.

### Hard-code a fixed physical production topology inside logical architecture ADRs

- **Good**, because every ADR carries concrete hosting details.
- **Bad**, because routine SKU or cloud region updates invalidate whole-system logical decision records.
