## Context and problem statement

BookWorm can run locally for development and be released to live environments. Some features change based on the environment, including background messaging, monitoring, stored information, and safe testing routes.

BookWorm needs to keep the overall design separate from details that change in each environment.

## Decision drivers

- **Operational accuracy:** Do not assume local test tools match live reliability or security settings.
- **Clear differences:** Make environment-specific behavior visible and testable.
- **Single release workflow:** Use one established process to prepare and release environments.

## Considered options

1. Separate the overall design from explicit environment settings
2. Treat local test setup as the live setup
3. Assume every environment uses identical settings
4. Record a fixed live setup inside the overall design decisions

## Decision outcome

Chosen option: **Separate the overall design from explicit environment settings**.

Local and live environments will use the same business agreements but may use different supporting equipment.

Local environments may use lightweight tools and test versions. Live environments use managed services, stronger security, and availability settings appropriate to the deployment.

Every release must verify that connections, monitoring, login permissions, and health checks work in the target environment.

### Consequences

- **Positive:** Overall diagrams remain stable while environment choices remain visible.
- **Negative:** Teams must maintain environment settings and protected connection details separately.
- **Follow-up:** Update environment guidance whenever live setup or release processes change.

## Pros and cons of the options

### Separate the overall design from explicit environment settings

- **Good**, because local development remains simple while live environments receive stronger protection and availability.
- **Good**, because business agreements stay portable.
- **Bad**, because environment switches must be checked before promotion.

### Treat local test setup as the live setup

- **Good**, because documentation covers only one configuration.
- **Bad**, because local tools do not provide live durability, availability, or security guarantees.

### Assume every environment uses identical settings

- **Good**, because fewer settings exist.
- **Bad**, because it hides important differences in size, monitoring, security, and availability.

### Record a fixed live setup inside the overall design decisions

- **Good**, because every decision carries concrete hosting details.
- **Bad**, because routine infrastructure updates invalidate logical architecture decisions.
