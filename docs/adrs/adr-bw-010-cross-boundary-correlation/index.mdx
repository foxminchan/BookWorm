## Context and problem statement

One customer action, such as placing an order or submitting a review, can pass through several parts of the system. Without stable references, teams cannot trace failures across those parts.

BookWorm needs consistent tracing without allowing tracing information to replace login or permission checks.

## Decision drivers

- **Interoperability:** Preserve stable names and routing information as updates move between areas.
- **Easy diagnosis:** Connect activity records without exposing private customer information.
- **Security:** Keep tracing separate from login and authorization.

## Considered options

1. Carry one trace reference across the whole journey and check permissions independently
2. Create a separate reference at each area
3. Guess relationships from timestamps or customer information
4. Use a trace reference as login or permission proof

## Decision outcome

Chosen option: **Carry one trace reference across the whole journey and check permissions independently**.

Every request and background update will carry identifying context for routing and diagnosis. That context helps teams follow the journey without giving reading or writing permission.

Permissions must still be verified through the normal secure login process.

### Consequences

- **Positive:** Operators can follow a journey from start to finish without exposing private data.
- **Negative:** Renaming or rerouting an update may require coordinated changes.
- **Follow-up:** Test tracing across major journeys and whenever update names or routes change.

## Pros and cons of the options

### Carry one trace reference across the whole journey and check permissions independently

- **Good**, because one trace works across web, internal, and background activity.
- **Good**, because tracing cannot be used to grant privileges.
- **Bad**, because every connected path must preserve the reference.

### Create a separate reference at each area

- **Good**, because each area needs no incoming tracing setup.
- **Bad**, because operators cannot connect later failures back to the original request.

### Guess relationships from timestamps or customer information

- **Good**, because areas do not need consistent tracing context.
- **Bad**, because this is unreliable and can expose private information.

### Use a trace reference as login or permission proof

- **Good**, because downstream areas avoid extra login checks.
- **Bad**, because tracing values can be forged and must not grant access.
