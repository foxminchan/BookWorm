## Context & Problem Statement

Customer journeys such as checkout and review projection span microfrontends, HTTP/gRPC boundaries, Kafka topics, and background workers. Without stable correlation and message identifiers, operators cannot trace failures end to end, yet correlation headers must never be trusted as authentication or authorization proof.

## Decision Drivers

- **End-to-end traceability:** Connect spans and logs across HTTP, gRPC, and Kafka hops.
- **PII-safe diagnostics:** Correlate journeys via opaque IDs without logging personal data.
- **Security isolation:** Keep correlation metadata strictly separate from Entra ID auth claims.

## Options Considered

| Option                                                       | Pros                                                                   | Cons                                                   |
| :----------------------------------------------------------- | :--------------------------------------------------------------------- | :----------------------------------------------------- |
| **Propagate trace/message IDs + enforce auth independently** | Unified tracing across sync and async paths; zero privilege escalation | Every hop must preserve correlation headers/envelopes  |
| **Generate isolated IDs per service**                        | Zero upstream propagation required                                     | Breaks end-to-end failure correlation                  |
| **Correlate by timestamp or customer email**                 | No extra headers needed                                                | Unreliable under load and leaks PII into logs          |
| **Trust correlation/user IDs as auth credentials**           | Fewer token checks downstream                                          | Vulnerable to header spoofing and privilege escalation |

## Decision & Consequences

**Chosen Option:** Propagate W3C trace context, request IDs, and stable CloudEvents message identities across all synchronous and asynchronous hops while verifying authentication and authorization independently at each boundary.

- **Positive:** Operators can trace a single request across [[service|order-api]], [[service|order-orchestration]], [[service|basket-api]], and [[service|notification-api]] without exposing PII.
- **Negative:** Changing event names or omitting envelope propagation breaks trace continuity.

### Compliance Criteria

- Integration events must carry stable message IDs and domain correlation keys (e.g., `OrderId`, `FeedbackId`).
- Handlers and endpoints must derive caller identity exclusively from validated Entra ID tokensâ€”never from correlation headers or payload fields.
- Incident logs and traces must correlate via opaque IDs rather than customer emails or names.
