## Context

A request can initiate work in multiple services. Without stable message identity and correlation, operators cannot reliably connect downstream execution to the initiating request, and routing changes can disrupt consumers.

## Decision

Preserve the documented integration-event namespace, naming pattern, message identity, and owner routing metadata. Reuse the shared envelope policy's CloudEvents-compatible mapping and propagation of request and user identifiers where available.

Correlation is diagnostic context, not an authorization token, immutable audit trail, or deduplication guarantee. Finance's order correlation rules remain in its local ADR.

## Decision drivers

- Interoperability through stable routing and identity.
- Cross-service diagnosis without serializing business payloads into logs.
- Clear separation of identity context from access control.

## Alternatives considered

| Alternative                                  | Assessment                                                              |
| -------------------------------------------- | ----------------------------------------------------------------------- |
| Independently generated context at every hop | Is locally simple but disconnects the end-to-end execution trail.       |
| Infer origin from payload or timestamps      | Avoids metadata but is ambiguous and encourages sensitive-data logging. |
| Treat user identifiers as credentials        | Removes authorization work by incorrectly trusting unverified context.  |

## Consequences

- Related execution can be traced where producers and consumers preserve context.
- Missing originating metadata leaves gaps that must be diagnosed explicitly.
- Namespace and identity changes are contract changes, not harmless refactoring.
