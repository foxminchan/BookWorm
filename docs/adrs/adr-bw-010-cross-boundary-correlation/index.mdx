## Context and problem statement

A single customer action—such as placing an order or submitting a book review—spans the API Gateway, synchronous gRPC lookups, asynchronous Kafka messages, Azure Durable Functions orchestrations, and outbound SMTP delivery. Without stable message identities and propagated correlation metadata, operators cannot trace failures across service boundaries, and uncoordinated contract renames disrupt Kafka routing.

BookWorm needs a system-wide correlation rule that connects distributed telemetry while preventing unverified correlation headers from being mistaken for security credentials.

## Decision drivers

- **Interoperability:** Preserve stable contract namespaces, topic routing metadata, and CloudEvents message identifiers across producers and consumers.
- **Diagnosability:** Correlate logs and spans across HTTP, gRPC, and Kafka hops without logging raw business payloads or sensitive personal data.
- **Security isolation:** Keep diagnostic correlation context strictly separate from Microsoft Entra ID authentication and authorization.

## Considered options

1. Propagate W3C trace context, `x-request-id`, and CloudEvents message metadata across all boundaries while enforcing Entra ID authorization independently
2. Generate isolated correlation identifiers independently at each service hop
3. Infer causal relationships from business payload fields or log timestamps
4. Reuse propagated `UserId` correlation headers as authorization credentials

## Decision outcome

Chosen option: **Propagate W3C trace context, `x-request-id`, and CloudEvents message metadata across all boundaries while enforcing Entra ID authorization independently**, because it delivers end-to-end distributed traceability without weakening security boundaries.

`BookWorm.ServiceDefaults` configures W3C `ActivityIdFormat` for OpenTelemetry tracing across ASP.NET Core, HttpClient, and gRPC calls, while `BookWorm.Constants` defines the `x-request-id` correlation header. On Kafka, `BookWorm.Chassis` uses `CloudEventsOnlyKafkaMapper` to serialize CloudEvents JSON envelopes carrying stable message IDs, W3C trace headers, `requestid`, and `UserId` context, with partition keys (`OrderId`, `BookId`, `FeedbackId`) preserving entity ordering. Correlation metadata serves strictly for routing and diagnostics; services never accept `UserId` or `x-request-id` headers in place of validated Entra ID JWTs or agent identities.

### Consequences

- **Positive:** Operators trace checkout, feedback, and ingestion chains end to end in the Aspire Dashboard and Azure Application Insights without exposing sensitive payloads in logs.
- **Negative:** Renaming an integration-event type, namespace, or topic-routing attribute becomes a breaking contract change requiring consumer coordination under ADR-BW-017, and missing upstream headers leave explicit correlation gaps.
- **Follow-up:** Verify message envelope compatibility through Pact contract tests and inspect Finance's Durable Task instance-ID correlation (`OrderId`) during saga changes.

## Pros and cons of the options

### Propagate W3C trace context, `x-request-id`, and CloudEvents message metadata across all boundaries while enforcing Entra ID authorization independently

- **Good**, because W3C standards integrate natively with OpenTelemetry, YARP, gRPC, Wolverine, and Next.js `@workspace/otel`.
- **Good**, because keeping correlation separate from authorization prevents header-spoofing privilege escalation.
- **Bad**, because every custom trigger (such as Azure Functions Kafka triggers in Finance and Catalog Ingestion) must preserve context explicitly.

### Generate isolated correlation identifiers independently at each service hop

- **Good**, because individual hosts require no incoming header parsing.
- **Bad**, because operators cannot connect a failed Notification email or Finance saga retry back to the originating checkout request.

### Infer causal relationships from business payload fields or log timestamps

- **Good**, because services avoid envelope metadata conventions.
- **Bad**, because timestamp matching fails under concurrency and tempts teams to log sensitive customer data.

### Reuse propagated `UserId` correlation headers as authorization credentials

- **Good**, because downstream consumers avoid validating tokens.
- **Bad**, because unverified metadata can be spoofed and violates defense-in-depth authorization requirements.
