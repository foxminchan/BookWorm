User checkout converts an authenticated customer's persisted basket into an immutable purchase snapshot in **Ordering API**, then delegates basket deletion and customer email delivery to asynchronous workflows coordinated by **Finance**. Checkout produces three independent outcomes: **order acceptance**, **basket cleanup**, and **email submission**. Returning HTTP `201 Created` confirms order acceptance only—not basket deletion, payment settlement, fulfillment, order completion, or email delivery.

## Context and motivation

BookWorm splits customer web experiences across two customer microfrontends (MFEs) behind **API Gateway** (YARP): **Storefront** (`@bookworm/storefront`) owns public discovery and Microsoft Entra ID authentication via Better Auth (PKCE), while **Commerce** (`@bookworm/commerce`) serves `/basket`, `/checkout/*`, and `/account/*` (`X-Mfe-Zone: commerce`).

Checkout coordinates six backend services without coupling customer response time to cleanup or SMTP latency:

- **Shopping (`Basket API`):** Owns mutable pre-order baskets in Redis and deletes the basket after checkout.
- **Catalog (`Catalog API`):** Supplies authoritative book records and current sale or regular prices over gRPC.
- **Ordering (`Ordering API`):** Owns the accepted order, item-price snapshot, business status (`New`, `Completed`, `Cancelled`), and soft-deletion state in PostgreSQL (`orderingdb`, EF Core + Marten + Wolverine outbox).
- **Ordering (`Finance`):** Runs the Azure Durable Functions `OrderOrchestrator` on Azure Durable Task Scheduler (`finance-taskhub`) with no PostgreSQL database. Despite its name, Finance coordinates post-checkout messages and bounded timeouts—it does not authorize or settle payments.
- **Platform (`Notification`):** Runs a stateless Kafka worker with Redis idempotency (`IIntegrationEventIdempotencyGuard`), Mjml.Net templates, and MailKit SMTP (**Mailpit** locally, SendGrid SMTP in Azure) with no PostgreSQL database.

Explicit order completion or cancellation, payment processing, and physical fulfillment are outside this flow's scope.

## How it works

Checkout splits into a synchronous order-acceptance path and an asynchronous post-checkout fan-out coordinated by Finance.

### Part 1: Synchronous checkout and order acceptance

This sequence diagram shows how Commerce submits checkout through API Gateway and how Ordering API resolves authoritative basket items and catalog prices before returning HTTP `201 Created`.

<MermaidFileLoader file="mermaids/user-checkout-diagram-1.mmd" />

1. **Authenticate and review basket:** The customer signs in with Microsoft Entra ID through **Storefront** (Better Auth PKCE) and reviews their basket in **Commerce** (`/basket`). Quantity edits must be saved to **Basket API** before checkout because **Ordering API** reads the persisted Redis basket, not unsaved browser state.
2. **Submit checkout request:** **Commerce** posts to `/ordering/api/v1/orders` through **API Gateway** with an `x-request-id` header for request-level idempotency. **Ordering API** enforces Microsoft Entra ID authorization (`customer` role, `ordering_read`/`ordering_write`), per-user rate limiting, and derives Buyer ID, full name, and email from authenticated identity claims rather than trusting client-supplied IDs.
   Commerce does not send a `basketId` field in a request body. Its checkout handler passes `basket.id` to the create-order mutation, while the basket page displays a shipping estimate from `DEFAULT_SHIPPING_COST`.
3. **Resolve authoritative basket and prices:** **Ordering API** fetches persisted item quantities via `basket.v1.BasketGrpcService.GetBasket` and resolves each book via `book.v1.BookGrpcService.GetBooks`. Each order item records the sale price when present, otherwise the regular price. Any missing book aborts order creation.
4. **Persist `New` order and publish checkout event:** Under a per-buyer Redis distributed lock, **Ordering API** saves the `New` order snapshot in PostgreSQL (`orderingdb`), maps `OrderPlacedEvent` to `UserCheckedOutIntegrationEvent` (carrying `OrderId`, `BasketId`, `FullName`, `Email`, and `TotalMoney`), and publishes it to Kafka (`bookworm.{env}.ordering.user-checked-out`) via Wolverine's transactional outbox. On HTTP `201 Created`, **Commerce** navigates to `/checkout/confirmation?orderId=<order-id>`.

### Part 2: Asynchronous Finance orchestration, cleanup, and email

This flowchart shows how Finance fans out `PlaceOrderCommand` independently to Basket API and Notification, routes cleanup outcomes back to Ordering API, and manages bounded retry timeouts.

<MermaidFileLoader file="mermaids/user-checkout-diagram-2.mmd" />

1. **Start Durable Functions orchestration:** **Finance** consumes `UserCheckedOutIntegrationEvent` and starts `OrderOrchestrator` in Azure Durable Task Scheduler (`finance-taskhub`), correlated by `OrderId`. Finance registers a `PublishCancelOrderActivity` compensation when customer contact details are valid, publishes `PlaceOrderCommand` to `bookworm.{env}.finance.place-order`, and enters its event-and-timer wait loop.
2. **Independent fan-out to Basket API and Notification:** **Basket API** and **Notification** consume `bookworm.{env}.finance.place-order` in parallel as independent consumers. Email submission does not wait for basket deletion, so a placement email can be submitted even if basket cleanup later fails.
3. **Basket cleanup outcome:**
   - **Success (`DeleteBasketAsync` returns `true`):** **Basket API** publishes `BasketDeletedCompleteIntegrationEvent` (`bookworm.{env}.basket.delete-complete`). **Finance** emits `DeleteBasketCompleteCommand` (`bookworm.{env}.finance.delete-basket-complete`) to **Ordering API**, which logs the cleanup. Neither step marks the order `Completed` or stops Finance's wait loop—the orchestration stays active until an explicit Ordering completion or cancellation event arrives or retries exhaust.
   - **Failure (`DeleteBasketAsync` returns `false`):** **Basket API** publishes `BasketDeletedFailedIntegrationEvent` (`bookworm.{env}.basket.delete-failed`). **Finance** emits `DeleteBasketFailedCommand` (`bookworm.{env}.finance.delete-basket-failed`) to **Ordering API**, which soft-deletes the order (`IsDeleted = true`) without changing its business status to `Cancelled` and without publishing an order-cancellation event. Repository exceptions propagate to Wolverine retries rather than fabricating a cleanup event.
4. **Notification rendering and SMTP submission:** **Notification** wraps `PlaceOrderCommandHandler` in Redis-backed `IIntegrationEventIdempotencyGuard` (24-hour TTL keyed by `message.Id`), skips blank email addresses, renders `Orders/OrderEmail.mjml` via Mjml.Net, and sends MIME email through MailKit's Polly resilience pipeline (**Mailpit** locally on port `587`, SendGrid SMTP in Azure). Exhausted failures route to `bookworm.{env}.notification.dead-letter-queue`.
5. **Bounded Finance timeout retries:** Checked-in `OrderStateMachine` settings in `BookWorm.Finance/appsettings.json` configure `MaxAttempts: 3` and `MaxRetryTimeout: 00:30:00` (30 minutes). While the orchestration remains non-terminal, timeout steps below `MaxAttempts` reissue `PlaceOrderCommand` (with a new `message.Id`) and wait for the next timer. When retries reach `MaxAttempts`, `OrderOrchestrator` cancels **the orchestration** (`CancelDueToMaxRetriesAsync`) and publishes `CancelOrderCommand` (`bookworm.{env}.finance.cancel-order`) to **Notification** if contact details are present. Timeout exhaustion does **not** send a cancel command to **Ordering API**.

## Design trade-offs

| Decision                                                            | Benefits                                                                                          | Costs and limits                                                                                                                                                 |
| :------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Asynchronous fan-out after HTTP `201 Created`**                   | Keeps checkout responsive and insulates order acceptance from Redis deletion or SMTP delays       | Basket deletion and email submission can succeed or fail independently after checkout confirmation                                                               |
| **Shared `finance.place-order` topic for Basket and Notification**  | Simplifies Finance's command contract with one placement broadcast                                | A Finance timeout reissue emits a new `PlaceOrderCommand` with a new `message.Id`, which bypasses per-message-ID deduplication and can trigger a duplicate email |
| **Durable Task Scheduler orchestration (no Finance PostgreSQL DB)** | Provides replay-safe durable timers and compensations without managing a relational saga database | Orchestration state lives in `finance-taskhub`, separate from `orderingdb`                                                                                       |
| **Soft-delete on cleanup failure vs. business `Cancelled` status**  | Prevents technical basket-cleanup faults from masquerading as customer cancellations              | Operators must check both `IsDeleted` and business `Status` in `orderingdb`; a placement email may already have been sent                                        |
| **Saga timeout cancellation without mutating Ordering**             | Preserves Ordering API as sole authority over order business status                               | If an order stays `New` past `MaxAttempts`, Finance sends a canceled-order email while Ordering's status remains unchanged until explicitly reconciled           |

## Alternatives considered

- **Synchronous basket deletion and email sending inside `CreateOrder`:** Rejected because transient Redis or SMTP errors would abort otherwise valid customer purchases.
- **Database-backed Notification outbox with scheduled resend jobs:** Rejected in favor of stateless Kafka consumption, Redis `IIntegrationEventIdempotencyGuard`, MailKit Polly resilience, and Kafka native DLQ.
- **Allowing Finance to update Ordering's `Status` directly:** Rejected to preserve strict bounded-context ownership in Ordering API.
