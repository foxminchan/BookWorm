## Purpose and scope

User checkout turns the authenticated customer's current [[entity|basket]] into
an accepted [[entity|order]]. [[service|order-api]] records the purchase snapshot,
then [[service|order-orchestration]] coordinates basket cleanup and the
placement email without keeping the customer waiting for either operation.

There are three separate outcomes: **order acceptance**, **basket cleanup**,
and **email submission**. A successful checkout response confirms the first,
not the other two. Finance is the workflow coordinator; despite its name, the
current implementation does not authorize or settle payments.

This flow covers sign-in, basket review, Order creation, asynchronous cleanup,
placement notifications, and Finance timeout handling. Explicit Order
completion and cancellation, payment processing, fulfilment, and scheduled
email maintenance are outside its scope.

### System boundaries

- [[system|identity-provider]] supplies customer authentication. The Storefront
  uses Entra ID through Better Auth with PKCE; BookWorm APIs remain responsible
  for authorization and customer-scoped access.
- [[system|cart-system]] owns basket contents and deletion through
  [[service|basket-api]]. It does not own the accepted purchase.
- [[system|product-catalog-system]] supplies current book details and prices
  through [[service|catalog-api]].
- [[system|order-system]] owns the Order, its item-price snapshot, business
  status, and soft-deletion state.
- [[system|finance-system]] owns the persisted coordination saga, cleanup
  commands, and timeout policy, not Order status or payment settlement.
- [[system|notification-system]] owns email rendering, durable outbox records,
  and submission attempts.
- [[system|sendgrid]] is the external mail provider when configured.
  Notification uses SMTP, not the provider's HTTP Mail Send API. Development
  uses MailPit instead.

## Processing walkthrough

### 1. Authenticate and review the basket

The customer signs in through the Identity Provider before accessing protected
basket and Ordering operations. Ordering derives Buyer ID from the
authenticated identity rather than accepting another customer's ID in the
checkout request. Name and email claims become notification details on the
checkout event.

Storefront loads the basket and displays Catalog-enriched item information.
Quantity edits must be saved before checkout: the Order handler reads the
persisted basket, not unsaved UI state.

### 2. Submit checkout and build the purchase snapshot

Storefront calls [[command|CreateOrder]] through the gateway at
`POST /ordering/api/v1/orders`, supplying a fresh `x-request-id` header.
The client sends `basketId`, but the backend command has no request-body
fields. The selected basket comes from the authenticated customer context.

Ordering obtains item quantities through [[query|GetBasketGrpc]] with a
ten-second deadline, then resolves the book IDs through
[[query|GetBooksGrpc]]. Each Order Item records the sale price when present,
otherwise the regular price. A missing Catalog book prevents Order creation.

The Order total is the sum of recorded item prices multiplied by quantities.
The Storefront's displayed shipping charge is not added by this handler;
the accepted Order total, rather than a UI estimate, is the purchase snapshot.

### 3. Persist the Order and return confirmation

The endpoint applies authorization, per-user rate limiting, and idempotency.
The handler uses a per-Buyer distributed lock when adding and saving the
Order. The new Order starts in **New** status and raises `OrderPlacedEvent`,
which is mapped to [[event|UserCheckedOutIntegrationEvent]].

The checkout event carries Order ID, Buyer ID as Basket ID, full name, email,
and the recorded total. On `201 Created`, Storefront navigates to its checkout
confirmation page using the returned Order ID. This response does not wait
for Finance, Basket cleanup, or Notification to finish.

### 4. Start Finance coordination and fan out placement

Finance consumes the checkout event and starts an `OrderSaga` in **Placed**
state, correlated by Order ID. It publishes [[command|PlaceOrderCommand]] and
schedules `PlaceOrderTimeout`.

The shared [[channel|bookworm.&#123;env&#125;.finance.place-order]] channel has
two independent consumers:

1. Basket deletes the submitted basket.
2. Notification prepares the new-order email.

Neither consumer confirms the other's success. In particular, Notification
can submit a placement email before a later cleanup failure causes Ordering
to soft-delete the Order.

### 5. Report the basket cleanup outcome

Basket publishes [[event|BasketDeletedCompleteIntegrationEvent]] when its
repository returns `true` from deletion. Finance forwards
[[command|DeleteBasketCompleteCommand]] to Ordering, whose handler logs the
Order ID and amount. It does **not** complete the Order or finalize the saga.

When deletion returns `false`, Basket publishes
[[event|BasketDeletedFailedIntegrationEvent]]. Finance marks its saga
**BasketDeletionFailed**, finalizes it, and sends
[[command|DeleteBasketFailedCommand]]. Ordering soft-deletes the Order if it
exists. Soft deletion changes `IsDeleted`, not the Order's business status,
and does not emit an Order cancellation event.

A repository exception propagates instead of being converted into either a
successful deletion or a fabricated failure event.

### 6. Persist and submit the email

Notification skips messages with a null, empty, or whitespace-only email
address. Otherwise, it renders `Orders/OrderEmail`, defaulting a null name to
`Customer`, and builds the MIME message.

`EmailOutboxService` saves the recipient, subject, and rendered body in
[[container|notification-database]] **before** calling MailKit. After the sender
returns successfully, it marks the record sent and saves again. Submission
uses the configured SMTP provider: SendGrid when configured, MailPit during
development.

Rendering, persistence, and sender failures propagate. If SMTP accepted the
message but the sent-state save fails, the durable record may still appear
unsent. A later retry can therefore submit the same email again. Notification
publishes no application-level delivery-result event.

### 7. Handle Finance timeouts separately

The checked-in configuration uses `MaxAttempts: 3` and a thirty-minute timeout.
Each handled timeout increments `TimeoutRetryCount`; counts below 3 reissue
the shared placement command and schedule another timeout. This permits two
timeout-driven reissues after the initial command while the saga remains
active, not three additional retries.

Successful basket cleanup alone does not finalize the saga or stop its
timeout path. Explicit Order completion or cancellation events can finalize
the active saga through the separate Order lifecycle.

At retry exhaustion, Finance marks **its saga** Cancelled and finalizes it.
It requests a cancellation email through [[command|CancelOrderCommand]] only
when both name and email are nonblank. That command is consumed by
Notification; it is not an instruction to Ordering to cancel the Order.

## Consistency and delivery guarantees

- **Ordering remains authoritative for the purchase.** Basket is transient
  shopping intent; deleting it does not delete the accepted item-price snapshot.
- **Checkout success is not downstream completion.** A `201` confirms
  acceptance, not cleanup, payment, fulfilment, or email delivery.
- **The branches are not one transaction.** Basket deletion and email
  submission can succeed or fail independently after Order acceptance.
- **Idempotency has a request boundary.** The checkout endpoint uses
  `x-request-id`, but the Storefront generates a new key for each create call.
  A new attempt must not be assumed to deduplicate against an earlier one.
- **Saga correlation is not exactly-once delivery.** Order ID correlates
  Finance work, but replayed placement commands can repeat cleanup and email
  work. The email outbox has no order-command deduplication check.
- **SMTP acceptance is not inbox delivery.** A sent outbox record records
  successful submission, not a provider delivery receipt.
- **Saga cancellation is not Order cancellation.** Timeout exhaustion changes
  coordination state; explicit Ordering operations own business-status changes.

## Outcomes and recovery

| Outcome                                           | State and behavior                                                                              | Operational interpretation                                                                                             |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Order accepted                                    | Ordering saves a New Order and returns its ID; downstream work proceeds asynchronously.         | Verify cleanup and notification independently rather than treating the confirmation page as proof of completion.       |
| Checkout dependency, lock, or persistence failure | Order creation does not return successful acceptance.                                           | Investigate the failing dependency and request outcome before submitting another purchase after an ambiguous response. |
| Basket deletion succeeds                          | Finance forwards success; Ordering logs it without changing business status.                    | Cleanup is complete, but the saga remains active for status events and timeouts.                                       |
| Basket deletion returns false                     | Finance finalizes the failed saga; Ordering soft-deletes the Order if present.                  | Do not describe the result as an Order Cancelled transition or assume the independent placement email was withheld.    |
| Recipient email is absent                         | Notification skips rendering, outbox creation, and sending.                                     | No email attempt is expected; Order acceptance and cleanup remain independent.                                         |
| SMTP or sent-state persistence fails              | The outbox can remain unsent even if the provider accepted the message.                         | Investigate before replaying; scheduled resend and message retries can create duplicate submissions.                   |
| Finance timeout is below the limit                | Placement is reissued to both consumers and another timeout is scheduled.                       | Check repeated cleanup outcomes and emails, not just saga retry counts.                                                |
| Finance retries are exhausted                     | The saga is finalized as Cancelled; a cancellation email is requested only with name and email. | Inspect the actual Order status separately; Finance did not cancel it in Ordering.                                     |

## Operational checks

When checkout appears incomplete or a customer reports conflicting messages:

1. Start with the accepted Order ID and checkout request outcome. Inspect the
   Order's business status and soft-deletion state in Ordering before retrying
   a purchase.
2. For access failures, verify the Identity Provider, authenticated customer
   identity, and API authorization. Do not copy tokens or identity claims into
   diagnostic notes.
3. For creation failures, inspect Basket and Catalog gRPC availability, missing
   book records, the per-Buyer lock, and Order persistence.
4. Correlate the checkout event and Finance saga by Order ID. Check whether
   placement was published, a cleanup outcome arrived, or a timeout reissued
   work.
5. Inspect Basket's deletion result and Ordering's corresponding cleanup
   handler. Distinguish success logging, soft deletion, and an explicit Order
   status transition.
6. Check Notification's outbox and SMTP errors independently of Basket. An
   absent outbox record can mean missing recipient data, rendering failure, or
   initial persistence failure; it is not proof that the Order was rejected.
7. For unsent mail, inspect scheduled resend activity and provider
   configuration. Verify a later sent-state save without treating it as proof
   of inbox delivery or replaying all placement consumers unnecessarily.

Use Order ID, request correlation, saga state, and outbox submission status
for diagnosis. Avoid logging tokens, recipient details, or rendered email
bodies. Recovery should preserve the distinction between an accepted purchase,
cleanup state, and customer communication rather than forcing them into one
success or failure flag.
