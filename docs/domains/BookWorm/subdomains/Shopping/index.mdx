Shopping is BookWorm's Core bounded context for pre-purchase customer intent (`Basket` and `Basket Item`). `Basket API` stores customer-scoped baskets authoritatively in **Redis** (with no SQL database), enriches item titles and live prices from `Catalog API` over gRPC at read time, exposes `basket.v1.BasketGrpcService` to `Ordering API` during checkout, and cleans up submitted baskets asynchronously when Finance issues `PlaceOrderCommand`.

## Scope and constraints

- **In scope:** Creating, retrieving, replacing (whole-set update), and deleting an authenticated customer's basket; enriching basket display items with live Catalog metadata; executing post-checkout basket cleanup and signaling explicit success or failure outcomes.
- **Out of scope:** Owning canonical book details (`Catalog`), creating or managing accepted orders (`Ordering`), coordinating post-checkout sagas (`Finance`), and payment settlement (external to BookWorm).
- **Key constraints:** A basket is mutable shopping intent, not an `Order` and not an inventory reservation. `Basket API` has no relational database; Redis is its system of record.

### HTTP and gRPC surface (`/api/v1`)

| Contract                                | Purpose                                                                        | Authorization and rules                                                   |
| :-------------------------------------- | :----------------------------------------------------------------------------- | :------------------------------------------------------------------------ |
| `GET /api/v1/baskets`                   | Retrieve the authenticated customer's basket enriched with live Catalog prices | `customer` role + `basket_read`, `basket_write`; per-user rate limit      |
| `POST /api/v1/baskets`                  | Create a basket with at least one item (`quantity > 0`)                        | `customer` role + `basket_read`, `basket_write`                           |
| `PUT /api/v1/baskets`                   | Replace the basket's entire item collection as a set                           | Whole-set replacement; Commerce removes items when quantity drops to zero |
| `DELETE /api/v1/baskets`                | Clear the authenticated customer's basket                                      | `customer` role + `basket_read`, `basket_write`                           |
| `basket.v1.BasketGrpcService.GetBasket` | Internal gRPC lookup invoked by Ordering API during checkout                   | Internal service-to-service gRPC                                          |

## Runtime view

1. **Basket management:** Authenticated shoppers view and edit `/basket` inside the **Commerce** microfrontend (`@bookworm/commerce`), while `@workspace/storefront-shell` keeps the shared header basket counter synchronized across Storefront and Commerce. Adding items through conversational assistance requires explicit customer confirmation before mutating Basket API.
2. **Checkout read:** When the shopper checks out in Commerce, Ordering API calls `basket.v1.BasketGrpcService.GetBasket` to read item IDs and quantities, then resolves live pricing from Catalog API.
3. **Post-checkout cleanup:** Finance publishes `PlaceOrderCommand` (`bookworm.{env}.finance.place-order`). Basket API deletes the customer's Redis basket (guarded by Redis idempotency) and publishes either `BasketDeletedCompleteIntegrationEvent` (`bookworm.{env}.basket.delete-complete`) or `BasketDeletedFailedIntegrationEvent` (`bookworm.{env}.basket.delete-failed`).

### Business invariants

- Every basket belongs to one authenticated customer identifier and requires at least one item with a positive quantity on creation.
- Basket updates replace the full item set rather than merging partial diffs.
- Basket items store only book UUIDs and quantities—never copied Catalog descriptions or locked Order prices.
- A `BasketDeletedFailedIntegrationEvent` signals explicit cleanup failure and must never be treated as successful cleanup or payment status.

## Deployment and cross-cutting concerns

- **Hosting and ingress:** `basket` runs behind the YARP API Gateway (`/basket/{**remainder}`) with internal Container App ingress.
- **Security and privacy:** Microsoft Entra ID enforces the `customer` role with `basket_read` and `basket_write` scopes, plus `HMAC__Key` signing and structured log redaction. `basket-identity` accesses Azure Managed Redis passwordlessly via Entra ID `default` access policy.
- **Observability and resilience:** OpenTelemetry correlates HTTP, gRPC, Redis, and Kafka spans by `OrderId`; exhausted Kafka consumers route to `bookworm.{env}.basket.dead-letter-queue`.

## Quality scenarios and known risks

| Quality attribute / risk | Scenario or exposure                                            | Current mitigation or gap                                                                      |
| :----------------------- | :-------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| **Performance**          | High-frequency basket reads during storefront browsing          | Authoritative Redis persistence + FusionCache keeps reads sub-millisecond                      |
| **Consistency**          | Duplicate `PlaceOrderCommand` delivery during Finance retries   | Redis idempotency guard (`IIntegrationEventIdempotencyGuard`) prevents unintended side effects |
| **Read dependency**      | Catalog API unavailable during `GET /api/v1/baskets` enrichment | Catalog gRPC calls use Aspire standard resilience with budgeted retries                        |
