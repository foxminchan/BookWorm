## 1. Context & Problem

Every online bookstore needs a seamless bridge between a shopper browsing books and a confirmed order entering fulfilment. Without a dedicated bounded context for that pre-purchase journey, cart management, live price presentation, checkout confirmation, and order creation quickly collapse into a single coupled workflow—making it difficult to evolve pricing, prevent duplicate orders, or isolate failures.

The **Shopping** subdomain solves this by owning the customer-facing path from selecting a [[entity|book]] in a personal [[entity|basket]] through handing an accepted purchase over to [[domain|ordering]] and the Finance workflow. Because cart and checkout behavior directly shape conversion and customer trust, Shopping is classified as a **Core Domain** and **Business Critical** capability, while deliberately leaving product descriptions in [[domain|catalog]], order lifecycles in [[domain|ordering]], and payment settlement in Finance.

## 2. Business Value

- **Higher conversion and smoother storefront experience:** Gives shoppers a fast, reliable way to add books, review live regular and sale prices, adjust quantities, or clear their cart before buying.
- **Safe conversational commerce:** Supports adding items through the storefront assistant while requiring explicit customer confirmation so automated suggestions never alter a cart unexpectedly.
- **Protection against duplicate purchases:** Ensures an accepted checkout cleans up the submitted basket so customers cannot accidentally submit the same purchase twice.
- **Clear operational visibility:** Turns post-checkout cleanup into explicit success or failure outcomes rather than silent state changes, enabling reliable recovery when downstream issues occur.
- **Independent service evolution:** Keeps pre-order shopping responsive and decoupled from order-history views, catalog administration, and payment settlement.

## 3. How It Works

Shopping manages the transient purchase context for each authenticated customer using clear domain concepts and strict boundaries:

### Domain language

- **[[entity|basket]]:** The customer's current collection of selected book references and requested quantities.
- **[[entity|basket-item]]:** A single book reference paired with a positive requested quantity; it does not take over ownership of Catalog's [[entity|book]] entity.
- **Checkout:** The boundary moment where the current basket is submitted to the order workflow.
- **Purchase handoff:** The coordination step that provides Ordering and Finance with everything needed to process an order without sharing Shopping's internal basket model.

### Customer & checkout flow

1. **Manage the basket:** An authenticated customer creates a basket with at least one book, reviews enriched product details (names, regular and sale prices, quantities, and totals), replaces the item selection when making changes (treating zero-quantity changes in the storefront as item removal), or clears the basket entirely.
2. **Confirm conversational actions:** When shoppers use the storefront's conversational assistant to add items, the assistant must obtain explicit customer confirmation before modifying the basket.
3. **Hand off at checkout:** At checkout, Shopping passes the purchase intent to [[domain|ordering]] and the Finance workflow, where purchase-time validity, payment, and fulfilment are owned.
4. **Clean up and signal outcome:** Once checkout hands off the purchase, Shopping deletes the submitted basket and emits an explicit completion or failure signal so the order workflow knows whether cleanup succeeded.

### Capability map

| Capability            | Responsibility                                                    | Strategic importance |
| --------------------- | ----------------------------------------------------------------- | -------------------- |
| Basket lifecycle      | Create, retrieve, replace, and delete a customer's basket         | Core                 |
| Basket composition    | Maintain book references and positive requested quantities        | Core                 |
| Purchase presentation | Show item details, sale prices, quantities, and calculated totals | Core                 |
| Checkout coordination | Hand an accepted basket to Ordering and the Finance workflow      | Core                 |
| Failure signalling    | Publish explicit basket-deletion success or failure outcomes      | Enabling             |

### Context boundaries

| Relationship        | Direction          | Integration intent                                                   |
| ------------------- | ------------------ | -------------------------------------------------------------------- |
| Customer → Shopping | Inbound            | Add books, manage quantities, inspect totals, and start checkout     |
| Catalog → Shopping  | Upstream reference | Supply book identity and product information used by the basket view |
| Shopping → Ordering | Handoff            | Submit the basket for order creation and confirmation                |
| Shopping → Finance  | Coordination       | Participate in the `place-order` workflow and basket cleanup         |

## 4. Trade-offs & Lessons Learned

- **A basket is not an Order:** Keeping the basket strictly as transient, pre-order intent prevents Ordering from depending on Shopping's internal storage, even though checkout must transfer full purchase details during the handoff.
- **Catalog remains the authority for product data:** Reading live book metadata and prices at display time ensures accuracy without duplicating Catalog ownership, though downstream checkout must still validate purchase-time prices and availability.
- **Whole-set basket replacement over incremental merging:** Replacing the full item set on updates prevents ambiguous partial-merge bugs and keeps customer-scoped state predictable.
- **Explicit handoff and cleanup signalling:** Crossing domain boundaries with asynchronous commands and outcome events avoids shared database tables, while requiring idempotent consumers and clear rules so a cleanup outcome is never mistaken for payment completion.
- **Per-user isolation and protection:** Scoping every action to an authenticated customer and applying per-user rate limits protects availability while preserving low-latency storefront performance.

## 5. Technical Reference

### Owned system and interaction surface

The [[system|cart-system]] contains the [[service|basket-api]], an internal HTTP and gRPC service secured per user. Its API supports:

| Operation                | Purpose                                      |
| ------------------------ | -------------------------------------------- |
| `GET /api/v1/baskets`    | Retrieve the authenticated customer's basket |
| `POST /api/v1/baskets`   | Create a basket with its initial items       |
| `PUT /api/v1/baskets`    | Replace the basket's current items           |
| `DELETE /api/v1/baskets` | Clear the authenticated customer's basket    |

The storefront can also expose these capabilities through conversational actions. Adding an item through the assistant requires explicit customer confirmation before the Basket API is updated.

### Checkout interaction

See [[diagram|checkout-interaction]] for the source-backed sequence from checkout through basket cleanup. It records the completion and failure paths that the Finance workflow receives after it issues [[command|PlaceOrderCommand]].

### Technical invariants & architecture principles

- Basket operations require an authenticated customer and are subject to the Basket API's per-user rate limit.
- A newly created basket contains at least one item; quantities must be greater than zero (setting an item to zero is treated by the storefront as a removal flow).
- Basket updates replace the current item set rather than merging arbitrary state into the existing basket.
- Shopping consumes published product representations and identifiers; it must not mutate Catalog data directly or expose its basket persistence model as an Order model.
- Checkout crosses the bounded-context boundary through commands and integration events rather than shared database tables.
- Basket deletion failure is represented by [[event|BasketDeletedFailedIntegrationEvent]]; consumers must not interpret it as a successful cleanup.
- Once a purchase is accepted, Ordering owns the Order lifecycle; Shopping owns only the pre-order basket experience.

### Quality attributes and operational concerns

| Concern       | High-level expectation                                                |
| ------------- | --------------------------------------------------------------------- |
| Security      | Every basket endpoint is authenticated and scoped to the current user |
| Consistency   | Checkout cleanup is explicit and duplicate basket reuse is prevented  |
| Availability  | Basket reads and updates remain independent from order-history views  |
| Performance   | Basket reads and writes support the low-latency storefront journey    |
| Resilience    | Completion and failure events make cross-service cleanup observable   |
| Accessibility | Storefront basket changes provide confirmation and status feedback    |
