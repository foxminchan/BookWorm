## Service Responsibility & Boundary

Basket API owns transient, customer-scoped shopping [[entity|basket]] and [[entity|basket-item]] state within the [[domain|shopping]] domain. It exposes authenticated HTTP endpoints for the storefront, serves internal gRPC basket snapshots to [[service|order-api]] during checkout, enriches basket reads with live titles and prices from [[service|catalog-api]] over gRPC, and performs asynchronous post-checkout cleanup with [[service|order-orchestration]] over Kafka.

## Service Profile

| Property                                  | Value                                                                                                                                                   |
| :---------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bounded Context / Domain**              | [[domain\|shopping]]                                                                                                                                    |
| **Owner Team**                            | [[team\|commerce-fulfillment-team]]                                                                                                                     |
| **Runtime Style**                         | REST API, gRPC Server/Client, and Async Kafka Consumer/Producer                                                                                         |
| **Public / Gateway Exposure**             | Yes via API Gateway (HTTP) and Internal Only (gRPC)                                                                                                     |
| **Authentication & Authorization Policy** | Microsoft Entra ID JWT via [[system\|identity-provider]]; `customer` role with basket read/write scopes; basket owner derived strictly from token       |
| **Owned Data Store(s)**                   | [[container\|basket-database]] (Redis key-value store, no SQL database)                                                                                 |
| **Key Resilience / Idempotency Pattern**  | 24-hour message-ID idempotency guard, per-user rate limiting, and dead-letter routing on [[channel\|bookworm.&#123;env&#125;.basket.dead-letter-queue]] |

## Contracts & Data Ownership

Basket API stores only customer ID, book IDs, and positive quantities in [[container|basket-database]]. Basket updates replace the entire item collection rather than merging partial changes, and basket records are never used to reconstruct accepted orders.

:::note
On read, Basket API batches distinct book IDs into a single gRPC lookup against [[service|catalog-api]] to attach current titles, regular prices, and sale prices. If Catalog returns no match for a book ID, the item remains in the response without inventing metadata.
:::

:::warning
Both Basket API and [[service|notification-api]] consume [[command|PlaceOrderCommand]] on the same Kafka topic. When [[service|order-orchestration]] retries on timeout, both consumers receive the retry.
:::
