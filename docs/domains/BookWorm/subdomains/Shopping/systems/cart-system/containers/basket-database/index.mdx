The Basket database is the authoritative Redis key-value store owned exclusively by [[service|basket-api]] in the Shopping bounded context. It persists each authenticated customer's active pre-checkout book selections while keeping product metadata in [[service|catalog-api]] and accepted purchases in [[service|order-api]].

## Overview

| Property               | Value                                                                                                                                                 |
| :--------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**              | Shopping bounded context — [[service\|basket-api]] (`basket`)                                                                                         |
| **Aspire resource ID** | `redis` (shared Azure Managed Redis resource)                                                                                                         |
| **Source**             | `src/Services/Basket/BookWorm.Basket/Infrastructure/Repositories/BasketRepository.cs`, `src/Services/Basket/BookWorm.Basket/Domain/CustomerBasket.cs` |
| **Engine**             | Redis (local container + RedisInsight in development; Azure Managed Redis in cloud)                                                                   |
| **Authoritative**      | Yes (`readWrite`) for active pre-checkout baskets                                                                                                     |
| **Classification**     | `internal`                                                                                                                                            |
| **Retention**          | Transient (persisted until replaced, explicitly deleted, or cleared after checkout)                                                                   |

## Architecture and data boundaries

Basket API is the sole service that reads from or writes to customer basket keys in Redis. Basket API has no relational SQL database; it resolves current book titles and prices from Catalog API over gRPC at read time and deletes the basket key upon receiving the post-checkout `PlaceOrderCommand` from Finance.

The diagram shows how Basket API persists customer baskets in Redis while hydrating product details from Catalog API and reporting cleanup results over Kafka.

<MermaidFileLoader file="mermaids/basket-database-diagram-1.mmd" />

- **Not a record of accepted orders:** Once checkout starts, [[service|order-api]] persists the immutable purchase snapshot in [[container|order-database]]. Downstream workflows never treat Redis basket records as confirmed orders.
- **No duplicated catalog metadata:** Titles, descriptions, and prices are never stored in Redis. Basket API fetches current metadata over gRPC when serving basket views.
- **Shared Redis resource:** Basket API shares the `redis` resource with Catalog API, Ordering API, Rating API, and Notification. Basket API also uses this Redis connection for FusionCache and its 24-hour integration event idempotency guard (`IIntegrationEventIdempotencyGuard`).

## Key model and data structure

`BasketRepository` accesses Redis directly via `IConnectionMultiplexer` and serializes `CustomerBasket` using source-generated `System.Text.Json` with camelCase property names (`BasketSerializationContext`).

| Property                 | Specification                                                                                                                    |
| :----------------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| **Key pattern**          | `basket:{userId}` where `{userId}` is the authenticated customer's GUID                                                          |
| **Redis type**           | `STRING` (UTF-8 JSON payload)                                                                                                    |
| **TTL / expiration**     | No explicit TTL is passed to `StringSetAsync`; entries persist until updated, deleted by the customer, or deleted after checkout |
| **Write semantics**      | Full-document replacement (`CustomerBasket.Update` clears existing items and writes the complete new item list)                  |
| **Validation invariant** | A `CustomerBasket` must contain at least one `BasketItem` (`BasketDomainException` if empty)                                     |

Neither the AppHost Redis configuration nor the generated `redis.bicep` declares an eviction policy. The generated artifact therefore does not establish what happens to idle basket keys under memory pressure; verify any policy configured outside this repository.

## Operations and cleanup behavior

| Operation                   | Redis command                | Behavior                                                                                                                                                                                                   |
| :-------------------------- | :--------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Read basket**             | `GET basket:{userId}`        | Returns deserialized `CustomerBasket` or `null` when absent. Basket API enriches items with Catalog gRPC details before returning HTTP/gRPC responses.                                                     |
| **Create or update basket** | `SET basket:{userId} <json>` | Overwrites the entire basket document atomically with the supplied item set; does not merge partial patches.                                                                                               |
| **Delete basket**           | `DEL basket:{userId}`        | Triggered by customer delete requests or post-checkout `PlaceOrderCommand` handling. Checkout cleanup publishes `BasketDeletedCompleteIntegrationEvent` or `BasketDeletedFailedIntegrationEvent` to Kafka. |

## Hosting and environment provisioning

AppHost provisions the shared `redis` resource via `src/Aspire/BookWorm.AppHost/Extensions/Infrastructure/AzureExtensions.Redis.cs`.

| Environment           | Provisioning & SKU                                                      | High availability | Local tooling |
| :-------------------- | :---------------------------------------------------------------------- | :---------------- | :------------ |
| **Local development** | Local Redis container (`ContainerLifetime.Persistent`) with data volume | Single container  | RedisInsight  |
| **Azure Development** | Azure Managed Redis (`BalancedB0`)                                      | Disabled          | —             |
| **Azure Staging**     | Azure Managed Redis (`BalancedB1`)                                      | Enabled           | —             |
| **Azure Production**  | Azure Managed Redis (`BalancedB5`)                                      | Enabled           | —             |

:::warning
Because `redis` is shared across five backend services, flushing the entire Redis instance clears active customer baskets, cached Catalog/Ordering/Rating responses, distributed locks, and active 24-hour integration event idempotency markers simultaneously.
:::
