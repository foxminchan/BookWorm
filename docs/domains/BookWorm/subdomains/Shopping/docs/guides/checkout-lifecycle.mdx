BookWorm draws a strict boundary between pre-purchase shopping intent and committed commercial orders: **Shopping** (**Basket API**, `basket`) owns the customer's mutable basket in **Redis** (`basket:{userId}`), **Catalog** (**Catalog API**, `catalog`) supplies live titles and prices, **Ordering** (**Ordering API**, `ordering`) locks in an immutable order snapshot in PostgreSQL (`orderingdb`), and **Finance** (`finance`) coordinates asynchronous basket deletion after checkout. Treating these responsibilities as distinct stages prevents accidental duplicate purchases and ensures a basket cleanup error is never confused with a failed order or payment.

## Context and motivation

Before a customer clicks checkout, their basket changes frequently and requires low-latency reads and writes with live catalog pricing. After checkout, the purchase must become an immutable commercial record that cannot shift when catalog prices change or when the customer starts shopping again.

Separating Shopping from Ordering and Finance ensures:

- **No shared mutable state:** Ordering never shares Redis basket keys with Shopping, and Shopping never writes to `orderingdb` or `catalogdb`.
- **Clean failure isolation:** A temporary Redis or Kafka issue during post-checkout cleanup never blocks or falsifies order status, while explicit cleanup events let Finance and Ordering react deterministically.

## How it works

Customers manage their basket and submit checkout through the **Commerce** (`@bookworm/commerce`) microfrontend (MFE), mounted at `/basket` and `/checkout/*` via **API Gateway** (`X-Mfe-Zone: commerce`).

### Four checkout stages

- **Review the live basket:** **Commerce** fetches the authenticated customer's basket from **Basket API** (`GET /basket/api/v1/baskets`). Basket API loads stored book IDs and quantities from Redis (`basket:{userId}`) and enriches them on read via Catalog API gRPC (`GetBooks`) so the customer confirms current titles and prices.
- **Confirm and hand off purchase intent:** When the customer confirms checkout, **Commerce** sends `POST /ordering/api/v1/orders` with a unique `x-request-id`. **Ordering API** reads the basket over gRPC (`GetBasket`), resolves and locks prices via Catalog API (`PriceSale ?? Price`), persists the immutable `Order` in `orderingdb` with status `New`, and publishes `UserCheckedOutIntegrationEvent` to Kafka.
- **Coordinate post-checkout cleanup:** **Finance** (`OrderOrchestrator` on Azure Functions + Durable Task Scheduler `finance-taskhub`) consumes `UserCheckedOutIntegrationEvent` and publishes `PlaceOrderCommand` to `bookworm.{env}.finance.place-order`.
- **Emit an explicit cleanup outcome:** Basket API's `PlaceOrderCommandHandler` acquires a 24-hour Redis `IIntegrationEventIdempotencyGuard` keyed by `OrderId` and deletes `basket:{BasketId}`:
  - When deletion succeeds (or the `OrderId` was already processed within 24 hours), Basket API emits `BasketDeletedCompleteIntegrationEvent` on `bookworm.{env}.basket.delete-complete`.
  - When deletion returns `false` (key absent/not deleted), Basket API emits `BasketDeletedFailedIntegrationEvent` on `bookworm.{env}.basket.delete-failed`.
  - Neither event proves payment settlement, order completion, or fulfillment; they report basket cleanup status only.

### Rules for callers and consumers

- **Verify before retrying ambiguous checkouts:** If `POST /ordering/api/v1/orders` times out, query Ordering API (`GET /ordering/api/v1/orders`) before retrying so the customer is not placed into a duplicate order.
- **Treat cleanup failure as distinct from deletion:** Never interpret `BasketDeletedFailedIntegrationEvent` as a successful cleanup or as a payment failure.
- **Design idempotent consumers:** Both Basket API and Finance tolerate at-least-once Kafka redelivery.

## Design trade-offs

| Decision                                                            | Benefits                                                                                                         | Costs and limits                                                                                                              |
| :------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------- |
| **gRPC snapshot read by Ordering API + asynchronous Kafka cleanup** | Keeps Shopping and Ordering storage decoupled and keeps checkout latency low                                     | Introduces a brief window after `201 Created` where basket cleanup is still in flight or can fail                             |
| **Live Catalog enrichment on basket read instead of stored prices** | Customers always see current prices before checkout without catalog-sync jobs                                    | Basket reads depend on Catalog API gRPC availability and degrade gracefully when a book is missing                            |
| **Explicit success and failure cleanup events**                     | Enables deterministic Finance/Ordering reactions (`DeleteBasketCompleteCommand` vs. `DeleteBasketFailedCommand`) | Adds two integration topics and requires disciplined incident triage so cleanup errors are not misread as order cancellations |

## Alternatives considered

- **Deleting the basket synchronously inside `POST /api/v1/orders`:** Rejected because coupling Ordering's PostgreSQL transaction to a remote Redis deletion creates dual-write failure modes when one store succeeds and the other fails.
- **Promoting the basket record directly into an Order entity:** Rejected because mutable pre-order browsing state and immutable financial order history have incompatible lifecycles, schemas, and retention rules.
