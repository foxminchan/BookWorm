Use this runbook when **Basket API** (`basket`) publishes `BasketDeletedFailedIntegrationEvent` on `bookworm.<env>.basket.delete-failed`, when `PlaceOrderCommand` messages land in `bookworm.<env>.basket.dead-letter-queue`, or when a customer's basket remains in **Redis** (`basket:<customer-id>`) after checkout. Always verify the downstream order status in **Ordering API** before deleting any basket. For Finance retry loops and Ordering soft-delete behavior, see How to troubleshoot stalled or failed checkout basket cleanup.

## Prerequisites

- Read access to **Ordering API** (`GET /ordering/api/v1/orders/{id}`) with an authorized administrator Microsoft Entra ID token.
- Read access to **Aspire Dashboard** (locally) or **Azure Log Analytics** for `basket`, `finance`, and `ordering` logs and traces.
- Read access to **Kafka UI** (locally) or **Confluent Cloud** for basket/finance topics and dead-letter queues (DLQs).
- Read-only access to **RedisInsight** (locally) or Azure Managed Redis monitoring for `redis` (Basket API uses Redis only—there is no SQL database).

## Steps

<Steps>
<Step title="Collect privacy-safe correlation identifiers">

Record the event ID, environment (`<env>`), UTC timestamp, `<customer-id>` / `<basket-id>`, and `<order-id>`. Do not include customer credentials, tokens, or personal details in incident tickets.

</Step>
<Step title="Check the downstream order status in Ordering API first">

Before touching the basket, verify whether **Ordering API** accepted, soft-deleted, or rejected the purchase:

<CodeGroup>

```bash
curl -sS -H "Authorization: Bearer <admin-token>" \
  "https://<gateway-host>/ordering/api/v1/orders/<order-id>"
```

</CodeGroup>

Where:

- `<admin-token>`: Valid Microsoft Entra ID bearer token with the `admin` role and `ordering_read` scope.
- `<gateway-host>`: API Gateway hostname (or local Aspire gateway address).
- `<order-id>`: UUID of the order associated with the cleanup failure.

<Admonition type="danger">
	Do not delete a customer's basket until you confirm the downstream order was accepted. If the
	order was not accepted or its status is ambiguous, stop immediately and escalate to the
	Ordering/Finance owners.
</Admonition>

</Step>
<Step title="Distinguish the two verified `PlaceOrderCommandHandler` failure modes">

Inspect `basket` logs, Redis key `basket:<customer-id>`, and Kafka topics (`bookworm.<env>.finance.place-order`, `bookworm.<env>.basket.delete-failed`, `bookworm.<env>.basket.dead-letter-queue`):

- **Mode A — `BasketDeletedFailedIntegrationEvent` emitted (`DeleteBasketAsync` returned `false`):** Redis was reachable, but key `basket:<customer-id>` was already absent when `PlaceOrderCommandHandler` attempted `KeyDeleteAsync`. Note that Finance reacts to `BasketDeletedFailedIntegrationEvent` by sending `DeleteBasketFailedCommand` to Ordering API, which soft-deletes the order (`order.Delete()`, causing `GET /ordering/api/v1/orders/<order-id>` to return `404 Not Found`).
- **Mode B — Transient Redis/broker exception (message retried or in DLQ):** If Redis threw an exception, `PlaceOrderCommandHandler` released its 24-hour `OrderId` idempotency guard and threw so Wolverine retried (`50ms / 250ms / 1s` with full jitter) before moving `PlaceOrderCommand` to `bookworm.<env>.basket.dead-letter-queue`. In this case, `basket:<customer-id>` typically still exists in Redis.

</Step>
<Step title="Execute the matching recovery path">

- **Transient Redis or consumer failure (Mode B, order accepted and `New`):**
  1. Restore `redis` or `basket` service health.
  2. Replay the failed `PlaceOrderCommand` from `bookworm.<env>.basket.dead-letter-queue` to `bookworm.<env>.finance.place-order` using approved broker tooling.
  3. Confirm `PlaceOrderCommandHandler` deletes `basket:<customer-id>` and emits `BasketDeletedCompleteIntegrationEvent` on `bookworm.<env>.basket.delete-complete`.
- **Order accepted, basket still present in Redis, no DLQ message:**
  1. Confirm `<order-id>` and `<basket-id>` belong to the same checkout attempt.
  2. Run the approved idempotent cleanup action (replay `PlaceOrderCommand` or authorized customer/admin basket delete) rather than ad-hoc raw Redis mutations whenever possible, so `BasketDeletedCompleteIntegrationEvent` stays synchronized with Finance.
- **Order soft-deleted (`404 Not Found` after Mode A) or purchase outcome ambiguous:**
  1. Stop without modifying Redis or issuing manual order transitions.
  2. Escalate to the Ordering and Finance maintainers with `<order-id>`, `<basket-id>`, `BasketDeletedFailedIntegrationEvent` metadata, and timestamps.

</Step>
</Steps>

## Verification

Confirm that cleanup completed and downstream consumers are healthy:

1. Verify `basket:<customer-id>` is no longer present in Redis (or `GET /basket/api/v1/baskets` for that customer returns `404 Not Found`).
2. Confirm `BasketDeletedCompleteIntegrationEvent` was published on `bookworm.<env>.basket.delete-complete` (and never emitted while the basket still existed).
3. Confirm consumer lag on `bookworm.<env>.finance.place-order` is `0` and `bookworm.<env>.basket.dead-letter-queue` is no longer growing.
4. Attach the original failure event ID and recovery outcome to the incident record without secrets or PII.

## Troubleshooting

| Symptom                                                                                                         | Cause                                                                                                                                                              | Fix                                                                                                          |
| :-------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------- |
| `PlaceOrderCommand` landed in `bookworm.<env>.basket.dead-letter-queue` and `basket:<customer-id>` still exists | Transient `redis` or `basket` outage caused `PlaceOrderCommandHandler` to release the `OrderId` guard and exhaust Wolverine retries                                | Restore `redis`/`basket`, confirm order exists in Ordering API, and replay the DLQ message                   |
| `BasketDeletedFailedIntegrationEvent` fired and `GET /ordering/api/v1/orders/<order-id>` returns `404`          | `basket:<customer-id>` was already absent when `PlaceOrderCommandHandler` ran; Finance sent `DeleteBasketFailedCommand` and Ordering soft-deleted the order        | Follow How to troubleshoot stalled or failed checkout basket cleanup and escalate to Ordering/Finance owners |
| Duplicate `PlaceOrderCommand` arrived within 24 hours after cleanup already succeeded                           | Finance open orchestration timer reissued `PlaceOrderCommand`; Basket's `OrderId` Redis guard deduplicated it and returned `BasketDeletedCompleteIntegrationEvent` | Expected Basket idempotency behavior; inspect Finance orchestration history if retries persist               |
| Order status is unknown or checkout timed out before creating an order                                          | Downstream order acceptance is unconfirmed                                                                                                                         | Stop immediately; do not delete `basket:<customer-id>` and escalate to Ordering/Finance owners               |
