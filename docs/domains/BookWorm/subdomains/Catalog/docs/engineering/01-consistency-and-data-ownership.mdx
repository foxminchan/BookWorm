This reference defines which data stores in the **Catalog** bounded context are authoritative systems of record, which are disposable or replayable derived projections, and how mutations propagate across PostgreSQL, Redis, Qdrant, Azure Blob Storage, and Kafka.

## Overview

| Property              | Value                                                                                                                             |
| :-------------------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**             | Catalog bounded context (`BookWorm.Catalog`, `BookWorm.Catalog.Ingestion`)                                                        |
| **Source**            | `src/Services/Catalog/BookWorm.Catalog`, `src/Services/Catalog/BookWorm.Catalog.Ingestion`                                        |
| **Protocol / format** | PostgreSQL (`catalogdb`), Redis (FusionCache), Qdrant (`vectordb`), Azure Blob Storage (`catalog-blob`), Kafka (CloudEvents JSON) |
| **Authentication**    | Managed Identity RBAC in Azure; Aspire local emulators/containers in Development                                                  |

## Store and projection ownership matrix

| Store / projection                                                     | Aspire resource ID            | Role                                                                                                                      | Rebuildable           | Consistency model                                                                        | Authoritative source                                    |
| :--------------------------------------------------------------------- | :---------------------------- | :------------------------------------------------------------------------------------------------------------------------ | :-------------------- | :--------------------------------------------------------------------------------------- | :------------------------------------------------------ |
| **Catalog database** (PostgreSQL)                                      | `catalogdb`                   | System of record for books, authors, categories, publishers, `pending_vector_updates`, and Wolverine outbox/inbox         | No                    | Strong (ACID)                                                                            | Self                                                    |
| **Catalog cover blobs** (Azure Blob Storage)                           | `catalog-blob`                | Binary cover artwork (`image/jpeg`, `image/png`, `image/webp`) referenced by URN (`urn:{account}:{container}:{blobName}`) | No                    | Strong per blob; read-only SAS URLs expire (`SasExpiryHours = 1` default)                | Self                                                    |
| **Catalog read cache** (Redis + FusionCache)                           | `redis`                       | L1 + L2 read cache with Redis backplane and 2-hour fail-safe                                                              | Yes (disposable)      | Eventual / short-lived (`Caching:Expiration = 00:30:00`; `catalog:dashboard:v1` = `15s`) | `catalogdb`                                             |
| **Catalog vector index** (Qdrant)                                      | `vectordb`                    | Derived semantic + keyword search candidates (`data-bookworm-snippets`) keyed by book UUID                                | Yes (full re-enqueue) | Eventual (5-minute Kafka batch queue, max 200 items/run)                                 | `catalogdb`                                             |
| **Book rating summary** (`average_rating`, `total_reviews` on `books`) | `catalogdb` (derived columns) | Local aggregate projection for storefront browsing and sorting                                                            | Yes (replayable)      | Eventual (Kafka events `bookworm.{env}.rating.feedback-create` / `feedback-delete`)      | **Rating API** Azure Cosmos DB (`ratingdb`/`feedbacks`) |

### Write-path propagation guarantees

1. **Transactional persistence (`catalogdb`):** **Catalog API** validates and commits changes to PostgreSQL (`catalogdb`). Database triggers atomically upsert affected `book_id` rows into `pending_vector_updates`, coalescing repeated edits under a new `revision` UUID and `updated_at` timestamp.
2. **Cache invalidation (`redis`):** Domain event handling removes the affected `book:{id}` key in FusionCache and propagates invalidation across instances via the Redis backplane. Dashboard totals (`catalog:dashboard:v1`) expire naturally every `15` seconds (`GetCatalogDashboardQuery.cs`).
3. **Asynchronous vector indexing (`vectordb`):** Every five minutes in UTC (`0 0/5 * * * ?`), **Scheduler** publishes `ProcessVectorBatchIntegrationEvent` to `scheduler.process-vector-batch`, triggering **Catalog Ingestion**. Under PostgreSQL advisory lock `740031001`, the worker reads up to `200` pending updates, generates Microsoft Foundry (`Cohere.EmbedV40`) embeddings, updates or deletes Qdrant vectors, and acknowledges only rows whose `(book_id, revision)` pair matches the batch snapshot.
4. **Cross-domain rating projection (`ratingdb` -> `catalogdb`):** **Catalog API** consumes `FeedbackCreatedIntegrationEvent` and `FeedbackDeletedIntegrationEvent` through Redis-backed `IIntegrationEventIdempotencyGuard` (24-hour TTL) and updates `average_rating` and `total_reviews` on `books`.

## Contributor invariants

- **Never use derived stores for purchase decisions:** **Ordering API** and **Basket API** must read prices and book existence through `book.v1.BookGrpcService` backed by authoritative `catalogdb` data—never from Qdrant records or stale client caches.
- **Keep indexed text and triggers synchronized:** When adding a searchable book attribute, update both `VectorBatchProcessor.ReadBatchAsync` and the PostgreSQL triggers populating `pending_vector_updates`.
- **Keep ingestion idempotent:** Re-processing the same `book_id` must overwrite the Qdrant `TextSnippet` deterministically by UUID.
- **Treat cache and vector stores as disposable:** Design code and tests so clearing Redis cache entries or rebuilding Qdrant from `catalogdb` never loses authoritative data.
