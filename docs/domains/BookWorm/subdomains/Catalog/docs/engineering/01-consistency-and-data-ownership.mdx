## 1. Context & Problem

The Catalog capability serves several different needs at once: displaying accurate book details and prices for checkout, delivering fast page loads during browsing, powering semantic and keyword search, storing cover images, and showing customer rating summaries. If all of those workloads relied on a single data layer or treated search indexes and fast-read copies as official product records, heavy browsing would slow down core operations or risk exposing stale prices during a purchase.

BookWorm resolves this by clearly separating what is authoritative and permanent from what is derived, temporary, and rebuildable.

## 2. Business Value

- **Purchase accuracy and trust**: Price and availability checks for buying decisions always come from the authoritative catalog record, never from temporary fast-read copies or search results.
- **Fast browsing and search**: Dedicated read and search layers absorb high customer traffic without slowing down core catalog updates.
- **Safe operational recovery**: Temporary speedups, search indexes, and rating summaries can be discarded, rebuilt, or replayed at any time without losing official book records or cover imagery.
- **Clean cross-domain boundaries**: Rating summaries appear alongside books without transferring ownership of customer reviews away from the Reviews domain.

## 3. How It Works

Catalog separates its information into permanent sources of truth and disposable or replayable helper views:

- **Authoritative book records and cover images**: The official catalog record is strongly consistent and cannot be rebuilt from elsewhere; cover image files are likewise permanent assets linked by reference.
- **Temporary read copies and search indexes**: Short-lived performance copies and queue-driven search indexes follow updates shortly after a change and can be completely regenerated if needed.
- **Customer rating summaries**: Aggregate ratings shown in Catalog are projections sourced from customer feedback in [[domain|reviews]] and can be replayed from review activity.

### How a book update flows through Catalog

1. **Validate and save**: An update to a [[entity|book]] is validated and saved in the authoritative catalog store.
2. **Clear stale read copies**: A change notification clears the short-lived fast-read copy for that book so browsers fetch fresh information.
3. **Queue search updates safely**: The change is recorded for search indexing; if multiple edits happen rapidly for the same book, they are combined so only the latest version needs indexing.
4. **Update search without losing concurrent edits**: A background worker processes queued updates in batches, coordinates exclusive access per batch, and only marks an item complete if no newer edit arrived while it was working—ensuring concurrent updates are never overwritten or lost.

## 4. Trade-offs & Lessons Learned

- **Eventual alignment vs. immediate search visibility**: Search results and rating summaries update asynchronously right after a book or review changes. Accepting a brief propagation lag keeps customer edits fast and isolates search outages from core catalog management.
- **Strict guardrails against stale reads**: Fast-read copies and search indexes must never be used to decide purchase price or stock availability; violating this boundary could let customers check out with outdated pricing.
- **Discipline when expanding search fields**: Adding new searchable book attributes requires updating both the text preparation logic and the change-detection mechanism so search indexes do not silently fall out of sync.
- **Idempotency and concurrency safety**: Re-processing the same book update must always produce the exact same search record, and version checks before acknowledging queued work prevent concurrent edits from being lost.

### Change propagation pipeline

1. API validates and commits the change to PostgreSQL ([[container|catalog-database]]).
2. A domain event invalidates `book:{id}` in [[container|catalog-cache]].
3. Database triggers upsert the [[entity|book]] into `pending_vector_updates`, coalescing repeated changes by `book_id` with a new `revision`.
4. [[service|catalog-ingestion]] processes batches under an advisory lock and acknowledges an item only if its `revision` is unchanged, so concurrent edits are never lost.

### Rules for contributors

- Add new indexed fields by updating both the searchable text builder and the triggers that enqueue changes.
- Never read price or availability for a purchase decision from [[container|catalog-cache]] or the [[container|catalog-vector]] record.
- Keep ingestion idempotent: re-processing a book must produce the same index record.
- Treat cache and vector stores as disposable in design and in tests.
