Use this guide when **Catalog API** returns outdated book details after a database update, when Backoffice dashboard totals appear stale, or when Redis connectivity errors increase Catalog read latency. Catalog's cache is disposable—PostgreSQL (`catalogdb`) is always the source of truth—and FusionCache (L1 memory + L2 Redis + Redis backplane + 2-hour fail-safe) falls back to `catalogdb` during Redis outages.

## Prerequisites

- Read access to PostgreSQL (`catalogdb`) and **Catalog API** logs/OpenTelemetry traces.
- Access to Redis (`redis-cli` or RedisInsight locally; Azure Managed Redis console/CLI in Azure).

## Steps

<Steps>
<Step title="Confirm the authoritative value in PostgreSQL (`catalogdb`)">

Query `catalogdb` to verify the book's current persisted values:

<CodeGroup>

```sql
SELECT id, name, price_original_price, price_discount_price, average_rating, total_reviews, is_deleted
FROM books
WHERE id = '<book-id>';
```

</CodeGroup>

Where:

- `<book-id>`: Target book UUID.

Compare the SQL result against `curl -sS "<gateway-url>/catalog/api/v1/books/<book-id>"`. If they match, the cache is not stale.

</Step>
<Step title="Identify whether the issue is a missed invalidation or a Redis outage">

- **Single book or dashboard stale:** Check **Catalog API** logs for failed domain-event cache invalidation (`book:<book-id>` has default `Caching:Expiration` = `00:30:00` in `BookWorm.Catalog/appsettings.json`; `catalog:dashboard:v1` expires every `15` seconds).
- **High read latency or Redis errors:** Check Redis health (`redis-cli -u "<redis-url>" PING`), Azure Managed Redis metrics, and FusionCache OpenTelemetry traces (`BookWorm` meter).

</Step>
<Step title="Apply targeted recovery">

<Admonition type="danger">
	Never run `FLUSHDB` or `FLUSHALL` on BookWorm's shared Redis instance (`redis`). The same Redis
	resource stores customer baskets (**Basket API**), distributed locks (**Ordering API**), and
	24-hour `IIntegrationEventIdempotencyGuard` keys across services.
</Admonition>

- **Single stale book:** Delete only that book's detail and summary keys in Redis:

  ```bash
  redis-cli -u "<redis-url>" UNLINK "book:<book-id>" "book:summary:<book-id>"
  ```

  Where:
  - `<redis-url>`: Connection URI for the target Redis instance.
  - `<book-id>`: Target book UUID.

  Because FusionCache also maintains an in-process L1 memory cache, direct Redis key deletion clears L2 immediately, while L1 entries on running replicas refresh via backplane invalidation or TTL expiry (`00:30:00`).

- **Wide Catalog staleness:** Evict only Catalog-prefixed keys (`catalog:*` and `book:*`) using non-blocking `SCAN` + `UNLINK` rather than flushing the database:

  ```bash
  redis-cli -u "<redis-url>" --scan --pattern "catalog:*" | xargs -r redis-cli -u "<redis-url>" UNLINK
  redis-cli -u "<redis-url>" --scan --pattern "book:*" | xargs -r redis-cli -u "<redis-url>" UNLINK
  ```

  Expect temporary extra read load on `catalogdb` while entries warm back up.

- **Redis outage:** **Catalog API** automatically falls back to `catalogdb` (or FusionCache fail-safe for up to 2 hours on cached keys). Monitor `catalogdb` CPU and PgBouncer connection saturation, restore Redis availability, and adjust **Catalog API** rate limits or replica scaling if `catalogdb` comes under pressure.

</Step>
</Steps>

## Verification

Fetch the book through **API Gateway** and confirm it returns the authoritative PostgreSQL values and baseline latency:

<CodeGroup>

```bash
curl -sS "<gateway-url>/catalog/api/v1/books/<book-id>"
```

</CodeGroup>

Expected output:

<CodeGroup>

```json
{
	"id": "<book-id>",
	"name": "<expected-title>",
	"price": 29.99
}
```

</CodeGroup>

Confirm Redis responds normally (`PING` returns `PONG`) and `catalogdb` read latency returns to baseline.

## Troubleshooting

| Symptom                                                               | Cause                                                                          | Fix                                                                                                                                                               |
| :-------------------------------------------------------------------- | :----------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Single book still shows old data immediately after `UNLINK` in Redis  | **Catalog API** replica is still serving its in-process FusionCache L1 entry   | Trigger a no-op update through **Catalog API** to broadcast a backplane invalidation, wait for `Caching:Expiration` (`00:30:00`), or restart the affected replica |
| Dashboard totals lag by a few seconds                                 | `catalog:dashboard:v1` uses a 15-second TTL (`GetCatalogDashboardQuery.cs`)    | Wait 15 seconds and re-fetch; no manual eviction is required                                                                                                      |
| Rising `catalogdb` CPU and slow `GET /catalog/api/v1/books` responses | Redis is unreachable and FusionCache is falling back to PostgreSQL             | Restore Azure Managed Redis connectivity; monitor `catalogdb` connections and enforce rate limits until Redis recovers                                            |
| Widespread stale list/search pages after a schema or DTO deployment   | Cached JSON shape changed without bumping key version in `CatalogCacheKeys.cs` | Evict `catalog:*` and `book:*` keys with `SCAN` + `UNLINK`, and bump the version suffix (`v2`) in `CatalogCacheKeys.cs`                                           |
