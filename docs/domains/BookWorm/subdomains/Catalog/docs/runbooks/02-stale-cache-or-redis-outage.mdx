## Trigger / Symptom & Blast Radius

[[service|catalog-api]] returns outdated book details after a database update, Backoffice dashboard totals lag, or Redis connectivity errors increase read latency. [[container|catalog-cache]] is disposableâ€”[[container|catalog-database]] is always the source of truthâ€”and [[service|catalog-api]] falls back to PostgreSQL or its 2-hour fail-safe during Redis outages.

<Admonition type="danger">
	Never run `FLUSHDB` or `FLUSHALL` on BookWorm's shared Redis instance. The same Redis cluster
	stores customer baskets ([[container|basket-database]]), distributed locks
	([[container|order-cache]]), and 24-hour idempotency keys across services.
</Admonition>

## Pre-Flight Check

Confirm Redis responsiveness and check the authoritative record in [[container|catalog-database]]:

```bash
redis-cli -u "<REDIS_URL>" PING
```

```sql
SELECT id, name, price_original_price, price_discount_price, average_rating, total_reviews, is_deleted
FROM books
WHERE id = '<BOOK_ID>';
```

## Quick Recovery Procedure

<Steps>
<Step title="Compare gateway output against PostgreSQL">

Fetch the book through the API Gateway and compare it to the SQL result:

```bash
curl -sS "https://<GATEWAY_HOST>/catalog/api/v1/books/<BOOK_ID>"
```

If they match, the cache is not stale.

</Step>
<Step title="Evict only affected Catalog keys">

For a single stale book, delete only its detail and summary keys (never flush the database):

```bash
redis-cli -u "<REDIS_URL>" UNLINK "book:<BOOK_ID>" "book:summary:<BOOK_ID>"
```

For wide Catalog staleness after a bulk change or schema update, evict only Catalog-prefixed keys using non-blocking `SCAN` + `UNLINK`:

```bash
redis-cli -u "<REDIS_URL>" --scan --pattern "catalog:*" | xargs -r redis-cli -u "<REDIS_URL>" UNLINK
redis-cli -u "<REDIS_URL>" --scan --pattern "book:*" | xargs -r redis-cli -u "<REDIS_URL>" UNLINK
```

</Step>
<Step title="Handle a full Redis outage">

During a Redis outage, [[service|catalog-api]] automatically falls back to [[container|catalog-database]]. Monitor PostgreSQL CPU and connection saturation, restore Azure Managed Redis connectivity, and scale [[service|catalog-api]] or enforce rate limits if database load spikes.

</Step>
</Steps>

## Verification

Re-fetch the book through the API Gateway and confirm it returns the authoritative PostgreSQL values:

```bash
curl -sS "https://<GATEWAY_HOST>/catalog/api/v1/books/<BOOK_ID>"
```

Expected output:

```json
{
	"id": "<BOOK_ID>",
	"name": "<EXPECTED_TITLE>",
	"price": 29.99
}
```

## Rollback / Escalation

- **Rollback:** Cache eviction is safe and self-healing; entries repopulate automatically on next read.
- **Escalation:** Escalate persistent Redis connectivity or backplane invalidation failures to [[team|platform-engineering-team]].

<AccordionGroup>
<Accordion title="Troubleshooting edge cases">

| Symptom                                      | Cause                                               | Fix                                                                                 |
| :------------------------------------------- | :-------------------------------------------------- | :---------------------------------------------------------------------------------- |
| Single book still stale after Redis `UNLINK` | Replica serving in-process L1 memory cache          | Trigger a no-op update via [[service\|catalog-api]] or restart the affected replica |
| Dashboard totals lag by a few seconds        | Dashboard cache uses a 15-second TTL                | Wait 15 seconds and re-fetch; no manual eviction needed                             |
| Rising [[container\|catalog-database]] CPU   | Redis unreachable; reads falling back to PostgreSQL | Restore Azure Managed Redis connectivity and monitor DB connections                 |

</Accordion>
</AccordionGroup>
