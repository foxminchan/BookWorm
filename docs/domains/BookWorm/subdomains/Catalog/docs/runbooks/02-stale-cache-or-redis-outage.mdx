## 1. Context & Problem

The catalog uses a high-speed read cache to serve frequently viewed [[entity|book]] details and administrative dashboard metrics without overloading the primary database. If an update fails to invalidate a cached entry, customers can see outdated book prices or metadata; if the cache service becomes unreachable, catalog reads slow down and increase load on the primary database.

## 2. Business Value

- **Continuous storefront availability:** Because the cache is strictly disposable and reads fall back to the primary database, a cache outage degrades performance rather than causing a total catalog outage.
- **Rapid price and data correction:** Enables support and operations teams to clear single stale items or flush the catalog cache safely with zero risk of data loss.
- **Clear operational boundaries:** Reinforces that the cache is never an authoritative store, preventing misuse during incidents or recovery.

## 3. How It Works

### Symptoms and background

Stale-cache or outage incidents show up when a [[entity|book]] displays old information after an update, dashboard summary figures appear outdated, or catalog read response times climb alongside cache connectivity errors.

The read cache is completely disposable. Whenever a book changes, its individual cached entry is automatically removed, while dashboard summaries refresh on a brief time-to-live window. The primary catalog database always remains the authoritative source of truth.

### Diagnosis and recovery flow

1. **Confirm the source of truth:** Verify that the primary database holds the expected book values and compare them with what catalog read lookups return.
2. **Pinpoint the cause:** If read responses differ from the database, invalidation failed—inspect catalog service logs for failed change handling. If reads are slow or failing overall, check cache connectivity, latency, and caching telemetry.
3. **Apply targeted recovery:**
   - **Single stale book:** Remove that book's cached entry or wait for its expiration window; the next read automatically repopulates it from the primary database.
   - **Widespread staleness:** Flush the catalog cache keys. This is safe and only introduces temporary extra load on the primary database while entries warm back up.
   - **Cache outage:** Reads fall back to the primary database through the cached query path, raising latency and database load. Restore cache availability and scale or rate-limit API traffic if the database comes under pressure.
4. **Verify recovery:** Confirm that book reads return the authoritative database values and that read latency and database load return to baseline.

## 4. Trade-offs & Lessons Learned

- **Disposable cache vs. persistent store:** Treating the cache as strictly disposable allows safe flushes during staleness incidents, accepting temporary database load spikes while cold entries repopulate (see [[adr|adr-004-fusioncache-redis-for-catalog-reads]]).
- **Automatic database fallback vs. failing fast:** Falling back to the primary database keeps the catalog available during cache outages, though high read volume can strain the database unless capacity scaling or rate limiting is ready.
- **Short timer for dashboard aggregates:** Using a short expiration window for dashboard summaries avoids complex multi-entity invalidation logic while accepting brief summary lag.

## 5. Technical Reference

### Symptoms

- A [[entity|book]] shows old data after an update.
- Dashboard numbers look outdated.
- Catalog read latency rises, or errors mention Redis connectivity.

### Background

[[container|catalog-cache]] is disposable. Keys: `book:{id}` (default
`Caching:Expiration`) and `catalog:dashboard:v1` (15 seconds). Book changes
remove the matching `book:{id}` entry.

### Diagnose

1. Confirm the database holds the expected value (it is the source of truth).
2. Compare with what [[query|GetBook]] returns.
3. If they differ, the entry was not invalidated: look for failed change
   handling in [[service|catalog-api]] logs.
4. If reads are slow or failing, check Redis connectivity and latency and the
   FusionCache metrics and traces.

### Recover

- **Single stale book:** delete the `book:{id}` key, or wait for expiry. The
  next read repopulates from [[container|catalog-database]].
- **Wide staleness:** flush the Catalog cache keys. This is safe; only
  temporary extra database load results.
- **Redis down:** reads fall back to the database through the cached query
  path, so expect higher latency and database load. Restore Redis, and
  scale or rate-limit the API if the database is under pressure.

### Verify

- [[query|GetBook]] returns the database value.
- Latency and database load return to baseline.

### Prevention

Never read Redis as an authority and never write catalog data there. See
[[adr|adr-004-fusioncache-redis-for-catalog-reads]].
