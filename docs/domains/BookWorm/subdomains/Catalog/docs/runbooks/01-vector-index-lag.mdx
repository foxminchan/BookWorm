Use this guide when newly created, edited, or deleted books appear in direct lookups (`GET /catalog/api/v1/books/{id}`) and filtered listings, but are missing or outdated in free-text search. **Catalog Ingestion** (`BookWorm.Catalog.Ingestion`) is an internal Azure Functions worker with **no HTTP API**—it is triggered every five minutes by **Scheduler** (`ProcessVectorBatchJob`) over Kafka topic `scheduler.process-vector-batch` (consumer group `catalog-ingestion`) to sync up to 200 queued rows per batch from PostgreSQL (`catalogdb`) into Qdrant (`vectordb`). Impact is limited to free-text search discovery; checkout and authoritative catalog browsing remain unaffected.

## Prerequisites

- Read access to PostgreSQL (`catalogdb`) and **Catalog Ingestion** / **Scheduler** logs.
- Access to **Quartz Dashboard** (`/quartz`, requires Microsoft Entra ID `admin` role) and Kafka topic inspection (Kafka UI locally or Confluent Cloud in Azure).
- Operational approval before terminating a stuck PostgreSQL backend session or running a full-index rebuild.

## Steps

<Steps>
<Step title="Measure the pending queue in `catalogdb`">

Run this read-only query against PostgreSQL (`catalogdb`) to check queue depth and oldest waiting timestamp:

<CodeGroup>

```sql
SELECT
    count(*) AS pending_books,
    min(updated_at) AS oldest_pending_update,
    clock_timestamp() - min(updated_at) AS oldest_pending_age
FROM pending_vector_updates;
```

</CodeGroup>

If `pending_books` is `0`, the queue is drained—verify whether the search result is cached (`catalog:books:search:v1:*`) or whether Qdrant collection `data-bookworm-snippets` was recreated.

</Step>
<Step title="Verify Scheduler and Kafka delivery">

Open **Quartz Dashboard** at `/quartz` and confirm `ProcessVectorBatchJob` (cron `0 0/5 * * * ?` UTC, `FireOnceNow` misfire policy) is firing without errors. Then inspect Kafka topic `scheduler.process-vector-batch` and consumer group `catalog-ingestion`:

- **No recent messages on `scheduler.process-vector-batch`:** Inspect **Scheduler** (`BookWorm.Scheduler`) logs and `schedulerdb` connectivity (note that **Scheduler** uses `.WithExplicitStart()` in local Aspire runs and must be started manually in the Aspire Dashboard).
- **Messages present, high lag on consumer group `catalog-ingestion`:** Inspect **Catalog Ingestion** (`BookWorm.Catalog.Ingestion`) container health and `ProcessVectorBatchFunction` logs.

</Step>
<Step title="Check for a stuck PostgreSQL advisory lock (`740031001`)">

`VectorBatchProcessor.ProcessAsync` acquires advisory lock `740031001` via `pg_try_advisory_lock(740031001)` and exits with `0` processed items if another session holds the lock. Check whether an orphaned session is holding it in `catalogdb`:

<CodeGroup>

```sql
SELECT l.pid, a.usename, a.application_name, a.state, a.query_start, a.query
FROM pg_locks l
JOIN pg_stat_activity a ON a.pid = l.pid
WHERE l.locktype = 'advisory'
  AND l.objid = 740031001;
```

</CodeGroup>

If a dead or hung session owns lock `740031001`, terminate only that verified PID:

<CodeGroup>

```sql
SELECT pg_terminate_backend(<stuck-pid>);
```

</CodeGroup>

Where:

- `<stuck-pid>`: PostgreSQL backend PID returned by the `pg_locks` query above.

</Step>
<Step title="Check Microsoft Foundry embeddings and Qdrant health">

Inspect **Catalog Ingestion** logs for exceptions from:

- **Microsoft Foundry (`Cohere.EmbedV40`):** `InvalidOperationException("The embedding service returned an incomplete batch.")` or HTTP/auth errors abort the batch before any Qdrant writes or queue acknowledgements.
- **Qdrant (`vectordb`, collection `data-bookworm-snippets`):** Connection timeouts or upsert/delete errors preserve unacknowledged rows in `pending_vector_updates` for safe retry on the next run.

</Step>
<Step title="Drain the backlog or run a full index rebuild">

Once the underlying dependency is healthy, unacknowledged rows retry automatically on the next 5-minute `ProcessVectorBatchJob` firing (up to `200` books per batch). Trigger `ProcessVectorBatchJob` repeatedly in **Quartz Dashboard** (`/quartz`) to drain a large backlog faster.

> [!CAUTION]
> Run a full index rebuild only as an approved operational action after Qdrant data loss or an indexed-field schema change. Never manually delete rows from `pending_vector_updates` to hide a backlog.

To re-enqueue every book in `catalogdb` for a full rebuild:

<CodeGroup>

```sql
INSERT INTO pending_vector_updates (book_id)
SELECT id FROM books
ON CONFLICT (book_id) DO UPDATE
SET revision = gen_random_uuid(), updated_at = clock_timestamp();
```

</CodeGroup>

</Step>
</Steps>

## Verification

Re-run the pending queue query in `catalogdb` and confirm `pending_books` trends to `0`:

<CodeGroup>

```sql
SELECT count(*) AS pending_books, min(updated_at) AS oldest_pending_update
FROM pending_vector_updates;
```

</CodeGroup>

Expected output:

<CodeGroup>

```text
 pending_books | oldest_pending_update
---------------+-----------------------
             0 |
```

</CodeGroup>

Search for a recently edited book through **API Gateway** (`GET /catalog/api/v1/books?search=<search-term>`) and confirm it appears in the results.

## Troubleshooting

| Symptom                                                                            | Cause                                                                                                            | Fix                                                                                                               |
| :--------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------- |
| `pending_books` grows locally and no events reach Kafka                            | **Scheduler** is configured with `.WithExplicitStart()` in `AppHost.cs` and is not running                       | Start `scheduler` in the Aspire Dashboard and trigger `ProcessVectorBatchJob`                                     |
| `ProcessVectorBatchFunction` executes cleanly but `pending_books` never shrinks    | Another session holds PostgreSQL advisory lock `740031001`                                                       | Query `pg_locks` for `objid = 740031001` and terminate the stuck session with `pg_terminate_backend(<stuck-pid>)` |
| Consumer lag increases on `scheduler.process-vector-batch` (`catalog-ingestion`)   | **Catalog Ingestion** Azure Function is down, crashing on CloudEvents deserialization, or unreachable from Kafka | Inspect `BookWorm.Catalog.Ingestion` logs and Kafka broker connection string (`ConnectionStrings__broker`)        |
| Logs report `The embedding service returned an incomplete batch` or Foundry errors | Microsoft Foundry `embedding` deployment (`Cohere.EmbedV40`) throttled or unreachable                            | Check Microsoft Foundry quota, health, and `CognitiveServicesUser` RBAC; rows remain queued for automatic retry   |
| Logs report Qdrant write errors                                                    | `vectordb` unreachable or `ConnectionStrings__vectordb` invalid                                                  | Restore Qdrant health and verify `data-bookworm-snippets` collection; re-trigger `ProcessVectorBatchJob`          |
