**Catalog API** serves book discovery through two complementary query paths: structured browsing (filtering by category, publisher, author, or price bounds directly against PostgreSQL `catalogdb`) and free-text discovery (generating query embeddings via Microsoft Foundry, retrieving candidate book UUIDs from Qdrant `vectordb`, and hydrating authoritative book details from PostgreSQL). Both **Storefront** (`GET /catalog/api/v1/books`) and **MCP Tools** (`search_catalog` over gRPC `book.v1.BookGrpcService.ListBooks`) share this architecture so displayed prices, availability, and cover links always come from the primary database.

## Context and motivation

Customers discover books in two distinct ways: navigating structured facets (categories, authors, publishers, price ranges, sorting) and entering natural-language search queries. Relational SQL filtering alone handles exact facets well but misses semantic intent and fuzzy phrasing. Conversely, serving prices and metadata directly from a vector search index risks exposing stale commercial data during price updates or book retirements.

BookWorm combines relational accuracy with vector recall by treating Qdrant as a **candidate-ranking projection** and PostgreSQL (`catalogdb`) as the **authoritative hydration source**.

## How it works

Every discovery request enters **Catalog API** (via **API Gateway** for Storefront REST traffic or internal gRPC from **MCP Tools** for AI chat) and branches based on whether a free-text search term is present.

### Query paths

| Discovery mode              | Entry condition                                                                         | Execution path                                                                                                                                                                                                                                                                                                | Authoritative data source                                |
| :-------------------------- | :-------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------- |
| **Structured browse**       | Category, publisher, author, price bounds, sort, or page parameters with no search term | Queries `catalogdb` directly and caches pages under `catalog:books:list:v1:{sha256}`                                                                                                                                                                                                                          | PostgreSQL (`catalogdb`)                                 |
| **Free-text hybrid search** | Search term provided (with optional facets and paging)                                  | Embeds query via Microsoft Foundry (`Cohere.EmbedV40`), runs hybrid vector + keyword search in Qdrant (`data-bookworm-snippets`) to obtain candidate book UUIDs, hydrates matching rows from PostgreSQL (`catalogdb`), applies filters/paging, and caches under `catalog:books:search:v1:{sha256}:{pageSize}` | Qdrant candidates hydrated from PostgreSQL (`catalogdb`) |

### Consistency expectations

- **Eventual search visibility:** Newly created or edited books appear in structured browse and direct lookups (`GET /catalog/api/v1/books/{id}`) immediately, but appear in free-text search only after **Catalog Ingestion** processes their `pending_vector_updates` row (triggered every five minutes by **Scheduler**).
- **Authoritative commercial details:** Prices, discount prices, availability, rating summaries, and freshly signed cover SAS URLs always come from PostgreSQL (`catalogdb`) and `BlobService`, never from Qdrant payloads.
- **Brief deletion transition window:** When a book is soft-deleted (`is_deleted = true`), Qdrant may still return its UUID as a candidate until the next **Catalog Ingestion** batch deletes the vector. PostgreSQL hydration filters out soft-deleted books so retired titles do not appear in returned results.

### Separating discovery symptoms

Because discovery touches Qdrant, Redis FusionCache, and expiring Blob Storage SAS URLs, isolate symptoms before escalating:

- **New or edited book missing from text search only:** Indicates ingestion lag — follow How to resolve Catalog vector index lag.
- **Old price or metadata shown after an update:** Indicates stale cache — follow How to resolve a Catalog stale cache or Redis outage.
- **Book cover image returns HTTP `403` or `404`:** Indicates an expired SAS URL or missing blob — follow How to resolve broken book images in Catalog.

## Design trade-offs

| Decision                                              | Benefits                                                                                           | Costs and limits                                                                                       |
| :---------------------------------------------------- | :------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| **Qdrant candidate lookup + PostgreSQL hydration**    | Guarantees authoritative prices, soft-delete filtering, and live SAS URLs on every search response | Adds a relational lookup step after Qdrant retrieval                                                   |
| **Asynchronous background vector indexing**           | Keeps catalog writes fast and shields **Catalog API** from Microsoft Foundry or Qdrant outages     | Creates a brief lag window before new or edited books appear in free-text search                       |
| **Hashed FusionCache keys for list and search pages** | Reduces repeated embedding and database load on popular queries                                    | Cached search/list pages can reflect brief staleness until tag invalidation or TTL expiry (`00:30:00`) |

## Alternatives considered

- **PostgreSQL full-text search alone:** Rejected because keyword-only matching struggles with semantic and conversational discovery queries from both Storefront and Chat API.
- **Serving book prices and metadata directly from Qdrant payloads:** Rejected because Qdrant is eventually consistent and would risk displaying outdated prices or retired books.
