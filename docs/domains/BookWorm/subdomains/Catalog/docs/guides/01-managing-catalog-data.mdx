**Catalog API** (`BookWorm.Catalog`) is the authoritative owner of BookWorm's books, authors, categories, publishers, pricing, and cover image references. Store administrators manage these records through **Backoffice** (`@bookworm/backoffice`) or authenticated REST calls to `/catalog/api/v1/{books,authors,categories,publishers}` (requiring Microsoft Entra ID `business_user` or `admin` roles with `read` and `write` scopes). Understanding entity creation order, deletion rules, read-only rating summaries, and asynchronous indexing prevents broken references and pricing surprises across **Storefront**, **Basket API**, and **Ordering API**.

## Context and motivation

Books depend on supporting taxonomy records (a category, a publisher, and one or more authors), carry promotional pricing rules, reference binary cover artwork in Azure Blob Storage (`catalog-blob`), and display derived customer ratings from **Reviews**. Without clear domain invariants at the **Catalog API** boundary, invalid discounts, orphaned author attributions, expired image links, or manual rating overrides would corrupt merchandising data across customer microfrontends (MFEs).

## How it works

Every catalog write enters **Catalog API**, validates domain invariants before committing to PostgreSQL (`catalogdb`), and triggers downstream cache invalidation and background vector indexing.

### Entity creation order

Because a book references supporting taxonomy records, create entities in dependency order:

1. **Create publishers and categories first:** Names must be unique within `catalogdb`.
2. **Create authors:** Authors exist independently before being linked via `book_authors`.
3. **Create the book with optional cover artwork:** Reference the created category, publisher, and author IDs via multipart form data on `/catalog/api/v1/books`. Direct reads (`GET /catalog/api/v1/books/{id}`) reflect the saved book immediately, while free-text search becomes discoverable after the next scheduled **Catalog Ingestion** batch runs.

### Domain invariants

- **Valid discount bounds:** A book's `DiscountPrice` must be greater than or equal to `0` and less than or equal to its `OriginalPrice` (`Price.cs`).
- **Category and publisher deletion:** Deleting a category or publisher preserves associated books and clears their reference rather than deleting books.
- **Author deletion protection:** **Catalog API** blocks deleting an author while any book still references that author (`DeleteBehavior.Restrict` in `BookAuthorConfiguration.cs`).
- **Book soft deletion:** Deleting a book sets `is_deleted = true`, hides it from active listings, and queues its UUID in `pending_vector_updates` so **Catalog Ingestion** deletes it from Qdrant (`vectordb`).
- **Read-only rating summaries:** `average_rating` and `total_reviews` are read-only projections updated by Kafka events from **Rating API**. Catalog users and integrators cannot edit rating fields manually.

### Cover artwork and post-change propagation

- **Multipart uploads and short-lived SAS URLs:** Upload cover artwork (`image/jpeg`, `image/png`, or `image/webp`) with the book create or update request. **Catalog API** stores only an internal URN (`urn:{account}:{container}:{blobName}`) in PostgreSQL (`books.image`) and generates read-only, time-limited SAS URLs on read (`SasExpiryHours = 1` default in `CatalogAppSettings.cs`). Clients must never persist those temporary SAS URLs as permanent image identifiers.
- **Immediate direct reads vs. eventual search:** Book writes invalidate `book:{id}` in Redis FusionCache so direct lookups return current values right away, while PostgreSQL triggers enqueue `book_id` in `pending_vector_updates` for asynchronous Qdrant indexing.
- **Immutable accepted orders:** **Basket API** and **Ordering API** re-validate current prices through gRPC (`book.v1.BookGrpcService`) at checkout. Editing a book's price or metadata in Catalog never retroactively alters an already accepted order in `orderingdb`.

## Design trade-offs

| Decision                                                        | Benefits                                                                                                     | Costs and limits                                                                                           |
| :-------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **Restrict author deletion; allow category/publisher deletion** | Protects author attribution integrity while keeping taxonomy reorganization low-friction                     | Removing an author requires unlinking or retiring their books first                                        |
| **Soft-delete books (`is_deleted = true`)**                     | Preserves historical book identity and order-audit traceability while removing titles from storefront search | Deleted rows remain in PostgreSQL and require filtering in queries and ingestion                           |
| **Store internal URN and sign short-lived SAS URLs on read**    | Prevents public blob scraping (`AllowBlobPublicAccess = false`) and decouples clients from storage internals | Clients that cache book payloads beyond `SasExpiryHours` encounter HTTP `403` until they re-fetch the book |
| **Read-only rating summary updated asynchronously**             | Keeps Reviews (`Cosmos DB`) authoritative and prevents manual tampering with customer scores                 | Rating changes appear in Catalog after brief Kafka propagation lag                                         |

## Alternatives considered

- **Hard-deleting books from PostgreSQL:** Rejected because removing primary keys breaks historical references in accepted orders and complicates vector cleanup.
- **Public anonymous blob URLs for book covers:** Rejected to keep Azure Storage locked down (`AllowBlobPublicAccess = false`) and signed through Managed Identity User Delegation Keys.
- **Allowing Catalog admins to edit `average_rating` directly:** Rejected because **Reviews** owns individual `Feedback` records and Catalog's summary must remain a faithful projection.
