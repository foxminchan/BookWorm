## 1. Context & Problem

Customer baskets and orders routinely contain several different [[entity|book]]s at once. If [[service|basket-api]] or [[service|order-api]] had to ask [[service|catalog-api]] about each item one by one during basket display, checkout, or order viewing, latency would climb quickly and internal traffic would multiply with basket size.

## 2. Business Value

- **Faster checkout and basket loading**: Fetches current names, prices, and availability for an entire set of books in one round trip.
- **Lower infrastructure load**: Replaces repeated per-item calls with a single compact batch lookup.
- **Reliable order and basket accuracy**: Ensures [[service|basket-api]] and [[service|order-api]] validate and display up-to-date catalog pricing and stock status before orders are finalized or displayed.
- **Caching friendliness**: Supports batch caching in [[service|order-api]] to further improve responsiveness on repeated order views.

## 3. How It Works

1. A consuming service—such as [[service|basket-api]] when enriching a shopping basket, or [[service|order-api]] during checkout and order detail enrichment—collects the unique identifiers of all [[entity|book]]s it needs to verify.
2. It sends that list of identifiers in a single direct request to [[service|catalog-api]].
3. [[service|catalog-api]] looks up the matching [[entity|book]] records synchronously and returns a compact summary (identity, pricing, and availability) for the requested items in one response.
4. Where appropriate, [[service|order-api]] caches the returned batch to avoid redundant calls for frequently accessed order details.

## 4. Trade-offs & Lessons Learned

- **Synchronous request-response vs. event-driven replication**: Using a direct synchronous lookup instead of an integration-event channel avoids maintaining duplicated catalog read tables inside [[service|basket-api]] and [[service|order-api]] and guarantees fresh pricing at checkout, though it introduces a runtime dependency on [[service|catalog-api]] availability.
- **Compact projection**: Returning only compact book fields keeps batch responses fast and small; callers needing full descriptions or author metadata must use a detailed lookup instead.
- **Batch caching trade-off**: Caching book batches in [[service|order-api]] improves speed and resilience, but teams must ensure cache lifetimes remain aligned with acceptable freshness for price or availability changes.

## 5. Technical Reference

`GetBooks` is a read-only RPC defined in the `book.v1` gRPC contract (`BookGrpcService`) that returns compact [[entity|book]] representations for multiple requested book identifiers in a single synchronous service-to-service call (not an integration-event channel).

- **Producers / Callers**:
  - [[service|basket-api]] produces this query to enrich basket items.
  - [[service|order-api]] produces this query during checkout and Order detail enrichment, caching book batches.
- **Consumer**: [[service|catalog-api]] consumes the query.
- **Request**: `GetBooksRequest` containing one or more book UUIDs in `book_ids`.
- **Response**: `GetBooksResponse` containing a repeated collection of `GetBookResponse` values.

### Examples

<CodeGroup dropdown>

```csharp title="GetBooks gRPC example"
using Grpc.Net.Client;
using BookWorm.Catalog.Grpc.Services;

using var channel = GrpcChannel.ForAddress(Services.CatalogApi);
var client = new BookGrpcService.BookGrpcServiceClient(channel);

var request = new GetBooksRequest();
request.BookIds.Add("0192f4d8-5f3c-7a11-b5dd-2c9e4a6f8b20");
request.BookIds.Add("0192f4d8-5f3c-7a11-b5dd-2c9e4a6f8b21");

var response = await client.GetBooksAsync(request);

foreach (var book in response.Books)
{
  Console.WriteLine($"{book.Name}: {book.Status}");
}
```
