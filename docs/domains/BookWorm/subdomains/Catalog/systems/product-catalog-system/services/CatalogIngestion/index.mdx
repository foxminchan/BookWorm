## 1. Context & Problem

BookWorm supports rich semantic search over its catalog so readers can find books by meaning, not only exact keywords. Generating search vectors and updating the search index ([[container|catalog-vector]]) is too slow and failure-prone to run synchronously every time someone creates, edits, or removes a [[entity|book]] through [[service|catalog-api]].

Catalog Ingestion solves this by moving search index maintenance to an asynchronous background worker. Book changes are recorded durably in [[container|catalog-database]] and processed in scheduled batches, keeping [[service|catalog-api]] fast and resilient while ensuring the search index stays accurate.

## 2. Business Value

- **Responsive catalog management**: [[service|catalog-api]] does not wait for search indexing before confirming book updates to users or administrators.
- **Reliable search accuracy**: Durable queuing and revision checks guarantee that search entries reflect the latest approved book details and deleted books are cleanly removed.
- **Resilience to external outages**: Temporary slowdowns or outages in the embedding provider or search store do not break catalog writes; pending updates remain safely queued for the next run.
- **Controlled processing cost**: Processing updates in bounded periodic batches prevents sudden bursts of book edits from overwhelming downstream AI and search services.

## 3. How It Works

Every five minutes, a scheduled batch signal ([[event|ProcessVectorBatchIntegrationEvent]]) triggers Catalog Ingestion to synchronize recent book changes into [[container|catalog-vector]]:

1. **Ensure single active runner**: The worker requests an exclusive processing lock so only one batch processor updates the search index at a time. If another instance already holds the lock, this run exits without doing duplicate work.
2. **Collect a bounded batch**: It reads up to 200 pending book updates from [[container|catalog-database]], ordered from oldest update to newest.
3. **Assemble searchable content**: For each active [[entity|book]], it builds searchable text from the book's title, description, [[entity|author]] names, [[entity|category]], and [[entity|publisher]].
4. **Update or remove search entries**: For active books, it generates semantic search vectors via the configured embedding service and updates the matching record in [[container|catalog-vector]]. When a queued book is missing or has been deleted, it removes the corresponding entry from [[container|catalog-vector]].
5. **Confirm completed items safely**: Each queued item is cleared only if its recorded revision still matches what the worker originally read. If a newer edit happened while the batch was running, that item stays queued so the newer change is picked up in a later batch.
6. **Release the lock**: Once finished—even if an error occurs—the worker releases the exclusive lock. If vector generation or search-store updates fail, affected items remain unconfirmed in the durable queue for automatic retry on a future run.

## 4. Trade-offs & Lessons Learned

- **Eventual search consistency vs. write speed**: Decoupling search indexing from [[service|catalog-api]] keeps book writes fast and reliable, at the trade-off of a short delay (governed by the five-minute schedule) before new or edited books appear in semantic search.
- **Single-batch exclusivity**: Using an exclusive lock and a fixed 200-record batch size prevents concurrent workers from overwriting each other out of order and keeps external embedding usage predictable, though very large bulk imports take multiple cycles to drain.
- **Coalescing durable queue**: Because the queue in [[container|catalog-database]] combines multiple edits to the same book and checks revisions before clearing work, rapid consecutive edits only need to be indexed once without risking lost updates.
- **Monitoring for silent lag**: If the scheduler stops triggering, credentials expire, or the database, embedding service, or vector store becomes unreachable, catalog writes continue normally while the pending queue grows—making queue depth and item age essential operational health metrics.

## 5. Technical Reference

### Trigger and event intake

- **Runtime**: Internal C# Azure Functions worker.
- **Trigger**: Kafka trigger (`ProcessVectorBatch`) bound to topic `scheduler.process-vector-batch` with consumer group `catalog-ingestion`.
- **Schedule**: The Scheduler service publishes [[event|ProcessVectorBatchIntegrationEvent]] to `scheduler.process-vector-batch` every five minutes via `ProcessVectorBatchJob`.
- **Batch sizing**: Each Kafka trigger invocation processes one bounded batch of up to 200 pending updates; the batch size is controlled by the worker rather than the trigger payload.

### Processing behavior

1. Acquire a PostgreSQL advisory lock so only one vector batch processor runs at a time.
2. Read up to 200 pending records ordered by update time and book ID.
3. Build searchable text from each active [[entity|book]]'s title, description, [[entity|author]] names, [[entity|category]], and [[entity|publisher]].
4. Generate embeddings for active books and upsert their content and vector into the `data-bookworm-snippets` collection in Qdrant ([[container|catalog-vector]]).
5. Delete the Qdrant record when the queued book is missing or soft-deleted.
6. Acknowledge each queue item only if its revision still matches the revision that was read, leaving newer concurrent changes queued for a subsequent batch.
7. Release the advisory lock, including when processing fails.

If another worker already holds the lock, the processor does no work during that invocation. If embedding generation or a Qdrant operation fails, the exception is propagated and affected queue items are not acknowledged, leaving pending work available for a later invocation.

### Data dependencies

- Reads book records, relationships, and pending update revisions from [[container|catalog-database]].
- Deletes acknowledged pending updates from [[container|catalog-database]] after successful index operations.
- Writes searchable records to [[container|catalog-vector]].
- Uses the configured embedding service to generate vectors (managed via application configuration).

### Operations

- Monitor the age and count of `pending_vector_updates` in [[container|catalog-database]] alongside Scheduler job outcomes and Qdrant health to detect ingestion lag.
- A growing queue can indicate that the scheduled job is not invoking this worker, credentials are rejected, or the database, embedding service, or vector store is unavailable.
- The queue is durable and coalesces changes by book ID. See [[container|catalog-database]] for triggers and queue semantics.
