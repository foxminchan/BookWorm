## Purpose & Ownership Boundary

Catalog Blob Storage (`catalog-blob`) is the authoritative object store owned exclusively by [[service|catalog-api]] in the Catalog bounded context for binary book cover images. Object storage keeps large binary payloads out of [[container|catalog-database]], which stores only permanent blob URNs (`books.image`) while [[service|catalog-api]] mints short-lived, read-only Shared Access Signature (SAS) URLs on demand.

## Logical Data Layout & Key Patterns

| Container / Key Pattern                         | Stored Data                                                        | TTL / Eviction                                             | Invalidation / Update Trigger                                                             |
| :---------------------------------------------- | :----------------------------------------------------------------- | :--------------------------------------------------------- | :---------------------------------------------------------------------------------------- |
| `catalog-blob` / `{uuidv7}-{safeName}{safeExt}` | Binary book cover images (`image/jpeg`, `image/png`, `image/webp`) | `10y` retention; `1 hour` default read-only SAS URL expiry | Explicit deletion (including snapshots) on image replacement or [[entity\|book]] removal. |
| URN reference (`books.image` in `catalogdb`)    | `urn:{account}:catalog-blob:{blobName}`                            | Permanent until book/image is updated or deleted           | Validated on every read/delete to match target storage account and container.             |

## Consistency, Isolation & Security Guardrails

- **No public blob access:** Public container/blob access is disabled (`AllowBlobPublicAccess = false`); access requires Managed Identity RBAC (`StorageBlobDataContributor`) for [[service|catalog-api]] and HTTPS-only, read-only SAS URLs (User Delegation Keys in Azure, account-key SAS in local Azurite) for browser downloads.
- **Strict URN & overwrite protection:** Uploads enforce non-empty allowed image MIME types, sanitize filenames (`[a-zA-Z0-9._-]`, max 100 chars), and guard against accidental overwrites via `If-None-Match: *`. URN validation rejects path traversal (`/`, `\`, `..`) or cross-account mismatches.
- **No cross-store distributed transaction:** Because PostgreSQL and Blob Storage do not share a two-phase commit, a failed database transaction after upload can leave an unreferenced blob that requires periodic reconciliation against `books.image`.

:::warning
**Shared Storage Account Isolation:** `catalog-blob` shares the Azure Storage Account with [[container|chat-session-blob]] (`chatting-blob`) and Azure Functions host storage. Services must use container-scoped references—[[service|catalog-api]] must never access `chatting-blob`, and external services must never read `catalog-blob` directly or persist expiring SAS URLs.
:::

## Operational & Resilience Notes

<AccordionGroup>
	<Accordion title="Hosting, redundancy, and failure recovery">
		- **Local vs. Cloud:** Local development uses a persistent Azurite emulator with Azure Storage
		Explorer; cloud environments use Azure Storage Account with TLS 1.2 minimum (`StandardLrs` in
		Dev, `StandardZrs` in Staging, `StandardGzrs` in Production). - **Expired SAS (`403`):**
		Re-fetch the book from [[service|catalog-api]] to mint a fresh 1-hour SAS URL. -
		**Cross-environment URN mismatch:** Never copy `books.image` URNs across environments without
		migrating the corresponding blobs and updating the storage account segment.
	</Accordion>
</AccordionGroup>
