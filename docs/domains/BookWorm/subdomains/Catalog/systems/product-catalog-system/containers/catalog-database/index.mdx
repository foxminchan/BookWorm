## 1. Context & Problem

The BookWorm Catalog needs an authoritative, durable system of record to manage core product entities—books, authors, categories, publishers, and their relationships—while enforcing business rules around uniqueness and deletions. At the same time, changes to any of these records must reliably trigger updates to the catalog search index without slowing down user requests or dropping updates during bursts of edits.

## 2. Business Value

- **Single source of truth:** Guarantees consistent, reliable storage for pricing, titles, descriptions, lifecycle status, and entity relationships.
- **Built-in data integrity:** Enforces unique category and publisher names and prevents accidental loss of books or broken author links during deletions.
- **Reliable search synchronization:** Automatically queues search-index updates whenever catalog data changes, coalescing repeated edits into a single pending job to avoid redundant background work.

## 3. How It Works

[[service|catalog-api]] serves as the primary reader and writer for day-to-day catalog operations, managing [[entity|book]]s, [[entity|author]]s, [[entity|category]]s, [[entity|publisher]]s, and [[entity|book-author]] relationships. Meanwhile, [[service|catalog-ingestion]] reads from a durable pending-update queue in this database to refresh search representations asynchronously.

### Stored information and integrity rules

- **Books:** Stores title, description, pricing, lifecycle status, deletion state, timestamps, a permanent media reference pointing to [[container|catalog-blob]], and a derived rating summary updated from [[domain|reviews]] [[entity|feedback]] notifications.
- **Authors, categories, and publishers:** Stores supporting catalog entities, enforcing unique names for categories and publishers and many-to-many links between books and authors.
- **Safe deletion behavior:** Deleting a category or publisher preserves affected books by clearing only that association. Deleting a book automatically removes its links to authors, while an author cannot be deleted as long as they remain linked to any book.
- **Automatic search queueing:** Whenever a book, book-author link, author, category, or publisher changes, the database automatically queues the affected books for search re-indexing. If a book is modified multiple times before background ingestion runs, the existing pending work item is updated in place rather than creating duplicate jobs.

## 4. Trade-offs & Lessons Learned

- **Trigger-driven queueing:** Relying on database triggers ensures no catalog or relationship edit is ever missed by the search pipeline, though it requires keeping trigger behavior aligned with schema updates.
- **Eventual search and rating freshness:** Search-index updates and review rating summaries are maintained asynchronously. Operators should monitor the count and age of pending search-update items to detect ingestion lag early.
- **Operational discipline:** Because this database is the authoritative system of record, catalog rows must not be edited directly outside approved operational corrections. Environment upgrades must run formal schema migrations rather than replaying a state-snapshot schema file.

- **Tables and integrity details:**
  - `books` ([[entity|book]]): Primary key and IDs across tables use PostgreSQL 18 `uuidv7()` defaults; `created_at` and `last_modified_at` use database-generated timestamps. `books.status` is stored as a `smallint` with application-owned status mapping. `books.image` stores a Blob Storage URN (managed by `catalog-api` in `catalog-blob`), not image bytes. `average_rating` and `total_reviews` store a denormalized projection maintained from `reviews` `feedback` integration messages.
  - `authors` ([[entity|author]]), `categories` ([[entity|category]], unique name), `publishers` ([[entity|publisher]], unique name), and `book_authors` ([[entity|book-author]]): Deleting a `category` or `publisher` sets the corresponding foreign key on `books` to `NULL`; deleting a `book` cascades to `book_authors`; deleting an `author` is restricted while `book_authors` rows exist.
  - `pending_vector_updates`: Coalescing work queue keyed by `book_id`. Repeated changes before ingestion runs update the existing row with a new `revision` and timestamp instead of inserting duplicates.
- **Triggers and ingestion coordination:**
  - `books_vector_update`, `book_authors_vector_update`, `authors_vector_update`, `categories_vector_update`, and `publishers_vector_update` enqueue affected books automatically. The initial schema load also queues existing books so the first ingestion batch builds their vector representations.
  - `catalog-ingestion` consumes `pending_vector_updates` asynchronously.
- **Operational guidance:** Monitor row age and count in `pending_vector_updates` for ingestion lag; apply EF Core migrations separately when upgrading existing environments rather than replaying `schema.sql`.
