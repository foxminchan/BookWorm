Catalog database (`catalogdb`) is the authoritative PostgreSQL system of record for the Catalog bounded context. [[service|catalog-api]] owns all domain writes and queries, while [[service|catalog-ingestion]] reads the trigger-maintained `pending_vector_updates` queue to synchronize search embeddings in [[container|catalog-vector]].

## Architecture and service boundaries

Catalog API handles all transactional writes to product tables and persists outbound integration messages atomically via the Wolverine PostgreSQL outbox in the `wolverine` schema. Database triggers enqueue changed books into `pending_vector_updates`, which Catalog Ingestion drains asynchronously in batches.

## Tables and integrity rules

All relational identifiers follow `snake_case`. Primary keys default to PostgreSQL 18 `uuidv7()`, and audit timestamps (`created_at`, `last_modified_at`) are database-generated.

| Table / schema           | Purpose                                                                                                                                                                                                                                    | Constraints and integrity rules                                                                                                  |
| :----------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| `books`                  | Authoritative book records: title (`name`), description, pricing, `status` (`smallint`), soft-delete flag (`is_deleted`), `image` (Blob URN pointing to `catalog-blob`), and derived rating projection (`average_rating`, `total_reviews`) | `books.image` stores a URN, never raw bytes or SAS URLs; rating projection is updated asynchronously from Reviews Kafka events   |
| `authors`                | Author records linked to books                                                                                                                                                                                                             | Deletion is restricted while any row exists in `book_authors`                                                                    |
| `categories`             | Product category taxonomy                                                                                                                                                                                                                  | Unique constraint on category `name`; deleting a category sets `books.category_id` to `NULL` (preserves books)                   |
| `publishers`             | Publisher records                                                                                                                                                                                                                          | Unique constraint on publisher `name`; deleting a publisher sets `books.publisher_id` to `NULL` (preserves books)                |
| `book_authors`           | Many-to-many join between `books` and `authors`                                                                                                                                                                                            | Deleting a book cascades to `book_authors`                                                                                       |
| `pending_vector_updates` | Coalescing queue keyed by `book_id` with a `revision` UUID and `updated_at` timestamp                                                                                                                                                      | Repeated edits before ingestion update the existing row's `revision` and timestamp in place rather than inserting duplicate rows |
| `wolverine` schema       | Wolverine transactional outbox and inbox message envelopes                                                                                                                                                                                 | Shares transactional boundary with EF Core via `UsePostgresOutbox`; partitions Kafka events by `BookId` and `FeedbackId`         |

## Triggers and vector-indexing coordination

Five PostgreSQL triggers automatically enqueue affected books into `pending_vector_updates` whenever catalog data changes:

- `books_vector_update` — Enqueues inserts, updates, or soft-deletes on `books`.
- `book_authors_vector_update` — Enqueues books whose author links change.
- `authors_vector_update` — Enqueues all books linked to a renamed author.
- `categories_vector_update` — Enqueues all books linked to a modified category.
- `publishers_vector_update` — Enqueues all books linked to a modified publisher.

During batch processing, `VectorBatchProcessor` (`BookWorm.Catalog.Ingestion`):

1. Acquires PostgreSQL session advisory lock `740031001` (`pg_try_advisory_lock`) so only one ingestion worker runs a batch at a time.
2. Reads up to `200` oldest rows ordered by `updated_at, book_id`.
3. Acknowledges processed rows using `DELETE FROM pending_vector_updates ... WHERE p.book_id = u.book_id AND p.revision = u.revision`, ensuring concurrent mid-batch edits survive for the next pass.

## Operational rules

- **Run EF Core migrations for upgrades:** Upgrade existing environments using EF Core migrations (`src/Services/Catalog/BookWorm.Catalog/Infrastructure/Migrations/`), never by replaying a static SQL state snapshot.
- **Monitor ingestion lag:** Track row count and oldest `updated_at` in `pending_vector_updates` to detect stalled `catalog-ingestion` runs or Scheduler delays.
- **Avoid direct row edits:** Perform catalog changes through Catalog API so cache eviction events (`book:{id}`), blob URN checks, and vector triggers remain consistent.
- **Eventual rating summary consistency:** `average_rating` and `total_reviews` on `books` are derived projections updated asynchronously from `FeedbackCreatedIntegrationEvent` and `FeedbackDeletedIntegrationEvent`. [[container|rating-database]] remains the sole authority for individual feedback records.
