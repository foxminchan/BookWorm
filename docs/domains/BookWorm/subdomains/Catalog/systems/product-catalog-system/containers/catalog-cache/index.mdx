Catalog cache is the non-authoritative, read-through caching layer used by [[service|catalog-api]] in front of [[container|catalog-database]]. It uses FusionCache (`2.10.0`) with an in-process L1 memory tier, a Redis L2 distributed tier, and a Redis backplane to accelerate book detail reads and dashboard summaries across service replicas.

## Overview

| Property               | Value                                                                                                                |
| :--------------------- | :------------------------------------------------------------------------------------------------------------------- |
| **Owner**              | Catalog bounded context — [[service\|catalog-api]] (`catalog`)                                                       |
| **Aspire resource ID** | `redis` (shared Azure Managed Redis resource)                                                                        |
| **Source**             | `src/BuildingBlocks/BookWorm.Chassis/Caching/`, `src/Services/Catalog/BookWorm.Catalog/Features/Books/CachedBook.cs` |
| **Engine**             | FusionCache (`2.10.0`) + Redis (local container + RedisInsight in development; Azure Managed Redis in cloud)         |
| **Authoritative**      | No (`authoritative: false`, `readWrite`)                                                                             |
| **Classification**     | `internal`                                                                                                           |
| **Retention**          | Transient (all entries are disposable and repopulated from `catalogdb`)                                              |

## Architecture and caching tiers

Catalog API registers FusionCache through `BookWorm.Chassis`, pairing local in-process memory (L1) with the shared Redis cluster (L2), a Redis backplane for cross-replica eviction notifications, and Redis distributed locking to prevent cache stampedes.

- **Disposable by design:** Never treat cached entries as the system of record for books, authors, categories, or publishers. Cache misses repopulate from `catalogdb`.
- **Resilience defaults (`BookWorm.Chassis`):** FusionCache uses `System.Text.Json` serialization, a 2-hour fail-safe window, soft/hard factory timeouts, and Redis distributed locks for cache-miss coordination.
- **Shared Redis resource:** Catalog API shares the `redis` resource with Basket API, Ordering API, Rating API, and Notification. Catalog API also uses Redis for its 24-hour integration event idempotency guard (`IIntegrationEventIdempotencyGuard`).

## Cached entries and invalidation

| Cached data                          | Logical key            | Authoritative source              | Expiration                   | Invalidation strategy                                                               |
| :----------------------------------- | :--------------------- | :-------------------------------- | :--------------------------- | :---------------------------------------------------------------------------------- |
| **Book lookup by ID** (`CachedBook`) | `book:{id}`            | `catalogdb` (`books` + relations) | `Caching:Expiration` default | Event-driven eviction on book mutations; propagated to replicas via Redis backplane |
| **Catalog dashboard summary**        | `catalog:dashboard:v1` | `catalogdb` aggregate query       | `15 seconds`                 | Time-based TTL expiration (no event-driven eviction)                                |

The shared `Caching:Expiration` default is 30 minutes. Catalog list queries cache `CachedBookPage` values as the resolved page payload under their own feature cache key.

### Cached book payload scope

`CachedBook` (`src/Services/Catalog/BookWorm.Catalog/Features/Books/CachedBook.cs`) caches the pre-DTO book projection before SAS URL resolution:

- **Fields included:** `Id`, `Name`, `Description`, `Image` (permanent blob URN, not an expiring SAS URL), `Price`, `PriceSale`, `Status`, `Category`, `Publisher`, `Authors`, `AverageRating`, `TotalReviews`, and `Version` (`RowVersion`).
- **Why SAS URLs are excluded:** Caching the permanent URN ensures each API read resolves a valid, non-expired SAS URL from [[container|catalog-blob]].

## Operational notes

- **Dashboard staleness window:** Dashboard totals (`catalog:dashboard:v1`) can lag live catalog writes by up to `15 seconds` because they expire by TTL rather than domain-event eviction.
- **Observability:** Inspect FusionCache OpenTelemetry metrics and traces (`ZiggyCreatures.Caching.Fusion.OpenTelemetry`) alongside Redis connectivity and latency when diagnosing slow Catalog reads.
- **Flush blast radius:** Clearing the shared Redis instance is safe for Catalog durability, but it simultaneously clears active customer baskets in [[container|basket-database]], locks/idempotency markers in [[container|order-cache]], and cached summaries in [[container|rating-cache]].
