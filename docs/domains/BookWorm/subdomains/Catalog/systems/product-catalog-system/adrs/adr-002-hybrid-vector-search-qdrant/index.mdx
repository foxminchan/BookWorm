## 1. Context & Problem

Customers look for [[entity|book]]s in two distinct ways: by meaning or theme (concepts described in a synopsis) and by exact words (titles or [[entity|author]] names). Traditional database text matching alone struggles to understand semantic intent when shoppers do not use the exact words stored in a book's description.

At the same time, search results must reflect current, authoritative values for filters, sorting, pricing, and availability. Storing a complete copy of every book inside a search engine would turn the search index into a second, potentially stale catalog.

## 2. Business Value

- **Higher discovery relevance:** Shoppers find relevant books whether they search by broad concept, topic, or exact title and author names.
- **Always-accurate product details:** Prices, availability, sorting, and structured filters always reflect the live authoritative catalog rather than a stale search copy.
- **Clean separation of concerns:** Search relevance tuning and indexing remain independent of the core product data contract, keeping stale search text clearly separated from current product truth.

## 3. How It Works

Catalog separates **finding candidate matches** from **delivering authoritative product data**:

1. **Maintain a focused search index:** [[container|catalog-vector]] holds one search entry for each active [[entity|book]]. Each entry contains searchable text built from the book's title, description, [[entity|author]]s, [[entity|category]], and [[entity|publisher]], paired with a semantic meaning representation. Prices, cover images, and rating summaries are intentionally left out, and retired books are removed.
2. **Match by meaning and keywords together:** When a customer runs a text search, [[service|catalog-api]] converts the search query into a semantic representation and performs a hybrid search in [[container|catalog-vector]] that combines conceptual similarity with exact keyword matching.
3. **Return candidate identifiers, not final records:** The search engine returns only a list of matching book identifiers—it never serves as the final product response.
4. **Hydrate and filter from the authoritative database:** [[service|catalog-api]] fetches the live book records for those candidates from [[container|catalog-database]], applying the customer's requested filters, sort order, and page bounds before returning the response.

Browsing and filtered listing requests that do not include a search term bypass the search index entirely and query [[container|catalog-database]] directly.

## 4. Trade-offs & Lessons Learned

### Alternatives considered

- **Database-only text search:** Simpler to operate and immediately consistent with edits, but performs poorly on semantic intent when queries do not match exact phrasing in descriptions.
- **Semantic vector-only search:** Strong at conceptual matching, but weaker on exact title and author lookups. Hybrid search combines semantic recall with exact-term precision.
- **Store the full book record in the search engine:** Eliminates the second database lookup, but duplicates canonical state and makes stale prices or partial updates difficult to isolate from authoritative data.

### Trade-offs & operational considerations

- **Asynchronous index freshness:** Because [[container|catalog-vector]] is updated in the background (see [[adr|adr-003-database-queue-for-vector-indexing]]), newly added or edited books can take time to appear in text-search results, even though browsing lists reflect changes immediately.
- **Additional runtime dependencies for text search:** Text search relies on query embedding generation and search-store availability; non-search browsing remains purely database-backed (see [[adr|adr-001-postgresql-system-of-record]]).
- **Reindexing cost on model or field changes:** Adding new searchable fields or upgrading the underlying embedding model requires coordinated updates and a full catalog rebuild, which consumes extra ingestion and embedding capacity.

## 5. Technical Reference

- **Search container:** [[container|catalog-vector]] (Qdrant), holding one record per active [[entity|book]] keyed by book UUID.
- **Indexed payload & vector contract:**
  - Searchable text built from: `title`, `description`, `authors`, `category`, and `publisher`.
  - Excluded from index: prices, images, rating summaries, and inactive/soft-deleted books.
  - Vector format: `1,536-dimension` embedding using **cosine similarity** (part of the index contract; changing the embedding model requires rebuilding the index so stored book vectors and query vectors stay compatible).
- **Query execution path ([[service|catalog-api]]):**
  1. Generate a query embedding for the search term.
  2. Run hybrid vector + keyword search in Qdrant to retrieve candidate book UUIDs.
  3. Query [[container|catalog-database]] (PostgreSQL) for the candidate IDs, applying SQL filters, sorting, and paging against canonical records.
- **Non-search paths:** Browse and filtered-list requests without a text-search term remain PostgreSQL-backed only.
- **Indexing pipeline & source of truth:** Maintained asynchronously via [[adr|adr-003-database-queue-for-vector-indexing]], with canonical authority governed by [[adr|adr-001-postgresql-system-of-record]]. Changing searchable fields requires coordinated updates to text construction, database queue triggers, and reindexing.
