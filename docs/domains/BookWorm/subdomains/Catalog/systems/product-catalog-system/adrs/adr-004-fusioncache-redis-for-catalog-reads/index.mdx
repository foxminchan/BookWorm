## 1. Context & Problem

Individual [[entity|book]] detail pages and the administrative dashboard summary are viewed far more frequently than they change. Sending every repeated lookup directly to the primary database adds avoidable load and slows down response times.

However, caching introduces a secondary copy of data that can briefly lag behind edits or become unavailable. Catalog therefore needed a targeted caching approach that speeds up the hottest reads while keeping the database as the undisputed source of truth.

## 2. Business Value

- **Faster customer and admin experience:** High-traffic book detail lookups and dashboard summaries respond quickly, improving browsing and operational responsiveness.
- **Protected database capacity:** Offloads repetitive read traffic from the primary database, keeping write operations and search resolution fast under heavy load.
- **Zero risk to data ownership:** Because cached entries are strictly disposable copies, cache loss or downtime affects speed temporarily without ever risking lost or corrupted catalog records.

## 3. How It Works

[[service|catalog-api]] uses a two-layer caching strategy designed strictly as a disposable performance helper:

- **Fast local + shared layers:** Each service instance keeps a small in-memory cache for instant repeat reads, backed by a shared distributed cache in [[container|catalog-cache]] across all instances.
- **Selective coverage:** Only two high-volume read paths are cached—individual [[entity|book]] lookups by identifier, and the administrative dashboard summary. Other queries go directly to the database.
- **Clear refresh rules:** Whenever a book is updated, its individual cached entry is immediately cleared so the next lookup reloads fresh details from the database. The dashboard summary refreshes automatically after a short 15-second expiration window.
- **Authoritative checkout safety:** Neither cache layer is ever treated as a source of truth; purchase-time price and availability decisions must rely on current authoritative data rather than cached copies.

## 4. Trade-offs & Lessons Learned

### Alternatives considered

- **No caching:** Simplest to operate and always strictly up to date, but leaves avoidable database pressure and higher latency on frequent book and dashboard reads.
- **Cache everything aggressively:** Maximizes database offload, but greatly increases the risk and business impact of stale prices, outdated metadata, and complex invalidation bugs.
- **Shared distributed cache only (no local memory layer):** Reduces caching layers, but forces every cache hit to make a network round trip instead of serving repeat reads directly from instance memory.

### Trade-offs & operational considerations

- **Brief staleness window:** Cached responses can briefly reflect prior values until invalidation or expiration takes effect, reinforcing why critical purchase checks must use authoritative data (see [[adr|adr-001-postgresql-system-of-record]]).
- **Additional operational concerns:** A two-layer cache introduces invalidation, expiration, data-shape versioning, and observability requirements. Changing the structure of a cached summary requires introducing a new versioned key so old and new data formats never collide.
- **Monitoring dependency:** Operations teams must monitor cache hit/miss telemetry alongside distributed-cache connectivity and latency to tell whether read slowdowns stem from the database or the cache layer.

## 5. Technical Reference

- **Caching implementation (`[[service|catalog-api]]`):** Registers **FusionCache** with an **L1 in-process memory cache** backed by a **Redis distributed cache** (`[[container|catalog-cache]]`), using JSON serialization and default expiration from `Caching:Expiration` (overridable per entry).
- **Selected cached entries:**

| Data                          | Key                    | Source           | Expiration           |
| ----------------------------- | ---------------------- | ---------------- | -------------------- |
| [[entity\|book]] lookup by ID | `book:{id}`            | Catalog Database | `Caching:Expiration` |
| Dashboard summary             | `catalog:dashboard:v1` | Catalog Database | 15 seconds           |

- **Invalidation & key versioning:**
  - Book mutations invalidate `book:{id}` so the next lookup reloads from PostgreSQL (`[[adr|adr-001-postgresql-system-of-record]]`).
  - `catalog:dashboard:v1` relies on its 15-second TTL.
  - Changes to cached payload shapes must increment the key version (for example, `catalog:dashboard:v2`) to avoid deserializing incompatible cached JSON.
- **Fallback & observability:**
  - Cache entries are disposable; cache misses or Redis outages fall back to the PostgreSQL-backed query path.
  - Monitor FusionCache metrics and traces, Redis connectivity, and Redis latency alongside PostgreSQL metrics.
