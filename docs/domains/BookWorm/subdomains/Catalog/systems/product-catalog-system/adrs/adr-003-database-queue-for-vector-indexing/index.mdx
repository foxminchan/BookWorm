## 1. Context & Problem

Generating AI search embeddings is relatively slow and relies on external services. Performing embedding generation inside [[service|catalog-api]] while an administrator saves a product would add noticeable delay to every catalog editâ€”and worse, an outage in the embedding model or search store would cause product updates to fail.

In addition, a [[entity|book]]'s searchable details do not change only when the book record itself is edited; they also change when an [[entity|author]], [[entity|category]], [[entity|publisher]], or `book_authors` link is updated. Relying on application code to remember every indirect path risks silent search drift. Catalog needed a durable handoff from committed database changes to the search projection without treating every intermediate edit as a separate event to replay.

## 2. Business Value

- **Fast, resilient catalog administration:** Product saves complete immediately and remain available even when AI embedding or search services are slow or degraded.
- **No missed indirect updates:** Database-level change capture automatically queues affected books whether an edit touches a book directly or updates an author, category, or publisher.
- **Lower cost on rapid edits:** Multiple edits to the same book before processing starts are collapsed into one pending refresh of the latest state.
- **Protection against race conditions:** Concurrent edits made while a search batch is already running are automatically preserved for the next cycle rather than being overwritten or discarded.

## 3. How It Works

1. **Capture pending work inside the save transaction:** Whenever changes are saved to [[entity|book]]s, [[entity|author]]s, [[entity|category]]s, [[entity|publisher]]s, or `book_authors` links in [[container|catalog-database]], automatic database rules record each affected book in a pending-work table as part of the exact same save.
2. **Coalesce repeated edits:** The queue keeps one pending entry per book. If a book changes multiple times before indexing runs, its existing waiting entry is updated with a fresh version marker so the worker reads only the latest product state rather than replaying every draft.
3. **Process bounded batches on a schedule:** Every five minutes, [[service|catalog-ingestion]] claims an exclusive turn so only one batch runs at a time, reads up to 200 waiting books, prepares searchable text and embeddings, and updates or removes the corresponding entries in [[container|catalog-vector]].
4. **Clear only matching versions:** After every search update in the batch succeeds, the worker removes each waiting entryâ€”but only if its version marker still matches what was read at the start of the batch. If a newer edit arrived mid-batch, that entry stays queued for the next scheduled run.

## 4. Trade-offs & Lessons Learned

### Alternatives considered

- **Update the search index synchronously inside Catalog API:** Keeps search fresher, but puts embedding latency directly on the user request path and turns a search outage into a catalog-write outage.
- **Use an external message broker for indexing:** Offers strong decoupling and fan-out, but adds another infrastructure dependency and makes it harder to guarantee that a committed product save and its queued indexing message stay atomic.
- **Trigger indexing directly from application code:** Straightforward for a single write endpoint, but too easy to forget across indirect updates to authors, categories, publishers, or book-author links.

### Trade-offs & operational considerations

- **Eventual consistency without a strict freshness SLA:** The five-minute cadence is an execution schedule, not a guarantee that search updates finish within five minutes. Large backlogs drain across multiple 200-item batches because only one batch runs at a time.
- **At-least-once retries instead of distributed transactions:** Because the database and search store do not share an all-or-nothing transaction, failures can leave partial search updates; stable book identifiers make retrying on the next cycle safe.
- **Database load and monitoring:** Trigger writes and batch reads add load to [[container|catalog-database]]. Operations teams must monitor pending queue size, oldest pending age, ingestion outcomes, and search-store health.

## 5. Technical Reference

- **Queue mechanism ([[container|catalog-database]]):** PostgreSQL triggers on [[entity|book]], [[entity|author]], [[entity|category]], [[entity|publisher]], and `book_authors` tables insert or update rows in the pending-update table keyed by book ID with a revision token, sharing the PostgreSQL transaction boundary (see [[adr|adr-001-postgresql-system-of-record]]).
- **Worker ([[service|catalog-ingestion]]):** Azure Functions worker invoked on a five-minute Scheduler cadence.
- **Concurrency control & batching:**
  - PostgreSQL advisory lock ensures only one batch processor executes at a time.
  - Reads a bounded batch of up to **200** pending rows per invocation, reading current book state from PostgreSQL and writing to [[container|catalog-vector]] (Qdrant; see [[adr|adr-002-hybrid-vector-search-qdrant]]).
- **Acknowledgement semantics:**
  - Acknowledgements run only after all vector upserts and deletes in the batch succeed.
  - Each pending row is deleted using both its **book ID** and the **revision** read at batch start, preserving any newer revision enqueued while the batch was in flight.
  - Repeated vector upserts/deletes on retry are idempotent by stable book UUID.
