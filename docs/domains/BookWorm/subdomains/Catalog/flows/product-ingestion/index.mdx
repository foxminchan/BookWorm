BookWorm decouples catalog edits from semantic search indexing so **Catalog API** writes complete fast without waiting on AI embedding generation or Qdrant writes. PostgreSQL triggers atomically coalesce affected book IDs into `pending_vector_updates` inside `catalogdb`, and **Scheduler** publishes `ProcessVectorBatchIntegrationEvent` over Kafka every five minutes to trigger the **Catalog Ingestion** Azure Function (`ProcessVectorBatchFunction`). The worker acquires a PostgreSQL advisory lock, refreshes or deletes up to 200 Qdrant vectors per batch using Microsoft Foundry embeddings, and acknowledges only rows whose revision token did not change during processing.

## Context and motivation

Updating semantic search requires generating dense vectors through Microsoft Foundry (`Cohere.EmbedV40`) and writing them to Qdrant (`vectordb`). Running those calls inside HTTP write handlers on **Catalog API** would add network latency to every administrator edit and cause AI or vector-store outages to block catalog saves.

BookWorm separates catalog writes from vector indexing across two services:

- **Catalog API (`catalog`) and Catalog Ingestion (`catalog-ingestion`):** Share PostgreSQL (`catalogdb`) for authoritative catalog records and the `pending_vector_updates` queue. **Catalog Ingestion** is an internal Azure Functions worker (`BookWorm.Catalog.Ingestion`) with **no HTTP or gRPC API**.
- **Scheduler (`scheduler`):** Runs Quartz.NET (`ProcessVectorBatchJob`) backed by PostgreSQL (`schedulerdb`) and Wolverine's outbox to emit periodic Kafka trigger events on unprefixed topic `scheduler.process-vector-batch`.

This flow covers creates, updates, and soft deletes on books, plus updates and deletes on related authors, categories, publishers, and `book_authors` links. Cover image storage (`catalog-blob`) and live customer search queries are outside this flow's scope.

## How it works

Catalog writes and background vector refreshes execute on two independent schedules connected by PostgreSQL (`pending_vector_updates`) and Kafka (`scheduler.process-vector-batch`).

This flowchart shows how catalog mutations enqueue revisions in PostgreSQL, how Scheduler triggers Catalog Ingestion over Kafka, and how Catalog Ingestion updates Qdrant with revision-checked acknowledgements.

### Stage 1: Persist catalog changes and coalesce pending work

When an administrator creates, updates, or soft-deletes a book—or modifies an author, category, publisher, or `book_authors` link—**Catalog API** commits the change in PostgreSQL (`catalogdb`). In the same database transaction, PostgreSQL triggers upsert each affected `book_id` into `pending_vector_updates` with a fresh `revision` UUID and `updated_at` timestamp. Repeated edits to the same book before the next batch replace the existing row so only the latest state is indexed.

### Stage 2: Schedule Kafka batch triggers

Every five minutes in UTC (`0 0/5 * * * ?`, misfire policy `FireOnceNow`, concurrent execution disallowed), **Scheduler** runs `ProcessVectorBatchJob` and publishes `ProcessVectorBatchIntegrationEvent` (CloudEvents JSON) through Wolverine's PostgreSQL outbox to the unprefixed Kafka topic `scheduler.process-vector-batch` (`AppendPrefix = false`).

### Stage 3: Acquire advisory lock and read a bounded batch

`ProcessVectorBatchFunction` (`[KafkaTrigger]`, consumer group `catalog-ingestion`) deserializes the CloudEvents message and calls `VectorBatchProcessor.ProcessAsync`:

1. **Exclusive lock:** Calls `SELECT pg_try_advisory_lock(740031001)` so at most one worker processes the queue at a time. If the lock is busy or no rows are waiting, the processor returns `0` cleanly without modifying Qdrant. The lock is always released in `finally` via `pg_advisory_unlock(740031001)`.
2. **Bounded read:** Reads up to `200` rows from `pending_vector_updates` ordered by `updated_at, book_id`, joining `books`, `book_authors`, `authors`, `categories`, and `publishers`. Active books produce formatted searchable text (`Title`, `Description`, comma-separated `Authors` ordered by `name, id`, `Category`, `Publisher`—excluding prices, images, and rating summaries). Missing or soft-deleted (`is_deleted = true`) books yield `NULL` content.

### Stage 4: Generate embeddings and update Qdrant

`VectorBatchProcessor.IngestDataAsync` ensures the Qdrant collection exists, then generates embeddings in a single batch call to Microsoft Foundry (`FoundryModel.Cohere.EmbedV40`) for all active books. If the embedding provider returns an incomplete count, the processor throws `InvalidOperationException` before writing to Qdrant. Otherwise, it deletes Qdrant records keyed by `BookId` for every missing or soft-deleted book and batch-upserts `TextSnippet` records (`Id`, `Content`, `Vector`) for all active books.

### Stage 5: Acknowledge only unchanged revisions

Only after all Qdrant deletions and upserts succeed does `VectorBatchProcessor` delete acknowledged rows in one batched SQL statement:

<CodeGroup>

```sql
DELETE FROM pending_vector_updates AS p
USING unnest($1::uuid[], $2::uuid[]) AS u(book_id, revision)
WHERE p.book_id = u.book_id AND p.revision = u.revision;
```

</CodeGroup>

If an administrator edited a book while the batch was running, its trigger replaced `revision` with a newer UUID. The `WHERE` predicate leaves the newer row intact so the next scheduled batch refreshes Qdrant with the latest content.

## Design trade-offs

| Decision                                   | Benefits                                                                                              | Costs and limits                                                                                                              |
| :----------------------------------------- | :---------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------- |
| **PostgreSQL queue + Kafka timer trigger** | Keeps Catalog API writes fast and survives Microsoft Foundry or Qdrant outages without losing updates | Introduces eventual-consistency lag (five-minute cadence plus backlog drain time for queues over 200 books)                   |
| **Coalescing one row per `book_id`**       | Collapses rapid draft edits into a single embedding call, reducing AI cost and Qdrant churn           | `updated_at` reflects the latest edit timestamp rather than when a repeatedly edited book first entered the queue             |
| **PostgreSQL advisory lock (`740031001`)** | Prevents concurrent batches from racing on the same Qdrant book UUIDs                                 | A stuck database session holding the lock causes subsequent runs to return `0` without shrinking the queue                    |
| **Revision-checked batch acknowledgement** | Eliminates distributed transactions across PostgreSQL and Qdrant while never losing concurrent edits  | A failure after Qdrant writes but before acknowledgement causes safe, idempotent vector replays by `BookId` on the next cycle |

## Alternatives considered

- **Synchronous embedding generation inside Catalog API requests:** Rejected because external AI embedding latency and outages would directly degrade or block catalog administration.
- **Authenticated HTTP endpoint (`POST /api/vectors/batch`) called by Scheduler:** Retired in favor of Kafka (`scheduler.process-vector-batch`) and `[KafkaTrigger]` on Azure Functions so Catalog Ingestion exposes zero HTTP surface area and inherits Kafka buffering and CloudEvents observability.
- **Immediate tight-loop retries on embedding failure:** Rejected because retrying immediately during a Microsoft Foundry or Qdrant outage amplifies load; waiting for the next five-minute Quartz trigger bounds retry pressure naturally.
