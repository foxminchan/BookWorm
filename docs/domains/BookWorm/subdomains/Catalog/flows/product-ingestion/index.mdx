## 1. Context & Problem

Product ingestion turns committed Catalog changes into searchable [[entity|book]] text and semantic search representations so customers can discover new, updated, or retired titles.

Updating search indexes requires generating AI embeddings and writing to a separate search store—steps that are relatively slow and depend on external services. If [[service|catalog-api]] waited for search indexing during every administrator edit, saving a book would feel sluggish, and any temporary hiccup in the AI or search service could block catalog updates altogether.

To avoid this coupling, BookWorm separates catalog editing from search indexing across three systems:

- [[system|product-catalog-system]] owns [[service|catalog-api]], [[service|catalog-ingestion]], [[container|catalog-database]], and [[container|catalog-vector]], including queue processing and search projection consistency.
- [[system|scheduler-system]] owns the recurring background schedule (surfaced operationally through [[service|sheduler-dashboard]], though the dashboard itself does not initiate ingestion).
- [[system|identity-provider]] provides the security credentials used to authenticate scheduled ingestion calls.

This flow covers book creation, updates, soft deletion, and changes to related [[entity|author]]s, [[entity|category]]s, [[entity|publisher]]s, and [[entity|book-author]] relationships. Image storage, customer search requests, and initial infrastructure provisioning are outside its scope.

## 2. Business Value

- **Responsive catalog management:** Administrators can create, update, and retire books immediately without waiting for AI embedding generation or search indexing.
- **Resilience and fault isolation:** Temporary slowdowns or outages in the embedding service or search store never prevent catalog saves or lose pending search updates.
- **Complete, automatic search coverage:** Changes to a book's author, category, or publisher automatically trigger a search refresh for every affected book—no manual reindexing steps required.
- **Lower processing cost and noise:** Repeated edits to the same book between scheduled runs are collapsed into a single pending refresh, avoiding wasted work on intermediate drafts.
- **No lost updates during concurrent edits:** If an administrator edits a book while a search batch is already running, the newer edit is automatically preserved for the next cycle.

## 3. How It Works

Product ingestion runs across two independent paths: administrators save product changes through [[service|catalog-api]], while [[system|scheduler-system]] periodically triggers [[service|catalog-ingestion]] to refresh [[container|catalog-vector]]. The API never calls the scheduler or updates the search store directly; pending work simply waits in the database for the next scheduled run.

1. **Save product changes and record pending work:** When an administrator adds, updates, or soft-deletes a book—or updates an [[entity|author]], [[entity|category]], [[entity|publisher]], or [[entity|book-author]] link—[[service|catalog-api]] saves the change in [[container|catalog-database]]. In the exact same save operation, the database records or refreshes a single waiting item for each affected book. Multiple edits to the same book simply overwrite its waiting marker so only the latest version is processed.
2. **Trigger ingestion on a five-minute schedule:** Every five minutes, [[system|scheduler-system]] requests an access credential from [[system|identity-provider]] and sends an authenticated trigger to [[service|catalog-ingestion]] to check for pending work. Only one scheduled run is allowed at a time, and missed runs catch up with a single run rather than replaying every missed interval.
3. **Claim an exclusive turn and read a bounded batch:** [[service|catalog-ingestion]] acquires an exclusive lock so two batches cannot run simultaneously. If the lock is busy or nothing is waiting, the run finishes cleanly without making changes. Otherwise, it reads up to 200 waiting books in order, along with each book's current title, description, authors, category, and publisher.
4. **Refresh or remove search entries:** For active books, the worker builds searchable text (title, description, authors, category, and publisher—excluding prices, images, and rating summaries), generates search embeddings, and updates [[container|catalog-vector]]. If any embedding fails to generate, the whole batch stops before modifying the search store. For missing or soft-deleted books, the worker deletes their entry from [[container|catalog-vector]].
5. **Confirm only unchanged items:** Only after every search update in the batch succeeds does the worker clear the waiting items—and only if each book's waiting marker still matches what was read at the start. If a book was edited again while the batch was running, its newer marker stays in the queue so the next scheduled run picks up the latest details.

## 4. Trade-offs & Lessons Learned

- **Eventual consistency vs. write availability:** [[container|catalog-database]] remains the single source of truth, while [[container|catalog-vector]] is a derived projection that can lag behind catalog edits. A successful product save confirms persistence, not that customer search already reflects the change.
- **Schedule cadence is not a freshness SLA:** Firing every five minutes does not guarantee search updates within five minutes. Large backlogs (beyond the 200-item batch cap), processing duration, lock contention, missed triggers, or downstream outages can extend lag.
- **Coalescing queue vs. full edit history:** Storing one pending entry per book keeps processing lean and avoids indexing superseded drafts, but means queue age measures the latest edit rather than when a frequently edited book first entered the queue.
- **Safe retries instead of distributed transactions:** Because the database and search store do not share an all-or-nothing transaction, a partial failure can leave some search writes applied while keeping the waiting items intact. Using stable book identifiers ensures repeated updates or deletions on the next scheduled cycle are safe.
- **Scheduled recovery over immediate retry loops:** Failures wait for a subsequent scheduled firing rather than retrying immediately in a tight loop, preventing cascading load during external outages.
- **Operational visibility lesson:** A completed run alone does not prove the backlog is clear (an empty queue or busy lock also finishes cleanly), so operations teams must monitor actual pending queue count and oldest pending age—and must never manually delete queue rows to hide a backlog.

### Implementation mechanics

- **Database queue (`pending_vector_updates`):** PostgreSQL triggers on book and book-author inserts/updates/deletes, plus author, category, and publisher updates/deletes (and migration seeding), maintain one row per `book_id` with `revision` and `updated_at` replaced on subsequent changes.
- **Schedule & authentication:** Quartz runs `ProcessVectorBatchJob` with cron expression `0 0/5 * * * ?` (UTC), misfire policy `FireOnceNow`, and concurrent execution disallowed, publishing `ProcessVectorBatchIntegrationEvent` to `scheduler.process-vector-batch` to trigger the Kafka-bound Azure Function in [[service|catalog-ingestion]]. Scheduler obtains an OAuth bearer token from [[service|oauthapi]]; Catalog Ingestion validates the token and requires the `azp` claim to identify Scheduler. The bodyless `POST /api/vectors/batch` request cannot override the batch size.
- **Locking & batching:** Catalog Ingestion acquires PostgreSQL advisory lock `740031001` (released in `finally`) and reads up to **200** rows ordered by `updated_at` and `book_id`, retaining each row's `revision`. Missing or soft-deleted books yield null content.
- **Vector projection (`data-bookworm-snippets`):** Ensures the Qdrant collection exists, generates embeddings for all active books in the batch (an incomplete embedding batch fails processing before vector writes), and builds searchable text from title, description, author names (ordered by name and ID), category name, and publisher name. Active books are upserted by book UUID; missing/soft-deleted books are deleted by UUID.
- **Revision-checked acknowledgement:** After every vector operation succeeds, queue rows are deleted only if both `book_id` and `revision` match, returning `204 No Content`:

<CodeGroup>

```sql title="Acknowledge processed revision"
DELETE FROM pending_vector_updates
WHERE book_id = $1 AND revision = $2;
```

</CodeGroup>

For example, if ingestion reads revision A and an administrator commits another edit creating revision B, the worker may temporarily write A's content to Qdrant; acknowledgement cannot delete B, so a later invocation refreshes the vector with current data.

| Outcome                                          | Queue and index behavior                                                                                                        | Operational interpretation                                                                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Successful batch                                 | Vector operations complete; matching queue revisions are removed. New revisions and rows beyond the batch limit remain pending. | `204` confirms invocation completion, not that the entire backlog is empty.                                                                           |
| Empty queue or busy advisory lock                | No vector operations occur; a busy lock leaves queued work untouched.                                                           | Also returns `204`; this response alone does not prove that any records were indexed.                                                                 |
| Token acquisition fails                          | No ingestion request is made and no batch is processed.                                                                         | Scheduler reports the failed invocation to Quartz; pending work remains queued.                                                                       |
| Authentication rejected                          | No batch is processed.                                                                                                          | `401` indicates missing or invalid credentials; `403` indicates a client other than Scheduler.                                                        |
| Collection, embedding, or vector operation fails | No batch acknowledgements have started. All its queue rows remain; some vector writes may already have succeeded.               | The error propagates; Scheduler logs it and reports a failed Quartz execution (`JobExecutionException`). Pending work is eligible for a later firing. |
| Acknowledgement fails partway through            | Earlier acknowledgements may have completed; remaining rows survive. Vector operations have already succeeded.                  | A later invocation may repeat vector operations for the remaining records.                                                                            |

### Operational checks

When search results are stale or ingestion appears stalled:

1. Check Scheduler's trigger state, next fire time, and `ProcessVectorBatchJob` execution history in [[service|sheduler-dashboard]].
2. For token acquisition failures, `401`, or `403`, verify Identity Provider availability, token validation, and the Scheduler client identity before investigating database or vector processing.
3. Check pending queue count and the oldest `updated_at` in [[container|catalog-database]]. A growing count or age indicates work is not keeping pace with catalog changes.
4. Correlate ingestion errors with PostgreSQL connectivity, advisory-lock contention, embedding-service availability, and Qdrant health.
5. After recovery, verify that pending work drains and the expected book UUIDs are refreshed or removed in [[container|catalog-vector]]. Do not treat a successful HTTP response as proof of an up-to-date index.

The following read-only query summarizes the current queue (an empty queue returns zero and null age/timestamp values; do not manually remove rows to hide a backlog):

<CodeGroup>

```sql title="Pending queue health"
SELECT
    count(*) AS pending_books,
    min(updated_at) AS oldest_pending_update,
    clock_timestamp() - min(updated_at) AS oldest_pending_age
FROM pending_vector_updates;
```

</CodeGroup>
