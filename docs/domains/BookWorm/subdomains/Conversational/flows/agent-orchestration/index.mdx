Chat API orchestrates customer conversations through a composed multi-stage workflow (`chat-workflow`) built on Microsoft Agent Framework and exposed over the AG-UI protocol at `/ag-ui`. The workflow separates input safety screening, fast non-LLM routing, human-in-the-loop disambiguation, specialist agent execution, and final response hygiene so each stage stays independently verifiable. Transactional actions—such as basket edits, checkout, order cancellation, and review submission—remain strictly outside this read-only conversational flow.

## Context and motivation

Customers open the BookWorm chat assistant in **Storefront** (`@bookworm/storefront`) with varied intents: searching the catalog, requesting personalized recommendations, asking for review summaries, or checking store policies. Routing every prompt to a single general-purpose assistant weakens tool isolation, increases prompt-injection exposure, and wastes model tokens on out-of-scope or non-English traffic.

BookWorm addresses this by composing deterministic guardrails and lightweight classification in front of specialized agents:

- **Edge security and privacy:** API Gateway routes `/chatting/{**remainder}` to **Chat API**, which enforces Microsoft Entra ID authentication (`customer` role with `chatting_read` and `chatting_write` scopes) and the `PerUserRateLimit` policy on `/ag-ui`. Presidio (`presidio-analyzer` and `presidio-anonymizer`) redacts PII, and Agent Governance (`Policies/chat-agents.yaml`) enforces tool and prompt policies.
- **Dedicated session storage:** Chat API persists multi-turn AG-UI session state in Azure Blob Storage (`chatting-blob`, prefix `ag-ui/`). Chat API uses no PostgreSQL database, Redis cache, or Kafka broker.
- **Cross-service read boundaries:** Specialist agents fetch live book facts from **MCP Tools** over Streamable HTTP (`/mcp`) and delegate review summaries to **Rating API** over Agent-to-Agent (A2A) gRPC using Entra Agent Identities (`chatAgentId` and `ratingAgentId`).

## How it works

The composed `chat-workflow` runs five sequential stages for every customer turn sent to `/ag-ui`.

### Stage 1: Input screening (`InputValidationExecutor`)

Before invoking any classifier or AI model, `InputValidationExecutor` trims whitespace and screens the message:

- **Empty input:** Rejects blank messages through `RejectedOutputExtractor` with a prompt asking for details.
- **Prompt injection:** Rejects messages matching suspicious patterns or flagged by the governance injection detector before routing begins.
- **Length enforcement:** Truncates accepted messages longer than 2,000 characters to a 1,900-character prefix with a truncation notice before forwarding to routing.

`UserPrompt.MaxLength` is 2,000 characters. Accepted longer prompts are truncated to `UserPrompt.TruncateLength` (1,900 characters) and append `"... [Message truncated due to length]"`.

### Stage 2: Fast classification (`DecisionRouterExecutor`)

`DecisionRouterExecutor` calls Microsoft Foundry's `decision` deployment (`Microsoft-Decision-1` via `IDecisionClient`) to evaluate language, BookWorm scope, and target specialist without invoking an LLM agent:

- **Non-English or out-of-scope:** Short-circuits directly to `DecisionRejectedOutputExtractor` with a brief boundary response, skipping specialist agents and the response formatter.
- **Store policies and support (`QA`):** Routes to the `qa` agent with `store-policies` context. Because the chat workflow has no live account, Basket, or Order lookup, `qa` directs account-specific questions to human support and can hand off book questions to `book`.
- **Book discovery and general reviews (`Book`):** Routes book search, recommendations, and review requests without a catalog book ID to the `book` agent.
- **Review summaries with a book ID (`Rating`):** Routes directly to the remote `rating` agent on **Rating API** via A2A gRPC.

The Chat routing guardrail rejects a decision when `is_safe`, `is_english`, or `is_in_scope` falls below `0.5`. Values at or above `0.5` continue to the normal route-selection path.

### Stage 3: Human-in-the-loop disambiguation (`RouteDisambiguationPort`)

When `DecisionRouterExecutor` returns a low-confidence in-scope route, `RouteDisambiguationPrepExecutor` prepares options (`BookAgent`, `QAAgent`, `RatingAgent`) and pauses the workflow at `RouteDisambiguationPort` (`RequestPort`). Storefront prompts the customer to pick the intended specialist via AG-UI (`disambiguateRoute`), and `RouteDisambiguationResolutionExecutor` resumes routing to the chosen specialist or boundary output.

### Stage 4: Specialist execution and parallel research

The three specialists collaborate through explicit handoffs and targeted delegation:

- **Direct responses and handoffs:** `book` answers catalog lookups directly via **MCP Tools** (`search_catalog`, `get_book`, `list_categories`, `list_authors`), hands off review analyses to `rating`, and hands off policy questions to `qa`. `qa` can hand off book-specific follow-ups back to `book`.
- **Parallel sub-researchers:** For complex multi-part discovery prompts, `book` delegates concurrently to `catalog-researcher` (factual book, author, category, and publisher lookup) and `recommendation-researcher` (preference-matched shortlist), then synthesizes and deduplicates both results before returning.
- **Direct A2A bypass caveat:** Calling an agent directly through `/agents` discovery or an A2A endpoint bypasses `InputValidationExecutor`, `DecisionRouterExecutor`, and `ResponseFormatterExecutor`. Customer traffic must enter through `/ag-ui`.

### Stage 5: Output normalization (`ResponseFormatterExecutor`)

`ResponseFormatterExecutor` takes the final assistant message from the specialist workflow, trims whitespace, strips accidental system-prompt fragments, ensures sentence-ending punctuation, and collapses excessive blank lines. If no usable assistant text remains, it returns a rephrasing prompt.

## Design trade-offs

| Decision                                                  | Benefits                                                                                          | Costs and limits                                                                                            |
| :-------------------------------------------------------- | :------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------------------------------------------- |
| **Non-LLM decision router before specialists**            | Cuts token cost and latency by filtering non-English and off-topic messages before LLM invocation | Mixed-intent prompts still require runtime handoffs or customer disambiguation                              |
| **Human-in-the-loop `RequestPort` disambiguation**        | Prevents silent misrouting on ambiguous prompts while keeping specialist tools isolated           | Adds an extra interactive round-trip when confidence is low                                                 |
| **Concurrent catalog and recommendation sub-researchers** | Delivers deeper answers on complex discovery queries without doubling serial wait time            | Improves depth rather than guaranteeing a fixed latency SLA; both branches must finish before synthesis     |
| **Read-only support boundary**                            | Protects Ordering, Basket, and account authorization boundaries from conversational manipulation  | Customers asking about live orders or accounts must be redirected to Commerce or human support              |
| **Azure Blob Storage session state (`chatting-blob`)**    | Keeps Chat API stateless across container replicas without requiring PostgreSQL or Redis          | Troubleshooting lost multi-turn context requires inspecting `ag-ui/` blobs separately from workflow routing |

## Alternatives considered

- **Single general-purpose chat agent:** Rejected because combining store policies, MCP catalog tools, and A2A review summarization under one prompt blurs authorization boundaries and widens the prompt-injection attack surface.
- **LLM-based router agent:** Rejected because invoking a full generative model for language and scope checks adds avoidable latency and token cost compared to `Microsoft-Decision-1`.
- **Direct database access from Chat API:** Rejected to preserve bounded-context ownership; Chat API reads catalog facts only through **MCP Tools** and review summaries only through **Rating API** A2A gRPC.
