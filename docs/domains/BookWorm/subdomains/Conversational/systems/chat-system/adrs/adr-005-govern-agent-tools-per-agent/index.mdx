## 1. Context & Problem

The chat host connects to a shared tool server that exposes capabilities for multiple consumers across the platform. Giving every conversational agent access to every available tool would blur agent responsibilities and unnecessarily widen the impact of any single invocation.

In addition, local delegation between agentsâ€”where one specialist asks research subagents to gather informationâ€”creates a distinct capability boundary from calling external tools directly. Both direct tool access and agent-to-agent delegation require explicit ownership and governance policies.

## 2. Business Value

- **Least-privilege safety:** Each agent only receives the minimum read-only capabilities needed for its role, limiting potential misuse or unintended side effects.
- **Clear accountability:** Architects, security reviewers, and product teams can easily trace which agents can look up live catalog data and which rely solely on provided context.
- **Defense in depth:** Per-agent capability restrictions on the client side reinforce authentication and authorization controls enforced by the tool server.

## 3. How It Works

Capabilities are assigned per agent role and paired with an explicit governance policy:

- **Question-and-answer specialist:** Operates with no live catalog lookup tools; it answers strictly from the context and instructions supplied to it.
- **Book specialist and its research helpers:** Receive only four declared read-only catalog lookup capabilitiesâ€”searching the catalog, retrieving a book's details, listing categories, and listing authors. None of these can create or update records.
- **Separated delegation governance:** Delegating work from the book specialist to its catalog and recommendation researchers is configured and governed separately from direct tool calls. The researchers inherit only the book specialist's approved read-only scope, never a broader server capability set.
- **Dual enforcement:** Having a capability registered for an agent never bypasses server-side security. Every tool request remains subject to server authentication, authorization filters, and server-side governance.

## 4. Trade-offs & Lessons Learned

- **Configuration and testing overhead:** Maintaining per-agent tool lists and governance policies adds configuration that must be updated and tested whenever agent roles or server capabilities change.
- **Mandatory change-review discipline:** When adding or removing a capability, teams must jointly review five elements: the agent's documented responsibility, its direct capability declarations, its governance policy, server-side authorization rules, and any delegation path. Reviewers must verify that agents without a business need cannot invoke the capability and that tool results are always treated as informational data rather than authorization to change owning-system records.
- **Alternatives considered:**
  - _Give every agent every tool:_ Would reduce configuration effort, but unnecessarily expands capabilities for agents that do not need catalog access and makes impact analysis harder.
  - _Rely only on server-side authorization:_ Server authorization is mandatory, but alone cannot differentiate the narrower responsibilities of individual agents sharing one authorized chat client.
  - _Treat delegated researchers as ordinary tools:_ Researchers are agent capabilities that can themselves invoke approved tools; governing only underlying tool calls would overlook the separate delegation decision.

## 5. Technical Reference

- **Target scope:** [[system|chat-system]] / [[service|chat-api]] covering `book-agent`, `qa-agent`, `book-catalog-researcher`, and `book-recommendation-researcher`.
- **Per-agent MCP tool assignments:**
  - `qa-agent`: No Catalog MCP tools; answers only from supplied context and instructions.
  - `book-agent`, `book-catalog-researcher`, and `book-recommendation-researcher`: Restricted to four read-only Catalog MCP tools: `search_catalog`, `get_book`, `list_categories`, and `list_authors`.
- **Delegation configuration:** `book-agent`'s researcher delegation is configured separately from its direct MCP tools; researchers inherit `book-agent`'s approved read capabilities.
- **Server-side governance:** Client-side allow-lists complement server authentication, authorization filters, and server-side governance documented in [[adr|adr-005-authenticate-and-govern-mcp-calls]].
