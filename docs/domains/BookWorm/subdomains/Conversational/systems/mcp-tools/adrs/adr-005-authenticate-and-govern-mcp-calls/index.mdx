## 1. Context & Problem

The shared AI integration boundary exposes [[domain|catalog]] and [[domain|reviews]] data to multiple internal AI clients. Because this capability is reachable over the network, it needs both caller identity verification and an explicit server-side permission boundary so a client cannot run capabilities simply because they exist on the server.

Relying only on which tools a client application chooses to load is not an adequate security control. A client could be misconfigured, or a caller could attempt to invoke a capability directly after discovering what the server offers.

## 2. Business Value

- **Defense in depth:** Prevents unauthorized callers or misconfigured AI clients from invoking capabilities they should not access.
- **Least-privilege access:** Ensures AI applications can only discover and run approved read-only capabilities aligned with their role.
- **Safer growth:** Allows new AI clients and capabilities to be introduced without relying on implicit network trust.
- **Clear accountability:** Separates identity verification and policy enforcement failures from upstream catalog or review data issues.

## 3. How It Works

Every incoming request to [[service|mcp-server]] passes through a strict two-layer security boundary before any book or review data is accessed:

1. **Caller authentication and read permission check:** Callers must present valid credentials verified through [[system|identity-provider]] showing they are authorized to read MCP capabilities. Internal consumers such as [[service|chat-api]] and [[service|rating-api]] obtain these credentials using service-to-service credential exchange.
2. **Server-side capability governance:** Even after a caller is authenticated, the server enforces a default-deny policy on tool invocations. Only explicitly approved tool categories are permitted, and unsafe tool patterns are blocked at the server boundary.

Client applications still configure which subset of tools they intend to use, while capability discovery only advertises what exists—it never grants permission to run a tool.

## 4. Trade-offs & Lessons Learned

- **Availability and latency dependency:** Token verification and governance checks are now on the critical path for every AI tool call. Operations teams must monitor authentication and policy failures separately from upstream [[domain|catalog]] and [[domain|reviews]] API health.
- **Onboarding and review overhead:** New AI clients cannot connect immediately; they must first be provisioned with service authentication and read permissions. Whenever tools or categories change, server allow rules and client tool configurations must be reviewed together.
- **Rejected alternatives:**
  - _Allowing unauthenticated internal-network access:_ Network placement alone does not identify who is calling or limit which tools can be run.
  - _Relying only on client-side tool declarations:_ Client configuration controls intended usage, not server enforcement against misconfiguration or direct calls.
  - _Allowing every authenticated caller to run all tools:_ Proving identity does not mean every caller should have unrestricted access to every capability.

## 5. Technical Reference

- **Decision status:** `accepted` (2026-11-04)

- **Protected endpoint:** `/mcp` on [[service|mcp-server]]
- **Required scope:** `mcptools_read`
- **Server-side controls:**
  - [[system|identity-provider]] token introspection
  - MCP authorization filters at the server boundary for requests and tool invocations
  - Default-deny MCP governance configuration with explicit allow rules for approved tool categories and denial of dangerous tool patterns
- **Client authentication pattern:** [[service|chat-api]] and [[service|rating-api]] connect using service-to-service token exchange
