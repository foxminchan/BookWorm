## 1. Context & Problem

BookWorm's AI assistants and external AI clients need up-to-date information from [[domain|catalog]] and [[domain|reviews]], along with reusable guidance for analyzing that information. However, allowing AI clients to read domain databases directly—or allowing AI-driven workflows to modify business records—would create serious architectural risks:

- It would tightly couple AI integrations to internal storage details of Catalog and Reviews.
- It would blur which system owns business rules and data integrity.
- It would increase the risk of unintended data changes triggered by automated model decisions.

BookWorm needed a shared, predictable integration layer that makes clear which capabilities simply retrieve information and which systems remain responsible for the underlying data.

## 2. Business Value

- **Clear data ownership**: Catalog and Reviews remain the single sources of truth for books, ratings, and reviews, preserving clean domain boundaries.
- **Safer AI adoption**: Restricting the shared AI integration layer to read-only access limits the impact of unexpected AI behavior and prevents accidental business-state changes.
- **Reusable integration across teams**: Multiple AI clients and agents can rely on one standardized integration boundary rather than building bespoke connections to each domain.
- **Explicit change management**: Business mutations continue to flow exclusively through established domain workflows with full validation and authorization.

## 3. How It Works

The [[system|mcp-tools]] system acts as a dedicated read-only adapter sitting in front of Catalog and Reviews:

- **Read-only retrieval**: AI clients use the adapter to look up book and review information or fetch reusable analysis instructions. None of these capabilities creates, updates, or deletes business records.
- **Selective capability access**: Each AI client requests only the specific capabilities it is permitted to use, governed by authentication, authorization, and client-level policies.
- **Authoritative source ownership**: Whenever data is requested, the owning domains remain solely responsible for their business rules, access controls, and stored records. Any action that changes business state must go through the owning domain's standard operations outside this adapter.

## 4. Trade-offs & Lessons Learned

- **Safety of read-only boundaries vs. conversational mutations**: Keeping the adapter strictly read-only prevents conversational workflows from appearing transactional or accidentally mutating state; supporting write actions later will require a separate, explicit architectural and authorization decision.
- **Contract stability responsibility**: Once exposed to AI clients, the adapter's tools, data references, and prompt templates become shared integration contracts that must be versioned and evolved carefully.
- **Live lookups without cross-domain snapshots**: Results reflect source systems at the moment each request runs; the adapter does not maintain a durable cache or guarantee a single consistent snapshot across separate lookups.
- **Read-only is not a substitute for security**: Limiting capabilities to reads reduces blast radius, but caller authentication, authorization, and client validation remain mandatory.

### Alternatives Evaluated

- **Direct database access for AI clients**: Rejected because it bypasses owning services, exposes private storage schemas and credentials, and weakens access control enforcement.
- **Exposing domain write operations through the adapter**: Rejected because model-selected writes would blur ownership of business decisions and expand failure consequences.
- **Point-to-point integration per AI client**: Rejected because each client would duplicate connection, discovery, and contract-mapping logic across domains.

## 5. Technical Reference

- **Decision status**: Accepted (`2026-11-04`)
- **Affected systems & services**: [[system|mcp-tools]], [[service|mcp-server]], `product-catalog-system`, `rating-system`
- **Adapter implementation**: [[service|mcp-server]] exposes three read-only MCP primitive categories:
  - **Tools**: Retrieve information on demand without changing domain records.
  - **Resources**: Expose URI-addressed domain data.
  - **Prompts**: Provide reusable task instructions.
- **Authoritative backends**: [[service|catalog-api]] and [[service|rating-api]] retain ownership of their respective API behavior, persistence, and write workflows.
- **Governance**: MCP clients select only the capabilities they need, subject to server-side authentication, authorization, and governance policies.
