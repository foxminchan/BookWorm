## 1. Context & Problem

Occasionally, a customer submits a chat message and receives no useful answer, sees a generic prompt asking them to rephrase, or experiences a flow that appears to stall before or after specialist handling. Without a structured triage procedure, operations and support teams can misdiagnose early input rejections as specialist outages, blindly retry unrecoverable requests, or overlook non-persistent session behavior after a service restart.

## 2. Business Value

- **Faster incident resolution**: Guides operators step by step from entry-point verification to specialist handoff and formatting checks.
- **Fewer wasted retries**: Distinguishes input rejections from downstream processing issues before retrying.
- **Customer privacy protection**: Ensures diagnostic escalations capture routing context without exposing unnecessary customer-sensitive data.

## 3. How It Works

### Observed Symptoms

- A customer submits a request but receives no useful answer.
- The workflow returns a rephrasing prompt instead of an expected response.
- A request appears to stop before or after specialist handling.

### Triage Steps

1. **Verify the Entry Point**: Confirm the customer used the interactive chat workflow rather than calling an individual specialist directly.
2. **Separate Screening Rejections from Accepted Requests**: Determine whether initial input validation rejected the message or accepted it for routing, keeping validation rejections distinct from specialist responses.
3. **Trace Specialist Selection and Handoff**: For accepted requests, identify which specialist was selected and whether any expected handoff completed.
4. **Check Final Response Formatting**: Inspect the final assistant message and formatting result—when no usable assistant text remains, the formatter falls back to a rephrasing prompt.
5. **Account for Host Restarts**: If the issue followed a service restart, note that chat sessions reside in temporary memory and are not recoverable as durable conversation history.

### Recovery and Escalation

- **Rejected input**: Explain the applicable input limitation and ask the customer to submit a suitable request.
- **Accepted request**: Retry only after confirming the request can be handled and the relevant specialist path is available. Never treat request acceptance as proof of successful completion.
- **Empty or unusable final message**: Capture the route, workflow outcome, and sanitized diagnostic details, then escalate to the responsible engineering team without including unnecessary customer-sensitive content.

## 4. Trade-offs & Lessons Learned

- **Acceptance is not completion**: Initial input acceptance only confirms a message can enter routing; diagnosing failures requires inspecting specialist execution, handoffs, and final response formatting.
- **Graceful rephrasing fallback vs. visibility**: Returning a rephrasing prompt prevents blank screens when usable text is missing, but requires diagnostic logging so teams can distinguish user-phrasing issues from broken downstream paths.
- **In-memory sessions vs. durability**: Keeping sessions in memory simplifies runtime state, at the cost of losing active conversation history across host restarts.

## 5. Technical Reference

### Diagnostic checklist

1. Confirm the customer used the interactive `/ag-ui` workflow rather than calling an individual agent endpoint.
2. Determine whether input validation rejected the message or accepted it for routing (acceptance only means it can proceed to agent handling, not success).
3. If accepted, identify the selected specialist and whether the request completed its handoff.
4. Check the final assistant message and response-formatting outcome (the formatter returns a rephrasing prompt when no usable assistant text remains).
5. If the issue followed a host restart, remember that Chat sessions are in-memory and are not recoverable durable conversation history.

Contact [[team\|contributor-team]] with:

- Environment
- Approximate time

- Validation outcome
- Selected specialist
- Observed final result
