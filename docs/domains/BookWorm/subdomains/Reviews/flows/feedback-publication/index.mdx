When a customer submits a book review, **Rating API** saves the authoritative `Feedback` document in Azure Cosmos DB (`ratingdb`/`feedbacks`) and publishes `FeedbackCreatedIntegrationEvent` over Kafka. **Catalog API** consumes that event to recalculate the book's derived rating summary (`average_rating` and `total_reviews`) in PostgreSQL, without ever storing review text or reviewer details. If the referenced book does not exist in Catalog, Catalog API publishes `BookUpdatedRatingFailedIntegrationEvent` so Rating API deletes the orphaned feedback record.

## Context and motivation

Storefront browsing and search listings display each book's average rating and total review count on high-traffic pages. Querying **Rating API** synchronously on every catalog read would couple catalog availability to the Reviews subdomain and add cross-service latency. Conversely, copying full customer comments into **Catalog API** would duplicate ownership of moderation history and reviewer data.

BookWorm separates ownership cleanly across two bounded contexts:

- **Reviews (`Rating API`):** Owns individual `Feedback` records in Azure Cosmos DB (`ratingdb`, container `feedbacks`, partition key `/bookId`) using EF Core Cosmos and Wolverine Cosmos DB persistence.
- **Catalog (`Catalog API`):** Owns books in PostgreSQL (`catalogdb`) and maintains only a derived, rebuildable rating summary (`average_rating` and `total_reviews`) updated via Kafka integration events.

## How it works

Customer feedback publication follows an optimistic asynchronous projection with a compensating rollback path when a book ID is invalid.

### Happy path: persist and project

1. **Validate and persist feedback:** A customer submits a rating and optional comment to `Rating API` (`/rating/api/v1/feedbacks`). Rating API validates the book ID, score, reviewer name, and comment, then commits the `Feedback` document to Azure Cosmos DB (`ratingdb`/`feedbacks`, partitioned by `/bookId`).
2. **Publish integration event:** Wolverine maps `FeedbackCreatedEvent` to `FeedbackCreatedIntegrationEvent` (`BookId`, `Rating`, `FeedbackId`) and publishes it as CloudEvents JSON to `bookworm.{env}.rating.feedback-create`, partitioned by `BookId` / `FeedbackId`.
3. **Apply derived summary in Catalog:** `FeedbackCreatedIntegrationEventHandler` in **Catalog API** guards duplicate delivery with Redis-backed `IIntegrationEventIdempotencyGuard` (24-hour window keyed by event ID), loads the book from PostgreSQL (`catalogdb`), calls `book.AddRating(@event.Rating)`, and commits the updated summary through EF Core and Wolverine's PostgreSQL outbox.

### Failure path: missing-book compensation

If `Catalog API` looks up `@event.BookId` and finds no active book, the handler commits its unit of work and returns `BookUpdatedRatingFailedIntegrationEvent(@event.FeedbackId)` as a Wolverine cascading message on `bookworm.{env}.catalog.book-update-rating-failed`. **Rating API** consumes this compensating event and deletes the orphaned `Feedback` document from Cosmos DB so Reviews and Catalog stay aligned.

:::note
Deleting a review follows a separate one-way contract: Rating API publishes `FeedbackDeletedIntegrationEvent` on `bookworm.{env}.rating.feedback-delete`, and Catalog API calls `book.RemoveRating(@event.Rating)` (treating a missing book as a safe no-op).
:::

## Design trade-offs

| Decision                                                                 | Benefits                                                                                                                    | Costs and limits                                                                                                                           |
| :----------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------- |
| **Optimistic acceptance with async compensation**                        | Keeps review submission available even if Catalog API is temporarily unreachable and avoids synchronous cross-service calls | Invalid book references exist briefly in Cosmos DB until the compensation event deletes them                                               |
| **Derived rating summary on `books`**                                    | Serves book listings and search results from PostgreSQL without calling Rating API on every page view                       | Introduces brief eventual-consistency lag between review submission and updated catalog scores                                             |
| **Redis-backed idempotency guard (`IIntegrationEventIdempotencyGuard`)** | Prevents duplicate Kafka deliveries from double-counting a rating during the 24-hour guard window                           | Messages replayed after the 24-hour window or delta drift after broker faults require reconciliation against Cosmos DB                     |
| **Separate Cosmos DB and PostgreSQL stores**                             | Matches each bounded context to its access pattern (partitioned document reviews vs. relational catalog)                    | Prohibits distributed database transactions; cross-domain recovery relies on Wolverine retries (`50ms / 250ms / 1s`) and native Kafka DLQs |

## Alternatives considered

- **Synchronous gRPC check from Rating API to Catalog API before saving:** Rejected because it creates tight runtime coupling and fails review submission whenever Catalog API experiences latency or downtime.
- **Querying Rating API live during catalog reads:** Rejected because product browsing and search are high-volume read paths that must remain isolated from Reviews traffic.
- **Storing full review records inside Catalog PostgreSQL:** Rejected because it violates bounded-context ownership and duplicates PII and moderation data across services.
