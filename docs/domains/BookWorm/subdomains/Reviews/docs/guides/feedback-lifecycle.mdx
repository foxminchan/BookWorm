BookWorm separates customer review storage from product catalog browsing across two independent bounded contexts: **Reviews** (**Rating API**, `rating`) owns individual `Feedback` documents in **Azure Cosmos DB** (`ratingdb` / `feedbacks`, partition key `/bookId`), while **Catalog** (**Catalog API**, `catalog`) owns `Book` records in **PostgreSQL** (`catalogdb`) and maintains only a derived rating summary (`average_rating` and `total_reviews`). Decoupling these stores lets customers submit reviews without synchronous cross-database transactions while keeping catalog reads fast.

## Context and motivation

Individual customer reviews and catalog product listings have different access patterns, scaling profiles, and consistency requirements:

- **Reviews** stores append-heavy, book-partitioned documents (`Feedback`) and supports both paginated browsing and AI-generated review summaries.
- **Catalog** serves high-volume browsing and search queries that only need an aggregate average score and review count per book.

Sharing a single database between Reviews and Catalog—or blocking review writes on synchronous Catalog updates—would couple deployment lifecycles and turn temporary Catalog slowdowns into customer review outages.

### Four lifecycle stages

- **Create feedback:** A caller submits `bookId`, `firstName`, `lastName`, an integer `rating` (`0`-`5`), and an optional `comment` (up to `1000` characters) to `POST /api/v1/feedbacks`. Rating API persists the `Feedback` document in Cosmos DB `ratingdb`/`feedbacks` (partitioned by `/bookId`), returns the new `FeedbackId` (`200 OK`), and publishes `FeedbackCreatedIntegrationEvent` to `bookworm.{env}.rating.feedback-create` after commit. Returning `200 OK` confirms review persistence—not that Catalog has finished updating its summary.
- **Read feedback and generate AI summaries:** `GET /api/v1/feedbacks` returns paginated reviews for a `bookId`, cached for `10` minutes in Redis via FusionCache (tagged by `BookId`). For an overview, authenticated callers invoke `GET /api/v1/feedbacks/{id}/summarize`, which runs `rating-agent` (Microsoft Agent Framework + Microsoft Foundry + Presidio PII protection). The agent reads live book context through **MCP Tools** (`get_book`) and raw reviews, returning a read-only derived summary that never mutates Cosmos DB or Catalog.
- **Delete feedback (moderation):** Authorized administrators (`admin` policy) remove a review via `DELETE /api/v1/feedbacks/{id}`. Missing IDs return `404 Not Found` rather than succeeding silently. Deleting an existing record invokes `Feedback.Remove()`, deletes the document from Cosmos DB, and publishes `FeedbackDeletedIntegrationEvent` to `bookworm.{env}.rating.feedback-delete` so Catalog decrements its projection asynchronously.
- **Asynchronous projection and compensation:** Catalog API consumes create and delete events with a 24-hour Redis `IIntegrationEventIdempotencyGuard` so at-least-once retries cannot double-count ratings. If a `FeedbackCreatedIntegrationEvent` arrives for a `bookId` that does not exist in `catalogdb`, Catalog publishes `BookUpdatedRatingFailedIntegrationEvent` (carrying `FeedbackId`) to `bookworm.{env}.catalog.book-update-rating-failed`. Rating API's compensation handler calls `feedback.Revert()` (which invalidates the Redis cache tag without emitting `FeedbackDeletedIntegrationEvent`) and deletes the orphaned document—treating an already-absent record as a no-op.

## Design trade-offs

| Decision                                                       | Benefits                                                                                                             | Costs and limits                                                                                                                      |
| :------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------ |
| **Cosmos DB for Reviews vs. PostgreSQL for Catalog**           | Partitioning `feedbacks` by `/bookId` gives fast per-book review queries and isolates write scaling from `catalogdb` | Two database technologies to operate; cross-domain consistency is eventual rather than transactional                                  |
| **Post-commit Kafka projection with compensation**             | Keeps review submissions fast and resilient even if Catalog is temporarily unavailable                               | Catalog's `average_rating` and `total_reviews` briefly lag behind Reviews; invalid `bookId` submissions are cleaned up asynchronously |
| **Idempotent consumers (`IIntegrationEventIdempotencyGuard`)** | Tolerates at-least-once Kafka redelivery without skewing Catalog totals or failing compensation                      | Requires healthy Redis (`redis`) alongside Kafka consumers                                                                            |
| **Read-only AI summarization (`rating-agent`)**                | Provides governed, PII-filtered insights without risking corruption of customer ratings                              | Summary generation incurs live LLM and MCP lookup latency                                                                             |

## Alternatives considered

- **Synchronous gRPC check against Catalog before saving feedback:** Rejected because a book can still be deleted between the check and projection, and synchronous validation would couple Reviews write availability directly to Catalog uptime.
- **Storing feedback in PostgreSQL inside `catalogdb`:** Rejected because sharing a database breaks bounded-context isolation between Reviews and Catalog.
