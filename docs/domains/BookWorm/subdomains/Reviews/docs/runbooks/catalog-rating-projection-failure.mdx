Use this runbook when **Catalog API** (`catalog`) publishes `BookUpdatedRatingFailedIntegrationEvent` on `bookworm.<env>.catalog.book-update-rating-failed` or when a created feedback record in **Rating API** (`rating`, **Azure Cosmos DB** `ratingdb`/`feedbacks`) fails to project onto a book in **Catalog API** (**PostgreSQL** `catalogdb`). This compensation path removes an orphaned review for a missing book; never communicate it to customers as a manual customer deletion.

## Prerequisites

- Read access to **Catalog API** (`GET /catalog/api/v1/books/{id}`) or read-only SQL access to `catalogdb` (PostgreSQL).
- Read access to **Azure Cosmos DB** Data Explorer (locally via Cosmos emulator or in Azure) for database `ratingdb`, container `feedbacks`.
- Read access to **Aspire Dashboard** (locally) or **Azure Log Analytics** for `catalog` and `rating` logs and OpenTelemetry traces.
- Read access to **Kafka UI** (locally) or **Confluent Cloud** for rating topics and dead-letter queues (DLQs).

## Steps

<Steps>
<Step title="Record failure identifiers before making any change">

Capture the `FeedbackId` from `BookUpdatedRatingFailedIntegrationEvent`, the CloudEvents `id`, W3C correlation/trace ID, environment (`<env>`), and failure UTC timestamp.

<Admonition type="note">
	`BookUpdatedRatingFailedIntegrationEvent` carries only `FeedbackId`—it does not include `BookId`.
	Resolve `BookId` in Step 2 from Catalog logs (`FeedbackCreatedIntegrationEvent`) or from the
	`Feedback` document in Cosmos DB `ratingdb`/`feedbacks`.
</Admonition>

</Step>
<Step title="Confirm whether the book is actually missing in Catalog">

Inspect `catalog` logs for the originating `FeedbackCreatedIntegrationEvent` matching `<feedback-id>` to obtain `<book-id>` and confirm why projection failed (missing book vs. transient `catalogdb` or Kafka fault). Then verify book existence via Catalog API:

<CodeGroup>

```bash
curl -sS -o /dev/null -w "%{http_code}\n" \
  "https://<gateway-host>/catalog/api/v1/books/<book-id>"
```

</CodeGroup>

Where:

- `<gateway-host>`: API Gateway hostname (or local Aspire gateway address).
- `<book-id>`: UUID of the book referenced by the feedback.

- If the response is **`404 Not Found`**, the book is absent and compensation is valid. Continue to Step 3.
- If the response is **`200 OK`**, **stop immediately**. Do not delete the feedback record—this indicates a transient database failure, malformed event, or contract defect. Escalate with Catalog logs and event metadata to Catalog/Reviews maintainers or platform infrastructure owners.

</Step>
<Step title="Inspect the feedback document in Cosmos DB (`ratingdb` / `feedbacks`)">

Query the `feedbacks` container in Azure Cosmos DB (`ratingdb`) by `id` (and `bookId` partition key when known) to check whether the orphaned document still exists:

<CodeGroup>

```sql
SELECT c.id, c.bookId, c.rating, c.createdAt
FROM c
WHERE c.id = "<feedback-id>"
```

</CodeGroup>

Where:

- `<feedback-id>`: Exact `FeedbackId` from `BookUpdatedRatingFailedIntegrationEvent`.

<Admonition type="danger">
	Never delete feedback records by `bookId` alone. Compensation targets only the exact `FeedbackId`
	reported by `BookUpdatedRatingFailedIntegrationEvent`.
</Admonition>

</Step>
<Step title="Check Kafka consumer health and dead-letter queues">

Inspect consumer lag and DLQ depth for:

- `bookworm.<env>.rating.feedback-create` (Catalog consumer)
- `bookworm.<env>.catalog.book-update-rating-failed` (Rating compensation consumer)
- `bookworm.<env>.catalog.dead-letter-queue` and `bookworm.<env>.rating.dead-letter-queue`

Check `rating` logs for `BookUpdatedRatingFailedIntegrationEventHandler` errors (such as Cosmos DB throttling/connectivity or Redis `IIntegrationEventIdempotencyGuard` faults).

</Step>
<Step title="Run recovery through the standard compensation handler">

- If `rating`, Cosmos DB, Redis, or Kafka experienced a transient outage, restore the unhealthy dependency and let `BookUpdatedRatingFailedIntegrationEventHandler` process (or replay from `bookworm.<env>.rating.dead-letter-queue` using approved broker tooling).
- The handler looks up `<feedback-id>` in Cosmos DB `ratingdb`/`feedbacks`:
  - If present, it calls `feedback.Revert()` (invalidating the Redis list cache tag without emitting `FeedbackDeletedIntegrationEvent`) and deletes the document.
  - If already absent, it completes as an idempotent no-op.
- Do not issue `DELETE /api/v1/feedbacks/<feedback-id>` as a substitute unless the compensation pipeline is unavailable and authorized by the Reviews owner, because manual API deletion publishes `FeedbackDeletedIntegrationEvent` back to Catalog.

</Step>
</Steps>

## Verification

Confirm that the orphaned review is removed and both domains are healthy:

1. Re-run the Cosmos DB query in `ratingdb`/`feedbacks` for `<feedback-id>` and confirm it returns `0` documents.
2. Confirm no unrelated feedback documents for `<book-id>` were modified.
3. Confirm consumer lag on `bookworm.<env>.catalog.book-update-rating-failed` and `bookworm.<env>.rating.feedback-create` is `0`, and neither `bookworm.<env>.rating.dead-letter-queue` nor `bookworm.<env>.catalog.dead-letter-queue` is growing.
4. Confirm in `rating` logs that `<feedback-id>` correlates cleanly to the `BookUpdatedRatingFailedIntegrationEvent` compensation completion.

## Troubleshooting

| Symptom                                                                                     | Cause                                                                                                      | Fix                                                                                            |
| :------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| `GET /catalog/api/v1/books/<book-id>` returns `200 OK`, yet failure event fired             | Transient `catalogdb` error, race condition, or malformed event payload—not a missing book                 | Stop compensation immediately; preserve logs and escalate to Catalog/Reviews maintainers       |
| `BookUpdatedRatingFailedIntegrationEvent` sits in `bookworm.<env>.rating.dead-letter-queue` | Transient Cosmos DB (`ratingdb`), Redis idempotency, or `rating` worker outage exhausted Wolverine retries | Restore Cosmos DB / Redis / `rating` health, verify book is `404`, then replay the DLQ message |
| Feedback document is already gone in Cosmos DB when replaying the failure event             | Earlier compensation or admin deletion already removed `<feedback-id>`                                     | Safe no-op; `BookUpdatedRatingFailedIntegrationEventHandler` exits cleanly without error       |
| List API still displays the removed review briefly after compensation                       | Stale 10-minute FusionCache entry in Redis if `FeedbackRevertedEvent` cache invalidation failed            | Verify Redis connectivity and allow cache TTL expiration or invalidate the `BookId` cache tag  |
