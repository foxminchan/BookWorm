## 1. Context & Problem

Because Reviews and Catalog operate independently, a customer may occasionally submit [[entity|feedback]] for a [[entity|book]] that has already been removed or never existed in Catalog. When Catalog tries to update its rating summary and cannot find the book, it emits a failure notification instead of silently dropping the review or storing a broken score.

Operations and engineering teams need a safe, repeatable runbook to verify that the failure truly stems from a missing book—not a temporary outage—and ensure the orphaned review is cleanly compensated without affecting valid reviews.

## 2. Business Value

- **Prevents silent data drift**: Stops orphaned reviews from accumulating in Reviews when their corresponding book does not exist in Catalog.
- **Avoids false-alarm escalations**: Distinguishes an expected missing-book compensation path from a full Reviews service outage.
- **Protects customer trust and auditability**: Preserves full evidence of what happened, avoids deleting valid feedback by mistake, and prevents miscommunicating corrective cleanup as a customer deletion.
- **Clear escalation ownership**: Routes infrastructure/messaging problems and service/contract bugs to the right owning teams quickly.

## 3. How It Works

When a rating projection fails because a book is missing, operators follow a four-step recovery process:

1. **Confirm the cause before acting**: Preserve the identifiers, environment, and timing from the failure notice. Verify that Catalog actually reported a missing book rather than a temporary connectivity, database, or messaging disruption.
2. **Verify book absence and review state**: Confirm whether the book still exists in Catalog and inspect the current state of the specific review record. If the book actually exists, stop immediately and escalate—the issue is a system or contract defect, not an invalid book reference.
3. **Run targeted compensation**: Restore any paused failure-processing dependencies if needed, then let the normal compensation handler remove the single invalid review by its exact feedback identifier. If the review was already deleted, treat it as complete without error. Never delete all reviews for a book identifier blindly, and avoid manual database edits unless authorized when normal recovery is unavailable.
4. **Verify system health**: Confirm that the invalid review is gone, no unrelated reviews were touched, audit evidence linking the failure to its cleanup is preserved, and normal review creation and deletion continue working smoothly.

## 4. Trade-offs & Lessons Learned

- **Targeted compensation vs. broad cleanup**: Deleting strictly by the individual feedback identifier—never by book identifier alone—prevents accidental mass deletion if a book record is only temporarily unavailable or misrouted.
- **Automated handler over manual database edits**: Routing recovery through the standard compensation handler guarantees idempotent, auditable cleanup and avoids human error in production data stores.
- **Strict escalation gate**: Stopping immediately when the book _does_ exist in Catalog prevents masking deeper messaging or schema mismatches as harmless cleanup.

## 5. Technical Reference

### When to use this runbook

Use this procedure when [[event|BookUpdatedRatingFailedIntegrationEvent]] is published on [[channel|bookworm.&#123;env&#125;.catalog.book-update-rating-failed]], or when a created [[entity|feedback]] record remains unprojectable because its Catalog [[entity|book]] no longer exists.

This is a compensating path for an invalid Book reference. It is not a generic Rating service outage and must not be described to the customer as a manual feedback deletion.

### Safety rules

- Preserve the `feedbackId`, `bookId`, event ID, correlation ID, environment, and failure timestamp before taking action.
- Confirm that Catalog's failure identifies a missing Book, not a transient database, Kafka, or application failure.
- Never delete a feedback record by Book ID alone. The compensation targets the feedback ID from the failed integration event.
- Do not modify Catalog's database or the Reviews database manually unless an approved recovery action is unavailable and the owner has authorized it.

### Investigate

1. Inspect the failure event and confirm its `feedbackId` and `bookId`.
2. Check Catalog logs for the original [[event|FeedbackCreatedIntegrationEvent]] and the reason the rating update failed.
3. Verify whether the Book exists in Catalog. If it exists, stop the compensation and escalate the projection or contract failure.
4. Check [[container|rating-database]] for the feedback ID and record its current state.
5. Check the failure-channel consumer and retry/dead-letter status for duplicate delivery or a processing outage.

### Recover an invalid reference

1. Restore the failure consumer or its dependency if the issue was transient.
2. Process the failure through the normal Rating compensation handler.
3. The handler locates the feedback by `feedbackId` and deletes it when present.
4. Treat an already-missing feedback record as an idempotent no-op.
5. Do not publish a second customer deletion action; retain the original failure event and compensation evidence for auditability.

### If the failure is not a missing Book

Stop before deleting feedback when the Book exists or the event is malformed. Escalate with the event payload, Catalog logs, consumer status, and database lookup result to [[team|platform-team]] for infrastructure or messaging failures and [[team|contributor-team]] for service or contract failures.

### Verify

- The invalid feedback record is removed, or the handler confirms it was already absent.
- No unrelated feedback record was changed.
- The failed event is correlated with the compensation result.
- The failure channel is healthy and no unbounded retry or dead-letter backlog remains.
- Valid feedback creation and deletion flows still publish their normal events.
