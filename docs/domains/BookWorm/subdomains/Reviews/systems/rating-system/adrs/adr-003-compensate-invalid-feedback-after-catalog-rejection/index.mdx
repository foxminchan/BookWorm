## 1. Context & Problem

Every [[entity|feedback]] entry references a [[entity|book]] owned by Catalog. Because [[domain|reviews]] and Catalog maintain separate data stores and communicate asynchronously, there is no shared database check or distributed transaction to guarantee that a referenced book still exists in Catalog at the exact moment feedback is created.

If Catalog receives a newly created feedback notice for a book it cannot find, leaving that feedback stored in Reviews would retain orphaned data that can never appear in Catalog's rating summary.

## 2. Business Value

- **Clean, accurate data:** Reviews does not retain orphaned feedback for nonexistent books indefinitely.
- **Resilient asynchronous design:** Both domains preserve full independence without brittle cross-system locks or distributed transactions.
- **Targeted, safe recovery:** Cleanup is tightly scoped to the exact rejected feedback record, preventing accidental removal of valid customer reviews.
- **Retry resilience:** Repeated rejection notices are handled harmlessly, avoiding error loops or dead-letter noise.

## 3. How It Works

When Catalog rejects a newly created feedback notice because the referenced book does not exist, a targeted compensation flow cleans up the invalid record:

1. **Catalog signals the missing book:** Catalog cannot apply the rating update, so it sends a specific failure notice identifying the rejected feedback entry.
2. **Reviews removes only that record:** The Rating service looks up the specific feedback record using the identifier in the notice and deletes it.
3. **Repeated notices are harmless:** If that feedback entry has already been removed, the service simply finishes without modifying any other feedback for the same book or reviewer and without retrying endlessly.
4. **Strictly scoped to missing books:** This cleanup runs only for missing-book rejections on newly created feedback—not for temporary outages, network glitches, or other processing errors.

## 4. Trade-offs & Lessons Learned

- **Temporary inconsistency window:** A feedback record referencing a missing book can exist briefly in Reviews until Catalog processes the creation notice and sends back the rejection signal.
- **Operational distinction required:** Support and operations teams must distinguish automated missing-book compensation from customer- or administrator-initiated deletions when auditing feedback history.
- **Correlation is essential for diagnostics:** Investigating why a review disappeared requires tracing the original creation notice, Catalog's rejection notice, and the targeted feedback identifier together.
- **Narrow scope prevents data loss:** Limiting compensation strictly to missing-book rejections ensures valid customer feedback is never deleted due to transient consumer or infrastructure failures.

### Alternatives Considered

- **Share a database or enforce a cross-system foreign key:** Rejected because it would couple Reviews persistence to Catalog storage and violate independent domain boundaries.
- **Keep the invalid feedback and retry the projection forever:** Rejected because repeated retries cannot make a nonexistent book appear, leaving unprojectable data indefinitely.
- **Delete feedback for any Catalog processing error:** Rejected because treating every error as a business rejection could delete legitimate customer reviews during a transient outage.

## 5. Technical Reference

- **Triggering flow:** [[service|rating-api]] emits [[event|FeedbackCreatedIntegrationEvent]] on `bookworm.{env}.rating.feedback-create`.
- **Compensation event & channel:** Catalog publishes [[event|BookUpdatedRatingFailedIntegrationEvent]] on `bookworm.{env}.catalog.book-update-rating-failed` when the referenced book is missing.
- **Consumer behavior in `rating-api`:**
  - Extracts `feedbackId` from `BookUpdatedRatingFailedIntegrationEvent` and deletes only that matching `Feedback` record.
  - **Idempotency:** If the record for `feedbackId` is already absent, the handler completes as an idempotent no-op without modifying other records for the same book or reviewer or triggering endless retries.
  - **Scope guard:** Strictly limited to missing-book rejection of a created-feedback event; other delivery, validation, or transient Catalog failures use separate error-handling paths.
- **Diagnostic correlation:** Correlate `FeedbackCreatedIntegrationEvent`, `BookUpdatedRatingFailedIntegrationEvent`, and `feedbackId` across logs and traces.
