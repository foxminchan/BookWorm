Rating database (`ratingdb`) is the authoritative **Azure Cosmos DB** system of record owned exclusively by [[service|rating-api]] in the Reviews bounded context. It stores individual customer `Feedback` JSON documents in the `feedbacks` container partitioned by `/bookId`, alongside Wolverine Cosmos DB message persistence. Rating API does **not** use PostgreSQL.

## Architecture and data boundaries

Rating API is the sole service that creates, queries, or deletes documents in `ratingdb`. Partitioning `feedbacks` by `/bookId` co-locates all reviews for a given book in one logical partition for efficient single-partition reads during listing and AI summarization.

- **Read-only agent access:** [[agent|rating-agent]] reads reviews through `GetCustomerReviews` under a `default_action: deny` governance policy capped at `30/minute`. Generated classifications and summaries are never written back to `ratingdb`.
- **Eventual consistency with Catalog:** [[service|catalog-api]] never queries Cosmos DB directly. It consumes `FeedbackCreatedIntegrationEvent` and `FeedbackDeletedIntegrationEvent` (partitioned by `BookId` and `FeedbackId`) to update its derived `average_rating` and `total_reviews` columns in [[container|catalog-database]].

## Cosmos DB document schema and mapping

`FeedbackConfiguration` maps the `Feedback` domain entity to the `feedbacks` container with `HasNoDiscriminator()`, `UseETagConcurrency()` (ignoring `RowVersion`), and default `QueryTrackingBehavior.NoTracking` on `RatingDbContext`.

| JSON property    | C# type               | Required | Constraints & behavior                                                                            |
| :--------------- | :-------------------- | :------- | :------------------------------------------------------------------------------------------------ |
| `id`             | `FeedbackId` (`Guid`) | Yes      | Document primary key (`HasKey`)                                                                   |
| `bookId`         | `Guid`                | Yes      | Cosmos DB partition key (`/bookId`) referencing the Catalog book                                  |
| `firstName`      | `string`              | Yes      | Reviewer first name (annotated `[PIIData]` in command logging; max 50 chars in domain validation) |
| `lastName`       | `string`              | Yes      | Reviewer last name (annotated `[PIIData]` in command logging; max 50 chars in domain validation)  |
| `comment`        | `string`              | No       | Optional written review (up to `1,000` characters)                                                |
| `rating`         | `int`                 | Yes      | Whole-number score validated as `0`–`5` in Rating API (no database-level check constraint)        |
| `createdAt`      | `DateTime`            | Yes      | UTC creation timestamp                                                                            |
| `lastModifiedAt` | `DateTime?`           | No       | Optional UTC modification timestamp                                                               |
| `_etag`          | `string`              | System   | Managed by Cosmos DB for optimistic concurrency (`UseETagConcurrency()`)                          |

## Concurrency, conflict handling, and messaging persistence

- **ETag optimistic concurrency:** `RatingDbContext.SaveEntitiesAsync` catches `DbUpdateConcurrencyException` and throws `InvalidOperationException("The feedback was modified or deleted by another request.")`.
- **Conflict handling (`409 Conflict`):** `SaveEntitiesAsync` catches `CosmosException` with `HttpStatusCode.Conflict` and throws `InvalidOperationException("A feedback from this author already exists for this book.")`.

The provisioned feedback container has partition key `/bookId` and no unique-key policy declared by `AppHost.cs`. Do not infer cross-feedback uniqueness from the EF Cosmos configuration.

- **Wolverine Cosmos DB persistence:** `BookWorm.Rating/Extensions/Extensions.cs` registers `opts.UseCosmosDbPersistence(Components.Database.Rating)` on `ratingdb` so Wolverine persists integration message state in Cosmos DB alongside feedback operations.

## Operational notes

- **No SQL migrations:** Because `ratingdb` runs on Azure Cosmos DB, do not run PostgreSQL DDL scripts or EF Core SQL migrations against Rating.
- **Service-layer validation required:** Always create or delete reviews through Rating API so rating bounds (`0`–`5`), PII redaction annotations, and `FeedbackCreatedIntegrationEvent` / `FeedbackDeletedIntegrationEvent` publications remain consistent.
