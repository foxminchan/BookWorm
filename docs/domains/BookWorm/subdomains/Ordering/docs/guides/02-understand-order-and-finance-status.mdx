BookWorm separates every checkout into two independent state machines: **Ordering API** (`ordering`) owns the authoritative commercial status of an order in PostgreSQL (`orderingdb`), while **Finance** (`finance`) coordinates post-checkout basket cleanup and notification commands using **Azure Functions** and **Azure Durable Task Scheduler** (`finance-taskhub`, with no PostgreSQL database). Never infer an order's business status from basket contents, Finance orchestration state, or delivered emails.

## Context and motivation

After a customer submits checkout, three asynchronous activities occur outside the original HTTP request: clearing the customer's shopping basket, tracking retry timers if cleanup stalls, and sending lifecycle emails. When a cleanup command fails, a retry timer expires, or a customer receives a cancellation email, support engineers and stakeholders can mistake those operational signals for changes to the commercial order record.

Keeping Ordering's domain model strictly isolated from Finance's workflow engine prevents transient infrastructure failures or retry exhaustion from corrupting commercial order records.

## How it works

**Ordering API** publishes `UserCheckedOutIntegrationEvent` when an order is created, triggering Finance's `OrderOrchestrator` Durable Function. From that point onward, the two services maintain independent state stores and communicate exclusively over Kafka.

### Two independent state models

| Dimension           | Ordering API (`orderingdb`, PostgreSQL)                                      | Finance (`finance-taskhub`, Durable Task Scheduler)                                                                   |
| :------------------ | :--------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------- |
| **Authority**       | Authoritative commercial order status and purchase snapshot                  | Post-checkout workflow coordination and compensation only                                                             |
| **Status values**   | `New`, `Completed`, `Cancelled` (plus separate `IsDeleted` soft-delete flag) | `Placed`, `Completed`, `Cancelled`, `BasketDeletionFailed`, `Failed`                                                  |
| **Persisted store** | PostgreSQL (`orderingdb`) via EF Core + Marten event store                   | Azure Durable Task Scheduler (`finance-taskhub`) + Azure Storage host storage (no PostgreSQL)                         |
| **How to inspect**  | `GET /api/v1/orders/{id}` or `GET /api/v1/orders`                            | Durable Task orchestration custom status (`OrderId`, `Status`, `BasketDeleted`, `TimeoutRetryCount`, `FailureReason`) |

### Interpreting cross-service outcomes

- **Basket deletion succeeds:** Basket API publishes `BasketDeletedCompleteIntegrationEvent`. Finance sets `BasketDeleted = true` in its orchestration state and publishes `DeleteBasketCompleteCommand` to Ordering API. Ordering API logs the event and leaves the order status `New` until an explicit completion or cancellation request arrives.
- **Basket deletion fails:** Basket API publishes `BasketDeletedFailedIntegrationEvent`. Finance marks its orchestration `BasketDeletionFailed` and sends `DeleteBasketFailedCommand` to Ordering API. Ordering API soft-deletes the matching order (`order.Delete()`) if it exists, hiding it from standard reads without changing `Status` to `Cancelled`.
- **Finance retry timers expire:** `OrderOrchestrator` waits in a loop with a configured timer (`MaxRetryTimeout: 00:30:00`, `MaxAttempts: 3`). If an open orchestration exhausts its retries, Finance marks its own orchestration `Cancelled` and publishes `CancelOrderCommand` to Notification (when recipient details exist). Finance never calls Ordering API to cancel the commercial order, so Ordering can still report `New`.
- **Explicit order completion or cancellation:** When Ordering API accepts `PATCH /api/v1/orders/{orderId}/complete` or `PATCH /api/v1/orders/{orderId}/cancel`, it publishes `OrderStatusChangedToCompleteIntegrationEvent` or `OrderStatusChangedToCancelIntegrationEvent`. Finance transitions its orchestration to `Completed` or `Cancelled` and publishes `CompleteOrderCommand` or `CancelOrderCommand` to Notification.
- **Customer email sent or missing:** Notification is a stateless Kafka + MailKit + Redis idempotency worker. Sending or skipping an email never proves or alters an order's business status.

## Design trade-offs

| Decision                                                 | Benefits                                                                                            | Costs and limits                                                                                         |
| :------------------------------------------------------- | :-------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| **Independent Finance Durable Functions orchestration**  | Isolates long-running timers, retries, and compensations from Ordering API's transactional database | Finance orchestration status can diverge from Ordering `Status` after retry exhaustion                   |
| **Soft deletion on explicit basket-cleanup failure**     | Removes broken checkouts from active listings without recording a false customer cancellation       | Operators must inspect both Ordering visibility and Finance orchestration status to see the full picture |
| **Bounded retry window (`MaxAttempts: 3`, 30m timeout)** | Prevents orphaned orchestrations from running indefinitely                                          | Transient outages longer than the retry window require operational investigation                         |

## Alternatives considered

- **Letting Finance mutate Ordering `Status` directly on timeout:** Rejected because infrastructure timeout exhaustion is not an explicit commercial cancellation by a customer or administrator, and coupling the two writes breaks bounded-context ownership.
- **Persisting Finance saga state in PostgreSQL:** Rejected in favor of Azure Durable Task Scheduler (`finance-taskhub`), which natively manages durable timers, replay-safe orchestration history, and external event correlation for Azure Functions without maintaining a separate SQL schema.
