## 1. Context & Problem

During checkout, network timeouts, user double-clicks, concurrent sessions, or temporary cache outages can cause an Order creation attempt to fail or return a conflict. When callers cannot tell whether the Order was actually saved, immediately retrying with a new request identifier—or wiping temporary coordination keys—risks creating duplicate orders for the same customer. Support and operations teams need a safe, privacy-conscious runbook to resolve conflicts and lock failures without causing duplicate purchases.

## 2. Business Value

- **Prevents duplicate purchases:** Stops unsafe retries from creating multiple orders when an earlier checkout attempt actually succeeded.
- **Protects customer privacy:** Keeps Buyer addresses and personal information out of routine incident reports.
- **Maintains platform stability:** Prevents broad cache resets that would disrupt concurrent checkouts for other customers.

## 3. How It Works

**Common symptoms:**

- An Order creation attempt is rejected as a conflict for a given request identifier.
- A timeout or error leaves the caller unsure whether the Order was saved.
- Order creation fails while another checkout request for the same Buyer may be running.
- Cache availability affects duplicate-request markers or concurrency locks.

**Investigation & safe recovery flow:**

1. **Record minimal context:** Note the authenticated Buyer, timestamp, environment, and unique request identifier. Exclude Buyer addresses and other unnecessary personal details from incident reports.
2. **Check the authoritative Order record first:** Inspect the customer's authorized Order history or Order lookup before trying again. If the Order already exists, use its identifier and do not submit another creation request.
3. **Understand duplicate-request markers:** Ordering records a temporary one-hour request marker before running the creation logic. If a marker already exists, a repeat attempt with the same identifier is rejected as a conflict. Crucially, the marker only proves a request was received—it is not a saved response and does not prove the Order succeeded.
4. **Check Buyer-scoped concurrency locks:** When creation fails alongside another active checkout for the same Buyer, check for lock acquisition or release errors. This lock covers the Order write step, not the earlier Basket and Catalog reads.
5. **Rely on the database as truth:** Even when the cache layer is unavailable (affecting markers, locks, and cached responses), the Order database remains the authoritative source of saved Orders.
6. **Follow safe recovery rules:** If a marker exists with no visible Order, keep the original request identifier and wait for investigation or marker expiration. Never immediately retry with a new request identifier (which bypasses duplicate detection), and never broadly flush the cache or delete marker keys (which disrupts active checkouts).

## 4. Trade-offs & Lessons Learned

- **Pre-execution request marker vs. stored response replay:** Saving a one-hour marker before the handler runs reliably blocks identical retries, at the cost that an ambiguous failure leaves behind a marker without a cached response to replay.
- **Write-scoped locking vs. full-checkout locking:** Limiting the Buyer lock to the Order write phase keeps earlier Basket and Catalog lookups fast and uncontended, while requiring log correlation when concurrent requests overlap.
- **Fast cache coordination vs. database authority:** Using a cache for locks, markers, and response caching improves performance, provided operators always treat the relational Order database as the final source of truth.

## 5. Technical Reference

### Symptoms

- `POST /api/v1/orders` returns `409 Conflict` for an `x-request-id`.
- The caller timed out or received an error and does not know whether an Order
  was persisted.
- Order creation fails while another request for the same Buyer may be
  running.
- Redis availability affects request markers or lock acquisition.

### Diagnose

1. Record the authenticated Buyer, request timestamp, environment, and
   `x-request-id`. Do not share Buyer address or other unnecessary personal
   data in an incident report.
2. Check for an existing Order using the customer's authorized Order history
   or Order lookup before attempting another create request.
3. Interpret a conflict carefully. Ordering stores an idempotency marker
   before the endpoint handler runs, and an existing marker causes a
   conflict. The marker lasts one hour and records a request; it is not a
   cached response or proof that Order creation succeeded.
4. If Order creation fails while another create is active for the Buyer,
   check [[container\|order-cache]] and [[service\|order-api]] logs for
   Buyer-scoped distributed lock acquisition or release failures. The lock
   covers the Order write, not the earlier Basket and Catalog reads.
5. If Redis is unavailable, consider both coordination and response caching:
   Redis supports idempotency markers and creation locks as well as cached
   responses. [[container\|order-database]] remains the source of truth for
   persisted Orders.

### Recover safely

- If the Order exists, use its ID and do not submit another create request.
- If the marker exists but no Order is visible, retain the original
  `x-request-id` and wait for the request to be investigated or the marker to
  expire. The marker's existence alone does not establish whether the write
  completed.
- Do not immediately retry with a new request ID: that can bypass the existing
  marker and create a duplicate Order if the first write succeeded.
- Do not flush Redis or delete marker keys broadly. Doing so can interfere
  with concurrent Order creation and remove duplicate-request detection.
- If the outcome remains ambiguous, escalate with the Buyer scope,
  `x-request-id`, timestamp, and observed API response. Avoid sharing the
  marker payload or personal data unless required by the incident process.

  issues.
- Contact [[team\|platform-team]] for Redis availability or infrastructure
  issues.
