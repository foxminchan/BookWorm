This reference defines the mandatory contract, persistence, lifecycle, security, and test checks for pull requests modifying **Ordering API** (`ordering`) or its integration with **Finance** (`finance`), **Basket API** (`basket`), and **Catalog API** (`catalog`).

## Overview

| Property              | Value                                                                                                                                                                             |
| :-------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**             | Ordering bounded context (`Ordering API`, `Finance`)                                                                                                                              |
| **Source**            | `src/Services/Ordering/BookWorm.Ordering/`, `src/Services/Finance/BookWorm.Finance/`                                                                                              |
| **Protocol / format** | HTTP v1 (`/api/v1/orders`, `/api/v1/buyers`, `/api/v1/dashboard`), gRPC clients (`basket.v1`, `book.v1`), Kafka CloudEvents JSON (Wolverine)                                      |
| **Authentication**    | Microsoft Entra ID JWT (`customer` or `admin` roles; `ordering_read`, `ordering_write` scopes); admin-only for `DELETE /api/v1/orders/{id}` and `GET /api/v1/orders/{id}/summary` |

## Integration boundary overview

Ordering API reads Basket API and Catalog API over gRPC during checkout, persists accepted orders in PostgreSQL, coordinates idempotency and locks in Redis, and exchanges checkout and lifecycle messages with Finance over Kafka.

## Pre-merge verification checklist

Verify every affected area before merging a change to `BookWorm.Ordering`:

- [ ] **HTTP API v1 contracts:** Update OpenAPI v1 metadata and endpoint documentation for any change to `POST /api/v1/orders`, `GET /api/v1/orders`, `GET /api/v1/orders/{id}`, `GET /api/v1/orders/{id}/history`, `GET /api/v1/orders/{id}/summary`, `PATCH /api/v1/orders/{orderId}/complete`, `PATCH /api/v1/orders/{orderId}/cancel`, `DELETE /api/v1/orders/{id}`, buyer routes, or dashboard routes.
- [ ] **Kafka integration events:** Keep CloudEvents schemas and Pact contracts aligned for `UserCheckedOutIntegrationEvent` (`bookworm.{env}.ordering.user-checked-out`), `OrderStatusChangedToCompleteIntegrationEvent` (`bookworm.{env}.ordering.order-status-change-to-complete`), and `OrderStatusChangedToCancelIntegrationEvent` (`bookworm.{env}.ordering.order-status-change-to-cancel`), all partitioned by `OrderId`.
- [ ] **Basket cleanup handoff:** Verify Finance's `DeleteBasketCompleteCommand` (`bookworm.{env}.finance.delete-basket-complete`) and `DeleteBasketFailedCommand` (`bookworm.{env}.finance.delete-basket-failed`) handlers. Keep Basket API, Ordering API, and Finance ownership boundaries distinct.
- [ ] **Immutable purchase snapshot:** Preserve the rule that each `OrderItem` stores `BookId`, positive quantity, and checkout unit price (`PriceSale ?? Price`), and that order total equals the sum of recorded line totals. Later Catalog API price updates never rewrite an accepted order.
- [ ] **Strict order lifecycle:** Restrict business status transitions to `New` → `Completed` and `New` → `Cancelled`. Keep soft deletion (`IsDeleted`) and Finance orchestration state separate from order `Status`.
- [ ] **Persistence and projections:** Add EF Core migrations and update schema notes when modifying `Buyer`, `Order`, or `OrderItem` tables in `orderingdb` (PostgreSQL `snake_case`), Wolverine `wolverine` outbox/inbox tables, or Marten event streams (`OrderSummary`, `OrderSummaryView`).
- [ ] **Authorization and idempotency:** Preserve `customer` and `admin` policy boundaries, `PerUserRateLimit`, and `WithIdempotency()` (`x-request-id` required on `POST` and `PATCH`; Redis key `{METHOD}:{PATH}:{x-request-id}` with 3600-second TTL, deleted automatically on unhandled exceptions or `>= 500` responses).
- [ ] **Buyer-scoped write lock:** Keep the Redis distributed lock (`order-create:{userId}`, 1-minute timeout) around `Order` persistence so concurrent checkout requests for the same buyer cannot race.
- [ ] **Privacy and correlation:** Keep buyer street addresses and personal data out of routine logs and error payloads. Correlate checkout and saga traces by `OrderId` and W3C trace context without treating logs or emails as authoritative order status.

## Core invariants to test

| Invariant                         | Verification requirement                                                                                                                       | Owning code path                                                                              |
| :-------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------- |
| **Valid checkout inputs**         | Order creation fails when the basket is missing/empty or any `BookId` fails to resolve in Catalog API                                          | `src/Services/Ordering/BookWorm.Ordering/Features/Orders/Create/`                             |
| **Locked purchase total**         | Persisted order total equals the sum of recorded item unit prices (`PriceSale ?? Price`) multiplied by quantities                              | `src/Services/Ordering/BookWorm.Ordering/Domain/AggregatesModel/OrderAggregate/`              |
| **Terminal status immutability**  | Only a `New` order can transition to `Completed` or `Cancelled`; neither terminal state can reopen or switch                                   | `src/Services/Ordering/BookWorm.Ordering/Domain/AggregatesModel/OrderAggregate/`              |
| **Cleanup vs. status separation** | `DeleteBasketCompleteCommand` leaves status `New`; `DeleteBasketFailedCommand` soft-deletes the order without changing status to `Cancelled`   | `src/Services/Ordering/BookWorm.Ordering/IntegrationEvents/EventHandlers/`                    |
| **Finance timeout isolation**     | Finance timeout exhaustion (`MaxAttempts: 3`, 30-minute timer) cancels Finance's orchestration in `finance-taskhub`, never Ordering's `Status` | `src/Services/Finance/BookWorm.Finance/Features/Orders/Orchestration/`                        |
| **Idempotency and lock safety**   | Duplicate `x-request-id` requests return `409 Conflict`, and concurrent creations for the same buyer cannot bypass `order-create:{userId}`     | `src/Services/Ordering/BookWorm.Ordering/Infrastructure/Filters/IdempotencyEndpointFilter.cs` |

## Verification commands

Run formatting, unit tests, architecture tests, and Pact contract tests from the repository root before opening a pull request:

<CodeGroup>

```bash
mise run format
mise run build
mise run test
```

</CodeGroup>

To run targeted Ordering unit tests during local iteration:

<CodeGroup>

```bash
dotnet test src/Services/Ordering/BookWorm.Ordering.UnitTests/BookWorm.Ordering.UnitTests.csproj
```

</CodeGroup>

Verify that both Ordering–Finance Pact suites pass when modifying integration events or commands (`tests/pacts/Ordering-Finance.json` and `tests/pacts/Finance-Ordering.json`).
