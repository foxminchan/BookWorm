This reference specifies which stores own authoritative order data, what **Ordering API** (`ordering`) snapshots at checkout, which views and caches are derived or transient, and how **Finance** (`finance`) maintains separate workflow state.

## Overview

| Property                       | Value                                                                                                                              |
| :----------------------------- | :--------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**                      | Ordering bounded context (`Ordering API`, `Finance`)                                                                               |
| **Primary store**              | PostgreSQL (`orderingdb`): EF Core relational tables (`snake_case`), Marten event store, Wolverine `wolverine` outbox/inbox schema |
| **Coordination & cache store** | Redis (`redis`): FusionCache L1/L2, HTTP idempotency markers, buyer write locks, integration event idempotency guards              |
| **Finance workflow store**     | Azure Durable Task Scheduler (`durable-task-scheduler` / `finance-taskhub`) + Azure Storage host storage (no PostgreSQL database)  |
| **Source**                     | `src/Services/Ordering/BookWorm.Ordering/`, `src/Services/Finance/BookWorm.Finance/`                                               |

## Sources of truth matrix

| Data                                  | Backing resource                                         | Owning service | Role and consistency model                                                                                                                                                                                   |
| :------------------------------------ | :------------------------------------------------------- | :------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Buyers, Orders, OrderItems**        | PostgreSQL `orderingdb` (EF Core)                        | Ordering API   | Authoritative transactional system of record for buyer profiles, accepted orders, locked purchase items, and `Status` (`New`, `Completed`, `Cancelled`).                                                     |
| **Order event streams & projections** | PostgreSQL `orderingdb` (Marten, `DaemonLockId = 44444`) | Ordering API   | Authoritative event stream for order audit history (`GET /api/v1/orders/{id}/history`) and derived live/async projections (`OrderSummary`, `OrderSummaryView`); never replaces the `Order` aggregate.        |
| **Outbox and inbox messages**         | PostgreSQL `orderingdb` (`wolverine` schema)             | Ordering API   | Durable transactional messaging buffer guaranteeing atomic commit with order mutations.                                                                                                                      |
| **Idempotency markers & write locks** | Redis (`redis`)                                          | Ordering API   | Transient coordination state: HTTP request markers (`{METHOD}:{PATH}:{x-request-id}`, 3600s TTL), buyer creation locks (`order-create:{userId}`, 60s TTL), and 24-hour integration event idempotency guards. |
| **Catalog & dashboard caches**        | Redis (`redis`, FusionCache)                             | Ordering API   | Non-authoritative read-through caches reducing read latency; safe to invalidate without losing orders.                                                                                                       |
| **Active shopping basket**            | Redis (`redis`, key `basket:{userId}`)                   | Basket API     | Mutable pre-order customer intent; read once over gRPC during checkout and deleted asynchronously afterward.                                                                                                 |
| **Catalog books & current prices**    | PostgreSQL `catalogdb`                                   | Catalog API    | Authoritative live product catalog; consulted over gRPC during checkout and optionally for display title enrichment on reads, never retroactively rewriting accepted order totals.                           |
| **Post-checkout orchestration state** | Azure Durable Task Scheduler (`finance-taskhub`)         | Finance        | Independent orchestration state (`Placed`, `Completed`, `Cancelled`, `BasketDeletionFailed`, `Failed`) correlated by `OrderId`; never authoritative for Ordering's `Status`.                                 |

## Checkout snapshot rules

During `POST /api/v1/orders`, Ordering API performs these deterministic snapshot steps:

1. Reads the authenticated customer's basket over gRPC (`basket.v1.BasketGrpcService/GetBasket`).
2. Resolves every distinct `BookId` over gRPC (`book.v1.BookGrpcService/GetBooks`). Missing books fail validation with `404 Not Found` and abort order creation.
3. Selects each item's checkout unit price using `book.PriceSale ?? book.Price` (active sale price if set, otherwise regular price).
4. Persists immutable `OrderItem` records (`BookId`, `Quantity`, `Price`) under a buyer-scoped Redis lock (`order-create:{userId}`, 1-minute timeout) and computes the order total from those recorded line totals.

Subsequent edits to Basket API or Catalog API prices never modify an accepted order's items or total. Read endpoints may enrich output with current book titles for display, but stored purchase prices remain immutable.

## Redis coordination boundaries

Redis (`redis`) supports both performance caching and active write coordination in Ordering API:

| Key pattern or mechanism            | TTL                         | Behavior and failure semantics                                                                                                                                                                                                                    |
| :---------------------------------- | :-------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `{METHOD}:{PATH}:{x-request-id}`    | 3600s (1 hour)              | Created atomically (`When.NotExists`) before `POST`/`PATCH` handlers run. Duplicate requests receive `409 Conflict`. Automatically deleted if the handler throws an exception or returns `>= 500`. Does **not** store a replayable response body. |
| `order-create:{userId}`             | 60s (1 minute)              | Distributed lock acquired after Basket/Catalog gRPC lookups, guarding only the PostgreSQL write. Contention throws `InvalidOperationException` (`"Other process is already creating an order"`).                                                  |
| `IIntegrationEventIdempotencyGuard` | 24 hours                    | FusionCache-backed guard deduplicating inbound Kafka commands such as `DeleteBasketFailedCommand` by `message.Id`.                                                                                                                                |
| FusionCache L1/L2 entries           | Configurable (2h fail-safe) | Non-authoritative response caching for Catalog lookups and dashboard reads.                                                                                                                                                                       |

:::warning
Do not flush Redis broadly during incidents. Flushing removes active HTTP idempotency markers and buyer write locks alongside read caches, exposing concurrent checkouts to duplicate order creation.
:::

## Ordering vs. Finance boundary rules

- **Ordering owns business status:** Only explicit calls to `POST /api/v1/orders`, `PATCH /api/v1/orders/{orderId}/complete`, and `PATCH /api/v1/orders/{orderId}/cancel` change an order's `Status`.
- **Basket cleanup success:** `DeleteBasketCompleteCommand` is logged by Ordering API; the order remains `New`.
- **Basket cleanup failure:** `DeleteBasketFailedCommand` calls `order.Delete()` (soft delete), hiding the order from standard queries without setting `Status` to `Cancelled`.
- **Finance retry exhaustion:** When Finance reaches `MaxAttempts: 3` (30-minute timer intervals), Finance transitions its own orchestration status in `finance-taskhub` to `Cancelled` and publishes `CancelOrderCommand` to Notification. Finance never calls Ordering API to cancel the order.
- **Email notifications:** Notification is a stateless worker with no order authority; email delivery never proves an order changed status.
