## Purpose & Scope

This lifecycle view defines the authoritative business states of an [[entity|order]] owned by [[service|order-api]] within the [[domain|ordering]] subdomain. Engineering, product, and operations teams should use this reference to distinguish core order status transitions from downstream [[service|order-orchestration]] coordination, email delivery, and technical soft deletion.

## Key Takeaways & Boundaries

- **Single status authority**: Only [[service|order-api]] transitions an [[entity|order]] from **New** (created via [[command|CreateOrder]]) to **Completed** ([[command|CompleteOrder]]) or **Cancelled** ([[command|CancelOrder]]).
- **Irreversible terminal states**: Once an order reaches **Completed** or **Cancelled**, it cannot be reopened; any subsequent adjustment requires a separate compensating process.
- **Explicit integration events**: Accepting an order emits [[event|UserCheckedOutIntegrationEvent]], while terminal transitions emit [[event|OrderStatusChangedToCompleteIntegrationEvent]] or [[event|OrderStatusChangedToCancelIntegrationEvent]].
- **Decoupled orchestration and notifications**: [[service|order-orchestration]] and [[service|notification-api]] react to order events but never own or mutate business order status.

:::warning
**Do not conflate orchestration timeouts, email delivery, or soft deletion with a Cancelled order.**

- When [[service|order-orchestration]] exhausts its bounded retry budget, it cancels its own coordination workflow and may request a cancellation email via [[command|CancelOrderCommand]]—without cancelling the [[entity|order]] in [[service|order-api]].
- When [[service|order-api]] handles [[command|DeleteBasketFailedCommand]], it soft-deletes the order record while preserving its existing **New** business status.
  :::
