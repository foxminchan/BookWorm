Finance (`finance`, also called Order Orchestration) is an internal Azure Functions isolated worker in the Ordering bounded context that runs one durable `OrderOrchestrator` saga instance per Order using Azure Durable Task Scheduler (DTS). It coordinates post-checkout basket cleanup retries and order lifecycle email commands over Kafka; it does **not** process payments, expose HTTP/gRPC endpoints, or use PostgreSQL.

| **Orchestration state**  | Azure Durable Task Scheduler (`durable-task-scheduler` / `finance-taskhub`, `Consumption` SKU via `Infra/durable-task-scheduler.bicep` injecting `DTS_CONNECTION_STRING` and `TASKHUB_NAME`) + Azure Storage host state (`storage`) — **no PostgreSQL, no EF Core** |
| **Messaging**            | Kafka triggers + Wolverine Kafka publisher (CloudEvents JSON, partitioned by `OrderId`)                                                                                                                                                                             |
| **Authentication**       | Internal worker (no public auth); Azure Managed Identity RBAC in Azure                                                                                                                                                                                              |

:::note
Despite the Finance name, this service does **not** authorize or settle payments. [[service|order-api]] remains the sole authority for Order aggregates and business status; Finance owns only coordination saga state.
:::

## Runtime architecture

Finance consumes checkout, basket-cleanup, and Order status events via five Kafka triggers, correlates each event to `OrderOrchestrator` keyed by `OrderId` inside `finance-taskhub`, and dispatches outbound Kafka commands via durable activity functions.

## Kafka triggers and orchestration matrix

Each `OrderOrchestrator` instance is keyed by `OrderId.ToString()`, ignoring duplicate checkout events and routing external events to the active orchestration.

| Trigger / timer                | Inbound event & Kafka topic                                                                                         | Orchestrator state transition                                     | Outbound Kafka command & topic                                                                                        |
| :----------------------------- | :------------------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------- |
| `UserCheckedOutTrigger`        | [[event\|UserCheckedOutIntegrationEvent]] (`bookworm.{env}.ordering.user-checked-out`)                              | Creates instance in `Placed`; schedules `30`-minute timeout       | [[command\|PlaceOrderCommand]] → `bookworm.{env}.finance.place-order`                                                 |
| `BasketDeletedCompleteTrigger` | [[event\|BasketDeletedCompleteIntegrationEvent]] (`bookworm.{env}.basket.delete-complete`)                          | Remains open waiting for explicit Order status                    | [[command\|DeleteBasketCompleteCommand]] → `bookworm.{env}.finance.delete-basket-complete`                            |
| `BasketDeletedFailedTrigger`   | [[event\|BasketDeletedFailedIntegrationEvent]] (`bookworm.{env}.basket.delete-failed`)                              | Marks `BasketDeletionFailed` and closes instance                  | [[command\|DeleteBasketFailedCommand]] → `bookworm.{env}.finance.delete-basket-failed`                                |
| `OrderCompletedTrigger`        | [[event\|OrderStatusChangedToCompleteIntegrationEvent]] (`bookworm.{env}.ordering.order-status-change-to-complete`) | Marks `Completed` and closes instance                             | [[command\|CompleteOrderCommand]] → `bookworm.{env}.finance.complete-order` (if name & email present)                 |
| `OrderCancelledTrigger`        | [[event\|OrderStatusChangedToCancelIntegrationEvent]] (`bookworm.{env}.ordering.order-status-change-to-cancel`)     | Marks `Cancelled` and closes instance                             | [[command\|CancelOrderCommand]] → `bookworm.{env}.finance.cancel-order` (if name & email present)                     |
| Durable timeout timer          | `MaxRetryTimeout` (`30` minutes)                                                                                    | Retries up to `3` total attempts; on exhaustion marks `Cancelled` | Reissues [[command\|PlaceOrderCommand]]; on exhaustion sends [[command\|CancelOrderCommand]] if contact details exist |

## Retry configuration and invariants

- **Retry policy (`OrderStateMachineSettings`):** Maximum `3` attempts spaced `30` minutes apart (`MaxRetryTimeout`).
- **Shared placement channel trade-off:** Both [[service|basket-api]] and [[service|notification-api]] consume `bookworm.{env}.finance.place-order`. When a durable timeout reissues `PlaceOrderCommand`, both consumers receive the retry, which can generate an additional email.
- **Separate lifecycle boundary:** Successful basket deletion does not complete an Order, and retry exhaustion in Finance marks the _orchestration_ `Cancelled` without calling Ordering API to cancel the Order aggregate.
- **Fire-and-forget notifications:** Publishing `PlaceOrderCommand`, `CompleteOrderCommand`, or `CancelOrderCommand` requests email delivery from Notification; Finance receives no delivery confirmation event.
