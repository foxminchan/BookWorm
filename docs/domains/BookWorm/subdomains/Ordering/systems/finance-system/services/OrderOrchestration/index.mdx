## 1. Context & Problem

Post-checkout coordination spans multiple asynchronous events and waiting periods: a customer checks out, the submitted basket must be deleted, missing cleanup outcomes must be retried safely, and final Order status changes must trigger customer emails. Handling these steps with disconnected message handlers would make timeouts, deduplication, and correlation across each Order fragile.

Order Orchestration serves as Finance System's dedicated workflow engine to track one durable coordination instance per Order from checkout through final outcome. Despite the Finance name, this service does **not** authorize or settle payments; Ordering owns the Order aggregate and business status, while Order Orchestration owns only the coordination workflow state.

## 2. Business Value

- **Duplicate-safe Order tracking:** Assigning one workflow instance per Order ID ensures repeated checkout notices do not create conflicting workflows for the same purchase.
- **Durable long-running reliability:** Persisted workflow state and timers survive service restarts and temporary downstream slowdowns.
- **Clear separation of responsibilities:** Basket cleanup, Order lifecycle authority, and email delivery stay cleanly isolated in their respective systems.
- **Controlled retry behavior:** Bounded, spaced retries handle transient cleanup delays without endlessly hammering downstream services.

## 3. How It Works

Order Orchestration listens for checkout, basket-cleanup, and Order-status events, routes each event to the matching Order's workflow instance, and dispatches follow-up requests through durable tasks:

| Responsibility                 | Behavior                                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Start checkout coordination    | Save a new workflow in a **Placed** state on checkout, send the initial basket-cleanup request, and schedule a follow-up timer.                        |
| Retry missing cleanup outcomes | Reissue the basket-cleanup request when a scheduled timeout fires, up to 3 total attempts spaced 30 minutes apart.                                     |
| Report basket outcomes         | Forward cleanup success or failure to Ordering without treating either outcome as an Order status change.                                              |
| Notify on Order status changes | Close the workflow and request completion or cancellation emails when Ordering reports an explicit final Order status and contact details are present. |
| Handle retry exhaustion        | Mark the workflow **Cancelled** and request a cancellation email if recipient details are available, without calling Ordering to cancel the Order.     |

## 4. Trade-offs & Lessons Learned

- **Duplicate processing on shared placement channel:** Because both Basket (for cleanup) and Notification (for the new-order email) consume the same initial placement request, timeout retries can repeat both consumers' work; this service does not provide exactly-once email delivery.
- **Workflow state is not Order truth:** Successful basket deletion does not complete the Order, and a cleanup failure or retry timeout in Order Orchestration is not equivalent to Ordering cancelling an Order.
- **Fire-and-forget email requests:** Publishing a notification command requests email processing from Notification, but does not confirm mail-server submission or final delivery.
- **Dedicated orchestration store:** Persisting durable orchestration state and timers in a managed task hub replaced the earlier general database and saga store, streamlining timer durability and Order-level correlation.

### Message Handling Matrix

| Input                                                   | Processing                                                                                                                                           |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| [[event\|UserCheckedOutIntegrationEvent]]               | Creates an orchestration/saga instance in **Placed** state correlated by Order ID; publishes [[command\|PlaceOrderCommand]] and schedules a timeout. |
| [[event\|BasketDeletedCompleteIntegrationEvent]]        | Sends [[command\|DeleteBasketCompleteCommand]] to Ordering. The saga stays open for an explicit Order status event.                                  |
| [[event\|BasketDeletedFailedIntegrationEvent]]          | Marks the saga **BasketDeletionFailed**, completes it, and sends [[command\|DeleteBasketFailedCommand]] to Ordering.                                 |
| [[event\|OrderStatusChangedToCompleteIntegrationEvent]] | Marks the saga **Completed**, completes it, and sends [[command\|CompleteOrderCommand]] if name and email are present.                               |
| [[event\|OrderStatusChangedToCancelIntegrationEvent]]   | Marks the saga **Cancelled**, completes it, and sends [[command\|CancelOrderCommand]] if name and email are present.                                 |
| Scheduled timeout                                       | Retries [[command\|PlaceOrderCommand]] until the configured limit; after exhaustion, cancels the saga and may send [[command\|CancelOrderCommand]].  |

Note: [[command|PlaceOrderCommand]] is a shared Finance channel consumed by both Basket and Notification.

### Runtime, Triggers & Configuration

- **Host & scheduler:** Azure Functions isolated worker service powered by **Azure Durable Task Scheduler (DTS)** using `financeTaskHub`, replacing the previous PostgreSQL and Wolverine saga store.
- **Kafka triggers:** `UserCheckedOutTrigger`, `BasketDeletedCompleteTrigger`, `BasketDeletedFailedTrigger`, `OrderCompletedTrigger`, and `OrderCancelledTrigger`.
- **Orchestrator & correlation:** Coordinates one durable `OrderOrchestrator` instance per Order keyed by `@event.OrderId.ToString()`, ignoring duplicate checkout events and routing external events to the active instance. Outbound commands are published via durable activity functions.
- **Retry settings:** `OrderStateMachineSettings` configures a maximum attempt value of `3` and a timeout delay of 30 minutes (`MaxRetryTimeout`).
- **Contract spec:** AsyncAPI V1 (`asyncapi-v1.yml`).
