`UserCheckedOutIntegrationEvent` (v1.0.0) reports that Ordering API accepted and persisted a new `Order` during customer checkout. Finance consumes this event to start an `OrderOrchestrator` Durable Task saga instance, which dispatches `PlaceOrderCommand` to Basket API (for basket cleanup) and Notification (for order confirmation email). Receiving this event confirms order placement only, not basket cleanup or order completion.

## Overview

| Property              | Value                                                                                                |
| :-------------------- | :--------------------------------------------------------------------------------------------------- |
| **Owner**             | Ordering bounded context (`Ordering API`)                                                            |
| **Producer**          | [[service\|order-api]]                                                                               |
| **Consumer**          | [[service\|order-orchestration]] (`OrderOrchestrator`)                                               |
| **Source**            | `src/Services/Ordering/BookWorm.Ordering/IntegrationEvents/Events/UserCheckedOutIntegrationEvent.cs` |
| **Protocol / format** | Kafka + CloudEvents JSON (Wolverine)                                                                 |
| **Kafka topic**       | `bookworm.{env}.ordering.user-checked-out` (where `{env}` is the kebab-case environment name)        |
| **Message identity**  | `BookWorm.Contracts.UserCheckedOutIntegrationEvent`                                                  |
| **Partition key**     | `OrderId` (preserves per-order saga ordering on Kafka)                                               |
| **Outbox**            | Wolverine PostgreSQL outbox (`orderingdb`, `wolverine` schema) with EF Core transactional middleware |

## Parameters and fields

The schema below defines the camelCase JSON `data` payload carried inside the CloudEvents envelope (`additionalProperties: false` in JSON Schema). All seven properties are present in the serialized contract, including nullable `fullName` and `email`.

| Name           | Type                 | Required | Default                 | Constraints                                              | Description                                                                                     |
| :------------- | :------------------- | :------- | :---------------------- | :------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| `id`           | `string` (UUID)      | Yes      | `Guid.CreateVersion7()` | UUID v7 inherited from `IntegrationEvent`                | Unique identifier for this integration event instance.                                          |
| `creationDate` | `string` (date-time) | Yes      | `DateTime.UtcNow`       | ISO 8601 UTC timestamp inherited from `IntegrationEvent` | UTC timestamp when Ordering API created the event.                                              |
| `orderId`      | `string` (UUID)      | Yes      | —                       | Valid UUID; also used as Kafka partition key             | Identifier of the accepted `Order`.                                                             |
| `basketId`     | `string` (UUID)      | Yes      | —                       | Valid UUID (currently populated from `Order.BuyerId`)    | Buyer-linked basket reference supplied by Ordering `EventMapper`.                               |
| `fullName`     | `string \| null`     | Yes      | `null`                  | Nullable string                                          | Customer full name when available on the buyer record.                                          |
| `email`        | `string \| null`     | Yes      | `null`                  | Nullable email format                                    | Customer email address when available; used by Finance to decide whether to send notifications. |
| `totalMoney`   | `number` (`decimal`) | Yes      | —                       | Non-negative monetary amount                             | Total purchase amount associated with the accepted order.                                       |

:::note
The current Ordering `EventMapper` populates `basketId` with the order's `BuyerId`. Downstream consumers must not treat `basketId` as an independently resolved Basket API record.
:::

## Error handling and delivery guarantees

| Condition                              | Behavior                                                                                                                                  | Recovery behavior                                                                                   |
| :------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| `email` or `fullName` is `null`        | Payload remains valid; Finance still coordinates basket cleanup and evaluates `order.CanSendNotification` before emitting email commands. | Consumers must tolerate `null` contact fields without failing deserialization.                      |
| Transient broker or Durable Task error | Wolverine outbox guarantees at-least-once publication from `orderingdb`; Finance starts the orchestration idempotently per `OrderId`.     | Inspect Durable Task Scheduler (`finance-taskhub`) and `bookworm.{env}.ordering.dead-letter-queue`. |
| Contract mismatch                      | Caught in CI by Pact consumer/provider verification.                                                                                      | Verify against `tests/pacts/Finance-Ordering.json`.                                                 |
