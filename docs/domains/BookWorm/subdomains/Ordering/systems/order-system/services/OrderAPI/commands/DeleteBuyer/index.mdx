The `DeleteBuyer` command (`DELETE /api/v1/buyers/{id}`) permanently removes a `Buyer` profile from **Ordering API** (v1.0.0). Access is restricted to callers holding the Microsoft Entra ID `admin` role, and external callers reach this endpoint through the YARP **API Gateway** at `/ordering/api/v1/buyers/{id}`.

## Parameters and fields

### Request parameters

`DeleteBuyer` accepts no request body and requires no `x-request-id` header.

| Name | Type            | Required | Default | Constraints                          | Description                                       |
| :--- | :-------------- | :------- | :------ | :----------------------------------- | :------------------------------------------------ |
| `id` | `string` (UUID) | Yes      | —       | Path parameter; valid `BuyerId` UUID | Unique identifier of the buyer profile to delete. |

### Response

`204 No Content` with an empty response body confirms the buyer profile was deleted.

## Behavior and side effects

- **Permanent hard delete:** Unlike `Order` (which implements `ISoftDelete`), `Buyer` does not implement `ISoftDelete`. `DeleteBuyerHandler` fetches the entity via `repository.GetByIdAsync((Guid)request.Id, cancellationToken)`, throws `NotFoundException` (`404 Not Found`) if absent, calls `repository.Delete(buyer)`, and commits inside a `[Transactional]` unit of work on PostgreSQL (`orderingdb`).
- **No events emitted:** Deleting a buyer raises no domain events and publishes no Kafka integration events.
- **Orders foreign-key relationship:** `BuyerConfiguration` configures `Buyer.Orders` with `OnDelete(DeleteBehavior.SetNull)`, while `OrderConfiguration` configures `Order.BuyerId` as `IsRequired()`.

The initial migration and current model snapshot define `orders.buyer_id` as non-nullable while the foreign key uses `ON DELETE SET NULL`. Deleting a buyer with orders therefore attempts to write `NULL` into a non-nullable column and is expected to fail with a database constraint error; the global handler maps unhandled persistence exceptions to HTTP `500`. This is a schema-derived expectation, not a live PostgreSQL test.

## Error responses

| Code / status               | Condition                                                                              | Recovery behavior                                                                  |
| :-------------------------- | :------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------- |
| `400 Bad Request`           | Path parameter `{id}` is not a valid UUID                                              | Supply a valid `BuyerId` UUID; do not retry unchanged.                             |
| `401 Unauthorized`          | Missing, expired, or invalid Entra ID bearer token                                     | Acquire a fresh Entra ID access token and retry.                                   |
| `403 Forbidden`             | Authenticated caller lacks the `admin` role or `ordering_read`/`ordering_write` scopes | Authenticate with an `admin` token that includes the required scopes.              |
| `404 Not Found`             | No buyer profile exists with the specified `{id}` (including repeat delete attempts)   | Verify the buyer identifier; treat as already absent if retrying a prior deletion. |
| `429 Too Many Requests`     | Caller exceeded `PerUserRateLimit` or global rate limits                               | Wait for the `Retry-After` header interval before retrying.                        |
| `500 Internal Server Error` | Unhandled database or constraint error                                                 | Inspect Ordering API logs and check whether dependent orders reference the buyer.  |
