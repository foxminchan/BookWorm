## 1. Context & Problem

Customers reviewing their purchase history and administrators monitoring store activity need to browse orders cleanly without retrieving every historical order at once, while enforcing strict privacy boundaries so shoppers only see their own orders.

## 2. Business Value

- **Data privacy by default**: Non-administrator callers are automatically restricted to their own [[entity|order]] records, preventing unauthorized cross-customer visibility.
- **Targeted order lookup**: Optional filtering by order status and buyer helps customers track open orders and enables staff to focus on specific lifecycle stages or accounts.
- **Predictable error handling**: Invalid filter values are caught immediately with clear validation feedback rather than returning misleading results.

## 3. How It Works

1. An authenticated caller requests a page of [[entity|order]] summaries, optionally specifying page size, page number, an order status filter (`New`, `Cancelled`, or `Completed`), or a buyer filter.
2. If paging preferences are omitted, the service applies standard default page settings.
3. Ordering enforces access scope: standard callers always receive only orders belonging to their own authenticated buyer profile, whereas administrators can filter across buyers.
4. If any filter or paging input is invalid, the service rejects the request with validation details; otherwise, it returns the matching page of order summaries containing identifier, date, total amount, and status.

## 4. Trade-offs & Lessons Learned

- **Server-enforced buyer scoping**: Scoping buyer filtering on the server for non-administrators guarantees privacy even if a caller supplies another buyer identifier, while requiring explicit administrative privileges for cross-customer queries.
- **Compact summary payload**: Returning order summaries (identifier, date, total, and status) rather than full line-item details keeps list views fast, though callers must retrieve individual orders when line items are needed.
- **Flat page response without total counts**: Returning a direct list of summaries keeps payloads lean, meaning client interfaces must infer pagination boundaries from returned item counts.

## 5. Technical Reference

- **Endpoint**: `GET /api/v1/orders`
- **Status codes**: `200`, `400`
- **Entities**: [[entity|order]]

### Query parameters and response

| Parameter   | Description                                                                                   | Default |
| ----------- | --------------------------------------------------------------------------------------------- | ------- |
| `PageIndex` | Page number to return.                                                                        | `1`     |
| `PageSize`  | Number of results per page.                                                                   | `20`    |
| `Status`    | Optional Order status filter: `New`, `Cancelled`, or `Completed`.                             | None    |
| `BuyerId`   | Optional Buyer identifier filter. Non-administrators are scoped to their authenticated Buyer. | None    |

The OpenAPI contract documents the `200 OK` response as a JSON array of
`OrderDto` values containing ID, date, total, and status. `400 Bad Request`
returns validation problem details.

### Query using CURL

<CodeGroup dropdown>

```sh list-orders.sh
curl -H "Authorization: Bearer <access-token>" \
  "https://api.example.com/api/v1/orders?PageIndex=1&PageSize=20&Status=New"
```
