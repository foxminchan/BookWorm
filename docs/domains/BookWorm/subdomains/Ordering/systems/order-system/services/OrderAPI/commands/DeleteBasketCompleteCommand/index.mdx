`DeleteBasketCompleteCommand` (v1.0.0) is a Kafka integration command published by **Finance** (Azure Functions + Azure Durable Task Scheduler `OrderOrchestrator`) to inform **Ordering API** that post-checkout basket cleanup succeeded. **Ordering API** logs the outcome for operational visibility without modifying the order's business status.

## Overview

| Property              | Value                                                                                                                                                                                                                                                                                                                                         |
| :-------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**             | Ordering bounded context — produced by [[service\|order-orchestration]], consumed by [[service\|order-api]]                                                                                                                                                                                                                                   |
| **Source**            | `src/Services/Ordering/BookWorm.Ordering/IntegrationEvents/Events/DeleteBasketCompleteCommand.cs`, `IntegrationEvents/EventHandlers/DeleteBasketCompleteCommandHandler.cs`, `src/Services/Finance/BookWorm.Finance/Features/Orders/BasketDeletion/PublishDeleteBasketCompleteActivity.cs`, `Orchestration/Steps/BasketDeletedCompleteStep.cs` |
| **Protocol / format** | Kafka + CloudEvents JSON (`CloudEventsOnlyKafkaMapper`, Wolverine)                                                                                                                                                                                                                                                                            |
| **Kafka topic**       | `bookworm.{env}.finance.delete-basket-complete` (where `{env}` is the kebab-case environment name)                                                                                                                                                                                                                                            |
| **Partition key**     | `OrderId` (preserves per-order message ordering on Kafka)                                                                                                                                                                                                                                                                                     |
| **Authentication**    | Internal Kafka broker transport (no HTTP endpoint or Microsoft Entra ID user token)                                                                                                                                                                                                                                                           |
| **Contract test**     | `tests/pacts/Ordering-Finance.json`                                                                                                                                                                                                                                                                                                           |

:::note
`DeleteBasketCompleteCommand` is distinct from [[event|BasketDeletedCompleteIntegrationEvent]]. **Basket API** publishes `BasketDeletedCompleteIntegrationEvent` to **Finance**; **Finance**'s Durable Functions `OrderOrchestrator` then publishes `DeleteBasketCompleteCommand` to **Ordering API**.
:::

## Behavior and side effects

- **Producer flow (Finance Durable Functions):** When `OrderOrchestrator` receives `BasketDeletedCompleteIntegrationEvent`, `BasketDeletedCompleteStep` marks the basket deleted in orchestration state, registers `PublishDeleteBasketFailedActivity` as a LIFO Saga compensation (in case a later orchestration step fails), and calls `PublishDeleteBasketCompleteActivity` (Durable Functions retry policy: 3 attempts, 5-second initial interval, 2.0 backoff coefficient) to publish `DeleteBasketCompleteCommand` over Wolverine Kafka.
- **Consumer flow (Ordering API):** `DeleteBasketCompleteCommandHandler` (`[WolverineHandler]`) writes a structured `LogLevel.Information` entry (`EventId = 0`, `LogBasketDeletionCompleted`: `"Basket deletion completed for Order {OrderId}, Amount: {TotalMoney}"`) with `orderId` annotated with `[SensitiveData]` for log redaction.
- **No order state mutation:** The handler performs no PostgreSQL write, leaves `Order.Status` unchanged, and does not wrap execution in `IIntegrationEventIdempotencyGuard` because logging is side-effect-free.

## Error responses

| Code / status                                  | Condition                                                                   | Recovery behavior                                                                                                                                                                           |
| :--------------------------------------------- | :-------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Activity publish failure (**Finance**)         | Transient Kafka broker failure during `PublishDeleteBasketCompleteActivity` | Durable Functions retries up to 3 times (5s initial delay, 2.0 backoff); if all retries fail, `OrderOrchestrator` catches `TaskFailedException` and executes LIFO `OrderSagaCompensations`. |
| Consumer processing failure (**Ordering API**) | Deserialization error or unexpected handler exception                       | Wolverine retries with cooldown (`50ms`, `250ms`, `1s` with full jitter) and routes persistent failures to `bookworm.{env}.ordering.dead-letter-queue`.                                     |
| Duplicate delivery                             | Kafka at-least-once redelivery of the same command                          | Handler logs the message again with no database or status side effects.                                                                                                                     |
