## Service Responsibility & Boundary

Order API is the system of record within the [[domain|ordering]] domain for [[entity|buyer]] profiles, accepted [[entity|order]] aggregates, purchase-time [[entity|order-item]] price snapshots, and Order lifecycle statuses (`New`, `Completed`, `Cancelled`). It serves versioned HTTP endpoints and Server-Sent Events (SSE) backoffice dashboards, queries [[service|basket-api]] and [[service|catalog-api]] over gRPC during checkout, and delegates post-checkout basket cleanup and email coordination to [[service|order-orchestration]] over Kafka.

| **Runtime Style**                         | REST API, SSE Dashboard Stream, gRPC Client, and Async Kafka Producer/Consumer                                                                                                                       |
| **Public / Gateway Exposure**             | Yes via API Gateway                                                                                                                                                                                  |

| **Owned Data Store(s)**                   | [[container\|order-database]] (relational, event-sourced history, and transactional outbox), [[container\|order-cache]] (distributed locks, idempotency markers, and dashboard cache)                |
| **Key Resilience / Idempotency Pattern**  | 1-hour `x-request-id` idempotency markers, buyer-scoped distributed write locks, per-user rate limiting, and dead-letter routing on [[channel\|bookworm.&#123;env&#125;.ordering.dead-letter-queue]] |

## Contracts & Data Ownership

Order API owns [[entity|buyer]], [[entity|order]], and [[entity|order-item]] in [[container|order-database]] and uses [[container|order-cache]] for checkout concurrency locks, idempotency markers, and short-lived dashboard caching.

:::note
Every new Order starts in `New` status with line totals locked to active Catalog prices (sale price when set, otherwise regular price). Later Catalog price edits never rewrite accepted Orders, and soft-deletion on failed basket cleanup preserves audit records without altering business status.
:::

:::warning
State-changing Order operations require an `x-request-id` idempotency header. Duplicate keys within the 1-hour idempotency window return `409 Conflict`—callers should inspect existing Order status before generating a new idempotency key.
:::

<Accordion title="Event Sourcing & Downstream Coordination">
	- **Order event stream:** Domain events append to an event stream in [[container|order-database]]
	to support chronological order history and time-travel summary views. - **Lifecycle separation:**
	Completing or cancelling an Order is permitted only from `New` status; receiving
	[[command|DeleteBasketCompleteCommand]] never auto-completes an Order, and
	[[command|DeleteBasketFailedCommand]] soft-deletes the Order without changing its business status.
</Accordion>
