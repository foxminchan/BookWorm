Ordering API (`ordering`) is the system of record in the Ordering bounded context for Buyer profiles, accepted Orders, purchase-time price snapshots, and Order lifecycle statuses (`New`, `Completed`, `Cancelled`). It exposes authenticated HTTP `v1` endpoints for Commerce and Backoffice (including Server-Sent Events (SSE) dashboard streaming), calls Basket API and Catalog API over gRPC during checkout and reporting, and coordinates post-checkout workflows with Finance over Kafka.

## Overview

| Property                       | Value                                                                                                                                                                                                                      |
| :----------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**                      | Ordering bounded context (`BookWorm.Ordering`)                                                                                                                                                                             |
| **Aspire resource ID**         | `ordering`                                                                                                                                                                                                                 |
| **Source**                     | `src/Services/Ordering/BookWorm.Ordering`                                                                                                                                                                                  |
| **Gateway path & local ports** | Gateway `/ordering/api/v1/*`; local HTTP `5244`, HTTPS `7203`                                                                                                                                                              |
| **Protocols**                  | HTTP REST + SSE (`ApiVersions.V1`), gRPC clients → Basket & Catalog, Kafka + Wolverine                                                                                                                                     |
| **Persistence & caching**      | PostgreSQL (`orderingdb`, EF Core + Marten event store w/ Async Daemon `DaemonLockId = 44444` + Wolverine outbox `wolverine` schema), Redis (`order-cache`: FusionCache, `IRequestManager` idempotency, distributed locks) |
| **Authentication**             | Microsoft Entra ID JWT — `customer` or `admin` roles + `ordering_read`/`ordering_write`; Backoffice dashboard also requires `admin` + `catalog_read`; `HMAC__Key` for log redaction                                        |

## Runtime architecture

Ordering API serves Commerce and Backoffice via the API Gateway, enriches checkouts from Basket API and Catalog API over gRPC, persists relational and Marten event-sourced state in PostgreSQL, uses Redis for buyer write locks and idempotency markers, and exchanges lifecycle messages with Finance over Kafka.

## HTTP API (`ApiVersions.V1`)

All routes require Microsoft Entra ID authentication (`ordering_read`/`ordering_write`), apply `PerUserRateLimit`, and are reachable through the API Gateway under `/ordering/api/v1/*`.

### Order endpoints

| Method   | Route (direct)                      | Access                           | Idempotency / notes                                                                                                   |
| :------- | :---------------------------------- | :------------------------------- | :-------------------------------------------------------------------------------------------------------------------- |
| `POST`   | `/api/v1/orders`                    | `customer`                       | [[command\|CreateOrder]] — Requires `x-request-id` header; returns `201 Created` with Order ID and location           |
| `GET`    | `/api/v1/orders`                    | `customer` (own) / `admin` (all) | [[query\|ListOrders]] — Paginated (default page `1`, size `20`); optional `Status` and `BuyerId` filters              |
| `GET`    | `/api/v1/orders/{id}`               | `customer` (own) / `admin` (all) | [[query\|GetOrder]] — Enriches display titles from Catalog while keeping locked checkout prices                       |
| `GET`    | `/api/v1/orders/{id}/history`       | Authenticated (scoped)           | Returns chronological Marten event-stream history for the Order                                                       |
| `GET`    | `/api/v1/orders/{id}/summary`       | `admin`                          | Reconstructs event-sourced `OrderSummary` (supports `version` and `at` time-travel); returns stream version in `ETag` |
| `PATCH`  | `/api/v1/orders/{orderId}/complete` | `admin` / authorized             | [[command\|CompleteOrder]] — Requires `x-request-id`; transitions `New` → `Completed` only                            |
| `PATCH`  | `/api/v1/orders/{orderId}/cancel`   | `customer` / `admin`             | [[command\|CancelOrder]] — Requires `x-request-id`; transitions `New` → `Cancelled` only                              |
| `DELETE` | `/api/v1/orders/{id}`               | `admin`                          | [[command\|DeleteOrder]] — Soft-deletes the Order without altering its business status                                |

### Backoffice dashboard endpoints

| Method | Route (direct)             | Access                   | Behavior                                                                                                                                         |
| :----- | :------------------------- | :----------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/v1/dashboard`        | `admin` + `catalog_read` | Returns store-wide totals, 7 UTC daily buckets, category summaries (via Catalog `GetDashboard` gRPC), and 5 newest Orders; cached `15s` in Redis |
| `GET`  | `/api/v1/dashboard/stream` | `admin` + `catalog_read` | Streams an initial SSE snapshot followed by refreshes every `15s`; terminates on token expiry or after `5` minutes                               |

### Error responses

| Status                  | Condition                                                                                                         | Recovery behavior                                                    |
| :---------------------- | :---------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------- |
| `400 Bad Request`       | Missing `x-request-id`, validation error, missing book in Catalog, or invalid status transition (non-`New` order) | Fix request or verify order status; do not retry unchanged           |
| `401 Unauthorized`      | Missing, expired, or invalid Entra ID JWT                                                                         | Re-authenticate and retry                                            |
| `403 Forbidden`         | Caller lacks required role (`admin` / `customer`) or scopes (`ordering_read`, `ordering_write`, `catalog_read`)   | Request token with required role and scopes                          |
| `404 Not Found`         | Order or Buyer missing or outside caller's permitted scope                                                        | Verify resource ID and ownership                                     |
| `409 Conflict`          | Duplicate `x-request-id` within the 1-hour Redis idempotency window or concurrent buyer checkout lock contention  | Inspect existing order status before generating a new `x-request-id` |
| `429 Too Many Requests` | Global or `PerUserRateLimit` exceeded (`Retry-After` header returned)                                             | Wait for `Retry-After` interval and retry                            |

## Domain invariants, locking, and persistence

- **Locked checkout prices:** Every new Order begins in `New` status with line totals calculated from active Catalog prices (sale price when set, otherwise regular price). Later Catalog price edits never rewrite accepted Orders.
- **Buyer-scoped write lock:** Redis serializes the Order write per Buyer (after Basket and Catalog gRPC reads) to prevent colliding concurrent checkouts without blocking reads.
- **Early idempotency markers:** `IRequestManager` writes `x-request-id` markers in Redis for `1` hour _before_ handler completion; a recorded marker blocks duplicate submissions but does not by itself prove the first request succeeded.
- **Marten event store:** Order domain events append to Marten streams in `orderingdb`, driving the live `OrderSummary` aggregation and asynchronous `OrderSummaryView` projection (`DaemonLockId = 44444`).

## Kafka messaging contracts

Wolverine persists outbound/inbound envelopes in `orderingdb` (`wolverine` schema), partitions by `OrderId`, and routes exhausted retries to [[channel|bookworm.&#123;env&#125;.ordering.dead-letter-queue]].

| Direction     | Message                                                 | Kafka topic                                               | Peer                             | Behavior                                                                          |
| :------------ | :------------------------------------------------------ | :-------------------------------------------------------- | :------------------------------- | :-------------------------------------------------------------------------------- |
| **Publishes** | [[event\|UserCheckedOutIntegrationEvent]]               | `bookworm.{env}.ordering.user-checked-out`                | [[service\|order-orchestration]] | Starts post-checkout Finance orchestration                                        |
| **Publishes** | [[event\|OrderStatusChangedToCompleteIntegrationEvent]] | `bookworm.{env}.ordering.order-status-change-to-complete` | [[service\|order-orchestration]] | Triggers completion notification and closes workflow                              |
| **Publishes** | [[event\|OrderStatusChangedToCancelIntegrationEvent]]   | `bookworm.{env}.ordering.order-status-change-to-cancel`   | [[service\|order-orchestration]] | Triggers cancellation notification and closes workflow                            |
| **Consumes**  | [[command\|DeleteBasketCompleteCommand]]                | `bookworm.{env}.finance.delete-basket-complete`           | [[service\|order-orchestration]] | Logs successful basket cleanup; does not change Order status                      |
| **Consumes**  | [[command\|DeleteBasketFailedCommand]]                  | `bookworm.{env}.finance.delete-basket-failed`             | [[service\|order-orchestration]] | Soft-deletes the matching Order (if present) without altering its business status |
