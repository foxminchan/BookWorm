`DeleteBasketFailedCommand` (v1.0.0) is a Kafka integration command published by **Finance** (Azure Functions + Azure Durable Task Scheduler `OrderOrchestrator`) instructing **Ordering API** to soft-delete an order whose post-checkout basket cleanup failed or whose orchestration rolled back. **Ordering API** marks the order deleted without transitioning its business status to `Cancelled`.

## Behavior and side effects

- **Producer paths (Finance Durable Functions):** **Finance** publishes `DeleteBasketFailedCommand` via `PublishDeleteBasketFailedActivity` (3 retries, 5-second initial interval, 2.0 backoff) in two scenarios:
  - **Direct basket-cleanup failure:** `BasketDeletedFailedStep` handles `BasketDeletedFailedIntegrationEvent` from **Basket API**, marks the orchestration failed, and publishes `DeleteBasketFailedCommand`.
  - **LIFO Saga compensation:** `BasketDeletedCompleteStep` registers `PublishDeleteBasketFailedActivity` with `OrderSagaCompensations` after basket deletion succeeds; if a subsequent orchestration step throws `TaskFailedException` or `FinanceDomainException`, `OrderOrchestrator` runs registered compensations in reverse order.
- **Consumer deduplication (Ordering API):** `DeleteBasketFailedCommandHandler` (`[WolverineHandler]`) executes inside `IIntegrationEventIdempotencyGuard.ExecuteAsync(message.Id, nameof(DeleteBasketFailedCommandHandler), ...)` using a 24-hour Redis/FusionCache lock so duplicate deliveries are skipped.
- **Soft-delete without status mutation:** The handler fetches the order with `repository.GetByIdAsync(message.OrderId, ct)` (which respects EF Core's global `HasQueryFilter(x => !x.IsDeleted)`). If the order exists, it calls `order.Delete()` (`IsDeleted = true`) and saves via `UnitOfWork.SaveEntitiesAsync(ct)` without changing `Order.Status` or emitting domain/integration events. If the order is already soft-deleted or does not exist, the handler completes as a no-op.

## Error responses

| Code / status                           | Condition                                                                     | Recovery behavior                                                                                                                                       |
| :-------------------------------------- | :---------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Order not found or already soft-deleted | `repository.GetByIdAsync(message.OrderId)` returns `null`                     | Handler exits cleanly without error (idempotent no-op).                                                                                                 |
| Duplicate message ID within 24 hours    | `IIntegrationEventIdempotencyGuard` detects prior processing of `message.Id`  | Handler skips execution without re-querying PostgreSQL.                                                                                                 |
| Transient database or broker failure    | PostgreSQL error or unhandled exception in `DeleteBasketFailedCommandHandler` | Wolverine retries with cooldown (`50ms`, `250ms`, `1s` with full jitter) and routes persistent failures to `bookworm.{env}.ordering.dead-letter-queue`. |
