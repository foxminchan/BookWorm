## Purpose & Ownership Boundary

Order Database (`orderingdb`) is the authoritative PostgreSQL system of record owned exclusively by [[service|order-api]] in the Ordering bounded context. PostgreSQL was chosen to combine ACID relational persistence for buyer profiles and immutable checkout snapshots with append-only order lifecycle event streams, read projections, and a transactional outbox over a single connection.

## Consistency, Isolation & Security Guardrails

- **Checkout price immutability:** `order_items` persists the unit price resolved at checkout so subsequent price edits in [[container|catalog-database]] never alter historical purchases.
- **Soft-delete audit preservation:** Administrative cleanup and failed basket-cleanup compensation mark orders as soft-deleted (filtered from normal reads) rather than physically erasing rows.
- **Eventually consistent summary views:** Asynchronous order summary projections can briefly lag transactional writes; `orders` remains the canonical source for order status.
- **Confidential PII posture:** Buyer names and street/city/province addresses are classified `confidential` and protected by encryption at rest, regional residency, and backup retention policies.

:::warning
**Database-per-Service Isolation:** Only [[service|order-api]] may read or write `orderingdb`. Active pre-checkout baskets live in [[container|basket-database]], temporary locks and HTTP idempotency markers live in [[container|order-cache]], and post-checkout saga state lives in [[service|order-orchestration]]. External services must never query `orderingdb` directly.
:::

## Operational & Resilience Notes

<AccordionGroup>
	<Accordion title="Hosting, backup retention, and environment parity">
		- **Local vs. Cloud:** Local development runs a persistent PostgreSQL container alongside
		`catalogdb` and `schedulerdb`; cloud environments run Azure Database for PostgreSQL Flexible
		Server. - **Scaling & HA:** Development uses `Standard_B1ms` (single zone, 7-day backup, 32 GB);
		Staging uses `Standard_D2ds_v5` (zone-redundant HA, PgBouncer, 14-day backup, 128 GB);
		Production uses `Standard_D4ds_v5` (zone-redundant HA, PgBouncer, 35-day backup, 256 GB). -
		**Active messaging schema:** Treat the `wolverine` schema as the sole authoritative messaging
		store; ignore any retired messaging tables from historical migrations.
	</Accordion>
</AccordionGroup>
