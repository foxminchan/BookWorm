Order database (`orderingdb`) is the authoritative PostgreSQL system of record owned exclusively by [[service|order-api]] in the Ordering bounded context. Over a single PostgreSQL database connection, it stores relational buyer and order records via EF Core, order lifecycle event streams and projections via Marten, and transactional integration message envelopes via Wolverine.

## Architecture and persistence layers

Ordering API accesses `orderingdb` exclusively; no other service queries or mutates this database. Active pre-checkout baskets live in [[container|basket-database]], temporary locks and HTTP idempotency markers live in [[container|order-cache]], and post-checkout saga state lives in Azure Durable Task Scheduler (`finance-taskhub`).

## Stored data and schemas

| Layer                         | Objects / entities                                | Purpose                                                                                                                                                                                                                                 | Key rules and configuration                                                                                                                                                             |
| :---------------------------- | :------------------------------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **EF Core (`public`)**        | `buyers`, `orders`, `order_items`                 | Authoritative buyer profiles (name, street, city, province), accepted orders (status `New`, `Cancelled`, `Completed`, note, timestamps, soft-delete flag), and checkout-time line item snapshots (book ID, quantity, locked unit price) | Unique constraint on (`book_id`, `order_id`) per order; row-version optimistic concurrency token on `orders`; global soft-delete query filter excludes deleted orders from normal reads |
| **Marten (`public` default)** | Event streams, `OrderSummary`, `OrderSummaryView` | Permanent order placement, completion, and cancellation events; live `OrderSummary` stream aggregation; asynchronous `OrderSummaryView` documents (order ID, status, total price)                                                       | Async daemon runs with `DaemonLockId = 44444` and `MartenEventPublisher` subscription; `DisableNpgsqlLogging = true`; `AutoCreateSchemaObjects = AutoCreate.All` in Development only    |
| **Wolverine (`wolverine`)**   | Outbox and inbox envelope tables                  | Durable integration messaging sharing EF Core transactions                                                                                                                                                                              | Publishes `UserCheckedOutIntegrationEvent`, `OrderStatusChangedToCompleteIntegrationEvent`, and `OrderStatusChangedToCancelIntegrationEvent` partitioned by `OrderId`                   |

## Operational and governance rules

- **Confidential customer data:** Buyer names and street/city/province addresses are classified `confidential`. Enforce backup retention, encryption, and regional residency policies at the Azure infrastructure level.
- **Eventually consistent projections:** Marten's asynchronous `OrderSummaryView` can briefly lag behind transactional EF Core writes. Treat `orders` as the authoritative source for order status (`New`, `Cancelled`, `Completed`).
- **Checkout price immutability:** `order_items` persists the unit price resolved at checkout so subsequent price edits in [[container|catalog-database]] never alter historical purchases.
- **Soft deletion:** Administrative cleanup and failed basket-cleanup compensation mark orders as soft-deleted rather than physically erasing rows, preserving audit trails.
- **Legacy migration artifacts:** Historical EF Core migrations may contain retired messaging tables; treat the active `wolverine` schema as the sole authoritative messaging store.
