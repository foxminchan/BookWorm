Order cache is [[service|order-api]]'s logical slice of the shared BookWorm Redis resource (`redis`). Ordering API reuses a single `IConnectionMultiplexer` to run four coordination and caching workloads: buyer-scoped order creation locks, atomic HTTP request idempotency markers, FusionCache L2 + backplane caching, and 24-hour Kafka integration event idempotency.

## Architecture and runtime wiring

Ordering API connects to the shared `redis` resource with Azure authentication (`WithAzureAuthentication()`) and `DisableAutoActivation = false`. Although Order cache is non-authoritative for purchases, its availability directly governs concurrent checkout serialization and duplicate-request rejection across Ordering API replicas.

## Keys, locks, and expiration

| Workload                      | Logical key or scope                                 | TTL / timeout                                  | Behavior                                                                                                                            |
| :---------------------------- | :--------------------------------------------------- | :--------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| **Order creation lock**       | Cache name `ordering`, lock `order-create:{BuyerId}` | `1 minute` acquisition timeout                 | Acquired around adding the `Order` and saving the EF Core unit of work; released in `finally`                                       |
| **HTTP idempotency marker**   | `{HTTP method}:{request path}:{x-request-id}`        | `3,600 seconds` (`1 hour`)                     | Stored atomically via `SET NX` (`When.NotExists`) as camelCase JSON `ClientRequest` (`id`, `name`, `time`)                          |
| **Catalog book batch**        | `books:{sorted comma-separated book IDs}`            | `30 minutes` default (`books`, `catalog` tags) | Caches Catalog gRPC book/price batch lookups during checkout; accepted orders still persist unit prices permanently in `orderingdb` |
| **Admin dashboard summary**   | `ordering:dashboard:v1`                              | `15 seconds`                                   | Caches aggregated Ordering and Catalog dashboard metrics                                                                            |
| **Order summary (versioned)** | `ordering:summary:v1:{orderId}:v{version}`           | `Caching:Expiration` default                   | Caches versioned Marten `OrderSummary` projections                                                                                  |
| **Order summary (terminal)**  | `ordering:summary:v1:{orderId}:terminal`             | `Caching:Expiration` default                   | Caches terminal-state order summary views                                                                                           |
| **Order history (terminal)**  | `ordering:history:v1:{orderId}:terminal`             | `Caching:Expiration` default                   | Caches terminal-state order event history                                                                                           |
| **Kafka event idempotency**   | `IIntegrationEventIdempotencyGuard` (chassis)        | `24 hours`                                     | Deduplicates re-delivered integration messages across Ordering consumers                                                            |

Terminal order summary and history entries use `Duration` and `DistributedCacheDuration` of one hour. Non-terminal summaries and histories are not cached by the terminal cache keys.

## Lock and idempotency semantics

### Buyer-scoped order creation lock

- **Scope:** Ordering API reads the customer's basket and resolves Catalog book prices _before_ acquiring `order-create:{BuyerId}`. The lock guards only adding the `Order` entity and committing the EF Core unit of work.
- **Contention failure:** If lock acquisition returns no handle, the handler throws `InvalidOperationException` indicating another process is already creating an order for that buyer.
- **Release and limits:** Lock release executes in a `finally` block even when persistence fails. The lock does not serialize order completion or cancellation and does not replace the PostgreSQL row-version concurrency token.

### Atomic HTTP idempotency filter (`WithIdempotency()`)

`IdempotencyEndpointFilter` protects non-idempotent HTTP methods (`POST` and `PATCH`; `GET`, `DELETE`, `PUT`, `HEAD`, and `OPTIONS` bypass the filter):

1. **Header validation:** Rejects requests missing a non-empty `x-request-id` header with a `ValidationException` (`400 Bad Request`).
2. **Atomic claim:** Calls `RequestManager.TryCreateAsync`, which writes the JSON `ClientRequest` with `StringSetAsync(..., TimeSpan.FromSeconds(3600), When.NotExists)`.
3. **Duplicate rejection:** If the key already exists, returns `409 Conflict` (`ProblemDetails`: `"You have already requested this operation."`).
4. **Failure rollback:** If the downstream handler throws an exception or returns an HTTP status `>= 500`, the filter deletes the idempotency key immediately (`DeleteAsync`) so the client can safely retry with the same `x-request-id`. Successful (`2xx`) and client-error (`4xx`) responses retain the marker for 1 hour.

## Hosting and environment provisioning

AppHost provisions the shared `redis` resource via `src/Aspire/BookWorm.AppHost/Extensions/Infrastructure/AzureExtensions.Redis.cs`.

| Environment           | Provisioning & SKU                                                      | High availability | Local tooling |
| :-------------------- | :---------------------------------------------------------------------- | :---------------- | :------------ |
| **Local development** | Local Redis container (`ContainerLifetime.Persistent`) with data volume | Single container  | RedisInsight  |
| **Azure Development** | Azure Managed Redis (`BalancedB0`)                                      | Disabled          | —             |
| **Azure Staging**     | Azure Managed Redis (`BalancedB1`)                                      | Enabled           | —             |
| **Azure Production**  | Azure Managed Redis (`BalancedB5`)                                      | Enabled           | —             |

:::warning
Flushing the shared `redis` instance does not delete persisted orders in `orderingdb`, but it drops active HTTP idempotency markers, releases in-flight coordination locks, and clears active customer baskets in [[container|basket-database]].
:::
