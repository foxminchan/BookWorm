## Purpose & Ownership Boundary

Order Cache and Distributed Locks is the non-authoritative Redis coordination and caching slice owned exclusively by [[service|order-api]] in the Ordering bounded context. Redis was chosen to provide low-latency distributed locking for concurrent checkout serialization, atomic HTTP `SET NX` idempotency markers, and FusionCache L2 + backplane caching across service replicas.

## Logical Data Layout & Key Patterns

| Key Pattern                                   | Stored Data                                                        | TTL / Eviction                                 | Invalidation / Update Trigger                                                                                        |
| :-------------------------------------------- | :----------------------------------------------------------------- | :--------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- |
| `order-create:{BuyerId}` (`ordering` lock)    | Distributed creation lock handle                                   | `1 minute` acquisition timeout                 | Released explicitly in `finally` after committing the order unit of work.                                            |
| `{HTTP method}:{request path}:{x-request-id}` | Atomic HTTP idempotency marker (`id`, `name`, `time`) via `SET NX` | `1 hour` (`3,600 seconds`)                     | Retained on `2xx`/`4xx` responses; deleted immediately on unhandled exceptions or `5xx` errors so clients can retry. |
| `books:{sorted book IDs}`                     | Cached Catalog gRPC book/price batch responses                     | `30 minutes` default (`books`, `catalog` tags) | TTL expiration or tag invalidation.                                                                                  |
| `ordering:dashboard:v1`                       | Aggregated Ordering and Catalog admin dashboard metrics            | `15 seconds`                                   | Time-based TTL expiration.                                                                                           |
| `ordering:summary:v1:{orderId}:v{version}`    | Versioned order summary projection                                 | `30 minutes` default                           | Immutable per version; expires by TTL.                                                                               |
| `ordering:summary:v1:{orderId}:terminal`      | Terminal-state order summary view                                  | `1 hour` (L1 & L2)                             | Cached only for terminal orders; expires by TTL.                                                                     |
| `ordering:history:v1:{orderId}:terminal`      | Terminal-state order event history                                 | `1 hour` (L1 & L2)                             | Cached only for terminal orders; expires by TTL.                                                                     |

## Consistency, Isolation & Security Guardrails

- **Buyer-scoped lock boundaries:** [[service|order-api]] reads the basket and resolves Catalog prices _before_ acquiring `order-create:{BuyerId}`, keeping the critical section scoped strictly to order creation and persistence. The lock does not replace the PostgreSQL row-version concurrency token.
- **Atomic HTTP idempotency (`POST` / `PATCH`):** Requests without a non-empty `x-request-id` header are rejected (`400 Bad Request`), and duplicate in-flight or completed requests return `409 Conflict`.
- **Non-authoritative for purchases:** Accepted orders and checkout-time prices are always committed to [[container|order-database]].

:::warning
**Shared Redis Key-Prefix & Flush Isolation:** Order Cache shares the `redis` cluster with [[container|basket-database]], [[container|catalog-cache]], [[container|rating-cache]], and Notification idempotency markers. Flushing the shared Redis instance does not delete persisted orders in `orderingdb`, but it drops active HTTP idempotency markers, releases in-flight creation locks, and erases active customer baskets in [[container|basket-database]].
:::
