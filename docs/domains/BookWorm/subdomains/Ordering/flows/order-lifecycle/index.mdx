**Ordering API** is the single system of record for accepted customer orders and owns every business status transition (`New`, `Completed`, and `Cancelled`). After Ordering API persists a `New` order snapshot in PostgreSQL (`orderingdb`), **Finance** (`OrderOrchestrator` on Azure Durable Functions) coordinates asynchronous basket cleanup and routes order-status notifications to **Notification** over Kafka. Neither Finance nor Notification ever modifies an order's business status.

## Context and motivation

Checkout turns mutable shopping intent in **Basket API** into an immutable purchase snapshot in **Ordering API**, then triggers downstream basket deletion and customer emails. Combining those steps into one synchronous call or allowing downstream workers to mutate order status would create brittle checkouts and conflicting records.

BookWorm separates responsibilities across four bounded contexts:

- **Shopping (`Basket API`):** Holds mutable pre-order items in Redis and deletes the basket after checkout.
- **Ordering (`Ordering API`):** Owns the accepted order, its item-price snapshot, event-sourced `OrderSummary` projections (Marten + EF Core in PostgreSQL `orderingdb`), and explicit status transitions (`New`, `Completed`, `Cancelled`).
- **Ordering (`Finance`):** Runs the Azure Durable Functions `OrderOrchestrator` on Azure Durable Task Scheduler (`finance-taskhub`) to coordinate basket cleanup, bounded retry timeouts, and notification commands. Finance has no PostgreSQL database and does not process card payments.
- **Platform (`Notification`):** Renders and sends order emails over SMTP as a pure downstream side effect.

### State transitions and soft deletion

This state diagram clarifies the difference between Ordering API's explicit business statuses (`New`, `Completed`, `Cancelled`) and technical soft deletion after failed basket cleanup.

<MermaidFileLoader file="mermaids/order-lifecycle-diagram-2.mmd" />

- **Creation (`New`):** **Ordering API** authenticates the buyer via Microsoft Entra ID, reads the persisted basket over gRPC (`basket.v1.BasketGrpcService`), resolves authoritative prices over gRPC (`book.v1.BookGrpcService`), persists the order in `orderingdb` (EF Core + Marten event store + Wolverine PostgreSQL outbox), and publishes `UserCheckedOutIntegrationEvent` (`bookworm.{env}.ordering.user-checked-out`).
- **Post-checkout coordination:** **Finance** consumes `UserCheckedOutIntegrationEvent` and starts an `OrderOrchestrator` instance correlated by `OrderId` in Azure Durable Task Scheduler (`finance-taskhub`). Finance publishes `PlaceOrderCommand` (`bookworm.{env}.finance.place-order`), consumed independently by **Basket API** (to delete the basket) and **Notification** (to send the placement email).
- **Explicit completion or cancellation:** When an authorized business operation marks an order `Completed` or `Cancelled`, **Ordering API** commits the new status and publishes `OrderStatusChangedToCompleteIntegrationEvent` (`bookworm.{env}.ordering.order-status-change-to-complete`) or `OrderStatusChangedToCancelIntegrationEvent` (`bookworm.{env}.ordering.order-status-change-to-cancel`). **Finance** consumes the status event, completes its orchestration, and publishes `CompleteOrderCommand` (`bookworm.{env}.finance.complete-order`) or `CancelOrderCommand` (`bookworm.{env}.finance.cancel-order`) for **Notification**.
- **Basket cleanup failure vs. cancellation:** If **Basket API** returns `false` on deletion, Finance sends `DeleteBasketFailedCommand` (`bookworm.{env}.finance.delete-basket-failed`) to **Ordering API**, which soft-deletes the order (`IsDeleted = true`) without changing its business status to `Cancelled` and without publishing `OrderStatusChangedToCancelIntegrationEvent`.

## Design trade-offs

| Decision                                                   | Benefits                                                                                                               | Costs and limits                                                                                               |
| :--------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------- |
| **Ordering owns status; Finance routes notifications**     | Keeps business status authoritative in one service and lets Finance cancel pending retry timers when an order finishes | Adds a Kafka hop through Finance between Ordering status events and Notification emails                        |
| **PostgreSQL outbox + Marten event store on Ordering API** | Guarantees atomic order persistence, `OrderSummary` read projections, and Kafka event publication                      | Requires operating Marten's Async Daemon (`DaemonLockId = 44444`) alongside EF Core migrations in `orderingdb` |
| **Soft deletion separate from `Cancelled` status**         | Distinguishes technical post-checkout cleanup failures from intentional business cancellations                         | Support and operators must inspect both business status and `IsDeleted` when troubleshooting missing orders    |
| **Asynchronous downstream side effects**                   | Keeps checkout fast and prevents email or basket outages from blocking order acceptance                                | Introduces eventual consistency between order status and customer emails                                       |

## Alternatives considered

- **Notification consuming Ordering status events directly:** Rejected because **Finance** must observe `OrderStatusChangedToCompleteIntegrationEvent` and `OrderStatusChangedToCancelIntegrationEvent` anyway to stop its active retry loop and clear compensations before issuing `CompleteOrderCommand` or `CancelOrderCommand`.
- **Finance owning order status:** Rejected because Finance is a coordination orchestrator on Durable Task Scheduler, not the domain authority for purchases, pricing snapshots, or buyer order history.
- **Synchronous distributed transaction across Ordering, Basket, and Notification:** Rejected because two-phase commits across PostgreSQL, Redis, and external SMTP providers cannot preserve checkout availability.
