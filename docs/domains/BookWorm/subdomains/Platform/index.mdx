Platform is BookWorm's Generic bounded context for cross-cutting background scheduling and transactional email delivery. It consists of two internal services—`Scheduler` (Quartz.NET backed by PostgreSQL `schedulerdb`) and `Notification` (a stateless Kafka + MailKit/Mjml.Net worker backed by Redis idempotency)—plus the external SMTP boundary (Mailpit locally, SendGrid SMTP in cloud). Neither service owns core business records from Catalog, Shopping, Ordering, or Reviews.

## Scope and constraints

- **In scope:** Recurring Quartz.NET job triggers (`ProcessVectorBatchJob`, `HeartbeatJob`), Quartz Dashboard operational visibility (`/quartz`), Kafka order-notification command consumption, MJML email rendering, Redis 24-hour message deduplication, and SMTP submission.
- **Out of scope:** Owning books, baskets, orders, payments, or reviews; guaranteeing recipient inbox placement after SMTP acceptance; persisting a relational email-outbox database (Notification uses **no PostgreSQL database**).
- **Key constraints:** Platform delivery outcomes and job completion statuses never mutate authoritative business state in upstream domains.

## Runtime view

- **Scheduled vector indexing:** Every 5 minutes, Scheduler publishes `ProcessVectorBatchIntegrationEvent` using its PostgreSQL Wolverine outbox. `Catalog Ingestion` validates and updates pending book vectors; a green Scheduler execution confirms publication only, not downstream indexing completion.
- **Transactional email delivery:** Notification consumes `PlaceOrderCommand` (`bookworm.{env}.finance.place-order`), `CompleteOrderCommand` (`bookworm.{env}.finance.complete-order`), and `CancelOrderCommand` (`bookworm.{env}.finance.cancel-order`). It skips blank recipient addresses, guards against duplicate delivery for 24 hours in Redis (`IIntegrationEventIdempotencyGuard`), renders MJML templates, and submits MIME messages over SMTP using MailKit's resilience pipeline.
- **Dead-letter handling:** Commands that fail JSON deserialization or exhaust Wolverine retry cooldowns (`50ms`, `250ms`, `1s` with jitter) route to `bookworm.{env}.notification.dead-letter-queue`.

## Deployment and cross-cutting concerns

- **Hosting and ingress:** Neither `scheduler` nor `notification` is routed through the YARP API Gateway; both expose `/health` and `/alive` endpoints in Development only. `quartz-dashboard` exposes an external HTTP endpoint secured by Entra ID OIDC (`admin` role).
- **Security and privacy:** Scheduler uses a user-assigned Managed Identity (`scheduler-identity`) for passwordless PostgreSQL (`schedulerdb`) access. Notification carries no Azure Managed Identity and authenticates to external Kafka and SMTP relays via deployment parameters (`email-smtp-endpoint`, `email-smtp-username`, `email-smtp-password`, `email-sender-address`) plus `HMAC__Key`.
- **Observability and resilience:** OpenTelemetry traces Quartz executions, Wolverine listeners, and MailKit SMTP operations; Scheduler retains up to 30 days (100k entries) of Quartz execution history in `schedulerdb`.

## Quality scenarios and known risks

| Quality attribute / risk | Scenario or exposure                                          | Current mitigation or gap                                                                   |
| :----------------------- | :------------------------------------------------------------ | :------------------------------------------------------------------------------------------ |
| **Reliability**          | Temporary SMTP relay latency or transient errors              | MailKit resilience pipeline + Wolverine jittered retries + `notification.dead-letter-queue` |
| **Idempotency**          | Duplicate Kafka delivery or upstream saga retries             | Redis 24-hour `IIntegrationEventIdempotencyGuard` deduplicates repeated commands            |
| **Local dev ergonomics** | Scheduler does not auto-start in Aspire (`WithExplicitStart`) | Start `scheduler` explicitly in the Aspire Dashboard when testing scheduled vector batches  |
