This reference defines the runtime ownership, Kafka contracts, storage boundaries, and operational rules for BookWorm's two **Platform** services: **Scheduler** (`scheduler`) and **Notification** (`notification`). Neither service is exposed through **API Gateway** (`gateway`).

## Overview

| Property                  | Scheduler (`scheduler`)                                                                                                | Notification (`notification`)                                                                              |
| :------------------------ | :--------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **Source**                | `src/Services/Scheduler/BookWorm.Scheduler/`                                                                           | `src/Services/Notification/BookWorm.Notification/`                                                         |
| **Runtime**               | .NET 11 web host (`Quartz.NET` + Dashboard Agent)                                                                      | .NET 11 worker (`Sdk.Worker` with Dev `/health`, `/alive`)                                                 |
| **Persistence**           | PostgreSQL (`schedulerdb`): Quartz persistent store, 30-day/100k execution history, Wolverine `wolverine` outbox/inbox | **No PostgreSQL database.** Redis (`redis`) only for FusionCache and 24-hour integration event idempotency |
| **External UI / ingress** | **Quartz Dashboard** (`quartz-dashboard` at `/quartz`, Microsoft Entra ID OIDC `admin` role)                           | None (internal Kafka consumer; local Mailpit UI in Dev only)                                               |
| **Messaging**             | Wolverine + Kafka + PostgreSQL outbox                                                                                  | Wolverine + Kafka + Redis idempotency + native Kafka DLQ                                                   |

## Platform integration topology

Scheduler publishes periodic indexing triggers to Kafka without calling Catalog directly, while Notification consumes Finance order commands from Kafka and dispatches rendered emails over SMTP.

## System contracts and ownership

| Interaction                          | Contract and topic / protocol                                                                                                                                                                                        | Owning boundary                                                                                                                                                                                                                                                                                                                 |
| :----------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Scheduler → Catalog Ingestion**    | `ProcessVectorBatchIntegrationEvent` on unprefixed Kafka topic `scheduler.process-vector-batch` (`AppendPrefix = false`)                                                                                             | **Scheduler** owns job schedule and publication (`ProcessVectorBatchJob`, cron `0 0/5 * * * ?` UTC, `[DisallowConcurrentExecution]`). **Catalog Ingestion** owns `pending_vector_updates` polling (`catalogdb`), advisory lock (`740031001`), batch size (`200`), Microsoft Foundry embeddings, and Qdrant (`vectordb`) writes. |
| **Scheduler self-liveness**          | `HeartbeatJob` (cron `0/30 * * * * ?` UTC) writing structured logs and OpenTelemetry telemetry                                                                                                                       | **Scheduler** owns liveness telemetry; emits no external Kafka messages.                                                                                                                                                                                                                                                        |
| **Finance → Notification**           | `PlaceOrderCommand` (`bookworm.{env}.finance.place-order`), `CompleteOrderCommand` (`bookworm.{env}.finance.complete-order`), `CancelOrderCommand` (`bookworm.{env}.finance.cancel-order`), partitioned by `OrderId` | **Finance** owns post-checkout orchestration; **Ordering API** owns authoritative order status; **Notification** owns template rendering and SMTP handoff only.                                                                                                                                                                 |
| **Notification → SMTP provider**     | `MailKit` over SMTP (port `587`): **Mailpit** (`mailpit`) in Development; parameterized SMTP (`email-smtp-endpoint`, default `smtp://smtp.sendgrid.net:587`) in Azure                                                | **Notification** renders `Mjml.Net` templates (`_Layout.mjml`, `Orders/OrderEmail.mjml`) and submits via Polly resilience pipeline; the SMTP provider owns downstream delivery.                                                                                                                                                 |
| **Notification → Dead-letter queue** | Native Kafka DLQ `bookworm.{env}.notification.dead-letter-queue`                                                                                                                                                     | **Notification** routes messages that exhaust Wolverine retries (`50ms / 250ms / 1s` with full jitter) to its service DLQ.                                                                                                                                                                                                      |

## Notification delivery and resilience rules

**Notification** operates as a stateless Kafka consumer with no relational database and no scheduled resend or cleanup jobs:

- **Blank email handling:** `OrderNotificationHelper.SendAsync` skips any command whose recipient email address is null, empty, or whitespace without throwing an error.
- **Duplicate suppression:** Every command handler (`PlaceOrderCommandHandler`, `CompleteOrderCommandHandler`, `CancelOrderCommandHandler`) wraps execution in `IIntegrationEventIdempotencyGuard` backed by Redis (24-hour TTL keyed on `message.Id` and handler name). Duplicate Kafka deliveries of the same `message.Id` are skipped; distinct retried commands from Finance carry new message IDs and are processed independently.
- **SMTP resilience pipeline:** `AddMailResiliencePipeline()` wraps `MailKitSender` in three Polly strategies:
  - `CircuitBreaker` (handles transient `CommandException`, `ProtocolException`, `IOException`, `TimeoutException`, `TimeoutRejectedException`)
  - `Retry` (exponential backoff with jitter on the same transient exceptions)
  - `Timeout` (default `30` seconds)
- **Failure escalation:** If transient retries fail through both Polly and Wolverine (`50ms / 250ms / 1s` with full jitter), Wolverine moves the CloudEvents payload to `bookworm.{env}.notification.dead-letter-queue`.
- **Provider boundary:** SMTP acceptance confirms only that the mail server accepted the message for relay—never that the message reached the recipient's inbox or that an order completed. BookWorm uses MailKit over SMTP rather than SendGrid's HTTP Web API.

## Scheduler boundary rules

- **No direct cross-database access:** Scheduler reads and writes only `schedulerdb` (Quartz tables, 30-day / 100,000-entry execution history, and Wolverine `wolverine` outbox). It never reads or writes `catalogdb`, `orderingdb`, or Qdrant.
- **Allowed job types:** The Quartz Dashboard Agent restricts remote/managed job execution strictly to types under `BookWorm.Scheduler.Jobs.*` (`ProcessVectorBatchJob`, `HeartbeatJob`).
- **Misfire semantics:** Both triggers in `src/Services/Scheduler/BookWorm.Scheduler/jobs.json` use UTC time zone and `FireOnceNow` misfire handling, firing one catch-up run rather than replaying every missed interval.
- **Trigger completion vs. target completion:** A completed `ProcessVectorBatchJob` run proves only that `ProcessVectorBatchIntegrationEvent` was published to Kafka (via the PostgreSQL outbox), not that Catalog Ingestion finished updating Qdrant.

## Rules for changes

- Keep business state in its owning bounded context; never treat SMTP handoff or Notification telemetry as authoritative order status.
- Preserve unprefixed topic routing (`AppendPrefix = false`) for `scheduler.process-vector-batch` so the Azure Functions `[KafkaTrigger]` consumer binding in `BookWorm.Catalog.Ingestion` continues to match.
- Keep SMTP credentials (`email-smtp-username`, `email-smtp-password`), `HMAC__Key`, and database connection strings in runtime secrets/parameters—never in source control or job definitions.
- Treat customer email addresses and rendered HTML bodies as confidential; emit only order IDs, message IDs, counts, timestamps, and sanitized exception types in logs.
- Run Pact contract tests (`Notification-Finance`, `Catalog-Scheduler`) via `mise run test` whenever changing Platform message schemas.
