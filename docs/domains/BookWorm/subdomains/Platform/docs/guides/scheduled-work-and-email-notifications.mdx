BookWorm's **Platform** subdomain separates recurring time-based orchestration from transactional email dispatch into two independent services: **Scheduler** (`scheduler`) runs recurring Quartz.NET jobs backed by PostgreSQL (`schedulerdb`), while **Notification** (`notification`) operates as a stateless Kafka + MailKit + Mjml.Net + Redis idempotency worker with **no PostgreSQL database**. Scheduler does not trigger email resend or cleanup jobs—Kafka retries, Polly SMTP resilience, and native dead-letter queues handle delivery reliability directly.

## Context and motivation

Two distinct operational needs exist across BookWorm's business domains:

- **Periodic batch triggers:** Catalog books change continuously, and generating Microsoft Foundry embeddings plus updating Qdrant (`vectordb`) is more efficient in scheduled batches than inside synchronous HTTP book writes.
- **Decoupled customer emails:** Order creation, completion, and cancellation should never block on external SMTP server latency or fail when an email provider is temporarily unreachable.

Separating these capabilities into dedicated Platform services keeps domain services focused on business invariants while avoiding cross-domain database coupling.

### Recurring work in Scheduler

**Scheduler** (`BookWorm.Scheduler`) loads job definitions from `src/Services/Scheduler/BookWorm.Scheduler/jobs.json` (scanned every 1 minute) and persists Quartz state, 30-day / 100,000-entry execution history, and Wolverine's `wolverine` outbox in PostgreSQL (`schedulerdb`). **Quartz Dashboard** (`quartz-dashboard`, exposed at `/quartz` behind Microsoft Entra ID OIDC with the `admin` role) provides operational visibility.

Scheduler runs exactly two UTC jobs, both configured with `FireOnceNow` misfire handling (a missed run triggers one immediate catch-up execution rather than replaying every missed interval):

| Job                     | Cron (UTC)       | Cadence          | Behavior                                                                                                                                          |
| :---------------------- | :--------------- | :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ProcessVectorBatchJob` | `0 0/5 * * * ?`  | Every 5 minutes  | Marked `[DisallowConcurrentExecution]`; publishes `ProcessVectorBatchIntegrationEvent` to unprefixed Kafka topic `scheduler.process-vector-batch` |
| `HeartbeatJob`          | `0/30 * * * * ?` | Every 30 seconds | Emits structured heartbeat logs (`FireTime`, `NextFireTime`) and OpenTelemetry telemetry                                                          |

When `ProcessVectorBatchJob` succeeds, Scheduler guarantees only that the Kafka event was published via its transactional outbox. **Catalog Ingestion** (`BookWorm.Catalog.Ingestion`) independently consumes `scheduler.process-vector-batch`, acquires PostgreSQL advisory lock `740031001` on `catalogdb`, reads up to `200` rows from `pending_vector_updates`, computes embeddings via Microsoft Foundry, updates Qdrant, and deletes acknowledged `(book_id, revision)` rows.

### Stateless email delivery in Notification

**Notification** (`BookWorm.Notification`) consumes Finance's Kafka order commands (`bookworm.{env}.finance.place-order`, `bookworm.{env}.finance.complete-order`, `bookworm.{env}.finance.cancel-order`), partitioned by `OrderId`:

1. **Idempotency check:** Each handler guards execution with a 24-hour Redis `IIntegrationEventIdempotencyGuard` keyed by `message.Id` and handler name, skipping duplicate deliveries of the same message ID.
2. **Blank-email filter:** `OrderNotificationHelper.SendAsync` returns cleanly without error when `Email` is blank or whitespace.
3. **Template rendering:** `MjmlTemplateRenderer` compiles `Orders/OrderEmail.mjml` (with `_Layout.mjml`) into HTML and builds a MIME message.
4. **Resilient SMTP handoff:** `MailKitSender` delivers the message over SMTP (**Mailpit** in Development, parameterized SMTP defaulting to SendGrid `smtp://smtp.sendgrid.net:587` in Azure) through a Polly pipeline (`CircuitBreaker`, exponential `Retry` with jitter, 30-second default `Timeout`).
5. **Dead-letter fallback:** If transient SMTP failures exhaust both Polly and Wolverine retries (`50ms / 250ms / 1s` with full jitter), Wolverine routes the message to `bookworm.{env}.notification.dead-letter-queue` for operator investigation and replay.

SMTP acceptance proves only that the relay server accepted the message; it never proves inbox delivery or commercial order status.

## Design trade-offs

| Decision                                                                                   | Benefits                                                                                                                    | Costs and limits                                                                                                         |
| :----------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------- |
| **Stateless Notification worker (Kafka + Redis + DLQ) instead of PostgreSQL email outbox** | Removes a database, schema migrations, and hourly Quartz resend/cleanup jobs; uses native Kafka durability and backpressure | Replaying failed emails requires Kafka DLQ tooling rather than SQL queries; Redis idempotency is time-bounded (24 hours) |
| **At-least-once Kafka delivery with `message.Id` deduplication**                           | Prevents lost order emails during transient network or SMTP outages                                                         | Ambiguous SMTP timeouts or reissued Finance commands (with new message IDs) can still produce duplicate emails           |
| **Kafka event trigger from Scheduler to Catalog Ingestion**                                | Eliminates synchronous HTTP coupling and auth token management between Scheduler and Catalog                                | Operators must inspect both Scheduler history and `catalogdb` (`pending_vector_updates`) to confirm end-to-end indexing  |
| **`FireOnceNow` misfire instruction**                                                      | Prevents catch-up storms after Scheduler downtime                                                                           | Intermediate missed 5-minute or 30-second windows are skipped                                                            |

## Alternatives considered

- **PostgreSQL outbox table in Notification with hourly Quartz resend and cleanup jobs:** Previously used in earlier designs, but retired because maintaining a dedicated relational database plus two hourly sweeping jobs duplicated Kafka's native durable log, retry, and dead-letter queue capabilities.
- **Direct HTTP calls from Scheduler to Catalog API:** Rejected because Kafka decouples ingestion availability from Scheduler execution and aligns Catalog Ingestion with BookWorm's event-driven Azure Functions model.
