**Notification** (`BookWorm.Notification`) is a stateless Kafka worker that renders order lifecycle emails with Mjml.Net and submits them over SMTP via MailKit—using **Mailpit** locally and SendGrid SMTP in Azure. It owns **no PostgreSQL database and no email outbox**: message durability comes from Kafka, duplicate-delivery protection comes from Redis (`IIntegrationEventIdempotencyGuard`), and transient SMTP failures are handled by a MailKit resilience pipeline followed by Wolverine retries and a native Kafka dead-letter queue.

## Context and motivation

Sending customer emails relies on external SMTP providers that can throttle connections, slow down, or reject requests. If **Ordering API** or **Finance** waited synchronously on SMTP handshakes, mail provider outages would block checkouts or stall order orchestration.

BookWorm isolates email delivery behind an asynchronous Kafka boundary:

- **Strict state separation:** Notification never owns order status or purchase history. Email delivery failures never roll back an accepted order, and SMTP acceptance never implies that an order succeeded.
- **Stateless worker footprint:** Instead of maintaining a separate relational email-outbox database or scheduled resend jobs, Notification relies on Kafka consumer durability, Redis idempotency keys, and bounded retries.
- **No public API:** Notification (`BookWorm.Notification`, `Sdk.Worker`) exposes no REST or gRPC endpoints. In Development only, it maps `/health` and `/alive` endpoints (local ports HTTP `5259`, HTTPS `7036`).

## How it works

Finance emits three order-notification commands over Kafka, each partitioned by `OrderId` and wrapped in a CloudEvents JSON envelope:

- `PlaceOrderCommand` on `bookworm.{env}.finance.place-order`
- `CompleteOrderCommand` on `bookworm.{env}.finance.complete-order`
- `CancelOrderCommand` on `bookworm.{env}.finance.cancel-order`

This flowchart shows how Notification consumes Finance commands from Kafka, applies Redis idempotency, renders MJML templates, and submits email over SMTP or routes exhausted messages to the dead-letter queue.

### Processing lifecycle

1. **Consume and deduplicate:** Each Wolverine command handler (`PlaceOrderCommandHandler`, `CompleteOrderCommandHandler`, `CancelOrderCommandHandler`) wraps execution in `IIntegrationEventIdempotencyGuard.ExecuteAsync` keyed by `message.Id` and handler name. Redis (via FusionCache, 24-hour TTL) prevents duplicate email sends if Kafka redelivers the same message ID.
2. **Validate recipient:** `OrderNotificationHelper.SendAsync` checks the recipient address. If the email is null, empty, or whitespace, the handler returns immediately without rendering or calling SMTP.
3. **Render MJML and build MIME:** For valid recipients, `IRenderer` renders `Orders/OrderEmail.mjml` (using `_Layout.mjml`) through Mjml.Net, and `OrderMimeMessageBuilder` constructs the MIME message with sender defaults from `MailKitSettings`.
4. **Submit over SMTP with resilience:** `MailKitSender` executes SMTP submission through a named Polly resilience pipeline (`Notification`). In local Aspire runs, MailKit connects to the **Mailpit** container on SMTP port `587`. In Azure publish mode, AppHost injects parameterized SMTP settings (`email-smtp-endpoint`, default `smtp://smtp.sendgrid.net:587`; `email-smtp-username`, default `apikey`; `email-smtp-password`; `email-sender-address`; optional `email-sender-name`).
5. **Handle failures and dead-lettering:** Non-cancellation exceptions throw `NotificationException` back to Wolverine. Wolverine retries on a `50ms / 250ms / 1s` cooldown schedule with full jitter, then routes exhausted messages to `bookworm.{env}.notification.dead-letter-queue`. Notification publishes no delivery-result event back to Finance or Ordering.

:::note
**Scheduler** (`BookWorm.Scheduler`) runs only `ProcessVectorBatchJob` and `HeartbeatJob`. It runs no email resend or outbox cleanup jobs for Notification.
:::

## Design trade-offs

| Decision                                                       | Benefits                                                                                         | Costs and limits                                                                                         |
| :------------------------------------------------------------- | :----------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| **Stateless Kafka + Redis idempotency (no PostgreSQL outbox)** | Eliminates a database dependency, schema migrations, and scheduled cleanup jobs                  | Relies on Kafka DLQ inspection for exhausted failures rather than querying an SQL outbox table           |
| **Idempotency keyed by `message.Id` (24-hour TTL)**            | Stops duplicate sends from Kafka consumer redeliveries and Wolverine retries of the same command | Does not deduplicate a new `PlaceOrderCommand` issued with a new `message.Id` by a Finance timeout retry |
| **MailKit over SMTP (not vendor HTTP API)**                    | Keeps local **Mailpit** and cloud **SendGrid** identical behind one standard protocol            | SMTP acceptance confirms provider handoff, not inbox delivery, bounce status, or customer open events    |
| **No delivery-result callback event**                          | Preserves unidirectional decoupling between business state and email side effects                | Finance and Ordering cannot automatically display email delivery receipts                                |

## Alternatives considered

- **PostgreSQL email outbox with Scheduler resend/cleanup jobs:** Retired from the architecture because Kafka durability, Wolverine retries/DLQ, and Redis idempotency already provide resilient delivery without operating a dedicated database and maintenance cron jobs.
- **Direct SendGrid HTTP Mail Send API:** Rejected in favor of standard SMTP via MailKit so local development with **Mailpit** exercises the exact same transport, MIME builder, and resilience pipeline as Azure deployments.
- **Synchronous email sending during checkout:** Rejected because external SMTP latency and outages would directly degrade checkout availability.
