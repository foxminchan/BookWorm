## 1. Context & Problem

Operations teams and administrators need a safe, unified way to see what recurring background jobs are registered in the [[system|scheduler-system]], when they are due to run, and why an execution was delayed or failed—without running manual queries against internal database tables or digging through unrelated domain services. At the same time, the service hosting these schedules needs to expose controlled management actions while keeping strict boundaries away from Catalog, Notification, and email business data.

## 2. Business Value

- **Faster incident diagnosis**: Gives support and operations staff one place to inspect active runs, execution history, durations, and missed-schedule recoveries.
- **Safe schedule control**: Enables authorized operators to pause, resume, or inspect schedules through a supported interface instead of risky manual database edits.
- **Clear failure visibility**: Distinguishes scheduler dispatch failures from downstream processing delays so teams focus on the right system immediately.
- **Protected operational surface**: Restricts administrative controls to authorized personnel and keeps secrets and sensitive customer data out of the dashboard.

## 3. How It Works

- **Operational inspection & management**: Scheduler Dashboard presents the scheduler's stored job definitions, trigger schedules, active runs, instance health check-ins, and execution history. Authorized operators can inspect timing, pause or resume schedules, and trace failures using correlation identifiers.
- **Coordinated background triggers**: The same host service executes recurring background jobs: one runs every five minutes to prompt [[service|catalog-ingestion]] to process pending search updates, and another emits a frequent liveness signal every 30 seconds for platform monitoring.
- **Controlled missed-run recovery**: If a scheduled window is missed during downtime, the scheduler runs one immediate catch-up execution rather than replaying every missed interval back-to-back.
- **Safe concurrency & failure handling**: If publishing a trigger fails, the scheduler records the failure so operators can see it. Preventing overlapping runs in the scheduler works alongside—and does not replace—the downstream service's own locking and duplicate-safe processing.
- **Guided troubleshooting**: When investigating an issue, operators check instance liveness and trigger state (paused, blocked, or misfired), review execution duration and errors, confirm the next scheduled run, and verify the downstream service's own queue or metrics.

## 4. Trade-offs & Lessons Learned

- **Shared host, distinct responsibilities**: Because the dashboard UI and the background job runner share one service host, teams must remember that outbound messages come from scheduled background jobs, not from operator clicks in the dashboard.
- **Dispatch completion vs. business completion**: A green run on the dashboard only proves the trigger was sent; operators must still inspect Catalog's pending queue and index health to confirm the backlog cleared.
- **Single catch-up over full replay**: Triggering once after a missed schedule avoids flooding downstream services after an outage, relying on downstream batch processors to catch up safely.
- **Administrative security boundary**: Because schedule controls can pause or disrupt platform-wide background maintenance, the dashboard must remain tightly secured and free of credentials, authorization headers, notification content, or personal data.

## 5. Technical Reference

### Operator capabilities & surface

Hosted by the Scheduler service (C# / .NET), exposing the Quartz dashboard together with the Quartz HTTP API over `sheduler-database`:

| Capability          | Operational use                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Job inspection      | Review the registered job type, group, durability, and description.                                                            |
| Trigger inspection  | Check cron expressions, time zone, next fire time, and misfire policy.                                                         |
| Runtime monitoring  | Inspect active firings, scheduler check-ins, execution duration, and failures.                                                 |
| Schedule management | Use the Quartz management surface to pause, resume, or otherwise control eligible schedules according to operator permissions. |
| Failure diagnosis   | Correlate a failed or delayed firing with its job, trigger, fire instance, and execution history.                              |

### Scheduled jobs

The current schedule is loaded from `jobs.json` and refreshed by Quartz periodically. All jobs use the `Scheduler` group, are durable, and use UTC cron triggers with the `FireOnceNow` misfire policy:

| Job                     | Cadence               | Responsibility                                                           | Downstream ownership                                                  |
| ----------------------- | --------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `ProcessVectorBatchJob` | Every 5 minutes, UTC  | Publishes `ProcessVectorBatchIntegrationEvent` to trigger vector updates | [[service\|catalog-ingestion]] owns queue processing and index state. |
| `HeartbeatJob`          | Every 30 seconds, UTC | Emits a scheduler liveness signal to logs and telemetry.                 | Operators and platform observability consume the signal.              |

### Messaging contract & execution semantics

- The dashboard shares the Scheduler host process with the Quartz jobs and Wolverine bus; its `sends` relationships document the host's Kafka publications (covered by `asyncapi-v1.yml`), not messages emitted by the dashboard UI.
- `ProcessVectorBatchJob` disallows concurrent Quartz executions, reports publication failures back to Quartz, and publishes [[event|ProcessVectorBatchIntegrationEvent]] (inheriting only `id` and `creationDate` from `IntegrationEvent`) to [[channel|scheduler.process-vector-batch]] to trigger one bounded Azure Functions batch in [[service|catalog-ingestion]] (which enforces its own PostgreSQL advisory lock and durable pending-update revisions).
- `HeartbeatJob` only logs liveness and does not publish a Kafka message.
- Timeouts and process interruptions can leave the caller uncertain about downstream completion; downstream services are responsible for idempotency and durable work preservation.

### Operational checks & security

1. Check the scheduler instance check-in and whether the expected trigger is paused, blocked, or misfired.
2. Inspect the fired-trigger and execution-history records for the job and trigger, including duration and failure details.
3. Confirm the next fire time and the trigger's UTC schedule.
4. Check the downstream system's own queue, outbox, or processing metrics.
5. Correlate the scheduler fire instance with sanitized application logs and traces; never use the dashboard as a substitute for downstream business state.

The dashboard and HTTP API must be protected as an administrative surface. Credentials, authorization headers, notification contents, and personal data must not be placed in Quartz job metadata or copied into routine logs.
