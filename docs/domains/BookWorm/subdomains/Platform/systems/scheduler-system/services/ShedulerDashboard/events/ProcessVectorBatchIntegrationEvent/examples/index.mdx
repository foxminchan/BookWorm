## 1. Context & Problem

Book records in the catalog change continuously as titles are added, edited, or removed, and semantic search relies on keeping vector embeddings synchronized with those updates. Rather than forcing the scheduler to inspect catalog databases or decide how many books to process at once, the platform needs a lightweight, recurring wake-up signal that prompts the catalog indexing service to handle waiting updates on a steady schedule.

## 2. Business Value

- **Fresh search results**: Ensures catalog additions, updates, and removals are reflected in vector search every few minutes without manual intervention.
- **Loose service coupling**: Keeps the scheduler completely independent of catalog batch sizes, selection order, and search storage internals.
- **Controlled processing load**: Groups continuous catalog edits into predictable, bounded intervals so indexing traffic stays smooth and manageable.
- **Duplicate-safe execution**: Prevents overlapping runs and stale overwrites even when multiple catalog edits happen concurrently.

## 3. How It Works

1. **Recurring trigger publication**: Every five minutes, [[service|sheduler-dashboard]] publishes a minimal wake-up event containing only a unique event identifier and creation timestamp, leaving batch sizing and ordering entirely to [[service|catalog-ingestion]].
2. **Single-runner check**: When [[service|catalog-ingestion]] receives the signal, it checks a coordination lock to ensure no other batch processor is already running; if one is active, the new invocation exits cleanly without duplicating work.
3. **Bounded batch indexing**: The processor reads a fixed-size batch of the oldest pending book updates, generates search embeddings for active books in [[container|catalog-vector]], and removes vectors for deleted books.
4. **Version-safe acknowledgment**: Each processed item is marked complete only if its record version still matches what was read at the start of the batch, ensuring any newer concurrent edits remain queued for the next cycle.

## 4. Trade-offs & Lessons Learned

- **At-least-once delivery requires safe concurrency**: Because the messaging channel guarantees at-least-once delivery rather than exactly-once delivery, duplicate or overlapping signals are handled safely through target-side locking and version checks.
- **Five-minute cadence vs. instant indexing**: Batching on a five-minute interval smooths compute cost and simplifies error recovery, at the trade-off of up to a five-minute delay before catalog edits appear in vector search.
- **Minimalist event contract**: Omitting book lists and batch parameters keeps the contract stable across indexing upgrades, while requiring the consumer to own its pending queue in [[container|catalog-database]].

### Publish a vector batch trigger

[[service|sheduler-dashboard]]'s `ProcessVectorBatchJob` publishes this event every five minutes in UTC (`0 0/5 * * * ?`, `FireOnceNow` misfire policy) to [[channel|scheduler.process-vector-batch]]. Because `IntegrationMessageOwnerAttribute` sets `AppendPrefix = false`, the Kafka topic is addressed directly as `scheduler.process-vector-batch` across environments.

- `id` uniquely identifies this integration event (`UUID`).
- `creationDate` records the UTC timestamp when the event was created.
- Batch size and selection order are intentionally omitted; they remain owned by [[service|catalog-ingestion]].

### Transport envelope and delivery

The JSON example above represents the camelCase data payload inside BookWorm's CloudEvents-compatible Kafka envelope (`application/cloudevents+json`), with distributed trace context propagated via the `traceparent` Kafka header.

- `ProcessVectorBatchJob` disallows concurrent Quartz executions and reports publication failures as `JobExecutionException`.
- Delivery on [[channel|scheduler.process-vector-batch]] is `at-least-once`.

### Consume in Catalog Ingestion

[[service|catalog-ingestion]] subscribes to [[channel|scheduler.process-vector-batch]] via the `ProcessVectorBatch` Azure Functions Kafka trigger (`ConsumerGroup = catalog-ingestion`). On each trigger:

1. Acquire PostgreSQL advisory lock `740031001` in [[container|catalog-database]] so only one batch processor runs at a time (if the lock is busy, the invocation exits without work).
2. Read up to `200` pending updates ordered by `updated_at` and `book_id`.
3. Generate embeddings for active books and upsert them into the `data-bookworm-snippets` collection in [[container|catalog-vector]], or delete records for missing/soft-deleted books.
4. Acknowledge each pending row only if its `revision` still matches the read snapshot, leaving newer concurrent updates queued for the next batch.
