## 1. Context & Problem

The scheduler triggers recurring work for domains such as Catalog (for search vector indexing) and Notification (for email maintenance), but it does not own the business rules behind those tasks. If scheduled jobs read or modified downstream domain databases directly, the scheduler would become tightly coupled to other teams' internal data structures, security boundaries would weaken, and a successful schedule firing could easily be mistaken for a completed business operation.

## 2. Business Value

- **Independent domain evolution**: Catalog, Notification, and future domain systems can update their internal storage and business rules without breaking scheduler deployments.
- **Stronger security and governance**: Each receiving system authenticates and validates incoming trigger requests and retains full control over its own data and concurrency rules.
- **Clear operational accountability**: Separates _when_ work is triggered (the scheduler's responsibility) from _how_ business work is executed, retried, and measured (each domain's responsibility).

## 3. How It Works

1. The scheduler serves purely as a timing and trigger boundary, carrying only the minimal invocation data needed by the target contract.
2. When a schedule fires, the job either publishes a versioned integration message to the target domain or invokes an authenticated domain entry point.
3. The receiving system determines which records qualify for work, enforces its own validation and concurrency rules, runs the processing, and manages domain-level retries and final outcomes.
4. The scheduler never reads or writes Catalog, Notification, or other domain tables directly. A successful firing confirms only that the scheduler completed its handoff—not that downstream processing succeeded.

## 4. Trade-offs & Lessons Learned

- **Eventual consistency**: Because triggering and execution are decoupled, there is a natural gap between when a schedule fires and when the downstream system finishes processing.
- **Correlated monitoring is required**: Operators must pair scheduler execution history and health checks with target-side queues and processing metrics to confirm whether business work actually completed.
- **Clear failure boundary**: Authentication errors, target outages, or message-delivery failures appear as scheduler invocation failures, while target-side recovery and data repair remain owned by the receiving system.
- **Alternatives considered**:
  - _Query or mutate downstream databases directly from jobs_: Avoids an integration hop, but couples the scheduler to domain schemas and bypasses target validation, authorization, and processing rules.
  - _Treat a successful firing as a successful business operation_: Endpoint acceptance or message publication only confirms handoff; the target may still reject, defer, or fail the work.
  - _Make the scheduler own target retries and result state_: Duplicates domain-specific work queues and recovery logic that belong inside each owning system.

## 5. Technical Reference

- **Decision status**: Accepted (`2026-10-27`)
- **Boundary owner**: [[system|scheduler-system]] acts strictly as an invocation and coordination boundary.
- **Integration pattern**:
  - Scheduled jobs publish versioned integration contracts such as [[event|ProcessVectorBatchIntegrationEvent]] over Kafka, or invoke authenticated target endpoints (for example, the Catalog Ingestion endpoint for vector batch processing, and email maintenance requests for Notification to select and process its own outbox records).
  - Receiving contracts must explicitly define authentication, request validation, and idempotency behavior.
  - Scheduler must never read or write Catalog, Notification, or other domain tables directly in Quartz jobs.
- **Observability**: Correlate Quartz execution history and health checks with downstream target queues, outboxes, and processing metrics to verify final business completion.
