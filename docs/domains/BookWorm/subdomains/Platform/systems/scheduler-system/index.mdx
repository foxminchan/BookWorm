The Scheduler System coordinates recurring work for BookWorm platform and
domain systems. It starts jobs and records execution state; the receiving
system remains responsible for authorization, processing, and business data.

## Overview

The Scheduler System is the platform coordination boundary for recurring
background work. It runs durable Quartz jobs, persists trigger and execution
state, and publishes authenticated service-to-service requests for Catalog and
Notification.

The Scheduler is not a general-purpose business workflow owner. A scheduled
job may start processing, but the target system owns validation, concurrency,
data changes, and the final business outcome. This separation keeps scheduling
reliable without coupling Quartz to another system's database or domain rules.

## Responsibilities and boundaries

| Responsibility         | Scheduler owns                                                                 | Target system owns                                                 |
| ---------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Schedule management    | Job definitions, trigger cadence, calendars, pause state, and misfire handling | The meaning of the work being scheduled                            |
| Invocation             | Starting a job and sending the authenticated request                           | Endpoint authorization and request validation                      |
| Execution coordination | Instance check-ins, fired-trigger records, locks, and job status               | Processing semantics and domain-level concurrency                  |
| Failure handling       | Recording execution failures and making eligible work runnable again           | Retrying or preserving the business work requested by the job      |
| Observability          | Scheduler health, trigger state, and execution history                         | Processing metrics, data quality, and downstream business outcomes |

The Scheduler must not read or write Catalog, Notification, or other domain
tables directly. It should use the receiving service's versioned command or
HTTP contract.

## Scheduled work

### Catalog vector maintenance

The Scheduler invokes [[command|ProcessCatalogVectorBatch]] on
[[service|catalog-ingestion]] as an authenticated Quartz job. Catalog Ingestion
uses [[container|catalog-vector]] for vector storage, then acquires its own
database advisory lock, processes a bounded batch, and
acknowledges only revisions that remain current. A successful scheduler
invocation therefore means that the worker was called, not that every pending
[[entity|book]] update has been indexed.

The target endpoint rejects missing or invalid credentials and distinguishes
unauthorized callers from callers using the wrong client identity. Scheduler
credentials belong in runtime secret configuration and must never be embedded
in job definitions or documentation.

### Notification maintenance

The Scheduler also coordinates Notification jobs for resend, cleanup, and
health-oriented processing. [[system|notification-system]] owns the durable
[[entity|outbox]] state and decides whether an email is eligible for delivery;
the Scheduler owns when the maintenance job is attempted.

- A resend job makes failed or still-eligible delivery work available for
  another controlled attempt.
- A cleanup job removes or archives only records that are no longer eligible
  for retry or audit.
- A heartbeat or health job provides a liveness signal for operators and
  should not be interpreted as proof that downstream notification delivery
  succeeded.

## Execution lifecycle

1. A Quartz job definition is persisted with its trigger and schedule.
2. The scheduler evaluates the trigger, calendar, pause state, and misfire
   policy.
3. An eligible firing is recorded for the active scheduler instance.
4. The Scheduler invokes the target contract with service-to-service
   authentication.
5. The target system validates the request, applies its own concurrency
   controls, and processes its owned data.
6. Quartz records completion, failure, status, and execution history for
   operations and later diagnosis.

Jobs should be safe to run more than once. A timeout or process interruption
can leave the caller uncertain whether the target completed, so the receiving
system must provide idempotency or a durable work queue where duplicate
invocations are harmless.

## Persistence model

Quartz tables are the Scheduler's operational state, not business entities.
They provide distinct responsibilities:

- [[entity|qrtz-job-details]] and [[entity|qrtz-triggers]] define what can run
  and when it is eligible.
- Cron, simple, blob, and calendar entities describe trigger timing and
  scheduling constraints.
- Paused trigger and job-group entities represent operator-controlled
  suspension.
- [[entity|qrtz-fired-triggers]] and [[entity|qrtz-scheduler-state]] record
  active firings and scheduler-instance check-ins.
- Lock, job-status, execution-history, and misfire-history entities support
  coordination, diagnosis, and recovery.

Quartz persistence should be treated as implementation-owned infrastructure.
Consumers must not use these tables as a substitute for a job API or infer
Catalog and Notification business state from scheduler rows.

## Reliability and failure handling

- Durable trigger state allows scheduled work to resume after a process restart.
- Misfires must be visible and handled according to the job's recovery policy;
  silently skipping a missed execution is not acceptable for durable work.
- Non-concurrent jobs and target-side locks prevent overlapping processing where
  the receiving contract requires it.
- A failed invocation must remain observable with its job, trigger, target, and
  execution context; it must not be reported as a successful business outcome.
- Retries must be bounded and compatible with the target's idempotency model.
- Backlogs should be diagnosed from both Scheduler execution state and the
  target system's durable queue or processing metrics.

## Operations and security

Operators should monitor scheduler-instance check-ins, fired-trigger age,
misfire and failure counts, execution duration, and the last successful run for
each critical job. For Catalog vector maintenance, compare Scheduler outcomes
with the age and count of pending vector updates. For Notification jobs,
compare execution outcomes with outbox delivery state and provider health.

All outbound job calls require restricted service-to-service credentials.
Credentials, authorization headers, notification contents, and personal data
must not be written to Quartz job metadata or routine logs. Correlation
identifiers and sanitized failure details should be retained so an operator can
trace a firing to the target system without exposing secrets.
