## 1. Context & Problem

When BookWorm needs to group related email notifications—such as messages intended for coordinated or scheduled delivery—it must first reserve a shared batch identifier from the email provider before submitting the individual emails.

If an error occurs while creating that identifier, blindly requesting a new one can orphan tracking state or cause duplicate batches, leaving the notification workflow unable to tell whether a retry is safe.

## 2. Business Value

- **Coordinated batch tracking**: Grouping related messages under a single batch identifier makes scheduled sends easier to manage, audit, and correlate across systems.
- **Safe failure recovery**: Preserving workflow state before retrying prevents duplicate batch creation and keeps operational diagnostics clear when provider responses are uncertain.

## 3. How It Works

The batch-creation workflow follows two core rules:

1. **Reserve and store the batch identifier first**: Before submitting messages that need to be grouped together, request a new batch identifier from SendGrid, store it within the notification workflow, and include it later in the [[command|SendMail]] request when required.
2. **Reconcile before replacing on unknown errors**: If batch creation fails with an uncertain outcome from the provider, do not immediately generate a replacement batch identifier. Preserve the current workflow state so the Notification System can check what happened and decide whether a retry is safe.

## 4. Trade-offs & Lessons Learned

- **Extra upfront step**: Reserving a batch identifier adds a separate call and state-persistence step before sending mail, so it should only be used when workflows genuinely require grouped or scheduled-send tracking.
- **Reconciliation complexity**: Avoiding duplicate batches after an ambiguous failure requires keeping durable workflow state rather than treating batch creation as a stateless, throwaway call.

using System.Net.Http.Headers;
using System.Net.Http.Json;
using System.Text.Json.Serialization;

var apiKey = Environment.GetEnvironmentVariable("SENDGRID_API_KEY")
    ?? throw new InvalidOperationException("SENDGRID_API_KEY is required.");

using var client = new HttpClient
{
	BaseAddress = new Uri("https://api.sendgrid.com")
};
client.DefaultRequestHeaders.Authorization =
	new AuthenticationHeaderValue("Bearer", apiKey);

using var response = await client.PostAsync("/v3/mail/batch", content: null);
response.EnsureSuccessStatusCode();

var result = await response.Content.ReadFromJsonAsync<CreateMailBatchResponse>()
    ?? throw new InvalidOperationException("SendGrid returned an empty response.");

Console.WriteLine(result.BatchId);

internal sealed record CreateMailBatchResponse(
	[property: JsonPropertyName("batch_id")] string BatchId);

### Step 2: Handle batch-creation failures

- **Endpoint**: `POST https://api.sendgrid.com/v3/mail/batch`
- **Authentication**: Bearer token supplied via `SENDGRID_API_KEY` environment/runtime secret configuration.
- **Recovery rule**: Do not create a replacement `batch_id` after an unknown provider failure without reconciling the original request; preserve workflow state so the Notification System can determine whether a retry is safe.
