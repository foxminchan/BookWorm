## Context

The [[system|sendgrid]] integration requires credentials and handles email addresses,
subjects, and message bodies. Exposing these values in source control,
architecture documentation, or routine logs would increase the impact of a
credential leak or an operational data disclosure. The durable Notification
outbox and provider calls also create more than one place where these values
may be accessible, so controls must cover both stored delivery work and
transient submission and diagnostic paths.

## Decision

[[system|sendgrid]] credentials are supplied only through runtime secret configuration and
are never stored in source control, catalog documentation, or logs. The
[[system|notification-system]] and [[service|sendgrid-api]] integration may access recipient,
sender, and message content only for the delivery operation and the minimum
support workflow required to diagnose it.

Logs and delivery records should prefer stable identifiers, provider status,
error categories, and correlation metadata over full message content. Any
diagnostic capture of sensitive values must be explicitly controlled, access
restricted, and subject to the platform's retention policy.

Only the components that need email details for rendering, submission, or
authorized support should have access to those values. Scheduler messages and
routine telemetry should use identifiers and aggregate status rather than
recipient or body content. Secret storage protects credentials but does not
replace access controls and retention decisions for the email itself.

## Consequences

- Credential rotation can be performed through deployment configuration without
  changing catalog resources.
- Operational telemetry is safer to share and retain, but may contain less
  detail than the original provider request.
- Support tooling must provide authorized access to the underlying notification
  record when message content is genuinely required.
- Secret scanning, access control, and retention monitoring remain required
  operational controls.
- The outbox remains confidential while pending and after submission until
  cleanup removes it. Current cleanup behavior does not define a formal
  privacy retention period or audit-retention policy.
- Routine logs should not contain full recipient and message data. The current
  Notification documentation identifies resend logs with recipient addresses
  and SMTP failure logs with recipients and subjects; those existing paths
  require remediation and must not be considered compliant merely because
  this policy is documented.
- Provider credentials, database credentials, notification records, and
  operational telemetry have separate access surfaces; each needs appropriate
  least-privilege controls and monitoring.
- Reducing data in logs may require support operators to inspect the protected
  Notification record using its stable identifier when detailed diagnosis is
  necessary.

## Alternatives considered

### Put provider credentials in source or Quartz job metadata

This would make credentials available through code or durable scheduler state
and complicate rotation. Runtime secret configuration keeps credentials out
of those surfaces.

### Copy full message content into logs and events

This can simplify some investigations but increases the number of systems
that store recipient and message data. Prefer stable identifiers, sanitized
status and errors, and controlled access to the outbox when necessary.

### Treat provider storage as the only confidential boundary

BookWorm stores rendered messages before submitting them and may log
diagnostic data locally. Its own database, telemetry, and support access
remain in scope regardless of the provider's controls.
