## 1. Context & Problem

Once an order is finalized, customers expect a completion confirmation email summarizing their order reference and final amount. Finance needs a dedicated request to trigger that communication without embedding email layout formatting or delivery mechanics inside financial orchestration.

## 2. Business Value

- **Clear post-purchase confirmation**: Keeps customers informed when their order completes, reinforcing trust with accurate order totals.
- **Fault-tolerant defaults**: Safely skips requests without an email address and falls back to `"Customer"` when a name is missing, avoiding unnecessary processing errors.
- **Clean service boundaries**: Preserves Ordering as the sole owner of order completion while letting Notification focus on message rendering and sending.

## 3. How It Works

1. When an order reaches completion, Finance publishes a complete-order notification request carrying a unique request identifier, timestamp, order reference, order total, and optional customer name and email address.
2. If the email address is missing or blank, the notification service skips email processing cleanly.
3. Otherwise, it defaults a missing customer name to `"Customer"`, prepares the completed-order email, logs a delivery record, and submits the email to the mail provider.
4. Any sending error propagates for retry handling, and no delivery-result event is returned after provider acceptance.

## 4. Trade-offs & Lessons Learned

- **Email request vs. order completion**: Handling this command only sends a customer email—it does not complete the order or confirm business completion.
- **Potential duplicate submissions**: Re-deliveries or repeated commands can result in duplicate completion emails because requests are not deduplicated across submissions.
- **Acceptance vs. recipient delivery**: Mail-provider acceptance confirms the send request was queued, not that the email landed in the recipient's inbox.

## 5. Technical Reference

- **Channel & consumer**: Published by Finance's order saga through [[channel|bookworm.&#123;env&#125;.finance.complete-order]] and consumed by [[service|notification-api]].
- **Message contract**:
  - Wolverine message identity: `BookWorm.Contracts.CompleteOrderCommand`
  - Inherited fields: `id` (UUID v7), `creationDate` (UTC timestamp)
  - Business fields: `orderId`, `totalMoney` (C# decimal), nullable `fullName` (null becomes `Customer`), nullable `email`
  - This command carries the payload schema (`schema.json`); Notification's AsyncAPI specification provides examples.
- **Handler behavior**:
  - Maps the command to the completed-order email status without mutating the order or confirming completion.
  - Null, empty, or whitespace-only `email` addresses skip email work.
  - Otherwise renders `Orders/OrderEmail`, saves an email outbox record, submits through SMTP, and marks the record sent on success.
  - Failures propagate; there is no notification result event.
