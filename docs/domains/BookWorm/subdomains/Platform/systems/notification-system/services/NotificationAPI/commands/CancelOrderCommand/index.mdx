## 1. Context & Problem

When an order is canceled, customers need timely confirmation showing which order was canceled and the amount involved. Finance orchestrates the order lifecycle and requires a dedicated message to ask Notification to send the cancellation email without embedding email layout or delivery logic inside Finance workflows.

## 2. Business Value

- **Timely customer transparency**: Confirms order cancellations promptly with accurate order references and totals.
- **Resilient handling of missing details**: Skips email work cleanly when an email address is missing and defaults a missing customer name to `"Customer"`, avoiding unnecessary failures.
- **Clear domain boundaries**: Keeps official order cancellation ownership in Ordering while delegating customer email delivery to Notification.

## 3. How It Works

1. After Finance finishes its cancellation workflow step, it publishes a cancel-order notification request containing a unique request identifier, timestamp, order reference, order total, and optional customer name and email address.
2. The notification service checks the email address; if it is missing or blank, it skips sending cleanly.
3. If an email address is present, the service uses `"Customer"` when the customer name is absent, formats the canceled-order email, saves a record for delivery, and hands the email off to the mail provider.
4. Any delivery failure surfaces for retry handling, and no delivery-result notification is emitted back once the provider accepts the message.

## 4. Trade-offs & Lessons Learned

- **Email trigger vs. business action**: Consuming this command only requests a cancellation email—it never cancels an order or confirms cancellation in business terms.
- **Duplicate submissions on retries**: Repeated commands or upstream retries can trigger duplicate email sends because delivery is not deduplicated across repeated requests.
- **Submission vs. delivery**: Mail-provider acceptance indicates the provider accepted the send request, not that the email reached the recipient's inbox.

## 5. Technical Reference

- **Channel & consumer**: Published by Finance's order saga through [[channel|bookworm.&#123;env&#125;.finance.cancel-order]] and consumed by [[service|notification-api]].
- **Message contract**:
  - Wolverine message identity: `BookWorm.Contracts.CancelOrderCommand`
  - Inherited fields: `id` (UUID v7), `creationDate` (UTC timestamp)
  - Business fields: `orderId`, `totalMoney` (C# decimal), nullable `fullName` (null becomes `Customer`), nullable `email`
  - This command carries the payload schema (`schema.json`); Notification's AsyncAPI specification provides examples.
- **Handler behavior**:
  - Maps the command to the canceled-order email status without mutating the order or confirming cancellation.
  - Null, empty, or whitespace-only `email` addresses skip email work.
  - Otherwise renders `Orders/OrderEmail`, saves an email outbox record, submits through SMTP, and marks the record sent on success.
  - Failures propagate; there is no notification result event.
