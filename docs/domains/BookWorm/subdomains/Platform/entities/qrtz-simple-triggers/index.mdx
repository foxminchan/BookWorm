## 1. Context & Problem

Not every background task follows a calendar rule such as "every Monday at 09:00 UTC." Many tasks—such as fixed-interval polling, delayed one-off executions, or running a job a fixed number of times—only require a repeat count and a fixed delay between runs. Separating repeat-based details from the core trigger record keeps the base trigger model clean while supporting interval-driven schedules durably.

## 2. Business Value

- **Predictable Fixed-Interval Execution:** Supports one-off delayed jobs, bounded repetition counts, and continuous interval-based tasks without complex calendar syntax.
- **Durable Progress Tracking:** Persists how many times a trigger has already run so bounded repetitions do not restart from zero after an application restart or cluster failover.
- **Clear Operational Diagnostics:** Exposes repeat limits, intervals, and execution counts directly so teams can verify why a task stopped or how often it runs.

## 3. How It Works

Each repeat-based trigger record extends a parent trigger in the core trigger registry. While the parent trigger manages lifecycle state, start and end boundaries, and the next scheduled fire time, this extension stores three interval-specific fields: the allowed repeat count, the interval between runs, and the number of times the trigger has already fired.

Each time the trigger fires, the scheduler increments the execution counter and computes the next run time by adding the repeat interval, continuing until the repeat count is exhausted or the parent trigger's end boundary is reached.

## 4. Trade-offs & Lessons Learned

- **Elapsed Time vs. Wall-Clock Alignment:** Interval triggers measure fixed elapsed time between runs rather than calendar boundaries, making them unsuitable when schedules must align to specific hours across daylight-saving or monthly changes.
- **Parent-Child Lifecycle Coupling:** This record cannot exist or operate independently; its pause state, misfire behavior, and lifecycle depend entirely on its parent trigger.
- **Counter Write Frequency:** Persisting the execution count on every firing guarantees durability across restarts, which means very short repeat intervals produce frequent storage updates.
