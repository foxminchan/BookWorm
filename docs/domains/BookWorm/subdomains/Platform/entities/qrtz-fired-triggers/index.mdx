## 1. Context & Problem

In a multi-instance platform where several scheduler nodes can pick up work simultaneously, the system needs a live coordination record of every trigger that has been claimed and is actively executing. Without tracking in-flight trigger firings, concurrent nodes could run exclusive jobs twice, lose track of active work after an instance crash, or lack a way to monitor and interrupt long-running executions.

## 2. Business Value

- **Duplicate-run prevention**: Tracks active firings and non-concurrency rules so sensitive jobs do not execute concurrently when overlap is forbidden.
- **Resilient crash recovery**: Identifies which scheduler instance owns an in-flight job so interrupted tasks eligible for recovery can be picked up after an unexpected shutdown.
- **Live operational control**: Surfaces execution state, progress updates, execution grouping, and cancellation request timestamps for running tasks.

## 3. How It Works

When a schedule trigger comes due and a scheduler instance acquires it, a live fired-trigger record is created to represent that active execution.

- **Ownership and timing**: The record tracks which instance claimed the trigger, its priority, its original scheduled time, when it actually fired, and its current execution state.
- **Execution guardrails**: It carries policy flags indicating whether concurrent runs of the job are disallowed and whether the execution should be recovered if the host instance stops unexpectedly.
- **In-flight monitoring**: While the task runs, optional progress values, status messages, execution group labels, and interruption request times can be tracked until the firing completes and the live record is removed.

## 4. Trade-offs & Lessons Learned

- **High-churn runtime data**: Active firing records are inserted, updated, and deleted continuously as jobs start and finish, so database responsiveness and proper indexing directly affect scheduling throughput.
- **Recovery policy accuracy**: Enabling crash recovery ensures critical tasks resume after a node failure, but jobs marked for recovery must be safe to re-run if they were partially completed before the crash.
- **Ephemeral visibility**: Because fired-trigger entries exist only for active executions, they cannot replace long-term audit logs for post-incident review after a job finishes.

### Entity Relationships

- The composite key is `sched_name` and `entry_id`.
- A fired trigger records runtime execution for
  [[entity|qrtz-triggers]] and may reference [[entity|qrtz-job-details]].
- Foreign key references map (`trigger_name`, `trigger_group`) to `qrtz-triggers` and optionally (`job_name`, `job_group`) to `qrtz-job-details`.
- Runtime coordination and progress fields include `instance_name`, `fired_time`, `sched_time`, `priority`, `state`, `is_nonconcurrent`, `requests_recovery`, `execution_group`, `progress`, `progress_message`, and `interrupt_requested_time`.
