## 1. Context & Problem

Standard recurring schedules (such as "every 5 minutes" or "hourly") fit neatly into fixed schedule fields. However, scheduling engines also need a place to persist specialized or custom trigger definitions whose rules do not match standard calendar or simple interval formats. Without a dedicated extension record, custom schedules could not survive service restarts or be shared across clustered scheduler instances.

## 2. Business Value

- **Schedule Durability:** Ensures even non-standard or custom trigger definitions survive restarts and deployments without manual reconfiguration.
- **Cluster Consistency:** Allows multiple scheduler nodes to read the same persisted trigger rules from shared storage rather than keeping schedules in local memory.
- **Extensibility:** Supports specialized scheduling behaviors without forcing schema changes to the core trigger table.

## 3. How It Works

Each custom blob trigger record acts as an extension attached to a parent trigger in the scheduler's core trigger registry. While the parent trigger tracks shared scheduling metadata (such as current state, priority, and next fire time), this extension holds the binary-encoded custom trigger definition alongside the scheduler name, trigger name, and trigger group that uniquely identify it.

Because it is not an independent root entity, its lifecycle is tied directly to its parent trigger: it is created when a custom trigger is registered and removed when that parent trigger is deleted.

## 4. Trade-offs & Lessons Learned

- **Opaque Binary Storage vs. Queryability:** Storing custom trigger rules as binary data makes the schema flexible for specialized triggers, but means operators cannot read or filter the trigger's internal rules directly using plain database queries.
- **No Direct Manual Edits:** Because the payload is serialized by the scheduling engine, modifying or repairing custom trigger records directly in storage risks corrupting the schedule; changes should always go through the scheduler application or dashboard.
- **Coupled Ownership:** Owned exclusively by the Platform team as internal scheduler infrastructure rather than a business domain record.
