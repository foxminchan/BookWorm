## 1. Context & Problem

To achieve high availability and distribute background work, multiple scheduler instances share access to the same persistent schedule store. If two instances attempt to claim the same due trigger or modify schedule state simultaneously without coordination, the platform risks duplicate job executions or inconsistent schedule records.

## 2. Business Value

- **Eliminates duplicate scheduling**: Ensures only one scheduler instance claims or transitions a trigger at any given moment.
- **Protects schedule integrity**: Serializes sensitive updates to jobs, triggers, and scheduling metadata across clustered instances.
- **Enables safe horizontal scaling**: Lets the platform run multiple scheduler workers without requiring separate distributed lock infrastructure.

## 3. How It Works

The scheduler defines a small set of named coordination locks scoped to each scheduler name.

- **Exclusive access for state changes**: Before a scheduler node performs sensitive store operations—such as acquiring due triggers or updating shared schedule state—it acquires the corresponding named lock.
- **Brief serialization across nodes**: While one instance holds the lock, other instances wait until the short state transition completes and the lock is released.
- **Parallel job execution**: Once a trigger is safely claimed and the lock is released, actual job execution proceeds independently across worker instances.

## 4. Trade-offs & Lessons Learned

- **Simplicity vs. lock contention**: Using the relational database for coordination avoids adding extra distributed lock services, but very high trigger acquisition rates or slow transactions can create lock contention across nodes.
- **Keep lock scope brief**: Locks must only guard short schedule-store updates; performing slow external operations while holding a scheduler lock will stall trigger acquisition cluster-wide.
- **Store availability dependency**: Coordinated scheduling relies directly on the latency, availability, and transaction locking behavior of the underlying database.
