Use this guide to navigate BookWorm's domain architecture documentation in the right order—from the top-level bounded-context map down to individual flows, engineering references, and operational runbooks. To set up your machine and run BookWorm locally, follow [[doc|development/000-local-quickstart]]; for the broader repository contributor overview, start with [[doc|development/001-developer-onboarding]].

## Context and motivation

BookWorm spans 10 deployable .NET 11 backend services/functions and 3 Next.js 16 web applications across six bounded contexts. Reading individual endpoint docs or runbooks before understanding domain ownership leads contributors to place business rules in the wrong service or bypass explicit contracts. Following a top-down reading path builds an accurate mental model before you edit code.

## How it works

This reading path moves from whole-system architecture down to service contracts and operational runbooks.

### Recommended reading order

1. **Whole-system map:** Read [[domain|bookworm]] and the [[doc|arc42/00-c4-overview]] to see how all six bounded contexts and three edge apps fit together.
2. **Owning subdomain:** Open the relevant bounded-context page ([[domain|catalog]], [[domain|shopping]], [[domain|ordering]], [[domain|reviews]], [[domain|conversational]], or [[domain|platform]]) to inspect its services, persistence stores, and invariants.
3. **End-to-end runtime flows:** Review the affected flow under `explanation/architecture/flows/` (such as [[flow|user-checkout]] or [[flow|agent-orchestration]]) before altering cross-service messages.
4. **Engineering standards and ADRs:** Check domain engineering checklists, [[doc|development/004-engineering-standards]], and [[doc|arc42/09-architecture-decisions]] before changing contracts or schemas.
5. **Runbooks:** Consult the domain runbooks under `how-to/domain-runbooks/` when diagnosing production or staging incidents.

### Subdomain ownership summary

For full team charters and repository maintainers, see [[team|business-strategy]].

| Subdomain                      | Core responsibility                                                 | Recorded domain owner                                                       |
| :----------------------------- | :------------------------------------------------------------------ | :-------------------------------------------------------------------------- |
| **[[domain\|catalog]]**        | Book metadata, pricing, availability, and hybrid vector search      | Business Strategy _(system co-owned by Platform Team and Contributor Team)_ |
| **[[domain\|shopping]]**       | Customer-scoped mutable basket and pre-order checkout handoff       | Business Strategy                                                           |
| **[[domain\|ordering]]**       | Accepted orders, purchase-time snapshots, and Finance checkout saga | Business Strategy                                                           |
| **[[domain\|reviews]]**        | Individual customer feedback (`Cosmos DB`) and AI summaries         | Business Strategy                                                           |
| **[[domain\|conversational]]** | Privacy-filtered multi-agent chat and read-only Catalog MCP tools   | Contributor Team                                                            |
| **[[domain\|platform]]**       | Recurring Quartz jobs and stateless Kafka-to-SMTP email delivery    | Platform Team                                                               |

## Design trade-offs

| Decision                                                              | Benefits                                                                                                                               | Costs and limits                                                                                         |
| :-------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| **Separate domain ownership from system implementation co-ownership** | Business stakeholders steer domain scope while Platform and Contributor engineers share technical stewardship (for example, `Catalog`) | Contributors must verify both domain boundaries and technical owners before proposing contract changes   |
| **Dedicated reading guide separate from hands-on setup**              | Keeps architecture orientation concise and avoids duplicating `mise` / Aspire setup commands across pages                              | Developers looking to run code locally must follow the link to [[doc\|development/000-local-quickstart]] |

## Alternatives considered

- **Combining local setup, engineering standards, and domain orientation into one monolithic onboarding page:** Mixes Diátaxis tutorials, reference, and explanation, making the page too long for returning readers and prone to setup-command drift.
