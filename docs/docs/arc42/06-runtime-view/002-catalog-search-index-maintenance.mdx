BookWorm decouples catalog writes from semantic search indexing by recording pending book revisions in PostgreSQL (`catalogdb`) and refreshing **Qdrant** (`vectordb`) asynchronously in 200-item batches. Every five minutes, **Scheduler** publishes `ProcessVectorBatchIntegrationEvent` to Kafka, waking the **Catalog Ingestion** Azure Functions worker to generate **Microsoft Foundry** embeddings and update Qdrant under a PostgreSQL advisory lock.

## Scope and constraints

- **Scope:** Propagating book creations, updates, and soft deletes from **Catalog API** (`catalogdb`) into the derived semantic search index in **Qdrant** (`vectordb`) via **Scheduler** and **Catalog Ingestion**.
- **Out of scope:** Customer hybrid-search query execution in **Catalog API** and rating-summary projections (see [[doc|arc42/06-runtime-view/003-feedback-and-rating-projection]]).
- **Key constraints:** **Catalog Ingestion** (`BookWorm.Catalog.Ingestion`) is an internal Azure Functions worker with **no HTTP or gRPC API**. It consumes the unprefixed Kafka topic `scheduler.process-vector-batch` (`AppendPrefix = false`) and reads `catalogdb` directly within the Catalog bounded context.

### Step-by-step behavior

1. **Atomic queue capture:** When **Catalog API** commits a book creation, edit, or soft delete in `catalogdb`, PostgreSQL triggers atomically insert or update a row in `pending_vector_updates` with a fresh `revision` UUID. Multiple edits to the same book before the next batch collapse into one row carrying the latest revision.
2. **Scheduled Kafka trigger:** Every five minutes (`0 0/5 * * * ?` UTC, misfire `FireOnceNow`, `[DisallowConcurrentExecution]`), **Scheduler** executes `ProcessVectorBatchJob`, which publishes `ProcessVectorBatchIntegrationEvent` through Wolverine's PostgreSQL outbox to the unprefixed Kafka topic `scheduler.process-vector-batch`.
3. **Exclusive batch acquisition:** `ProcessVectorBatchFunction` (`[KafkaTrigger]`, consumer group `catalog-ingestion`) deserializes the CloudEvents payload and invokes `VectorBatchProcessor.ProcessAsync`. The processor attempts `SELECT pg_try_advisory_lock(740031001)` on `catalogdb`. If another worker holds the lock, the invocation exits immediately without overlapping work.
4. **Searchable text and embedding generation:** The processor reads up to **200** pending rows ordered by `(updated_at, book_id)`. For active books, it builds a text snippet combining title, description, ordered author names, category, and publisher, then calls **Microsoft Foundry** (`Cohere.EmbedV40`) to generate embeddings in a single batch.
5. **Qdrant sync and revision-safe acknowledgement:** Active snippets upsert into Qdrant (`vectordb`), while missing or soft-deleted books (`is_deleted = true`) have their vector deleted by `BookId`. The processor then deletes processed rows from `pending_vector_updates` **only where both `book_id` and `revision` still match** (`WHERE p.book_id = u.book_id AND p.revision = u.revision`). Any concurrent edit that advanced `revision` while the batch ran survives automatically for the next five-minute cycle.

## Failure and recovery semantics

- **Lock contention or empty queue:** A busy advisory lock (`740031001`) or empty `pending_vector_updates` table returns `0` cleanly with no error, preventing duplicate embedding calls or out-of-order Qdrant overwrites.
- **Incomplete embeddings or Qdrant failure:** If Microsoft Foundry returns an incomplete embedding batch or Qdrant throws an error, `VectorBatchProcessor` aborts before running the `DELETE` acknowledgement. All unprocessed rows remain in `pending_vector_updates` for the next batch, and the `finally` block releases the advisory lock.
- **Scheduler status does not prove index freshness:** A successful `ProcessVectorBatchJob` run confirms only that `ProcessVectorBatchIntegrationEvent` reached Kafka. Monitor `pending_vector_updates` row count and oldest `updated_at` age in `catalogdb` alongside Qdrant and Foundry health.

## Quality scenarios and known risks

| Quality attribute / risk | Scenario or exposure                                                      | Current mitigation or gap                                                                                                                                 |
| :----------------------- | :------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Freshness lag**        | Bulk import inserts 1,000 new books at once.                              | Fixed 5-minute schedule and 200-book batch cap mean 1,000 books require ~25 minutes (5 cycles) to finish indexing.                                        |
| **Concurrency safety**   | An administrator edits a book while its prior revision is being embedded. | Conditional `DELETE ... WHERE book_id = u.book_id AND revision = u.revision` preserves the newer revision for the next cycle.                             |
| **Test coverage gap**    | Regression in `VectorBatchProcessor` batch or lock logic.                 | `BookWorm.Catalog.Ingestion` currently has no dedicated `.UnitTests` project (see [[doc\|arc42/08-crosscutting-concepts/006-testing-and-change-safety]]). |
