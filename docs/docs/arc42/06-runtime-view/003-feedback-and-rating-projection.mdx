BookWorm separates authoritative customer reviews from catalog read performance by storing individual `Feedback` documents in **Rating API** (**Azure Cosmos DB**) and projecting derived average ratings and review counts onto **Catalog API** (**PostgreSQL**) over Kafka. If a customer submits feedback for a non-existent book, **Catalog API** emits a failure event so **Rating API** compensates by deleting the orphaned record without distributed locks.

## Scope and constraints

- **Scope:** Creating and deleting `Feedback` records in **Rating API**, asynchronous rating-summary updates in **Catalog API**, and invalid-book compensation back to **Rating API**.
- **Out of scope:** AI-generated review summarization via `rating-agent` (see [[doc|arc42/06-runtime-view/004-conversational-book-discovery]]) and catalog search indexing (see [[doc|arc42/06-runtime-view/002-catalog-search-index-maintenance]]).
- **Key constraints:** **Rating API** uses **Azure Cosmos DB** (`ratingdb`, container `feedbacks`, partition key `/bookId`) with EF Core Cosmos and Wolverine Cosmos DB persistence (`UseCosmosDbPersistence`)—**not PostgreSQL**. **Catalog API** never queries Cosmos DB; it stores only the derived average rating and review count on `Book`.

### Step-by-step behavior

1. **Feedback write in Reviews:** A customer (via **Storefront**) or administrator (via **Backoffice**) sends `POST /rating/api/v1/feedbacks` or `DELETE /rating/api/v1/feedbacks/{id}` through **API Gateway**. **Rating API** validates the payload (`FluentValidation`) and persists or removes the `Feedback` document in Azure Cosmos DB (`ratingdb` / `feedbacks`, partitioned by `/bookId`).
2. **Event publication:** After committing the change, **Rating API** publishes `FeedbackCreatedIntegrationEvent` (`bookworm.{env}.rating.feedback-create`) or `FeedbackDeletedIntegrationEvent` (`bookworm.{env}.rating.feedback-delete`) using Wolverine Cosmos DB persistence. Both services partition Kafka messages by `BookId` and `FeedbackId` so concurrent updates for the same book process in partition order.
3. **Derived projection update:** **Catalog API** consumes the event through its PostgreSQL Wolverine inbox (`wolverine` schema) and Redis idempotency guard (`IIntegrationEventIdempotencyGuard`), then recalculates the book's derived average rating and review count in `catalogdb` and invalidates affected FusionCache entries.
4. **Invalid-book compensation:** If `FeedbackCreatedIntegrationEvent` references a `BookId` that does not exist in `catalogdb`, **Catalog API** publishes `BookUpdatedRatingFailedIntegrationEvent` (`bookworm.{env}.catalog.book-update-rating-failed`). **Rating API** consumes this event and deletes the orphaned `Feedback` document from Cosmos DB.

## Consistency, retries, and operational boundaries

- **Eventual consistency window:** New or deleted reviews appear immediately in **Rating API**, while the aggregate rating displayed on catalog listings updates moments later after Kafka processing completes.
- **Strict domain separation:** **Reviews** owns individual `Feedback` records (comment, rating value, reviewer); **Catalog** owns only the derived numeric rating summary. Never treat Catalog's projection as a copy of review history.
- **Retry and dead-letter behavior:** Transient database or broker failures retry with Wolverine's `50ms`, `250ms`, and `1s` full-jitter cooldowns before moving exhausted envelopes to `bookworm.{env}.catalog.dead-letter-queue` or `bookworm.{env}.rating.dead-letter-queue` (7-day expiration).

## Quality scenarios and known risks

| Quality attribute / risk    | Scenario or exposure                                                                      | Current mitigation or gap                                                                                                                                  |
| :-------------------------- | :---------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Read scalability**        | High traffic browses catalog pages with star ratings.                                     | **Catalog API** reads precomputed rating summaries from `catalogdb` and Redis FusionCache without cross-service calls to **Rating API**.                   |
| **Cross-service integrity** | Client submits feedback for a deleted or fabricated `BookId`.                             | Explicit compensation via `BookUpdatedRatingFailedIntegrationEvent` deletes the invalid `Feedback` document from Cosmos DB.                                |
| **Projection drift**        | Kafka consumer lag or DLQ buildup causes displayed rating counts to lag behind Cosmos DB. | Track Catalog consumer lag and `bookworm.{env}.catalog.dead-letter-queue` independently of Rating write availability; see Rating summary mismatch runbook. |
