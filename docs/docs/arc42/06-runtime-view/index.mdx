The runtime view explains how BookWorm's services collaborate over time across five representative commerce, discovery, feedback, AI, and platform journeys. Use this chapter to trace synchronous request paths, asynchronous Kafka choreography, compensation boundaries, and authoritative state ownership across bounded contexts.

## Scope and constraints

- **Scope:** End-to-end runtime interactions across BookWorm's microfrontends (**Storefront**, **Commerce**, **Backoffice**), **API Gateway** (YARP), 10 backend services/workers, and their backing data stores and brokers.
- **Out of scope:** Exhaustive CRUD endpoint documentation (see [[doc|platform/006-api-and-contracts]]) and Azure hosting/networking topology (see [[doc|arc42/07-deployment-view]]).
- **Key constraint:** Each bounded context owns its private persistence store. Services never share databases and interact exclusively through versioned HTTP/REST APIs, gRPC, Kafka CloudEvents, AG-UI, Agent-to-Agent (A2A) gRPC, or Model Context Protocol (MCP).

## Authoritative state ownership

| Bounded context    | Authoritative owner              | Persistence store                                             | Owned business state                                                                                           | Derived or transient state elsewhere                                                                                           |
| :----------------- | :------------------------------- | :------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| **Catalog**        | **Catalog API**                  | PostgreSQL (`catalogdb`) + Azure Blob (`catalog-blob`)        | Canonical books, authors, categories, publishers, prices, cover images, pending vector queue                   | Qdrant (`vectordb`) semantic index; derived average rating & review count on `Book`; purchase-time price snapshots in Ordering |
| **Shopping**       | **Basket API**                   | Redis (`redis`)                                               | Customer-scoped mutable pre-order baskets                                                                      | None (no relational DB)                                                                                                        |
| **Ordering**       | **Ordering API**                 | PostgreSQL (`orderingdb`, EF Core + Marten event store)       | Accepted orders, immutable purchase snapshots, lifecycle statuses (`New`, `Cancelled`, `Completed`)            | Durable orchestration state in **Finance** (`finance-taskhub`)                                                                 |
| **Reviews**        | **Rating API**                   | Azure Cosmos DB (`ratingdb`/`feedbacks`, partition `/bookId`) | Individual customer `Feedback` records                                                                         | Derived book rating summary in **Catalog API**                                                                                 |
| **Conversational** | **Chat API**                     | Azure Blob Storage (`chatting-blob`, prefix `ag-ui/`)         | AG-UI conversation session transcripts                                                                         | None (read-only access to Catalog via MCP and Rating via A2A)                                                                  |
| **Platform**       | **Scheduler** / **Notification** | PostgreSQL (`schedulerdb`) / Redis (`redis`)                  | Quartz job definitions and 30-day history (**Scheduler**); 24-hour email deduplication keys (**Notification**) | Notification holds no persistent email outbox                                                                                  |

## Cross-scenario runtime invariants

1. **Authoritative state stays with its owner:** Downstream caches, search indexes, rating projections, and saga states are derived or operational views. Always query the owning service to confirm business truth.
2. **Handoff is not completion:** Returning `201 Created`, publishing a Kafka command, firing a Quartz trigger, or receiving SMTP `250 OK` proves only that the handoff succeeded—not that downstream processing or mailbox delivery finished.
3. **At-least-once delivery requires idempotent consumers:** Network retries, Wolverine cooldown retries (`50ms / 250ms / 1s`), and Finance saga reissues can repeat work. Consumers rely on PostgreSQL/Cosmos DB durable inboxes or Redis 24-hour idempotency guards to stay safe.
4. **Explicit compensation beats distributed locks:** When cross-service invariants fail asynchronously (such as failed basket cleanup or feedback referencing a missing book), services emit explicit failure events to trigger bounded compensation rather than holding cross-service transactions.
