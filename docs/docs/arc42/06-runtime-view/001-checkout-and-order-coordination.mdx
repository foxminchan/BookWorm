## 6.1 Checkout and Order coordination

Checkout turns a customer's mutable Basket into an Order owned by Ordering. The Order API reads the persisted Basket and current Catalog facts, stores the accepted purchase and its item-price snapshot, and returns the Order ID. It then publishes a checkout event for Finance's asynchronous coordination workflow.

### Interaction and ownership

1. The storefront submits checkout to Ordering.
2. Ordering reads the customer's persisted quantities from Basket and resolves current book details and prices from Catalog. Shopping and Catalog remain the sources of truth for those respective records.
3. Ordering persists the new Order and purchase-time item snapshot before returning `201 Created` with the Order ID.
4. The checkout event starts a Finance saga correlated by Order ID. Finance persists coordination state and publishes `PlaceOrderCommand`, which is consumed independently by Basket and Notification.
5. Basket deletes the submitted Basket and reports an explicit success or failure outcome. Finance forwards that cleanup outcome to Ordering; cleanup success is not Order completion.
6. On cleanup failure, Ordering may soft-delete the Order if it is still present. This does not change its business status or mean Ordering published a cancellation event.

### Timeout and failure behavior

Finance schedules a 30-minute timeout and allows a maximum of three attempts (the initial command and up to two reissues). An unresolved cleanup outcome can therefore cause `PlaceOrderCommand` to be published again. Because Basket and Notification consume that command independently, repeated processing can repeat cleanup and email work.

Finance timeout exhaustion cancels the saga and may request a cancellation email when recipient details are available. It does **not** call Ordering to cancel the Order. Confirm the Order's actual status through Ordering rather than inferring it from the Basket, saga state, or an email.
