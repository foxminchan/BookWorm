Customer checkout converts a mutable Redis basket into an authoritative, purchase-time order snapshot in **Ordering API** (PostgreSQL + Marten) before handing post-checkout basket cleanup and email dispatch to **Finance** (Azure Durable Functions). This split returns an immediate `201 Created` order ID to **Commerce** while isolating checkout latency from asynchronous cleanup and email delivery.

## Scope and constraints

- **Scope:** Synchronous order creation from **Commerce** (`/basket`, `/checkout`) through **API Gateway** (YARP) to **Ordering API**, synchronous gRPC reads to **Basket API** and **Catalog API**, and asynchronous saga coordination across **Finance**, **Basket API**, **Ordering API**, and **Notification**.
- **Out of scope:** Payment gateway settlement (**Finance** is an order-coordination saga orchestrator, not a payment processor) and post-order administrative fulfillment workflows.
- **Key constraints:** Mutating `POST` and `PATCH` endpoints on **Ordering API** require an `x-request-id` header enforced by `IdempotencyEndpointFilter` (atomic Redis `SET NX`, 1-hour TTL). All checkout Kafka topics partition by `OrderId` to preserve per-order message ordering.

### Step-by-step behavior

1. **Idempotent checkout submission:** **Commerce** submits `POST /ordering/api/v1/orders` through **API Gateway** with a unique `x-request-id` header and Microsoft Entra ID bearer token (`customer` role + `ordering_write` scope). **Ordering API** atomically claims `POST:/api/v1/orders:{requestId}` in Redis (`When.NotExists`, 1-hour TTL), returning `409 Conflict` for duplicates and deleting the key if a `5xx` error or exception occurs.
2. **Authoritative fact assembly:** **Ordering API** reads current item quantities from **Basket API** over gRPC (`GetBasket`) and resolves authoritative book titles and prices from **Catalog API** over gRPC (`GetBooks`).
3. **Order persistence and immediate response:** **Ordering API** persists the new `Order` with an immutable purchase-time item/price snapshot in PostgreSQL (`orderingdb`), records the domain event in Marten (`OrderSummary` projection), writes `UserCheckedOutIntegrationEvent` to its PostgreSQL Wolverine outbox in the same transaction, and returns `201 Created` with the order ID.
4. **Saga start and parallel fan-out:** **Finance** receives `UserCheckedOutIntegrationEvent` (`bookworm.{env}.ordering.user-checked-out`) via Kafka trigger, starts an `OrderOrchestrator` instance correlated by `OrderId` in Azure Durable Task Scheduler (`finance-taskhub`), registers a `CancelOrderCommand` compensation if an email address exists, and publishes `PlaceOrderCommand` (`bookworm.{env}.finance.place-order`).
5. **Independent downstream consumption:**
   - **Basket API** consumes `PlaceOrderCommand`, deletes the customer's basket from Redis, and publishes `BasketDeletedCompleteIntegrationEvent` (`bookworm.{env}.basket.delete-complete`) or `BasketDeletedFailedIntegrationEvent` (`bookworm.{env}.basket.delete-failed`).
   - **Notification** consumes `PlaceOrderCommand` independently, checks its 24-hour Redis idempotency guard, renders the MJML order confirmation template, and sends the email via MailKit SMTP (Mailpit locally, SendGrid SMTP in cloud).
6. **Outcome forwarding and compensation:** **Finance** forwards the basket outcome to **Ordering API** via `DeleteBasketCompleteCommand` (`bookworm.{env}.finance.delete-basket-complete`) or `DeleteBasketFailedCommand` (`bookworm.{env}.finance.delete-basket-failed`). On cleanup failure, **Ordering API** may soft-delete the order if still present without changing its business status to `Cancelled` or publishing a business cancellation event.

## Timeout, retry, and consistency rules

- **Bounded retry window:** `OrderStateMachine` defaults (`src/Services/Finance/BookWorm.Finance/appsettings.json`) set `MaxAttempts: 3` and `MaxRetryTimeout: 00:30:00` (30 minutes). If basket cleanup remains unresolved when a timer expires, **Finance** reissues `PlaceOrderCommand` (up to 2 reissues after the initial publish).
- **Duplicate downstream work:** Reissuing `PlaceOrderCommand` triggers both **Basket API** and **Notification** again. Deleting an already-absent basket is safe, while a reissued `PlaceOrderCommand` with a new message ID can cause **Notification** to send a second confirmation email.
- **Timeout expiration does not cancel the order:** When all 3 attempts exhaust the coordination window, **Finance** runs its registered compensation—publishing `CancelOrderCommand` (`bookworm.{env}.finance.cancel-order`) to **Notification** if customer email details exist—and terminates the orchestration. **Finance** does not call **Ordering API** to transition the order to `Cancelled`.
- **Authoritative status verification:** Never infer order status from a missing basket, an expired Finance orchestration, or a cancellation email. Always read authoritative order status (`New`, `Cancelled`, `Completed`) from **Ordering API**.

## Quality scenarios and known risks

| Quality attribute / risk | Scenario or exposure                                                                                                 | Current mitigation or gap                                                                                                                        |
| :----------------------- | :------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Performance**          | Checkout completes while SMTP provider is slow or degraded.                                                          | Order commits synchronously in **Ordering API** (`201 Created`); basket cleanup and email dispatch run asynchronously via Kafka and **Finance**. |
| **Data consistency**     | Book price changes in **Catalog API** immediately after checkout.                                                    | **Ordering API** stores an immutable purchase-time price snapshot at order creation; later catalog price edits do not alter existing orders.     |
| **Compensation clarity** | Finance times out after 30 minutes and sends a cancellation email while the order remains `New` in **Ordering API**. | Documented operational boundary: support and operators verify order state in **Ordering API** and follow Ordering runbooks.                      |
