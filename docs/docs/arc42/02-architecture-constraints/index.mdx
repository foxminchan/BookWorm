This chapter defines the guardrails for decisions that shape BookWorm across .NET 11 services, Next.js 16 microfrontends, and Aspire 17 orchestration. It separates mandatory constraints from engineering conventions and open commitments: constraints limit options, while principles guide choices and exceptions.

The catalog distinguishes:

- **Mandatory constraints:** changes require an approved exception or an architecture decision record (ADR).
- **Engineering conventions:** repository standards that automated checks or review should enforce.
- **Open commitments:** targets or controls that are not yet signed off and must not be presented as guarantees.

## Executive summary

- Preserve bounded-context ownership and explicit interoperability.
- Resolve breaking changes through impact and migration planning.
- Name an owner and approver for every material exception.
- Enforce platform standards and evidence-based architecture changes.
- Avoid uncontrolled technology, compliance, vendor, or operational commitments.

BookWorm is an open-source reference architecture. It does not, by itself, establish organization-specific procurement mandates, staffing models, regulatory certification, approved service levels, or named production approvers.

## Architecture constraint principles

These principles translate architecture governance into practical BookWorm rules.

1. **Domain ownership is explicit.** One bounded context owns one domain and its authoritative data.
2. **Contracts are products.** Consumers depend on stable, versioned interfaces owned and evolved by a producer.
3. **Standards reduce variance.** Approved runtimes, frameworks, protocols, and verification tools take precedence over local alternatives.
4. **Independent deployment follows compatibility.** Deployment autonomy is earned through validated contracts and operational readiness.
5. **Infrastructure is supportive.** Shared platform components must not become hidden domain owners or transaction coordinators.
6. **Decisions must be traceable.** Material changes include an ADR, updated documentation, and recorded evidence.
7. **Gaps remain visible.** Proposed targets remain proposals until scope, owners, budgets, and acceptance evidence are approved.

## Organizational constraints

| ID      | Mandatory constraint                                                                                                                                                           | Enforcement and governance                                                                                                                   |
| :------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------- |
| **OC1** | **Assign bounded-context ownership.** Every service, contract, and cross-context flow has an explicit owner and escalation path before production adoption or boundary change. | Architecture review confirms ownership; the owning team maintains implementation and contract evolution.                                     |
| **OC2** | **Keep architecture artifacts synchronized.** Behavior, contract, persistence, or boundary changes update the relevant architecture views and ADR set.                         | Pull-request review and documentation/architecture fitness checks identify drift.                                                            |
| **OC3** | **Protect credentials and toolchain baselines.** Secrets remain outside source control. SDK and package-feed configuration changes require explicit approval.                  | GitHub Actions or Azure OIDC, user secrets, or environment variables contain credentials; `global.json` and `NuGet.config` remain protected. |
| **OC4** | **Record material architecture decisions.** Non-reversible or cross-team decisions require an ADR describing context, options, consequences, and ownership.                    | Accepted ADRs are reviewed and linked to implementation, roadmap, and operational runbooks.                                                  |
| **OC5** | **Use evidence for production commitments.** Availability, recovery, latency, privacy, security, and AI safeguards require frozen test conditions and recorded evidence.       | Service owners report evidence; designated review forums grant production status.                                                            |

## Architecture governance

Architecture governance should make constraints visible, proportionate, and reviewable before implementation.

| Governance stage            | Required output                                                                                        | Decision authority                        |
| :-------------------------- | :----------------------------------------------------------------------------------------------------- | :---------------------------------------- |
| **Architecture principles** | Confirm that the proposal follows the principles in this chapter                                       | Architecture review                       |
| **Baseline and target**     | Compare current and target business, application, data, and technology states                          | Product and architecture review           |
| **Impact assessment**       | Identify affected bounded contexts, consumers, data, security, operations, cost, and rollout risk      | Domain owners and delivery management     |
| **Decision and roadmap**    | Record an ADR and sequence migrations, compatibility periods, and verification                         | Delegated architecture authority          |
| **Implementation review**   | Demonstrate contract compatibility, automated checks, operational readiness, and documentation updates | Engineering leads and governance forum    |
| **Benefit and risk review** | Record outcomes and unresolved risks against the approved target                                       | Executive sponsor and architecture review |

### Exception process

An exception is a documented, time-bound deviation; it is not an informal bypass.

1. Identify the constraint or convention, affected systems, and the reason the baseline is unsuitable.
2. Assess user, security, compliance, delivery, cost, operability, and migration impacts.
3. Define compensating controls, an expiry or exit condition, and a named accountable owner.
4. Obtain approval from the authority appropriate to the risk.
5. Record the exception in an ADR or governed exception register.
6. Review the exception before expiry and remove or renew it with evidence.

## Open commitments and scope limits

The following items require formal approval and are intentionally not represented as current guarantees:

- Numerical latency, availability, throughput, freshness, recovery, and retention budgets.
- Named production SLAs, RTO/RPO targets, and contractual compliance obligations.
- Organization-specific regulatory scope, security certification, vendor procurement, and staffing requirements.
- End-to-end operational evidence for all proposed quality scenarios.

Unresolved numerical budgets belong in the quality requirements and decisions records rather than this constraint catalog.
