BookWorm protects services from invalid inputs, duplicate submissions, traffic spikes, and transient downstream outages by combining a pre-handler `FluentValidation` pipeline (`Mediator.SourceGenerator`), standardized RFC 9457 `ProblemDetails` exception mapping, layered ASP.NET Core rate limiting, atomic Redis idempotency guards, and targeted Polly/FusionCache resilience policies.

## Request validation and error-handling pipeline

This flowchart shows how an incoming HTTP request traverses rate limiting, optional idempotency, `FluentValidation`, and standardized exception mapping before reaching domain persistence.

### Standardized HTTP and gRPC error mapping

Each API host explicitly registers `AddValidationExceptionHandler()`, `AddNotFoundExceptionHandler()`, `AddGlobalExceptionHandler()`, and `AddProblemDetails()` from `BookWorm.Chassis.Exceptions` (gRPC services add `GrpcExceptionInterceptor`).

| Exception or condition                                                         | Handler                                                | HTTP status                 | Caller response behavior                                                                   |
| :----------------------------------------------------------------------------- | :----------------------------------------------------- | :-------------------------- | :----------------------------------------------------------------------------------------- |
| `FluentValidation.ValidationException`                                         | `ValidationExceptionHandler`                           | `400 Bad Request`           | Field-grouped `ValidationProblemDetails`                                                   |
| `ArgumentException`, `ArgumentNullException`, `ArgumentOutOfRangeException`    | `GlobalExceptionHandler`                               | `400 Bad Request`           | Safe generic message + `traceId`                                                           |
| Domain not-found exception                                                     | `NotFoundExceptionHandler`                             | `404 Not Found`             | `ProblemDetails` without internal stack trace                                              |
| `InvalidOperationException`, `NotSupportedException`, duplicate `x-request-id` | `GlobalExceptionHandler` / `IdempotencyEndpointFilter` | `409 Conflict`              | State conflict or duplicate operation `ProblemDetails`                                     |
| `DbUpdateConcurrencyException`                                                 | `GlobalExceptionHandler`                               | `412 Precondition Failed`   | Prompts caller to retry with latest entity version / ETag                                  |
| Rate limiter rejection                                                         | `AddRateLimiting()`                                    | `429 Too Many Requests`     | `ProblemDetails` + `Retry-After` header                                                    |
| Any unhandled exception                                                        | `GlobalExceptionHandler`                               | `500 Internal Server Error` | Flushes `GlobalLogBuffer`, logs full error internally, returns generic message + `traceId` |

## Rate limiting and load shedding

`AddRateLimiting()` in `BookWorm.ServiceDefaults` (`Kestrel/RateLimiterExtensions.cs`) protects API hosts against burst traffic and resource exhaustion:

- **Global chained limiter:** Combines concurrency load-shedding (`PermitLimit = 100`, `QueueLimit = 0`) with a per-IP/Host fixed-window limiter (`30` requests per `1 minute`, `QueueLimit = 0`).
- **Named `PerUserRateLimit` policy:** Token bucket keyed by user `NameIdentifier` (`TokenLimit = 30`, `TokensPerPeriod = 20`, `ReplenishmentPeriod = 10s`, `QueueLimit = 5`), applied to expensive endpoints such as **Chat API** `/ag-ui`.
- **Kestrel transport limits:** `RequestHeadersTimeout = 10s`, HTTP/2 `MaxStreamsPerConnection = 250`, `InitialConnectionWindowSize = 1 MB`, `InitialStreamWindowSize = 768 KB`, `KeepAlivePingDelay = 30s`, `KeepAlivePingTimeout = 10s`.

## Idempotency controls

| Boundary                                       | Mechanism                                                           | Scope & TTL                                                                                                                                        | Failure / rollback behavior                                                                                                                                           |
| :--------------------------------------------- | :------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ordering API** HTTP writes (`POST`, `PATCH`) | `IdempotencyEndpointFilter` + `RequestManager.TryCreateAsync`       | Requires `x-request-id` header; atomic Redis `StringSetAsync(..., When.NotExists)` keyed as `{method}:{path}:{requestId}` for **1 hour (`3600s`)** | Returns `409 Conflict` on duplicate key; automatically deletes the Redis key if the handler returns `>= 500` or throws an unhandled exception so safe retries succeed |
| **Kafka integration event consumers**          | `IIntegrationEventIdempotencyGuard` (`FusionCacheIdempotencyGuard`) | Atomic Redis `SET NX` keyed as `idempotency:{consumerName}:{eventId:N}` for **24 hours** (mirrored to FusionCache L1)                              | Releases the Redis key on handler failure so Wolverine retries can re-execute                                                                                         |

## Capability-specific resilience policies

- **Outbound `HttpClient` defaults:** `BookWorm.ServiceDefaults` configures service discovery and the standard resilience handler with **budgeted retries** (`UseBudgetedRetries()`) to prevent retry storms across service hops.
- **FusionCache (L1 + L2 Redis):** `BookWorm.Chassis.Caching` configures FusionCache `2.10.0` with Redis distributed cache, Redis backplane, distributed Redis locking, **2-hour fail-safe** (serving stale values during backing-store outages), and soft/hard timeouts.
- **Notification SMTP pipeline (`AddMailResiliencePipeline`):** Wraps `MailKitSender` in a Polly pipeline combining a circuit breaker, exponential backoff retry with jitter, and a **30-second timeout** for transient `CommandException`, `ProtocolException`, `IOException`, `TimeoutException`, and `TimeoutRejectedException` faults. Notification uses Redis idempotency and Kafka DLQ—not a database outbox (see [[doc|arc42/06-runtime-view/005-notification-delivery-and-maintenance]]).
- **Finance checkout saga:** `OrderOrchestrator` (Azure Durable Functions) enforces `MaxAttempts: 3` and `MaxRetryTimeout: 00:30:00` before running compensation without mutating authoritative order status in **Ordering API** (see [[doc|arc42/06-runtime-view/001-checkout-and-order-coordination]]).
- **Wolverine Kafka retries:** Retries transient transport/DB faults with `50ms`, `250ms`, and `1s` full-jitter cooldowns before routing exhausted messages to per-service native DLQs (see [[doc|arc42/08-crosscutting-concepts/002-contracts-and-messaging]]).

## Operational limits and trade-offs

- **Per-host registration required:** Exception handlers, rate limiting, and idempotency filters live in shared packages but take effect only when registered on each host's startup and endpoint pipeline.
- **Retries do not prove business completion:** Always confirm final state against the owning service rather than assuming a retried HTTP call, Kafka command, or SMTP send completed exactly once.
- **No universal retry budget:** Safe reads and idempotent state checks use automated retries; mutating commands and external side effects rely on explicit idempotency keys and bounded compensations.
