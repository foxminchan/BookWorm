## 1. Context & Problem

When a customer action travels across multiple services and asynchronous events, troubleshooting failures with isolated plain-text logs becomes slow and unreliable. At the same time, overly verbose logging can overwhelm monitoring tools with routine noise or accidentally capture sensitive customer information.

BookWorm establishes a consistent baseline of operational signals—structured logs, distributed traces, performance metrics, and process health checks—so teams can see where work ran and which capability owns a failure without compromising privacy.

## 2. Business Value

- **Faster incident resolution:** Shared trace references connect customer-reported errors directly to the exact cross-service execution path.
- **Consistent operational visibility:** Every service built on shared defaults emits structured logs, traces, and metrics in a uniform format without extra per-team boilerplate.
- **Built-in privacy hygiene:** Default command and event logging captures operation names, timing, and structure rather than raw customer payloads.
- **Cleaner monitoring signals:** Routine health checks are filtered out of request traces, keeping diagnostics focused on real business traffic.

## 3. How It Works

Every BookWorm service host built on the shared service defaults follows a consistent observability flow:

1. **Unified signal collection:** Incoming requests, outgoing service calls, asynchronous message handling, and runtime health metrics are instrumented automatically and linked with shared correlation identifiers.
2. **Environment-aware detail:** During local development, all traces are captured to aid debugging. In deployed environments, trace sampling can be tuned probabilistically and exported to the organization's chosen monitoring backend when configured.
3. **Privacy-conscious logging:** Command and query logging records which operation ran, how long it took, and what fields were present—without recording the actual customer-supplied values. Services handling classified information also apply dedicated redaction rules.
4. **Correlating customer errors and async flows:** When an unexpected failure occurs at an API boundary, the caller receives a generic error containing a trace identifier. Support or engineering teams use that identifier—and propagated request or user identifiers for background events—to locate the failing step and then inspect the owning service's business state.
5. **Process health checks:** Services expose liveness and readiness checks to indicate whether a running process is healthy and able to accept traffic.

## 4. Trade-offs & Lessons Learned

- **Telemetry proves execution, not business completion:** A trace or log entry shows that code ran or a message was picked up, not that a business outcome succeeded or satisfied a service-level objective. Teams must check the owning service's state to confirm business completion.
- **No universal production backend or SLA targets assumed:** The codebase standardizes signal generation and export hooks, leaving dashboarding, retention, alert thresholds, latency targets, and recovery objectives to be agreed with stakeholders for each deployment.
- **Health endpoints differ between local and deployed setups:** Default readiness and liveness endpoints are mapped automatically in local development only; production probe paths and behavior must be explicitly verified against the deployed host configuration.
- **Sampling trades completeness for cost:** Full tracing works well in development, while probabilistic sampling in production balances diagnostic coverage against telemetry volume and cost.
- **Discipline at service boundaries:** Teams must actively avoid logging tokens, secrets, or raw user content and enable redaction wherever classified data is processed.

## 5. Technical Reference

### Telemetry, Tracing, and Logging Defaults

- **Shared Aspire service defaults:** Configure structured logging, log enrichment, and OpenTelemetry covering ASP.NET Core requests, outgoing HTTP clients, runtime metrics, and gRPC/HTTP client traces.
- **Distributed tracing & filtering:** Uses W3C activity identifiers; health-check requests are excluded from request tracing to reduce noise. Development environments sample traces at 100%, while non-development environments use a configurable probabilistic sampler. Telemetry exports via OTLP when an exporter endpoint is configured.
- **Messaging instrumentation:** When the shared Wolverine event framework is enabled, it adds Wolverine and Kafka trace sources, logs message starts at `Debug` level, and propagates request and user identifiers in envelope correlation without including message payloads in traces.
- **CQRS logging behavior:** Records message and response type names, elapsed time, and property names without serializing request or response object values. Hosts handling classified data must enable the applicable redaction configuration (see [[doc|arc42/08-crosscutting-concepts/001-security-and-privacy]]).

### Health Endpoints & Diagnostics

- **Health checks:** Shared defaults register a liveness health check. Default readiness and liveness HTTP endpoints are mapped only in development within the shared service-defaults extension; verify deployed host configuration for production probes.
- **Exception correlation:** Unhandled HTTP exceptions are logged with a trace identifier and returned in the generic error response so operators can correlate client reports with telemetry.
