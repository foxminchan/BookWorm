## 1. Context & Problem

In a modular platform like BookWorm, different business capabilities—such as catalog management, shopping baskets, ratings, and ordering—evolve at different speeds. If one capability reads or writes directly inside another capability's internal database, small internal changes can unexpectedly break other parts of the business, blur ownership of business rules, and make releases risky.

BookWorm solves this by requiring capabilities to interact exclusively through explicit, published contracts and asynchronous business announcements. Each capability owns both the meaning and the lifecycle of its data.

## 2. Business Value

- **Clear business ownership:** Each team controls its own business rules and internal data without external consumers coupling to private storage details.
- **Safer, faster delivery:** Teams can evolve internal implementations independently as long as published contracts remain compatible.
- **Resilient cross-capability workflows:** Asynchronous event delivery allows downstream capabilities to react to business changes without requiring every downstream system to be online at the exact same moment.
- **End-to-end traceability:** Correlating originating request and user context across asynchronous steps helps support and operations teams trace a business flow from start to finish.

## 3. How It Works

BookWorm connects capabilities using two main styles of interaction:

1. **Direct service contracts (request/response):** When one capability needs an immediate answer or action from another, it calls a published service interface rather than accessing internal logic or data storage directly.
2. **Asynchronous business events (publish/subscribe):** When something meaningful happens in one capability—such as new customer feedback being created—the owning capability publishes an event announcement. Interested capabilities listen to that announcement and update their own local view without taking ownership of the source data.

To keep asynchronous announcements reliable and traceable:

- **Durable message handling:** When a message broker is active for a host, outgoing announcements and incoming receipts are durably recorded alongside local state changes so work is not silently lost during process restarts.
- **Correlation context:** Message envelopes carry routing metadata along with the originating request and user identifiers where available, linking downstream work back to the initiating user action.
- **Coordinated contract changes:** Updating any shared contract follows a disciplined five-step process:
  1. Identify the owning capability and all known consumers.
  2. Prefer additive changes that preserve existing consumer behavior.
  3. Verify asynchronous contract compatibility between consumers and providers before release.
  4. Run schema linting and breaking-change checks against the committed baseline for binary service interfaces.
  5. Update service and flow documentation whenever business meaning—not just field structure—changes.

## 4. Trade-offs & Lessons Learned

- **Eventual consistency over shared databases:** Downstream views (such as catalog feedback projections) may lag slightly behind the source capability. This is an intentional trade-off to preserve service independence and resilience.
- **At-least-once delivery requires duplicate safety:** Durable storage protects work across restarts, but it does not guarantee that a business effect happens only once. Consumers must tolerate repeated delivery and rely on their own owned state to detect whether work is already complete.
- **Host-dependent messaging activation:** The durable messaging transport is only enabled when a broker connection is configured; hosts without a broker configuration skip transport setup rather than failing to start, so deployment configuration determines whether asynchronous paths are active.
- **Correlation is not authorization:** Propagated request and user identifiers exist strictly for tracing and diagnosis—they must never be treated as security credentials or proof of permission.

## 5. Technical Reference

### Contract Forms

- **HTTP APIs:** Expose service-owned REST operations, with OpenAPI documents defining the REST contracts where provided. Clients must use the owning service's contract rather than coupling to internal handlers or persistence models.
- **gRPC APIs:** Use Protocol Buffer (`.proto`) definitions for the documented [[service|basket-api]] and [[service|catalog-api]] interfaces. Schema changes must pass Protocol Buffer lint and breaking-change checks against the committed baseline before consumers adopt them or update the baseline.
- **Integration events:** Use shared contract types following the `IntegrationEvent` naming pattern with explicit ownership and identity metadata for routing. Contracts describe the boundary, not the implementation's persistence model—for example, [[event|FeedbackCreatedIntegrationEvent]] communicates a feedback change without making Catalog authoritative for the source feedback data.

### Event Transport, Durability, and Correlation

- **Broker & outbox/inbox:** Where a broker connection string is configured, the shared Wolverine integration configures Kafka transport with CloudEvents-compatible mapping and per-service PostgreSQL durable outbox and inbox policies. The [[system|product-catalog-system]] and [[system|rating-system]] use this path for their documented feedback projection. When no broker connection string is present, the event framework returns without configuring a transport.
- **Native dead-letter channels & retry policy:** Each Wolverine host configures a per-service Kafka dead-letter topic named `bookworm.{env}.{service}.dead-letter-queue` via `KafkaTopicRouter.CreateDeadLetterTopicName` and attaches `EnableNativeDeadLetterQueue()` to every handled integration topic (`[WolverineHandler]`). `ConfigureDefaultErrorHandling` retries transient failures (`TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, and transient `NpgsqlException`) with `50ms`, `250ms`, and `1s` full-jitter cooldowns before moving exhausted envelopes to the error queue, moves `JsonException` deserialization errors immediately, and sets a 7-day durable DLQ expiration (`DeadLetterQueueExpiration`). In the catalog, every Kafka channel sets `type: stream` and Wolverine-consumed channels link their `deadLetterChannel`.
- **Envelope metadata:** The envelope policy supplies message type, destination, response address, and source metadata when available, and propagates request and user identifiers from an originating message as correlation context.
