BookWorm enforces strict service isolation by forbidding cross-service database access: every bounded context communicates exclusively through versioned synchronous contracts (REST, gRPC, MCP, A2A gRPC) or asynchronous Kafka CloudEvents messages orchestrated by **Wolverine**. Each messaging host selects a durability strategy matching its persistence store—PostgreSQL outbox/inbox, Azure Cosmos DB persistence, or Redis idempotency—backed by standardized retries and native per-service Kafka dead-letter queues.

### Topic naming and partitioning rules

`KafkaTopicRouter` (`src/BuildingBlocks/BookWorm.Chassis/EventBus/Wolverine/KafkaTopicRouter.cs`) enforces deterministic topic naming and partition affinity:

- **Standard prefixed topics (`AppendPrefix = true`):** `bookworm.{environment-kebab}.{owner-service}.{topic-name}` (13 of 14 integration topics).
- **Unprefixed topic exception (`AppendPrefix = false`):** `scheduler.process-vector-batch` (`ProcessVectorBatchIntegrationEvent`, consumed by **Catalog Ingestion**'s `[KafkaTrigger]`).
- **Native dead-letter topic:** `bookworm.{environment-kebab}.{service-kebab}.dead-letter-queue`, attached to every `[WolverineHandler]` listener via `EnableNativeDeadLetterQueue()`.
- **Partition keys (`PropagateGroupIdToPartitionKey()`):** Ordering, Basket, Finance, and Notification partition by `OrderId`; Catalog and Rating partition by `BookId` and `FeedbackId` so related events stay ordered within one Kafka partition.

### Topic creation and broker-managed settings

Aspire and Wolverine have separate responsibilities. In `AppHost.cs`, `AddKafka(Components.Broker).WithKafkaUI()` runs only in Aspire Run mode and provides a local development broker; publish mode uses `AddConnectionString(Components.Broker)` and expects an externally managed broker connection string. The [Aspire Kafka guide](https://aspire.dev/integrations/messaging/apache-kafka/apache-kafka-host/) describes its `confluent-local` container as intended for local experimentation, not production. This repository does not provision a production Kafka cluster or configure broker-level topic settings through Aspire.

When a `broker` connection string is configured, `UseEventFramework()` registers Wolverine's Kafka transport with `.AutoProvision()`. `ConfigureIntegrationEventTopicsIn()` discovers integration messages and registers their publish/listener routes; Wolverine creates those declared topics and the configured native DLQ when the broker permits topic creation. BookWorm does not manually provision application topics through Kafka UI or CLI; Wolverine handles topic creation at startup. With no broker connection string, `UseEventFramework()` returns without configuring Kafka.

Auto-provisioning does not define a BookWorm-specific production sizing or retention policy. With no explicit topic specification, Wolverine uses broker defaults for partition count (usually one) and replication factor; BookWorm supplies no topic retention configuration. No in-repository value overrides those defaults. Verify the effective production settings with the external broker owner or add an explicitly approved Wolverine topic specification. The declared endpoints are not marked `.ExternallyOwned()`, so the broker credentials must permit Wolverine's topic provisioning. See the [Wolverine Kafka transport guide](https://github.com/JasperFx/wolverine/blob/main/docs/guide/messaging/transports/kafka.md) for topic defaults, specifications, and externally owned topics.

### Per-service durability and idempotency tiers

When no `broker` connection string is configured, `UseEventFramework()` returns without registering a transport so services can start in isolated modes. When Kafka is active, hosts use one of three verified persistence models:

| Durability tier                             | Services                                                                | Mechanism                                                                                                                               |
| :------------------------------------------ | :---------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- |
| **PostgreSQL durable outbox/inbox**         | **Catalog API**, **Catalog Ingestion**, **Ordering API**, **Scheduler** | `UsePostgresOutbox` (`wolverine` schema + EF Core transactions, `KeepAfterMessageHandling = 1h`); Catalog also layers Redis idempotency |
| **Cosmos DB persistence**                   | **Rating API**                                                          | `UseCosmosDbPersistence("ratingdb")` + Redis `IIntegrationEventIdempotencyGuard` (no PostgreSQL)                                        |
| **Stateless transport + Redis idempotency** | **Basket API**, **Notification**                                        | No database outbox; `FusionCacheIdempotencyGuard` executes atomic Redis `SET NX` (24-hour TTL, released on failure)                     |
| **Azure Functions Kafka triggers**          | **Finance**, **Catalog Ingestion**                                      | `[KafkaTrigger]` inputs + Wolverine Kafka publisher; Finance checkpoints saga state in Durable Task Scheduler (`finance-taskhub`)       |
| **No Kafka / EventBus**                     | **Chat API**, **MCP Tools**                                             | Synchronous HTTP/gRPC/AG-UI/A2A/MCP only                                                                                                |

### Serialization, correlation, retries, and DLQ

- **CloudEvents envelope:** `CloudEventsOnlyKafkaMapper` serializes payloads as CloudEvents JSON (`JsonSerializerDefaults.Web`), stamps `source = urn:bookworm:{service}`, propagates W3C trace context and `requestid`, and attaches HTTP `UserId` via `UserIdEnvelopeMiddleware`. Propagated IDs are for tracing only—never treat them as authorization credentials.
- **Retry and error policy (`ConfigureDefaultErrorHandling`):**
  - Transient exceptions (`TimeoutException`, `HttpRequestException`, `DbUpdateConcurrencyException`, transient `NpgsqlException`) retry with `50ms`, `250ms`, and `1s` full-jitter cooldowns, then move to the native Kafka DLQ.
  - Deserialization errors (`JsonException`, `FormatException`) move immediately to the DLQ without retrying.
  - Wolverine durable message-store DLQ expiration is **7 days** (`DeadLetterQueueExpiration = TimeSpan.FromDays(7)`). This is not Kafka topic retention; Kafka DLQ records follow the broker topic's retention policy.
- **At-least-once delivery:** Durable outboxes and retries prevent silent message loss across restarts, not duplicate delivery. Consumers must remain idempotent and verify authoritative state where side effects matter.

## Contract evolution workflow

When modifying any REST, gRPC, or Kafka integration contract:

1. Identify the owning service and all registered consumers (check `tests/pacts/` for messaging pairs).
2. Prefer additive, backward-compatible field changes over renames or removals.
3. Run consumer-then-provider Pact tests (`mise run test`) so generated consumer pacts verify against providers in order.
4. Run Buf lint and breaking-change checks against committed `.proto` baselines for `BookGrpcService` and `BasketGrpcService`.
5. Update service and runtime documentation whenever business semantics—not only field shapes—change.
