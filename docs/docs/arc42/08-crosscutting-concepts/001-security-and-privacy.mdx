Security controls are applied at the boundaries where a request enters a service, where an AI agent processes content, and where application data is recorded. They complement service ownership, a shared identity provider or redaction helper does not make every service's policy identical.

## Identity and authorization

Entra ID is the identity provider used by the application. [[service|order-api]] configures bearer authentication and token introspection, then applies authorization policies that combine a role with service-specific OAuth scopes. Its default policy requires an authenticated user with the user role and an Ordering read or write scope, the admin and reporter policies make their own role and scope requirements explicit.

The shared `RequireScope` helper accepts a request when the token contains **any** of the scopes listed by the policy. It does not require every listed scope. Endpoint-level authorization still needs to be checked against the policy and role expected for that operation.

These policies are evidenced in [[system|order-system]]'s authorization setup. Do not infer that every API uses the same policy: verify each service's startup and endpoint configuration when adding or reviewing a new boundary.

## Security boundaries

The diagram distinguishes the API identity and authorization path from the AI data-protection path. The AI path applies to [[service|chat-api]] and [[service|rating-api]] agent clients, including the [[agent|rating-agent]], where the middleware is registered; it is not a universal control on every model integration.

## Personal and sensitive data

- [[service|chat-api]] and [[service|rating-api]] agent clients register Presidio-backed middleware that anonymizes text sent to the model and text returned by it. This is a processing safeguard, not a substitute for limiting the data collected or deciding which data an agent needs.
- The shared logging building block defines separate classifications for sensitive data and personally identifiable information (PII). Its redactors mask sensitive values and apply deterministic HMAC redaction to PII when a host enables the helper.
- The CQRS logging behavior records message and response type names and property names, rather than serializing request or response values. Properties marked as classified are explicitly logged as redacted.
- [[service|order-api]] currently wires the shared logging redaction helper. Treat the helper's availability as reusable capability, not evidence that every host has enabled the same redaction configuration.

## STRIDE threat model

This high-level assessment covers the documented Ordering identity and authorization path, Chat and Rating agent paths, their model and tool interactions, and operational logging. It identifies threats to validate during design and deployment; it is not a penetration test or a claim that every control is enabled on every service. ## Boundary checklist

When introducing a new API or agent:

1. Define who may call it and which role and scope authorize the operation.
2. Keep tokens, credentials, PII, and user content out of logs unless there is a documented and approved need.
3. If an AI model receives user data, determine whether it needs the raw value and apply the established PII and governance middleware.
4. Confirm the control is registered on the actual service path, a helper defined in the chassis is not automatically active everywhere.
