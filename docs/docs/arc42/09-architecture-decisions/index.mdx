This register is the central index for BookWorm's Architecture Decision Records (ADRs), fulfilling arc42 Chapter 9 without duplicating decision rationale. It indexes **18 whole-system platform ADRs**, **4 new superseding infrastructure ADRs** aligning documentation with the live codebase, and all **55 existing system-specific ADRs** across BookWorm's twelve systems (correcting the earlier documentation count of 54).

:::warning
Four legacy system ADRs in `docs/domains/` still specify PostgreSQL databases or in-memory sessions that were replaced in the live codebase. Always consult the **Superseded and drifted infrastructure ADRs** section below before relying on legacy system persistence ADRs.
:::

## Governance and record conventions

- **Two-layer structure:** Platform-wide ADRs (`ADR-BW-001` through `ADR-BW-018`) govern cross-cutting principles under `./platform/`. System-specific ADRs belong to their owning bounded context; superseding MADR records live under `./systems/`.
- **MADR format:** Rewritten ADRs follow Markdown Any Decision Records (MADR) structure: Status, Date, Scope, Deciders, Context and problem statement, Decision drivers, Considered options, Decision outcome and consequences, Pros and cons, and Verification links.
- **Lifecycle rules:** Supported statuses are `Proposed`, `Accepted`, `Deprecated`, and `Superseded`. Never edit history silently—create a new superseding ADR and mark the replaced record `Superseded by [ADR-...]`.
- **Single source of rationale:** Keep full rationale inside each ADR file; update this register only when adding, deprecating, or superseding records.

## Superseded and drifted infrastructure ADRs

Codebase verification (`docs-review/_ground-truth.md` and `src/Aspire/BookWorm.AppHost/AppHost.cs`) confirmed four major infrastructure migrations that superseded earlier system ADRs. Each live runtime choice now has an accepted MADR record:

| New superseding ADR                     | Live runtime architecture (verified)                                                                                                                     | Superseded legacy ADR(s)                                                                                                   |
| :-------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| ADR-Rating-Cosmos-DB                    | `Rating API` persists `Feedback` in **Azure Cosmos DB** (`ratingdb`/`feedbacks`, partition key `/bookId`) with EF Core Cosmos + `WolverineFx.CosmosDb`   | `rating-system/adr-001-postgresql-feedback-system-of-record`                                                               |
| ADR-Finance-Durable-Task-Scheduler      | `Finance` runs **Azure Durable Functions** backed by **Azure Durable Task Scheduler** (`finance-taskhub`) and Azure Storage host state (no PostgreSQL)   | `finance-system/adr-002-finance-postgresql-message-persistence`                                                            |
| ADR-Notification-Stateless-Kafka-Worker | `Notification` runs as a stateless **Kafka + MailKit + Mjml.Net** worker with **Redis 24-hour idempotency** (no PostgreSQL email outbox)                 | `notification-system/adr-002-notification-postgresql-email-outbox` (and outbox portions of `adr-005` / `sendgrid/adr-002`) |
| ADR-Chat-Blob-Sessions                  | `Chat API` persists Agent-User Interaction (AG-UI) sessions in **Azure Blob Storage** (`chatting-blob`, prefix `ag-ui/`; no PostgreSQL, Redis, or Kafka) | `chat-system/adr-004-in-memory-chat-sessions` (and PostgreSQL memory references in `adr-006`)                              |

## Whole-system platform ADRs (18 records)

The 18 root platform ADRs are reconstructed in MADR format under `./platform/`. Each record carries its current status (`Proposed` pending maintainer sign-off unless updated) and verified codebase links.

| ADR                                               | Architectural choice                                                                                                            | Principal quality driver / trade-off                                                      |
| :------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------------------------- |
| ADR-BW-001: Capability-aligned boundaries         | Decompose BookWorm into six bounded contexts                                                                                    | Modifiability and clear ownership vs. distributed coordination                            |
| ADR-BW-002: .NET platform foundation              | Standardize backend services on .NET 11 and C# 15                                                                               | Ecosystem consistency vs. coordinated SDK upgrades                                        |
| ADR-BW-003: Aspire shared service defaults        | Orchestrate hosting and defaults via Aspire 17 and BuildingBlocks                                                               | Consistent telemetry and resilience vs. shared-library blast radius                       |
| ADR-BW-004: Explicit HTTP and gRPC contracts      | Use versioned REST (`/api/v1/*`) and protobuf gRPC (`book.v1`, `basket.v1`)                                                     | Explicit interoperability vs. contract maintenance                                        |
| ADR-BW-005: Kafka integration backbone            | Use Wolverine and Kafka CloudEvents for asynchronous messaging                                                                  | Cross-context decoupling vs. broker operations and eventual consistency                   |
| ADR-BW-006: Service-owned business state          | Isolate authoritative persistence inside each owning service                                                                    | Schema autonomy vs. cross-boundary data composition                                       |
| ADR-BW-007: Derived eventually consistent views   | Separate authoritative stores from derived projections (Qdrant, rating summaries, Marten projections)                           | Read scalability vs. explicit propagation lag                                             |
| ADR-BW-008: Durable message handoffs              | Match message durability to backing store (PostgreSQL outbox, Cosmos DB persistence, Durable Task Scheduler, Redis idempotency) | Recoverable delivery without pretending exactly-once business effects                     |
| ADR-BW-009: Local CQRS building blocks            | Use `Mediator.SourceGenerator` and FluentValidation inside services (not `MediatR`)                                             | Zero-reflection handler pipelines vs. vertical-slice conventions                          |
| ADR-BW-010: Cross-boundary correlation            | Propagate W3C trace context, `x-request-id`, and `UserId` across HTTP, gRPC, and Kafka                                          | End-to-end diagnostics without treating correlation headers as credentials                |
| ADR-BW-011: Shared validation and error contracts | Standardize FluentValidation and RFC 9457 `ProblemDetails` responses                                                            | Predictable client error handling vs. per-host registration discipline                    |
| ADR-BW-012: Operation-aware resilience            | Apply budgeted HTTP retries, FusionCache fail-safe, rate limiting, and Kafka cooldown/DLQs by operation semantics               | Fault tolerance without amplifying duplicate side effects                                 |
| ADR-BW-013: OpenTelemetry observability           | Emit unified OpenTelemetry traces, metrics, and structured logs                                                                 | Consistent diagnostics vs. sampling and retention costs                                   |
| ADR-BW-014: Composable AI governance              | Layer Microsoft Agent Governance policies, Presidio PII redaction, Entra Agent Identities, and MCP scoping on AI paths          | Safe read-only AI execution vs. path-specific policy maintenance                          |
| ADR-BW-015: Explicit environment configuration    | Separate logical topology from environment tiers and `aspire deploy` parameters                                                 | Clean local-to-Azure parity without false production guarantees                           |
| ADR-BW-016: Layered architecture verification     | Combine TUnit unit tests, ArchUnitNET fitness tests, Pact contract tests, Vitest, and Playwright BDD                            | High change safety across multiple test layers (note: no backend `.IntegrationTests` yet) |
| ADR-BW-017: Compatible contract evolution         | Evolve HTTP, gRPC, and Kafka schemas with Pact verification and backward-compatible changes                                     | Independent service deployment vs. coordinated breaking migrations                        |
| ADR-BW-018: Single-source decision documentation  | Maintain one canonical MADR file per decision linked from architecture views                                                    | Traceability without copy-pasted rationale                                                |
