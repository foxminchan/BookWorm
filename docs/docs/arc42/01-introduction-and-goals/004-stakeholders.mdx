This page documents the stakeholder roles that rely on BookWorm's architecture, what each group expects from the system, and where each group finds answers in the documentation. Because BookWorm is an open-source reference platform whose maintainers evolve over time, this register tracks **roles** rather than named individuals.

## Stakeholder roles and documentation routing

| Stakeholder role                                                             | Expectations and concerns                                                                                                                                                                      | Primary architecture views                                                                                                                                                                               |
| :--------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Customers** (`customer` role)                                              | Discover books accurately, manage a persisted basket, complete trustworthy checkouts, track orders, submit reviews, and receive grounded AI assistance across **Storefront** and **Commerce**. | [[doc\|arc42/01-introduction-and-goals/001-introduction]], [[doc\|arc42/03-context-and-scope/002-business-context]]                                                                                      |
| **Store administrators and business users** (`admin`, `business_user` roles) | Manage catalog entries, process order lifecycle transitions, review customer feedback in **Backoffice**, and monitor scheduled jobs in Quartz Dashboard with strict role-based access control. | [[doc\|arc42/01-introduction-and-goals/002-requirements-overview]], [[doc\|arc42/08-crosscutting-concepts/001-security-and-privacy]]                                                                     |
| **Product and business stakeholders**                                        | Understand which capabilities drive business outcomes, where new features belong, and which quality trade-offs take priority.                                                                  | [[doc\|arc42/01-introduction-and-goals/002-requirements-overview]], [[doc\|arc42/01-introduction-and-goals/003-quality-goals]], [[doc\|arc42/10-quality-requirements/001-quality-requirements-overview]] |
| **Domain and service engineers**                                             | Build and evolve services inside clear bounded contexts without introducing hidden database coupling or breaking downstream consumers.                                                         | [[doc\|arc42/00-c4-overview]], [[doc\|arc42/02-architecture-constraints]], [[doc\|arc42/04-solution-strategy]], [[doc\|arc42/05-building-block-view]]                                                    |
| **Platform and infrastructure engineers**                                    | Operate shared foundations (**Aspire** 17, **API Gateway**, Kafka, Redis, PostgreSQL, Cosmos DB, **Scheduler**, **Notification**, **Microsoft Entra ID**) without absorbing domain rules.      | [[doc\|arc42/03-context-and-scope/003-technical-context]], [[doc\|arc42/07-deployment-view]], [[doc\|arc42/08-crosscutting-concepts]]                                                                    |

## Governance boundaries

- **Role catalog vs. formal approver directory:** Documenting roles keeps this architecture baseline durable across contributor changes, but it does not assign named decision-makers or formal SLA sign-off authority.
- **Logical team ownership:** Repository ownership conventions are documented in [[team|business-strategy]].
