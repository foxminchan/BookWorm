This page defines 17 measurable usage and change scenarios (`QR-01`–`QR-17`) that refine BookWorm's quality tree in [[doc|arc42/10-quality-requirements/001-quality-requirements-overview]]. Each scenario specifies its context, trigger stimulus, required response, and verification evidence.

:::note
All 17 scenarios start as **proposed / not evaluated**. Numerical budgets marked **proposed** are review baselines, not approved production service-level agreements (SLAs).
:::

- **Design links:** [[doc|arc42/06-runtime-view/001-checkout-and-order-coordination]], [[doc|arc42/08-crosscutting-concepts/002-contracts-and-messaging]], [[doc|arc42/08-crosscutting-concepts/006-testing-and-change-safety]].
- **Known limits:** **Ordering API**'s Redis duplicate-request guard (`IRequestManager`) is not an atomic exactly-once transaction across concurrent requests or post-key handler failures. **Finance** retries can also repeat **Basket** cleanup and **Notification** commands.

`RequestManager.TryCreateAsync` uses a single Redis `StringSetAsync` with `When.NotExists` and a 3,600-second expiry, making the key creation atomic. `CreateAsync` uses an unconditional set, so callers must use `TryCreateAsync` for duplicate protection; this is not an exactly-once transaction spanning request handling.

## Operability, durable work, and recovery

| ID                                     | Type / Tier | Context and artifact                                                                                                                                                                                                               | Source and stimulus                                                                                                      | Response and acceptance criteria                                                                                                                                                                                                                                                                    | Verification evidence                                                                                                                                                |
| :------------------------------------- | :---------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **QR-06** Locate failed processing     | Usage / P2  | A scheduled job, email submission, or asynchronous checkout step fails in a deployed verification environment.                                                                                                                     | An operator receives an incident report with a request, message, job, or `Order` identifier.                             | Identify the owning capability, failed boundary, and actual execution state without treating a successful scheduler invocation or trace as business completion. **Proposed budget:** diagnosis within 15 minutes.                                                                                   | Fault-injection exercise recording time to diagnosis plus the OpenTelemetry traces (`x-request-id`), Quartz history, Durable Task state, and Kafka DLQ records used. |
| **QR-07** Recoverable vector freshness | Usage / P1  | **Catalog** (`catalogdb`), **Scheduler** (`ProcessVectorBatchJob`, cron every 5 min UTC), **Catalog Ingestion**, and **Qdrant** (`vectordb`); includes active, deleted, concurrent-update, and failed cases.                       | A **Catalog** change commits; embedding generation or a Qdrant write fails, or a newer update arrives during processing. | Failed vector writes leave pending work recoverable; older revisions never overwrite newer updates; deleted books are removed from **Qdrant**. **Proposed freshness budget:** p95 commit-to-index lag at most 10 minutes over 1,000 changes at 10 changes/minute with healthy dependencies.         | Commit, ingestion, and Qdrant index timestamps plus fault-injected convergence verification.                                                                         |
| **QR-08** Observable email failure     | Usage / P1  | Stateless **Notification** worker (**Wolverine** + **Kafka**, Redis 24-hour idempotency guard, `MailKit` + `Mjml.Net`), native DLQ (`bookworm.{env}.notification.dead-letter-queue`), and SMTP relay (**Mailpit** / **SendGrid**). | SMTP relay or Redis fails before acceptance, or fails after SMTP acceptance before idempotency recording.                | Transient failures follow Wolverine retry cooldown (`50ms / 250ms / 1s` with jitter) and route exhausted messages to the native Kafka DLQ; no failure is silently reported as recipient delivery. Account for attempted submissions, DLQ records, and possible duplicates under ambiguous outcomes. | Captured SMTP submissions, Kafka DLQ contents, Redis idempotency keys, and OpenTelemetry logs across injected failures.                                              |
| **QR-13** Customer-path availability   | Usage / P2  | Externally observed browse (**Storefront**), basket, and checkout (**Commerce**) paths through **API Gateway** in a production-like environment.                                                                                   | Synthetic probes exercise each path every minute over a rolling 30-day window.                                           | **Proposed SLO:** at least 99.9% successful eligible executions per path within `QR-12` latency budgets. Timeouts and wrong results count as failures; include BookWorm and required dependency outages; exclude intentional invalid-input and authorization-denial probes.                         | Per-path synthetic ratio, dependency outage log, and latency distribution. Aggregate averages must not hide a failing checkout path.                                 |
| **QR-14** Restore owned state          | Usage / P2  | One service and its authoritative store (`catalogdb`, `orderingdb`, `schedulerdb`, Cosmos `ratingdb`, Redis, `chatting-blob`, or `finance-taskhub`) fail.                                                                          | Operations restores the service and store after simulated loss.                                                          | **Proposed objectives:** RTO at most 30 minutes to verified usable service; RPO at most 5 minutes of committed authoritative data. Reconcile queued/saga work without claiming exactly-once effects; rebuild derived Qdrant vectors from **Catalog** rather than restoring them as authoritative.   | Isolated restore drill recording timestamps, backup age, missing fixtures, health checks, and reconciliation results per store.                                      |

- **Design links:** [[doc|arc42/06-runtime-view/002-catalog-search-index-maintenance]], [[doc|arc42/06-runtime-view/005-notification-delivery-and-maintenance]], [[doc|arc42/07-deployment-view]], [[doc|arc42/08-crosscutting-concepts/004-observability]].
- **Known limits:** **Scheduler**'s 5-minute cron (`0 0/5 * * * ?` UTC) does not guarantee freshness during sustained outages or backlog spikes. **Notification** has no PostgreSQL database outbox—it relies on Kafka durability, native DLQ replay, and 24-hour Redis idempotency, and SMTP relay acceptance does not prove recipient inbox delivery. Although `AppHost.cs` configures Azure HA and Postgres backups (7/14/35 days), production restore drills and external SaaS SLAs (Confluent Cloud, Qdrant Cloud, SendGrid) remain unverified.

`VectorBatchProcessor` reads at most 200 pending vector updates per invocation (`BatchSize = 200`).

- **Design links:** [[doc|arc42/08-crosscutting-concepts/001-security-and-privacy]], [[doc|arc42/08-crosscutting-concepts/005-ai-governance]].

## Measurement and evidence rules

Follow six rules whenever evaluating any scenario:

1. **Freeze test conditions:** Record versions, dataset, environment, dependency state, active governance policies, and tools before measuring.
2. **Measure at the true business boundary:** Checkout ends when the `Order` is persisted; vector freshness ends when **Qdrant** serves the updated revision; SMTP relay acceptance is not recipient inbox delivery.
3. **Count failures honestly:** Include unexpected errors, timeouts, and incorrect results; report expected validation (`400`) and authorization (`401`/`403`) denials separately; never exclude dependency outages from availability math.
4. **Preserve per-path metrics:** Calculate percentiles and error rates per operation group so healthy browsing never masks failing checkout. For `QR-07`, report every change's lag and convergence status.
5. **Verify stored side effects:** Inspect databases, **Qdrant**, **Redis**, Durable Task state, Kafka DLQs, and captured SMTP traffic—surface HTTP status codes alone are insufficient.
6. **Use synthetic fixtures only:** Run fault injection and PII tests exclusively against synthetic data in isolated environments.

### Evidence record schema

Maintain evaluation records in the owning team's release or acceptance log rather than duplicating raw test output in this document:

| Field                   | Required information                                                                 |
| :---------------------- | :----------------------------------------------------------------------------------- |
| **Scenario and owner**  | `QR` identifier, owning service/team, and reviewer                                   |
| **Requirement status**  | `Proposed`, `Agreed`, or `Deferred`, plus approval reference and any revised budget  |
| **Verification status** | `Not evaluated`, `Passed`, `Failed`, or `Blocked`, plus evaluation date              |
| **Conditions**          | Versions, topology, dataset, workload, dependency configuration, and active policies |
| **Result**              | Observed behavior, numerical metrics, and sanitized evidence links                   |
| **Gap and follow-up**   | Known limits, risk decision, remediation owner, and re-evaluation trigger            |

## Architectural trade-offs and open agreements

| Tension                                               | Architectural position                                                                                                                                     | Agreement or evidence still required                                                                                     |
| :---------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------- |
| **Correctness vs. latency**                           | Checkout always validates against persisted **Basket** and authoritative **Catalog** facts over gRPC; never accept client prices to meet a latency budget. | Validate `QR-01` and `QR-12` together; agree explicit degradation behavior when dependencies fail.                       |
| **Durable async work vs. immediate freshness**        | **Catalog** commits never block on embeddings or **Qdrant**; **Scheduler** and **Catalog Ingestion** converge vectors asynchronously.                      | Agree freshness/backlog budgets and alerting for `QR-07` under sustained outages.                                        |
| **Retry durability vs. duplicate side effects**       | Wolverine retries, Durable Task sagas, and Kafka DLQs preserve work but can repeat **Basket** or SMTP actions.                                             | Evaluate `QR-02` and `QR-08`; verify idempotency and uncertain-outcome handling without claiming exactly-once semantics. |
| **Independent release vs. contract coordination**     | Compatible changes deploy independently; breaking contracts require coordinated migration.                                                                 | Agree supported mixed-version windows and rollback criteria for `QR-03` and `QR-04`.                                     |
| **Diagnosis vs. privacy and telemetry cost**          | OpenTelemetry correlation and execution stores enable triage without logging raw PII or secrets.                                                           | Agree sampling, retention, access, and redaction coverage across `QR-06` and `QR-10`.                                    |
| **Availability and recovery vs. infrastructure cost** | **Aspire** 17 provisions Azure HA and Postgres backups, but infrastructure code alone does not prove restore times.                                        | Run isolated restore drills and confirm external SaaS SLAs for `QR-13` and `QR-14`.                                      |
| **AI usefulness vs. least privilege**                 | Agent workflows enforce explicit tool policies and **Presidio** PII guardrails; failed tools never fabricate answers.                                      | Verify policy coverage and provider data handling across all `QR-15` fixtures before expanding agent tools.              |
| **Focused scope vs. exhaustive coverage**             | Prioritize high-risk journeys without claiming every generic quality attribute is verified today.                                                          | Confirm browser matrix, **Commerce** E2E coverage (`QR-16`), and `QR-17` onboarding fixture.                             |
