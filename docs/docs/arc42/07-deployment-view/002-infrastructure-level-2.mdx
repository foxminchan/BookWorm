## 7.2.1 Service execution environment

All 16 core Container Apps plus `quartz-dashboard` run inside one Azure Container Apps environment (`aca`, `Consumption` workload profile, `WithDashboard()`, `WithAzdResourceNaming()`), backed by Azure Container Registry and Log Analytics (`90`-day retention in Production, `30`-day retention in non-Production).

| :-------------------------------------------------------- | :------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 7.2.3 External dependencies and `aspire deploy` parameters

Cloud deployments run via `.github/workflows/apphost-cd.yml` (`workflow_dispatch`, default region `southeastasia`) using `aspire deploy` and require the following parameters:

- **Azure OIDC authentication:** `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP`, `AZURE_LOCATION`.
- **External messaging and search:** `KAFKA_BROKER` (Confluent Cloud connection string) and `QDRANT_CLOUD_CONNECTION` (Qdrant Cloud connection string).
- **Outbound email (SMTP):** `EMAIL_SMTP_ENDPOINT` (defaults to `smtp://smtp.sendgrid.net:587`), `EMAIL_SMTP_USERNAME` (defaults to `apikey`), `EMAIL_SMTP_PASSWORD`, `EMAIL_SENDER_ADDRESS`, and optional `EMAIL_SENDER_NAME`.

## 7.2.4 Open operational decisions before production rollout

The Aspire provisioning model establishes baseline HA, backups, and managed-identity authentication, but the following production hardening items remain open:

The generated `temp/` Bicep snapshot sets all 17 Container Apps to single-revision mode with one minimum replica. It declares no maximum replicas, CPU/memory requests, or scale rules; gateway ingress targets port `5000`. These values do not prove the settings of a deployed environment.

The Durable Task Scheduler Bicep allows `0.0.0.0/0`. The generated templates contain no private-endpoint resources for PostgreSQL, Redis, Cosmos DB, Storage, or Foundry; any separately managed network controls were not inspected.

1. **Multi-region and promotion strategy:** Finalize target Azure regions beyond the workflow default (`southeastasia`) and define promotion gates across `Development`, `Staging`, and `Production`.
2. **Bounded autoscaling:** Configure maximum replica limits and HTTP/CPU/Kafka lag triggers for each Container App.
3. **Private network perimeter:** Add Azure Virtual Network integration, private endpoints for managed data/AI stores, custom DNS, TLS certificates, and WAF rules in front of `API Gateway`.
4. **Tested recovery drills:** Validate backup restoration and disaster-recovery runbooks across PostgreSQL, Cosmos DB, Azure Storage, Qdrant Cloud, and Confluent Cloud.
5. **Credential rotation:** Establish rotation procedures for external Kafka, Qdrant Cloud, SMTP, `HMAC__Key`, and `BETTER_AUTH_SECRET` values.
6. **SLOs and alerting:** Define availability, latency, RU consumption, and DLQ-depth alerts in Log Analytics and Application Insights.
