## 7.2 Infrastructure Level 2

This level refines the Azure Container Apps topology from [[doc|arc42/07-deployment-view/001-infrastructure-level-1]]. It records infrastructure responsibilities and the operational details that remain open.

### 7.2.1 Service execution environment

All 15 container apps run in a single Azure Container Apps managed environment (Consumption workload profile), backed by Azure Container Registry, Log Analytics (90-day retention), and the Aspire Dashboard. Every app runs in single-revision mode with a minimum of one replica. Only the API gateway is externally reachable (port 5000); all other container apps use internal-only ingress.

The table distinguishes what the infrastructure templates provision from the operational configuration still needed to run it. Provisioning a zone-redundant PostgreSQL flexible server with 35-day geo-redundant backups, for example, does not replace tested restore procedures or private virtual network rules.

### 7.2.3 External infrastructure

- **Identity provider:** [[system|identity-provider]] (Microsoft Entra ID) resources are provisioned via Microsoft Graph—creating the application registration, 3 app roles (Admin, BusinessUser, Customer), 14 OAuth2 scopes, gateway callback URIs, per-service managed identities, and Entra Agent Identities for [[agent|book-agent]] and [[agent|rating-agent]] for on-behalf-of token exchange. Tenant conditional access and network policies are managed outside the deployment.
- **Email delivery:** [[service|notification-api]] submits email via SMTP (defaulting to [[system|sendgrid]]). SMTP acceptance does not guarantee recipient delivery.
- **Vector search & messaging:** Qdrant Cloud ([[container|catalog-vector]]) and the Kafka broker are externally hosted and configured via secure deployment parameters.
- **Customer client:** Storefront and Back office run as internal-only container apps (port 3000) behind the externally exposed API gateway; CDN, custom DNS, TLS certificates, and WAF/ingress policies are not yet defined.

### Operational details to complete

The following operational decisions are needed before this view can serve as a production runbook:

1. Target Azure region(s) and environment promotion strategy beyond template defaults.
2. Upper autoscaling rules (maximum replicas and CPU, memory, or event-driven triggers) for each container app.
3. Virtual network integration, private endpoints (replacing public access on PostgreSQL, Redis, Storage, Foundry, and Durable Task Scheduler), custom DNS, and TLS certificates.
4. Tested backup restoration, retention, and disaster-recovery procedures across PostgreSQL, Cosmos DB, Storage, Qdrant Cloud, and Kafka.
5. Secret rotation and deployment authorization for external Kafka, Qdrant Cloud, SMTP credentials, and application signing secrets.
6. Availability, capacity, scaling, latency, and recovery targets, with corresponding alerts on Log Analytics and Application Insights.

Until these details are confirmed in the service and operations documentation, this chapter describes component placement and ownership rather than a complete production topology.
