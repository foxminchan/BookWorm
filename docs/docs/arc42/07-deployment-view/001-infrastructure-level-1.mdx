## 1. Context & Problem

As [[domain|BookWorm]] transitions from logical business capabilities to cloud-hosted software, stakeholders need a clear Level 1 view of how web storefronts, internal services, databases, AI capabilities, and external providers map to cloud infrastructure. Without this baseline, solution architects, project managers, and operations teams lack visibility into hosting boundaries, shared dependencies, security exposure, and which operational details remain unconfirmed before production rollout.

## 2. Business Value

- **Clear operational ownership:** Separating application compute, service-owned data stores, and asynchronous background processing allows teams to evolve and scale business capabilities independently.
- **Reduced exposure and credential risk:** Routing all external traffic through a single gateway while keeping services on internal networking—and relying on passwordless identity access across managed cloud resources—minimizes attack surface and secret-management overhead.
- **Predictable resilience and cost structure:** Consumption-based container compute paired with zone-redundant databases, high-availability caching, and geo-redundant storage establishes a solid baseline for availability without unnecessary idle infrastructure.
- **Smooth developer-to-cloud parity:** Local containers and emulators mirror cloud services so teams can build and test realistically before deploying.
- **Explicit gap tracking:** Calling out unconfirmed items (such as target regions, private networking, scaling ceilings, and SLAs) prevents teams from mistaking a deployment template for a finished production runbook.

## 3. How It Works

At Level 1, the BookWorm deployment organizes software and supporting services into four logical layers:

1. **Single public entry point and private application compute:** Customers and staff access the Storefront and Back office web applications exclusively through a single public API gateway. That gateway routes requests over private internal networking to the web clients and core business services. All 15 application components—including web clients, business services, and privacy-redaction containers—run in a shared managed container environment with at least one active instance each, backed by a container registry and centralized monitoring dashboards.
2. **Managed data, caching, and AI services:** Core business records (catalog items, orders, scheduled jobs), customer feedback, shopping baskets, uploaded files, workflow state, and AI model capabilities run on dedicated cloud-managed services. Services authenticate to these resources without stored passwords using cloud-managed identities.
3. **Background work and asynchronous messaging:** Tasks that do not need to finish while a customer waits—such as updating the catalog search index or sending emails—run asynchronously through scheduled triggers, durable task queues, and event messaging. For further detail on these flows, see [[doc|arc42/06-runtime-view/002-catalog-search-index-maintenance]] and [[doc|arc42/06-runtime-view/005-notification-delivery-and-maintenance]].
4. **Identity, external providers, and local parity:** User authentication, role permissions, and AI agent identities are managed through a central identity provider. Event messaging, vector search, and email delivery connect as external services. During local development, containers and emulators stand in for managed cloud and external providers.

## 4. Trade-offs & Lessons Learned

- **Independent service deployment vs. shared infrastructure:** While each business capability deploys as its own container app, several services share a single relational database server and a single caching cluster, creating shared operational and capacity dependencies.
- **Offloading slow work vs. immediate consistency:** Moving search indexing and email delivery into background queues and scheduled batches keeps user-facing requests responsive, while accepting that search indexes and notification delivery complete asynchronously.
- **Baseline security and HA vs. production hardening:** The deployment template defines hosting tiers, high-availability modes, and passwordless authentication, but intentionally leaves target regions, private virtual networking, custom domains, TLS certificates, upper autoscaling caps, and formal service-level targets (availability, latency, throughput, recovery time, and capacity) for environment-specific operations configuration.
- **Next level of detail:** See [[doc|arc42/07-deployment-view/002-infrastructure-level-2]] for lower-level infrastructure configuration and open operational questions.

## 5. Technical Reference

### 7.1 Infrastructure Level 1

#### System distribution

<LikeC4View viewId="bookwormDeployment" project="deployment" />

This deployment view shows how [[domain|BookWorm]] is published to Azure:

- **Application compute:** Both web clients (Storefront and Back office), the YARP API gateway, all business services, and the [[system|data-privacy]] PII containers ([[service|PresidioAPI]]) run as 15 container apps in one Azure Container Apps environment (Consumption tier, minimum 1 replica each), paired with Azure Container Registry, Log Analytics, and the Aspire Dashboard.
- **Traffic entry point:** Users reach the platform only through the API gateway, which is the sole externally exposed container app. It routes requests to Storefront, Back office, Entra proxy, [[service|chat-api]], [[service|rating-api]], [[service|order-api]], [[service|basket-api]], and [[service|catalog-api]] over internal-only networking.
- **Azure-managed services:** PostgreSQL Flexible Server (zone-redundant, holding [[container|catalog-database]], [[container|order-database]], and [[container|sheduler-database]]), Azure Cosmos DB ([[container|rating-database]]), Azure Durable Task Scheduler (for [[service|order-orchestration]]), Azure Managed Redis (high availability enabled), Azure Storage (geo-zone-redundant), and Microsoft Foundry (with Application Insights) all use passwordless managed-identity authentication.
- **Identity & external systems:** [[system|identity-provider]] (Microsoft Entra ID app registrations, managed identities, and Entra Agent Identities for [[agent|book-agent]] and [[agent|rating-agent]]) is provisioned via Microsoft Graph. Kafka, Qdrant Cloud ([[container|catalog-vector]]), and [[system|sendgrid]] (SMTP) are connected as external services.

For asynchronous search indexing, [[service|sheduler-dashboard]] publishes [[event|ProcessVectorBatchIntegrationEvent]] on [[channel|scheduler.process-vector-batch]] to trigger [[service|catalog-ingestion]]. When run locally, containers and emulators substitute for managed Azure and external services.

#### Environments

The deployment distinguishes local development from Azure publishing. Locally, containers and emulators run Kafka, Entra ID, MailPit, Redis, PostgreSQL, Cosmos DB, Durable Task Scheduler, Qdrant, and Azure Storage; in Azure, these map to Azure-managed services or external endpoints. Document environment-specific sizing, external endpoints, data isolation, and access boundaries as each environment is confirmed.
