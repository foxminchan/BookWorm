BookWorm divides its customer-facing website into two independent Next.js 16 microfrontends (MFEs)—**Storefront** (`@bookworm/storefront`) for public discovery and **Commerce** (`@bookworm/commerce`) for authenticated shopping—served behind a single YARP API Gateway origin. This split isolates public caching and SEO optimization from private, always-fresh checkout and order workflows while preserving one seamless browser experience.

## Context and motivation

An online bookstore serves two fundamentally different workloads under one domain:

- **Public discovery (Storefront):** Home page, catalog browsing, book details, customer reviews, static policy pages, authentication entrypoints, and the AI book assistant. Most visitors see identical content, so aggressive component caching (`cacheComponents: true`), static optimization, and search-engine indexing (`@workspace/seo`) directly improve conversion and latency.
- **Authenticated transactions (Commerce):** Shopping basket (`/basket`), checkout confirmation (`/checkout/confirmation`), account profile (`/account`), and order history (`/account/orders`). Every response is user-specific, must never be served from a shared cache (`cacheComponents: false`), and must stay excluded from search indexing.

Keeping both workloads in one Next.js deployment couples caching settings, release cadences, and failure blast radii. Splitting them into two Next.js zones lets each application tune its rendering pipeline and deploy independently without forcing shoppers onto separate subdomains.

## How it works

### Single origin and shared routing manifest

Customers interact with one HTTPS origin terminated by the YARP API Gateway (`gateway`). Both Aspire (`FrontendExtensions.cs` + `ApiGatewayProxyBuilder.cs`) and the two Next.js apps (`@vercel/microfrontends` `^2.4.2`) read the same routing manifest: `src/Clients/apps/storefront/microfrontends.json`.

- **Deterministic YARP precedence:** Backend API prefixes (`/chatting`, `/rating`, `/ordering`, `/basket`, `/catalog`) receive orders `0` through `4`, followed by `/entra` at order `5`, explicit frontend routes, and Storefront's catch-all `/{**remainder}` at `int.MaxValue`.
- **Exact-match collision handling:** Because Commerce serves `/basket` while **Basket API** owns `/basket/{**remainder}`, `ProxyExtensions.cs` assigns exact-match colliding frontend routes `order = -1`. A browser navigation to `/basket` reaches Commerce, while `/basket/api/v1/baskets` routes to **Basket API**.
- **Isolated static assets:** Commerce sets `assetPrefix: "commerce-assets"` and registers `/commerce-assets/:path*` so its JavaScript, CSS, and image chunks never collide with Storefront's `/_next/static/*` assets.
- **Zone observability:** YARP attaches `X-Mfe-Zone` (`storefront`, `commerce`, or `backoffice`) to every frontend response for rapid routing verification and diagnostics.

### Shared chrome and single sign-in across zones

Even though Storefront and Commerce run as separate Next.js processes, shoppers experience one continuous interface:

- **Shared shell (`@workspace/storefront-shell`):** Both apps render the identical header, footer, mobile bottom navigation, cross-zone `MfeLink` transitions, and Jotai-backed basket badge.
- **Single authentication owner:** Storefront owns `/api/auth/[...all]` (Better Auth + Microsoft Entra ID). Commerce runs with `.WithoutEntraId()` in `FrontendExtensions.cs` and reads the same origin-scoped Better Auth session cookie.

## Design trade-offs

| Decision                                             | Benefits                                                                                                                                                | Costs and limits                                                                                                                     |
| :--------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------- |
| Multi-zone split behind YARP + `microfrontends.json` | Independent caching (`cacheComponents: true` vs. `false`), independent container builds/scaling, single origin without CORS or cookie-domain complexity | Two customer Next.js containers to deploy and monitor; top-level Commerce routes must be registered in `microfrontends.json`         |
| Shared shell package (`@workspace/storefront-shell`) | Visual and behavioral consistency across header, footer, and basket badge without runtime bundle federation                                             | Shell changes rebuild both Storefront and Commerce (mitigated by Turborepo caching)                                                  |
| Storefront as sole customer auth owner               | One Better Auth callback and Entra ID registration for all customer zones                                                                               | Commerce depends on Storefront availability for initial sign-in (`/login`) and `/api/auth/[...all]`                                  |
| Full-document transitions across zones               | Clean isolation between app runtimes and React trees with zero shared global state bugs                                                                 | Slightly heavier navigation cost across the Storefront-to-Commerce boundary than intra-app client routing (mitigated by prefetching) |

## Alternatives considered

- **Single customer Next.js monolith:** Simpler to deploy initially, but forces public catalog caching, AI chat runtime dependencies (`@copilotkit/*`, `@ag-ui/client`), and authenticated checkout routes into one build and runtime profile.
- **Separate subdomains (`shop.*` and `checkout.*`):** Eliminates gateway path routing, but introduces cross-subdomain cookie scoping, extra Entra ID redirect URIs, and fragmented SEO/origin boundaries.
- **Client-side Module Federation:** Enables SPA transitions without document reloads, but adds webpack/bundler runtime coupling, version-skew risks across React 19 / Next.js 16 App Router Server Components, and harder SSR hydration.
