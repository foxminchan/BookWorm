## Explanation: Why Vertical Multi-Zone Microfrontends?

BookWorm's customer-facing experience spans two very different runtime profiles:

- **Public discovery (`@bookworm/storefront`):** Landing pages, catalog browsing, book details, reviews, informational pages, authentication entrypoints, and the CopilotKit AI assistant. These routes benefit from Next.js `cacheComponents` (Partial Prerendering), SEO metadata, and public caching.
- **Authenticated commerce (`@bookworm/commerce`):** Shopping basket, checkout confirmation, customer profile, and order history. These routes are strictly user-specific, dynamic (`cacheComponents: false`), and excluded from search indexing (`robots: { index: false, follow: false }`).

Separating these into vertical Next.js multi-zones using `@vercel/microfrontends` lets each zone tune its rendering, caching, and deployment lifecycle independently while presenting a single unified origin to the customer through the YARP API gateway.

### Gateway Routing & Single Source of Truth

<MermaidFileLoader file="mermaids/mfe-gateway-routing.mmd" />

Both Next.js zones and the Aspire AppHost read from the same `src/Clients/apps/storefront/microfrontends.config.json` file:

1. **Next.js build/runtime (`withMicrofrontends`):** Both `storefront` and `commerce` wrap their `next.config.mjs` with `withMicrofrontends(...)` from `@vercel/microfrontends/next/config` (with `skipTransforms: ["redirects"]`). `commerce` declares `assetPrefix: "commerce-assets"` so its static assets never collide with `storefront`'s `/_next/static` paths.
2. **YARP gateway translation (`MicrofrontendsConfigLoader`):** In `BookWorm.AppHost`, `ApiGatewayProxyBuilder.WithMicrofrontends(...)` parses `microfrontends.config.json`, translates Vercel `path-to-regexp` expressions (such as `/checkout/:path*` and `/account/:path*`) and `assetPrefix` paths into ASP.NET Core/YARP patterns, and attaches an `X-Mfe-Zone` response header (`storefront`, `commerce`, or `backoffice`) for observability.
3. **Deterministic route ordering:** Backend service prefixes (`/catalog`, `/basket`, `/ordering`, `/rating`, `/chat`) and `/entra` are registered ahead of frontend zones. `MicrofrontendsConfigLoader.CollidesWithService` guards against accidental leading-segment collisions, and `storefront` serves as the catch-all fallback (`/{**remainder}` at `int.MaxValue`).

### Shared Shell & Cross-Zone Navigation

To keep navigation seamless across zones without duplicating layout code, shared customer chrome lives in `@workspace/storefront-shell` (`domain` tier):

- **Shared layout & navigation:** `StorefrontShell` composes `Header`, `Footer`, and `MobileBottomNav` using centralized routes from `nav-config.ts` and `app-config.ts`.
- **Cross-zone links & prefetching:** `mfe-link.tsx` re-exports `Link`, `PrefetchCrossZoneLinks`, and `PrefetchCrossZoneLinksProvider` from `@vercel/microfrontends/next/client` so transitions between `storefront` and `commerce` prefetch cleanly across zone boundaries.
- **Shared ephemeral state:** `basket-atom.ts` holds the Jotai basket state in the shared shell package so the header badge stays consistent across both zones.

### Cross-Zone Authentication & Proxy Origin Resolution

Authentication remains centralized in `storefront` so there is only one OAuth callback and Better Auth route handler:

- **Single auth owner:** `storefront` exposes `/api/auth/[...all]` and is wired with Microsoft Entra ID in `FrontendExtensions`. `commerce` calls `.WithoutEntraId()` in `FrontendExtensions` and exposes `/api/health` for Aspire health checks.
- **Shared auth client:** `@workspace/storefront-shell/auth-client` configures `createAppAuthClient` against the unified gateway origin, allowing `commerce` components and hooks (`useSession`, `useLogout`) to read the shared session cookie.
- **Edge protection (`proxy.ts`) & origin resolution:** Both `storefront` and `commerce` use `resolvePublicOrigin` from `@workspace/storefront-shell/lib/proxy`, which honors `x-forwarded-proto` and `x-forwarded-host` headers so internal HTTP hops behind Azure Container Apps never downgrade redirect `Location` headers to `http://`. In `commerce`, `proxy.ts` checks `getSessionCookie` for `/basket`, `/checkout`, and `/account` and redirects unauthenticated requests to `/login?callbackUrl=...` on the `storefront` zone.

## How-to Guide: Adding a Route to a Microfrontend Zone

When adding a new customer-facing route:

1. **Choose the owning zone:** Place public, cacheable, or SEO-indexed routes in `apps/storefront/app/`, and authenticated, user-specific routes in `apps/commerce/app/`.
2. **Register child zone paths:** If the route belongs to `commerce` (or a new child zone), add its path pattern to `routing[].paths` in `src/Clients/apps/storefront/microfrontends.config.json`.
3. **Avoid backend prefix collisions:** Ensure the leading path segment does not match a backend service prefix registered on the YARP gateway (such as `/catalog`, `/basket`, `/ordering`, `/rating`, `/chat`, or `/entra`).
4. **Update route protection if needed:** If the new `commerce` route requires authentication, verify it is covered by `protectedRoutes` in `src/Clients/apps/commerce/proxy.ts`.
5. **Verify gateway & frontend checks:** Run `bun run boundaries`, `bun run check-types`, `bun run lint`, `bun run test`, and `bun run build` from `src/Clients`.
