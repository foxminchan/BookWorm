BookWorm organizes its three Next.js 16 applications (**Storefront**, **Commerce**, and **Backoffice**) and 16 shared `@workspace/*` packages inside a single Bun and Turborepo workspace (`src/Clients/`). By enforcing one-way dependency tiers, keeping App Router pages thin, and separating server cache from ephemeral client state, the frontend mirrors BookWorm's backend Vertical Slice Architecture without circular dependencies or duplicated configuration.

## Context and motivation

All three frontend applications share Microsoft Entra ID authentication (via Better Auth), typed API clients, Valibot validation schemas, OpenTelemetry startup instrumentation, Tailwind CSS v4 UI components, and Vitest/Playwright test harnesses. Without structural guardrails, shared frontend code typically degrades in three ways:

- **Circular imports:** Low-level helpers import domain UI or app-specific config, making packages impossible to reuse or test in isolation.
- **Fat route files:** Next.js `page.tsx` files mix metadata, data fetching, form validation, and layout markup, blurring Server and Client Component boundaries.
- **Ad-hoc data fetching:** Scattered `fetch` calls duplicate cache keys, skip retries, overwrite concurrent edits in **Backoffice**, and trigger unnecessary anonymous requests for signed-out shoppers.

## How it works

### Four-tier workspace boundaries

Every workspace member declares a `tags` entry in its `turbo.json` (`config`, `foundation`, `domain`, or `app`). `turbo boundaries` validates imports on every pull request so dependencies flow strictly downward.

- **Direct source resolution:** Next.js and Vitest resolve `@workspace/*` packages directly from TypeScript source (with Turborepo `transit` edges invalidating `lint` and `check-types`), avoiding slow cascading pre-build steps while preserving strict boundary checks.
- **Scoped environment validation:** `@workspace/env` exposes composable schemas per capability (authentication, API Gateway, telemetry, AI chat) so each application validates only the variables it requires at build and startup time.
- **Single Bun lockfile:** Standardizing on `bun@1.4.4` and one root `src/Clients/bun.lock` eliminates lockfile drift across local development and CI.

### Thin routes and domain-aligned feature slices

Inside each Next.js application (`apps/storefront`, `apps/commerce`, `apps/backoffice`), route files under `app/` stay intentionally thin:

- **Route entrypoints (`app/`):** Define metadata, loading/error boundaries, and server-side query prefetching via `HydrationBoundary`, then render a single view component from `features/`.
- **Feature slices (`features/`):** Group UI components, tables, filters, and Formisch forms by business capability (Catalog, Shopping, Ordering, Reviews), mirroring backend bounded contexts.
- **Scoped authentication:** Storefront and Commerce share one customer Better Auth session (`/api/auth/[...all]`), whereas Backoffice mounts its own staff session (`/backoffice/api/auth/[...all]`) with separate Entra ID scopes. Backend APIs still enforce authorization independently on every request.

### Layered data pipeline and state boundaries

Instead of calling `fetch` inside components, data flows through a typed, resilient pipeline from React components to the five gateway-routed backend services (**Catalog API**, **Basket API**, **Ordering API**, **Rating API**, and **Chat API**).

<MermaidFileLoader file="mermaids/007-architecture-and-state-design-diagram-2.mmd" />

- **Shared contracts and single cache-key source:** `@workspace/types` and `@workspace/validations` define DTOs and Valibot schemas once. `@workspace/api-hooks/keys` and query factories pair keys with fetchers so server prefetching and client hooks never drift on hydration.
- **Optimistic concurrency with ETags:** Editable **Backoffice** resources (books and order summaries) exchange `ETag`, `If-None-Match`, and `If-Match` headers. Concurrent edits fail explicitly with `412 Precondition Failed` instead of silently overwriting newer changes.
- **Targeted real-time channels:** Backoffice overview metrics load an initial snapshot and subscribe to an authenticated SSE stream (`/ordering/api/v1/dashboard/stream`), while Storefront's AI assistant streams over CopilotKit AG-UI (`/chatting/ag-ui`) and renders declarative A2UI components.
- **Minimal client-only state:** Jotai holds only lightweight session-derived and feature-flag state (`isAuthenticatedAtom`, `basketItemCountAtom`, `isCopilotEnabledAtom`). Gating `basketAtom` on `isAuthenticatedAtom` prevents anonymous shoppers from triggering failing `401` basket calls.

## Design trade-offs

| Decision                                                     | Benefits                                                                          | Costs and limits                                                                           |
| :----------------------------------------------------------- | :-------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------- |
| Four-tier Turborepo boundaries (`turbo boundaries`)          | Prevents circular dependencies and enforces clear ownership across 19 packages    | Contributors must place shared code in the correct tier before importing it                |
| Direct TypeScript source imports for `@workspace/*`          | Fast local iteration and no per-package publish/compile boilerplate               | Apps must register workspace packages in Next.js/Vitest config (`@workspace/app-config`)   |
| Thin routes + feature slices                                 | Easier unit testing with MSW and cleaner Server/Client Component boundaries       | Adds one level of indirection between `app/**/page.tsx` and `features/`                    |
| TanStack Query for server state + Jotai for minimal UI state | Eliminates manual Redux/store synchronization and handles SSR hydration + retries | Contributors must distinguish server state (TanStack Query) from client-only state (Jotai) |

## Alternatives considered

- **Separate repositories per frontend app:** Would force publishing versioned npm packages for `@workspace/ui`, `@workspace/api-client`, and `@workspace/storefront-shell`, slowing cross-cutting changes across Storefront, Commerce, and Backoffice.
- **Single global client store (Redux / Zustand) for all API data:** Duplicates caching, deduplication, SSR dehydration, and invalidation logic that TanStack Query already provides.
- **Last-write-wins updates in Backoffice:** Simpler than ETag headers, but risks silent data loss when two administrators edit the same book or order concurrently.
