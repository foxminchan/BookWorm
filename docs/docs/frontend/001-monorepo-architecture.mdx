## 1. Context & Problem

BookWorm serves two distinct web experiences—the customer-facing storefront (`@bookworm/storefront`) and the staff administration dashboard (`@bookworm/backoffice`). Both applications share authentication flows against [[system|identity-provider]], typed backend API clients, Zod validation schemas, OpenTelemetry setup, UI primitives, and test harnesses.

Without explicit package boundaries and centralized workspace tooling, shared modules quickly accumulate circular imports, duplicate configuration code, or direct coupling between foundation helpers and application UI code. Organizing `src/Clients` as a layered Bun + Turborepo monorepo keeps cross-cutting concerns reusable while enforcing dependency direction automatically.

## 2. Business Value

- **Enforced architectural hygiene:** Turborepo package tags block invalid upward dependencies (`config` -> `foundation` -> `domain` -> `app`) before code is merged.
- **Zero-duplication cross-cutting capabilities:** Environment validation, Entra ID authentication, OpenTelemetry registration, and SEO metadata live once in `@workspace/*` packages instead of drifting between apps.
- **Consistent developer & CI workflows:** Shared TypeScript, ESLint, Next.js, Vitest, Playwright, and Allure presets reduce boilerplate and guarantee consistent quality checks across all 17 workspace packages.

## 3. How It Works

The frontend workspace lives under `src/Clients` and uses Bun workspaces (`apps/*`, `packages/*`) orchestrated by Turborepo:

<MermaidFileLoader file="mermaids/monorepo-package-layers.mmd" />

1. **Strict unidirectional dependency flow:** Configuration packages sit at the base with no upward dependencies; foundation packages hold framework-agnostic schemas, environment validators, telemetry, and domain types; domain packages compose API clients, query hooks, authentication, SEO, mocks, and UI components; application packages assemble routes and features for end users.
2. **Composable environment validation:** Each domain capability (`authKeys`, `gatewayKeys`, `otelKeys`, `copilotKeys`) declares and validates its own environment variables in `@workspace/env`. Each Next.js app composes only the slices it requires in `env.mjs` using `@t3-oss/env-nextjs` `extends`.
3. **Unified OpenTelemetry startup:** Next.js instrumentation entrypoints (`instrumentation.ts`) in both apps delegate directly to `@workspace/otel/instrumentation` so service naming and trace export stay uniform across local runs and Azure Container Apps.
4. **Workspace package resolution without build fragility:** Both [next.mjs](https://github.com/foxminchan/BookWorm/blob/main/src/Clients/packages/app-config/next.mjs) (`transpilePackages`) and [vitest.mjs](https://github.com/foxminchan/BookWorm/blob/main/src/Clients/packages/app-config/vitest.mjs) (`resolve.alias`) resolve workspace source modules consistently across production builds and unit tests.

## 4. Trade-offs & Lessons Learned

- **Tag-based boundary checks vs. ad-hoc imports:** Requiring every package to declare a `turbo.json` boundary tag adds minor setup when creating a new package, yet catches accidental layering violations immediately with `bun run boundaries`.
- **Direct workspace TypeScript consumption vs. per-package build artifacts:** Transpiling `@workspace/*` packages directly from `src/` via Next.js `transpilePackages` and Vitest aliases avoids cascading pre-build steps in local development, though Node-evaluated configs such as `env.mjs` must reference explicit subpath exports in `package.json`.
- **Bun as a single JS package manager:** Standardizing on `bun@1.4.4` and a single root `bun.lock` eliminates npm/pnpm lockfile drift while speeding up dependency installation and workspace task execution.

## 5. Technical Reference

### Repository Root Layout (`src/Clients`)

```text
src/Clients/
├── apps/
│   ├── backoffice/         # Next.js 16 Admin dashboard (@bookworm/backoffice)
│   └── storefront/         # Next.js 16 Customer storefront (@bookworm/storefront)
├── packages/               # 15 internal @workspace/* packages
├── allurerc.mjs            # Unified Allure test reporting configuration
├── eslint.config.js        # Root ESLint flat config entrypoint
├── package.json            # Bun workspaces and Turborepo task scripts
└── turbo.json              # Task pipeline graph and package boundary rules
```

### Package Boundary Tiers (`turbo.json`)

The root `turbo.json` defines `boundaries.tags` so `bun run boundaries` inspects every import across all 17 workspace packages:

| Tier Tag     | Allowed Dependencies             | Denied Dependencies           | Purpose                                                                              |
| :----------- | :------------------------------- | :---------------------------- | :----------------------------------------------------------------------------------- |
| `config`     | None within workspace            | `app`, `domain`, `foundation` | Shared ESLint, TypeScript, Next.js, Vitest, Playwright, and Allure presets           |
| `foundation` | `config`, `foundation`           | `app`, `domain`               | Pure types, utility helpers, env schemas, and OpenTelemetry registration             |
| `domain`     | `config`, `foundation`, `domain` | `app`                         | UI design system, API clients, query hooks, auth, SEO, validation schemas, MSW mocks |
| `app`        | All tiers                        | —                             | End-user Next.js applications (`storefront`, `backoffice`)                           |

### Environment & Instrumentation Wiring

Apps compose only the environment slices they use in `env.mjs`:

```ts
import { createEnv } from "@t3-oss/env-nextjs";

import { authKeys } from "@workspace/env/auth";
import { gatewayKeys } from "@workspace/env/gateway";
import { otelKeys } from "@workspace/env/otel";

export const env = createEnv({
	extends: [authKeys(), gatewayKeys(), otelKeys()],
	server: {},
	client: {},
	runtimeEnv: {},
	skipValidation: !!process.env.SKIP_ENV_VALIDATION,
	emptyStringAsUndefined: true,
});
```

Both `apps/storefront/instrumentation.ts` and `apps/backoffice/instrumentation.ts` re-export telemetry initialization in one line:

```ts
export { register } from "@workspace/otel/instrumentation";
```
