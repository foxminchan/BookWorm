BookWorm's Azure infrastructure is synthesized by .NET Aspire from `BookWorm.AppHost` as a subscription-scoped deployment. It provisions a dedicated resource group containing an Azure Container Apps (ACA) environment, managed data and AI services, passwordless Microsoft Entra ID authentication, and per-service user-assigned managed identities.

## 1. Context & Problem

BookWorm spans multiple storefronts, domain microservices, background orchestration workers, personal-data protection sidecars, databases, and AI capabilities. Maintaining separate hand-written cloud scripts apart from the application architecture leads to drift between what developers build locally and what runs in the cloud, while exposing individual services to the internet increases security and routing complexity. The platform needs a single, application-driven topology with a clear shared backbone and strict perimeter boundaries.

## 2. Business Value

- **Architecture-to-Cloud Alignment:** Cloud infrastructure is synthesized directly from the application composition model, reducing configuration drift and onboarding friction.
- **Reduced Attack Surface:** Only a single public gateway faces external traffic, keeping all internal services, web frontends, workers, and privacy sidecars off the public internet.
- **Idempotent, Predictable Deployments:** Deterministic resource naming within a dedicated resource group ensures repeat deployments update reliably without duplicating environments.
- **Lower Operational Overhead:** Serverless container hosting, managed passwordless identities, and built-in 90-day observability minimize infrastructure maintenance for delivery teams.

## 3. How It Works

BookWorm organizes its cloud footprint into three clear layers:

1. **Subscription-Scoped Provisioning:** Each deployment targets a dedicated resource group in a chosen region and derives deterministic resource names so updates are repeatable. Optional naming suffixes isolate directory identity registrations across environments such as staging and production.
2. **Shared Platform Backbone:** Core platform modules establish a private container image registry, a shared registry-pull identity, a serverless container hosting environment, a centralized 90-day log analytics workspace, and a managed live observability dashboard.
3. **Single-Gateway Ingress Boundary:** Only the API gateway accepts external requests from users and external clients. All fourteen remaining workloads—including customer and backoffice web storefronts, backend microservices, background workers, and privacy redaction sidecars—are reachable solely on the private internal network, with the gateway forwarding requests and user context headers to the appropriate internal service.

## 4. Trade-offs & Lessons Learned

- **Single Gateway as a Critical Chokepoint:** Routing every external request through one gateway simplifies edge security, authentication callbacks, and path routing, but makes gateway availability, scaling, and edge firewall protection critical to the entire platform.
- **Serverless Consumption vs. Dedicated Compute:** Running workloads on a consumption hosting profile keeps baseline infrastructure lean and scales automatically with demand, though teams must account for scaling thresholds and right-size latency-sensitive components.
- **Generated Baseline vs. Production Hardening:** Synthesizing infrastructure from the application host accelerates environment creation, while production deployments still require layering on private virtual networking, upper replica limits, and backup drills as separate hardening steps.
- **Deterministic Naming Scope:** Deriving unique suffixes from the resource group ensures idempotency inside one group, so deploying multiple isolated environments requires distinct resource groups and optional identity suffixes.

### Deployment Scope & Naming Convention

The root deployment targets `targetScope = 'subscription'` and provisions a dedicated resource group (`resourceGroupName`) in the specified `location`.

| Parameter              | Purpose                                                       | Default / Notes                              |
| :--------------------- | :------------------------------------------------------------ | :------------------------------------------- |
| `resourceGroupName`    | Target Azure resource group created at subscription scope     | Required                                     |
| `location`             | Azure region for all regional resources                       | Required                                     |
| `principalId`          | Object ID of the deploying user or CI/CD service principal    | Required (used for ACR/Foundry project RBAC) |
| `tenantResourceSuffix` | Optional suffix appended to Entra ID app display/unique names | `''` (empty string)                          |

Most Azure resources derive a deterministic suffix using `uniqueString(resourceGroup().id)` (`resourceToken`) so deployments are idempotent within a resource group.

### Shared Platform Layer

The `aca-acr` and `aca` Bicep modules establish the shared compute, registry, and observability backbone:

| Module    | Azure Resource                             | Configuration                                                      |
| :-------- | :----------------------------------------- | :----------------------------------------------------------------- |
| `aca-acr` | Azure Container Registry (`acr<token>`)    | Standard SKU container image registry                              |
| `aca`     | Managed Identity (`mi-<token>`)            | Assigned `AcrPull` (`7f951dda-4ed3-4680-a7ca-43fe172d538d`) on ACR |
| `aca`     | Log Analytics Workspace (`law-<token>`)    | `PerGB2018` SKU with **90-day** log retention                      |
| `aca`     | Container Apps Environment (`cae-<token>`) | `Consumption` workload profile wired to Log Analytics              |
| `aca`     | Aspire Dashboard (`aspire-dashboard`)      | Managed `dotNetComponents` (`AspireDashboard`) in ACA              |

### Network & Ingress Boundary

Only the YARP API Gateway (`gateway`) is exposed to external traffic. All other 14 container apps—including the Next.js frontends (`storefront`, `backoffice`), microservices, Azure Functions workers, and PII sidecars—use **internal-only** ACA ingress (`external: false`).

- **External entry point:** `https://gateway.<AZURE_CONTAINER_APPS_ENVIRONMENT_DEFAULT_DOMAIN>` on port `5000`.
- **Internal service-to-service URLs:** `https://<app>.internal.<AZURE_CONTAINER_APPS_ENVIRONMENT_DEFAULT_DOMAIN>`.
- **Gateway routing:** YARP terminates external HTTP traffic and routes paths (`/chatting`, `/rating`, `/ordering`, `/basket`, `/catalog`, `/backoffice`, `/`) to internal container apps with `X-Forwarded-*` headers.
