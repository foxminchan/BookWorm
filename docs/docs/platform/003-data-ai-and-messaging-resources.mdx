Each BookWorm bounded context owns its authoritative persistence, isolated behind service APIs and authenticated via Microsoft Entra ID RBAC. This reference documents the Azure-managed data and AI stores alongside external messaging, vector search, and email dependencies.

### Kafka Messaging Conventions

- **Transport:** Wolverine with Kafka transport and CloudEvents JSON serialization (propagates W3C trace context, request ID, and user identity).
- **Default topic naming:** `bookworm.{env}.{owner-service}.{topic-name}` (exception: `scheduler.process-vector-batch` is unprefixed).
- **Dead-letter queues:** One native dead-letter queue per service (`bookworm.{env}.{service}.dead-letter-queue`).
- **Retry policy:** Cooldowns of `50ms`, `250ms`, and `1s` with full jitter before routing to the native dead-letter queue.

## Guardrails & Constraints

<Admonition type="warning" title="Restrict Network & CORS Policies Before Production">
	Azure Storage Blob CORS currently permits all origins (`*`, 1-hour cache), and Durable Task
	Scheduler declares an open IP allowlist (`0.0.0.0/0`). Restrict both to known gateway and workload
	boundaries before Production; see [[doc|operational/004-security-hardening-checklist]].
</Admonition>

<Admonition type="info" title="PostgreSQL Database Isolation">
	PostgreSQL hosts **only** [[container|catalog-database]], [[container|order-database]], and
	[[container|scheduler-database]]. [[service|order-orchestration]], [[service|notification-api]],
	[[service|basket-api]], [[service|rating-api]], and [[service|chat-api]] must never provision
	relational PostgreSQL databases.
</Admonition>
