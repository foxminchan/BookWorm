# MS Decisions Model (`Microsoft-Decision-1`) in BookWorm Chat

## 1. Context & Problem

In BookWorm's multi-agent chat experience ([[system|chat-system]]), two frequent steps occur before a specialist AI assistant generates a customer-facing response:

1. **Request screening and routing**: Determining whether an incoming message is safe, written in English, and relevant to BookWorm, and deciding which specialist assistant should handle it.
2. **Per-turn tool filtering**: Selecting which backend actions (tools) are genuinely relevant to the current turn out of all actions available to the assistant.

Both tasks are **classification decisions** (answering yes/no or multiple-choice questions) rather than open-ended text generation. Using a full conversational AI model for these rapid checks adds noticeable response delay, increases token costs, and risks formatting errors in structured responses.

## 2. Business Value

- **Faster customer responses**: Evaluating safety, language, scope, and routing in a single pass removes the latency of a separate conversational router call.
- **Lower AI operating cost**: Filtering out irrelevant tools before invoking the assistant reduces token usage on every turn.
- **Consistent, measurable governance**: Calibrated confidence thresholds provide repeatable rules for stopping unsafe, unsupported-language, or off-topic requests before specialist assistants run.
- **Higher assistant accuracy**: Giving assistants only the tools relevant to the current conversation prevents distraction from unrelated actions.

## 3. How It Works

BookWorm uses Microsoft Foundry's `Microsoft-Decision-1` model in [[system|chat-system]] to evaluate multiple yes/no and multiple-choice questions in a **single pass**, returning calibrated confidence scores for each decision.

### Use Case 1: Single-Pass Screening & Routing

<MermaidFileLoader file="mermaids/decision-routing-and-safety-flow.mmd" />

Before any specialist assistant is invoked, every incoming customer message goes through one combined pre-screening step that evaluates four checks at once:

| Check          | Type     | What it evaluates                                                     | Decision Rule                                                          |
| -------------- | -------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Safety**     | Yes / No | Detects prompt-injection, jailbreak, or instruction-override attempts | Confidence below 50% stops the request as unsafe                       |
| **Language**   | Yes / No | Verifies the message is written in English                            | Confidence below 50% stops the request as unsupported language         |
| **Scope**      | Yes / No | Checks relevance to BookWorm (books, orders, store policies, etc.)    | Confidence below 50% stops the request as out of scope                 |
| **Specialist** | Choice   | Picks the best assistant: **Book**, **Q&A**, or **Rating**            | **Rating** is selected only when a specific book catalog ID is present |

Combining safety, language, scope, and specialist routing into one step replaces a slower standalone router call and applies consistent, measurable thresholds.

### Use Case 2: Dynamic Per-Turn Tool Selection

<MermaidFileLoader file="mermaids/decision-tool-selection-flow.mmd" />

BookWorm's **Book** and **Q&A** assistants have access to many backend tools (for searching the catalog, looking up policies, and similar tasks). Instead of sending every tool description on every turn:

1. The system reviews the recent conversation context (the last **6 messages** by default).
2. It asks the decision model whether each optional tool is relevant to the current turn.
3. Only tools scoring **50% confidence or higher** are passed to the AI assistant.
4. Tools marked as **always included** or **explicitly required** for the current action bypass filtering so they are never removed.

## 4. Trade-offs & Lessons Learned

### 1. Isolate vendor-specific protocols from business logic

Early prototypes mixed Microsoft Foundry's specific payload format directly with client logic. Separating a reusable decision contract from the provider-specific protocol mapping keeps BookWorm's chat rules clean and makes it straightforward to swap or upgrade decision providers later without touching business workflows.

### 2. Plan explicit fallbacks for partial or unanswered decisions

A decision model can occasionally skip an individual question or time out. Treating any partial response as a total failure would either drop valid safety blocks or break the customer's chat:

- **Routing**: If the model skips the specialist selection question, the system still enforces any safety, language, or scope rejections it _did_ answer, and safely defaults to the **Book Assistant**.
- **Tool selection**: Fails open—if the decision call fails, times out, or unexpectedly selects zero tools, the system logs the issue and keeps all original tools so the assistant can still respond.

### 3. Never filter out mandatory or explicitly required tools

When a workflow explicitly requires a specific tool (or marks core tools as always available), those tools are separated before calling the decision model so they are guaranteed to reach the assistant.

### 4. Pre-generate data formatting at build time for performance and reliability

Generating data-serialization rules at compile time rather than inspecting structures at runtime eliminates runtime overhead, prevents deployment trimming warnings, and keeps the codebase compliant with strict static-analysis rules.

### 5. Layer AI-based safety with deterministic checks

AI-based safety screening is a strong first-pass filter, but it complements—rather than replaces—fast rule-based input validation (such as empty-input checks, length limits, and known pattern matching) and downstream privacy and guardrail filters.

### 6. Test decision contracts and thresholds with simulated responses

Because question definitions, descriptions, and the 50% confidence cutoff directly control user-facing behavior, automated unit and workflow tests use simulated decision clients to verify boundary cutoffs, fallback paths, and context propagation without calling a live AI endpoint.

## 5. Technical Reference

### Decision parameters and screening identifiers

- **Confidence score range**: `0.0` to `1.0`, with a `0.5` (`50%`) cutoff threshold.
- **Screening question IDs**: `is_safe` (Safety), `is_english` (Language), `is_in_scope` (Scope), and `route` (Specialist).
- **Routing fallback**: Unanswered `route` defaults to the **Book Assistant** while preserving any answered `is_safe`, `is_english`, or `is_in_scope` rejections.
- **Tool-selection context window**: Last `6` messages (`MaxContextMessages = 6`).
