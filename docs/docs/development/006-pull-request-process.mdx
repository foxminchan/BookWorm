Open a pull request when the change is understandable, scoped, and locally verified. Keep it in draft while implementation or validation is still in progress.

_Pull Request Lifecycle_

<MermaidFileLoader file="mermaids/pull-request-process.mmd" />

## Before opening

- Keep the change to one cohesive outcome. Split unrelated work; discuss unusually broad changes before investing in them.
- Format changed files and run the relevant checks from [[doc|development/005-testing]].
- Use a Conventional Commit-style title, such as `fix: prevent duplicate checkout`.
- Include the user-visible or technical outcome, relevant context, test evidence, and any rollout or compatibility notes in the description.

## Move from draft to review

<Steps>
<Step title="Open a draft pull request">

Push your branch and create a draft with the GitHub CLI or web interface. Link related work and state what remains before review.

```bash
gh pr create --draft --title "<type>: <summary>" --body "<change, rationale, and verification>"
```

</Step>
<Step title="Complete the change and mark it ready">

Address unfinished work, update documentation when behavior or contracts change, and mark the pull request ready for review.

</Step>
<Step title="Resolve automated checks">

Required checks depend on changed areas. They can include backend formatting and analyzers, backend tests and contracts, frontend boundaries/types/lint/build/tests, documentation lint/fitness/build, and dependency review.

Check the current status with:

```bash
gh pr checks
```

Fix failures and push updates; changed commits rerun affected checks.

</Step>
<Step title="Respond to review and merge">

Address requested changes, keep the branch conflict-free, and request re-review when ready. Merge only after at least one maintainer approval and all required checks pass. Use the merge method enabled by the repository.

</Step>
</Steps>

<Admonition type="warning" title="Security reports">
	Do not disclose a security vulnerability in a public pull request or issue. Use the project's
	private security reporting channel.
</Admonition>

For branch naming and synchronization, see [[doc|development/003-development-workflow]]. For test-layer selection and commands, see [[doc|development/008-testing-matrix]] and [[doc|development/005-testing]].
