Use this guide to diagnose and recover from common local setup and runtime failures when running BookWorm with `mise`, Aspire 17, Docker, and Bun. For production Azure Container Apps incidents, see [[doc|operational/003-incident-response-and-runbooks]].

## Prerequisites

- Local toolchain installed via [[doc|development/002-getting-started]]
- Access to the Aspire Dashboard (`https://localhost:17290` or `http://localhost:15061`) when diagnosing running services

## Steps

<Steps>
<Step title="Confirm Docker and pinned tool versions first">

Verify that Docker is running and `mise` exposes the expected versions before inspecting individual services:

<CodeGroup>

```bash
docker info --format '{{.ServerVersion}}'
dotnet --version
aspire --version
bun --version
```

</CodeGroup>

</Step>
<Step title="Inspect container and service logs in the Aspire Dashboard">

Open `https://localhost:17290`, filter to the failing resource (`Console` or `Structured` logs), and verify whether its upstream backing container (`postgres`, `redis`, `broker`, `vectordb`, `cosmos`, `storage`, `presidio-analyzer`, `presidio-anonymizer`) reached the **Running** state first.

</Step>
<Step title="Reset persistent local container volumes when state is corrupted">

BookWorm configures `ContainerLifetime.Persistent` and data volumes on `postgres`, `redis`, `vectordb`, `broker`, `cosmos`, `storage`, `durable-task-scheduler`, `presidio-analyzer`, and `presidio-anonymizer`. Stop Aspire, then remove stuck containers or volumes for the affected dependency:

<CodeGroup>

```bash
docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
```

```bash
docker rm -f <container-name>
```

</CodeGroup>

Where:

- `<container-name>`: The Docker container name shown by `docker ps -a`.

</Step>
<Step title="Re-run isolated checks without Docker when debugging code">

Isolate code failures from container failures by running unit tests or frontend checks directly:

<CodeGroup>

```bash
mise run test:unit
```

```bash
cd src/Clients && bun run check-types && bun run test
```

</CodeGroup>

</Step>
</Steps>

## Verification

Restart the Aspire AppHost and confirm all required resources (excluding explicit-start `scheduler`) reach **Running** in the Aspire Dashboard:

<CodeGroup>

```bash
mise run run
```

</CodeGroup>

Expected output:

<CodeGroup>

```text
Login to the dashboard at https://localhost:17290/login?t=<one-time-token>
```

</CodeGroup>

## Troubleshooting

| Symptom                                                                                              | Cause                                                                                                                                       | Fix                                                                                                                                                                                                                                         |
| :--------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `aspire start` fails immediately with container runtime error                                        | Docker Desktop is stopped or unreachable                                                                                                    | Start Docker Desktop, verify `docker info` succeeds, and re-run `mise run run`                                                                                                                                                              |
| Port conflict on `17290`, `15061`, `3000`, `3001`, `5026`–`5278`, `7071`, or `7072`                  | Another local process or leftover BookWorm container holds the port                                                                         | Run `docker ps` to stop stale containers or stop conflicting local dev servers; check `launchSettings.json` ports in `_ground-truth`                                                                                                        |
| `storefront` or `backoffice` login redirects fail with `400` / `invalid_client` or callback mismatch | Local Microsoft Entra ID app registration or `BETTER_AUTH_SECRET` / dev HTTPS cert is missing or mismatched                                 | Trust the local dev certificate (`dotnet dev-certs https --trust`), verify Entra ID redirect URIs include `/api/auth/oauth2/callback/microsoft-entra-id` and `/backoffice/api/auth/oauth2/callback/microsoft-entra-id`, and restart AppHost |
| `catalog`, `ordering`, `basket`, or `finance` fails to connect to `broker` (Kafka)                   | Kafka container is still initializing or persistent Kafka state is stale after an unclean shutdown                                          | Wait for `broker` health in Aspire Dashboard; if stuck, remove the `broker` container via `docker rm -f <container-name>` and restart `mise run run`                                                                                        |
| Semantic search returns empty results or `catalog-ingestion` logs Qdrant errors                      | `vectordb` (Qdrant) is not healthy, Microsoft Foundry `embedding` (`EmbedV40`) credentials are missing, or `scheduler` has not been started | Confirm `vectordb` is Running, verify Microsoft Foundry parameters, and manually click **Start** on `scheduler` in Aspire Dashboard (it uses `.WithExplicitStart()`)                                                                        |
| `basket`, `catalog`, `ordering`, `rating`, or `notification` logs Redis connection errors            | Local `redis` container failed to bind or ran out of memory                                                                                 | Inspect `redis` logs in Aspire Dashboard, check Docker memory allocation (16+ GB RAM recommended), and recreate the container if needed                                                                                                     |
| `rating` fails on startup with Cosmos DB emulator TLS or timeout error                               | Azure Cosmos DB Linux/Windows emulator takes longer to initialize on first boot or lacks trusted dev cert                                   | Wait 60–90 seconds for the `cosmos` container to finish booting, ensure Docker has sufficient RAM, and verify `cosmos` Data Explorer responds before restarting `rating`                                                                    |
| `chatting` or `rating` returns `502`/`503` on AI calls                                               | `presidio-analyzer` / `presidio-anonymizer` containers are unhealthy or Microsoft Foundry credentials/quotas are invalid                    | Check `presidio-analyzer` and `presidio-anonymizer` `/health` endpoints (port `3000`) in Aspire Dashboard and verify Foundry `chat` (`ModelRouter`) and `decision` (`MicrosoftDecision1`) parameters                                        |
| `bun install` or `bun run dev` fails in `src/Clients` or `docs`                                      | Wrong Bun version, corrupted `node_modules`, or accidental `package-lock.json` / `pnpm-lock.yaml`                                           | Confirm `bun --version` is `1.4.4` via `mise install`, delete any non-Bun lockfile, and re-run `bun install`                                                                                                                                |
| `finance` or `catalog-ingestion` fails to start on port `7071` / `7072`                              | Azurite (`storage`) emulator is unavailable or `Azure.Functions.Sdk` host storage failed                                                    | Confirm `storage` (Azurite) is Running in Aspire Dashboard and `durable-task-scheduler` is healthy for `finance`                                                                                                                            |

Clear the AppHost's stored parameters with `dotnet user-secrets clear --project src/Aspire/BookWorm.AppHost`, then start it again to be prompted for values. The AppHost project declares a `UserSecretsId`; do not use an undocumented `aspire secret` command.
