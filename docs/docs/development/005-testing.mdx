# Testing changes

## 1. Context & Problem

In a distributed system with independent microservices, asynchronous messaging, frontend applications, and architecture documentation, manual verification cannot reliably catch regressions. Teams need a structured automated testing approach that validates business rules in isolation, verifies cross-service message agreements, and checks frontend and documentation quality before changes are merged.

## 2. Business Value

- **Higher release confidence**: Automated checks across business logic, architecture rules, service contracts, and user interfaces reduce defects reaching production.
- **Fast developer feedback**: Isolated, deterministic tests execute quickly without requiring full infrastructure, allowing issues to be fixed immediately during development.
- **Safe cross-service evolution**: Consumer-driven contract verification confirms that message producers and consumers stay compatible even when services evolve independently.

## 3. How It Works

BookWorm structures testing around verifying observable behavior rather than internal implementation details, keeping checks fast, repeatable, and independent of shared state:

1. **Business logic and unit verification**: Tests are organized by feature or business entity and cover normal outcomes, boundary conditions, validation rejections, and error handling—targeting at least 80% coverage of core domain logic. External dependencies such as databases and infrastructure components are simulated so tests remain isolated, and test names clearly express the initial condition, action taken, and expected outcome.
2. **Architecture verification**: Automated architecture checks enforce structural boundaries and conventions across services so unintended coupling does not creep in over time.
3. **Cross-service contract verification**: Asynchronous integration contracts are validated in two ordered stages. First, consumer tests generate contract expectations defining the messages they rely on. Second, provider tests verify that message producers satisfy those recorded expectations. Running consumer generation before provider verification guarantees both sides validate against up-to-date agreements.
4. **Frontend and documentation checks**: Changes to client applications are verified through code linting, type-safety checks, unit tests, and end-to-end tests. Changes to architecture documentation are validated for catalog linting, formatting compliance, and architecture fitness rules.

## 4. Trade-offs & Lessons Learned

- **Testing behavior vs. implementation details**: Focusing tests on business outcomes lets teams refactor internals without rewriting tests, though it requires clear isolation boundaries and well-designed test doubles for external dependencies.
- **Strict order in contract testing**: Because provider verification reads the contract files generated by consumer tests, running stages out of order risks validating against stale expectations.
- **Targeted local runs vs. full-suite verification**: Running a single service's test suite accelerates local iteration, while running the full solution suite and coverage collection provides complete release assurance at the expense of longer runtime.

## 5. Technical Reference

### Test practices

- Test business logic and domain behavior; aim for at least 80% coverage in domain logic.
- Name tests descriptively, using the `GivenCondition_WhenAction_ThenExpectedResult` pattern. For example: `GivenValidBook_WhenAddingToLibrary_ThenSuccessReturned`.
- Group tests by feature or domain entity, with separate fixtures for distinct scenarios.
- Mock external dependencies such as repositories, services, and infrastructure components.
- Avoid testing implementation details. Keep tests fast, independent, repeatable, and free of shared state.
- Follow TUnit conventions and use appropriate test attributes for categorization.

### Frameworks and tools

- **Test framework:** TUnit (not xUnit, NUnit, or MSTest)
- **Mocking:** Moq
- **Assertions:** Shouldly
- **Consumer-driven contracts:** Pact.NET asynchronous-message consumer contracts and provider verification
- **Architecture tests:** ArchUnitNET.TUnit in `tests/BookWorm.ArchTests/`
- **Coverage:** Microsoft.Testing.Extensions.CodeCoverage

For backend test authoring, use the [TUnit skill](https://github.com/foxminchan/BookWorm/tree/main/.agents/skills/tunit).

### Run tests

The repository defines common tasks in [`mise.toml`](https://github.com/foxminchan/BookWorm/blob/main/mise.toml). From the repository root:

```bash
mise run test:unit
mise run test:contracts
mise run test:coverage
mise run test
```

`mise run test:unit` runs the service unit tests and architecture tests. `mise run test:contracts` generates consumer pacts before verifying providers. `mise run test:coverage` collects code coverage matching SonarCloud, and `mise run test` builds the solution, then runs both unit and contract suites. For a focused change, run a single test project directly (for example, `dotnet test src/Services/Catalog/BookWorm.Catalog.UnitTests/BookWorm.Catalog.UnitTests.csproj`); consult `mise.toml` for the current project paths and filters.

### Contract tests

The contract task runs consumer tests first to generate pact files under `tests/pacts/`, then runs provider verification against those files. Preserve this order when running contract tests manually because both stages share the generated artifacts.

### Frontend and documentation checks

When changing frontend code under `src/Clients`, run the relevant checks from `src/Clients` (see [[doc|frontend/004-testing-and-quality-gates]] for details):

```bash
bun run boundaries
bun run lint
bun run check-types
bun run test
bun run build
bun run e2e
```

When changing documentation under `docs/`, validate EventCatalog linting, formatting, and architecture fitness rules from `docs/`:

```bash
bun run check
bun run fitness
```
