## Day 1: orient and verify

1. Read this roadmap, then skim [[doc|arc42/01-introduction-and-goals/001-introduction]].
2. To run BookWorm immediately, follow [[doc|development/000-local-quickstart]]. For a more deliberate environment setup, use [[doc|development/002-getting-started]] instead.
3. Identify the service or frontend that owns the behavior you want to understand. Keep changes inside that boundary and follow [[doc|development/004-engineering-standards]].
4. Verify one local application endpoint and one relevant check before changing code. Use [[doc|development/007-troubleshoot-local-dev]] if setup blocks you.

| Milestone            | Evidence                                                                        |
| :------------------- | :------------------------------------------------------------------------------ |
| Workspace ready      | The required tools are available and dependencies are restored.                 |
| Application verified | The Aspire dashboard is reachable and the public application endpoint responds. |
| Change identified    | You can name the owning business capability and the behavior to change.         |

## A good first contribution

Choose a change with a clear owner, observable outcome, and testable acceptance criteria. Confirm the expected behavior with a maintainer when those criteria are unclear. Keep the patch focused, run the checks for the changed area, and describe both the change and its verification in the pull request.

For common startup failures, use [[doc|development/007-troubleshoot-local-dev]]. For production-only incidents, follow [[doc|operational/003-incident-response-and-runbooks]].
