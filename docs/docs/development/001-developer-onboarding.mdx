BookWorm is an open-source, cloud-native online bookstore demonstrating .NET 11 microservices orchestrated by Aspire 17, Domain-Driven Design (DDD), Vertical Slice Architecture (VSA), event-driven choreography and sagas with Wolverine over Kafka, Next.js 16 microfrontends, and governed multi-agent AI built on Microsoft Foundry. Understanding how its six bounded contexts own state and communicate lets you locate changes accurately without introducing cross-service coupling.

## Context and motivation

E-commerce systems combine fast-changing product discovery, transient customer shopping intent, durable financial orders, user-generated reviews, and conversational AI support. Grouping all of those capabilities into a shared database or layered middle tier blurs accountability: a basket schema edit can break order reporting, or a review query spike can degrade checkout latency.

BookWorm decomposes the platform along **business capabilities (bounded contexts)**. Each service owns its business state and persistence technology, exposes explicit HTTP/gRPC or Kafka contracts, and relies on a shared technical chassis (`BookWorm.Chassis`, `BookWorm.ServiceDefaults`, `BookWorm.AppHost`) only for infrastructure plumbing—never for shared business logic.

## How it works

External traffic enters exclusively through a single YARP **API Gateway** (`gateway`), which routes browser requests to three Next.js 16 web applications and API requests to internal .NET 11 services. Services communicate synchronously over **gRPC** when immediate read data is required (for example, Ordering reading Basket and Catalog prices during checkout) and asynchronously via **Wolverine + Kafka** CloudEvents for cross-context state propagation.

### Bounded contexts and repository shape

| Bounded context       | Services / Apps                                                                                                      | Primary backing store                                                                       | Repository path                                           | Authoritative ownership                                                                                                                   |
| :-------------------- | :------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ | :-------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------- |
| **Catalog**           | **Catalog API** (`catalog`), **Catalog Ingestion** (`catalog-ingestion`)                                             | PostgreSQL (`catalogdb`), Qdrant (`vectordb`), Azure Blob (`catalog-blob`), Redis           | `src/Services/Catalog/`                                   | Canonical books, categories, authors, publishers, prices, search index, and derived rating summary                                        |
| **Shopping**          | **Basket API** (`basket`)                                                                                            | Redis (`redis`)                                                                             | `src/Services/Basket/`                                    | Mutable, customer-scoped pre-order baskets (not orders or inventory reservations)                                                         |
| **Ordering**          | **Ordering API** (`ordering`), **Finance** (`finance`)                                                               | PostgreSQL (`orderingdb` + Marten), Redis; Azure Durable Task Scheduler (`finance-taskhub`) | `src/Services/Ordering/`, `src/Services/Finance/`         | Accepted orders, purchase-time price snapshots, lifecycle statuses (`New`, `Cancelled`, `Completed`), and post-checkout saga coordination |
| **Reviews**           | **Rating API** (`rating`)                                                                                            | Azure Cosmos DB (`ratingdb`/`feedbacks`), Redis                                             | `src/Services/Rating/`                                    | Individual customer `Feedback` records and AI-generated review summaries                                                                  |
| **Conversational**    | **Chat API** (`chatting`), **MCP Tools** (`mcptools`)                                                                | Azure Blob Storage (`chatting-blob`); stateless MCP server                                  | `src/Services/Chat/`, `src/Services/McpTools/`            | Read-only advisory multi-agent book discovery, Q&A, and scoped Catalog MCP tools                                                          |
| **Platform**          | **Notification** (`notification`), **Scheduler** (`scheduler`)                                                       | Redis (Notification idempotency; no SQL DB); PostgreSQL (`schedulerdb`)                     | `src/Services/Notification/`, `src/Services/Scheduler/`   | Asynchronous SMTP email delivery (Mailpit locally, SendGrid in cloud) and recurring Quartz.NET batch jobs                                 |
| **Edge & Frontend**   | **API Gateway** (`gateway`), **Storefront** (`storefront`), **Commerce** (`commerce`), **Backoffice** (`backoffice`) | Shared Better Auth + Microsoft Entra ID sessions                                            | `src/Aspire/BookWorm.AppHost/`, `src/Clients/`            | Public routing, customer microfrontends (Storefront + Commerce), and staff dashboard (Backoffice)                                         |
| **Shared Foundation** | **AppHost**, **ServiceDefaults**, **BuildingBlocks**, **Presidio**                                                   | —                                                                                           | `src/Aspire/`, `src/BuildingBlocks/`, `src/Integrations/` | Aspire 17 orchestration, OpenTelemetry, FusionCache, Wolverine setup, DDD primitives, and PII redaction sidecars                          |

## Design trade-offs

| Decision                                                                                                        | Benefits                                                                                                                         | Costs and limits                                                                                                                        |
| :-------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- |
| **Polyglot service-owned storage** (PostgreSQL, Cosmos DB, Redis, Qdrant, Blob Storage, Durable Task Scheduler) | Matches each workload to the right storage model and prevents cross-service table coupling                                       | Increases operational surface area and requires eventual consistency for projections (such as book rating summaries and search vectors) |
| **Single YARP API Gateway for external traffic**                                                                | Centralizes TLS termination, Microsoft Entra ID auth routing, and microfrontend zone routing while keeping 15+ workloads private | Makes gateway availability and scaling critical to all customer and staff journeys                                                      |
| **Advisory-only conversational AI**                                                                             | Eliminates transactional risk from LLM hallucinations by keeping Chat API and MCP Tools read-only                                | Customers still complete basket edits and checkout through standard Storefront/Commerce UI flows                                        |
| **Shared technical chassis, zero shared business layer**                                                        | Standardizes resilience, OpenTelemetry, versioning, and Entra ID auth across all 10 backend projects                             | Cross-context business workflows require explicit integration events, Pact contracts, and Finance sagas                                 |

## Alternatives considered

- **Single modular monolith:** Reduces network hops and deployment complexity, but would not demonstrate independent service deployment, polyglot persistence, Kafka choreography, or Aspire distributed orchestration—BookWorm's primary showcase goals.
- **Technical-layer microservices (shared database or shared business-logic tier):** Simplifies ad-hoc joins across books, orders, and reviews, but causes schema coupling and breaks bounded-context ownership.
