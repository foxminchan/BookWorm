# Engineering standards

## 1. Context & Problem

BookWorm is built as a set of independent backend services paired with customer-facing and back-office web applications. Without shared engineering standards, teams risk introducing hidden cross-service coupling, breaking asynchronous event routing, drifting in data naming conventions, or duplicating user-interface components across applications.

## 2. Business Value

- **Independent service delivery**: Clean boundaries allow teams to build, test, and deploy individual services without unintentionally breaking neighboring capabilities.
- **Reliable cross-service communication**: Consistent event naming, minimal payloads, and compatibility checks prevent silent messaging failures or breaking interface updates.
- **Lower maintenance cost**: Centralized package management, shared frontend primitives, and consistent domain modeling keep the codebase understandable and easier to evolve.

## 3. How It Works

BookWorm's engineering standards align backend services, cross-service messaging, contract schemas, and client applications around four core practices:

1. **Preserve service boundaries and centralized governance**: Each service owns its business domain and avoids direct dependencies on other services. Software dependency versions are managed centrally across the repository, and business-logic changes are paired with automated tests and updated documentation.
2. **Keep cross-service events focused and stable**: Services exchange state changes through integration events that carry only the minimum data consumers need. Event naming follows a consistent action-and-entity convention, and routing metadata stays fixed so the messaging layer delivers events accurately.
3. **Validate shared service contracts before merging**: Changes to shared service-to-service interface definitions are checked for style compliance and backward compatibility against a committed baseline. Any intentionally breaking update requires team coordination and a migration plan.
4. **Apply consistent domain and frontend architecture**: Services model business rules using established patterns—separating reads from writes, encapsulating business invariants, isolating persistence, and using consistent database naming. Client applications reuse shared visual building blocks across the storefront and back-office apps while preserving strict type safety and clear separation between server-rendered and interactive client behavior.

## 4. Trade-offs & Lessons Learned

- **Strict service isolation vs. convenience**: Avoiding direct cross-service dependencies requires explicit contracts and asynchronous messaging, trading extra upfront design effort for independent deployment and fault isolation.
- **Compatibility locks on interface schemas**: Validating contract changes against a committed lock baseline prevents accidental breaking changes for consumers, but requires explicit coordination and migration planning whenever incompatible changes are needed.
- **Immutable integration-event routing**: Because the event bus routes messages using consistent naming and namespace conventions, renaming or relocating published event types can silently break downstream subscribers.
- **Shared frontend packages and centralized dependencies**: Managing package versions and UI components centrally prevents drift and duplication across apps, though updates to shared modules affect multiple consumers at once.

## 5. Technical Reference

Follow established repository patterns first. These guidelines help keep BookWorm's services maintainable and independently deployable.

### General coding practices

- Apply Domain-Driven Design principles and preserve service boundaries; avoid direct cross-service dependencies.
- BookWorm targets .NET 11 and uses C# 15. Use the repository SDK and language settings, and follow `.editorconfig` for formatting.
- Prefer explicit type declarations when the type is not obvious.
- Use primary constructors for classes with immutable properties and expression-bodied members where they improve clarity.
- Keep endpoints, handlers, DbContexts, and tests `sealed` by default.
- Propagate `CancellationToken` through asynchronous operations, and use `async`/`await` consistently.
- Use `Mediator.SourceGenerator` for CQRS; do not introduce MediatR.
- Keep package versions centralized in `Directory.Packages.props`.
- Implement tests for business logic and update relevant documentation when behavior changes.

### Integration events

Integration events communicate across service boundaries:

- Declare integration events in the `BookWorm.Contracts` namespace.
- Use the `[Action][Entity]IntegrationEvent` naming pattern, such as `BookCreatedIntegrationEvent`.
- Include only the data consumers need to keep payloads focused.
- Preserve the `IntegrationMessageOwner` topic routing and `MessageIdentity` metadata used by the event bus.

:::danger
Do not change integration-event namespaces. The event bus relies on consistent namespace conventions for routing.
:::

```csharp
using BookWorm.Constants.Aspire;
using Wolverine.Attributes;

namespace BookWorm.Contracts;

[IntegrationMessageOwner(ServiceName = Services.Ordering, TopicName = "user-checked-out")]
[MessageIdentity("BookWorm.Contracts.UserCheckedOutIntegrationEvent")]
public sealed record UserCheckedOutIntegrationEvent(
   Guid OrderId,
   Guid BasketId,
   string? FullName,
   string? Email,
   decimal TotalMoney
) : IntegrationEvent;
```

### Protocol Buffers

When changing `.proto` files, ensure `buf` is installed (`mise run setup:buf`) and validate the schema and compatibility before submitting:

```bash
# Run from the service's Grpc/Protos directory (Basket or Catalog).
buf lint
buf breaking --against lock.binpb
buf build -o lock.binpb
```

Run the commands in order: lint the schema, check for breaking changes against that module's committed `lock.binpb`, then update the lock file after validation. Commit the schema and updated lock file together. Breaking changes require coordination and a migration plan.

### Design patterns

Use patterns where they fit the service and its domain:

- CQRS with Mediator
- Repository pattern for data access
- Domain events for domain side effects
- Value Objects for immutable domain concepts
- Domain Services for complex business logic
- Factories or Builders for object creation
- Specification pattern for complex queries

Avoid circular dependencies and keep services independently deployable. Use `snake_case` for PostgreSQL identifiers and raw SQL.

### Frontend (`src/Clients`)

The client applications live in a Bun + Turborepo monorepo under `src/Clients` (`apps/storefront`, `apps/backoffice`, and 15 shared `packages/*` packages):

- Use `bun` and `bun run` from `src/Clients`; do not introduce `npm`, `pnpm`, or `yarn` lockfiles.
- Enforce the 4-tier Turborepo dependency hierarchy (`config` -> `foundation` -> `domain` -> `app`) with `bun run boundaries`.
- Target Next.js 16 (App Router) and idiomatic React 19 with explicit server/client boundaries; keep `app/**/page.tsx` routes thin and delegate interactive views to `features/<domain>/`.
- Centralize data fetching in `@workspace/api-hooks` `queryOptions` factories and typed HTTP/SSE clients in `@workspace/api-client`.
- Keep TypeScript strict; avoid `any` and prefer typed interfaces and discriminated unions.
- Reuse shared UI primitives, environment schemas, auth factories, telemetry setup, and SEO utilities from `@workspace/*` packages instead of duplicating code across apps.
